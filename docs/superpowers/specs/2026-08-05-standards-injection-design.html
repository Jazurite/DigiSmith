Problem & Goal

DigiSmith's roadmap (MEMORY.md) defines G as: "Jack's coding standards + style guide carried into every implementer subagent's brief." Right now no standards content exists anywhere, and there is no mechanism to carry whatever standards do exist into an implementer subagent's prompt.

The goal is to build both:

  1. A place to capture coding standards — extracted from real codebases, or entered manually — organized so they stay scannable rather than becoming a wall of text.
  2. A mechanism that reads the applicable standards and folds them into context at the moments that need them: plain conversation, building a new DigiSmith skill, brainstorming/planning, and — the case G exists for — dispatching an implementer subagent.

Reference & Departures

Modeled on Agent OS (D:\Workspace\Library\AgentOS), specifically its discover-standards / index-standards / inject-standards commands and its standards/[folder]/[standard].md + index.yml layout. Two deliberate departures, decided during brainstorming:

  • Skills, not slash commands. DigiSmith is a single plugin whose stages are all skills (per MEMORY.md's structure section); G follows that convention rather than introducing commands.
  • No profile/install system. Agent OS's profile-inheritance and project-install.sh exist to serve many unrelated projects with different stacks from one shared base. DigiSmith is personal and singular (philosophy #1: "not a framework"). Standards live once, inside the DigiSmith repo itself — no per-project copy step, no profiles.
Format note (this document): per-conversation decision, DigiSmith specs are now authored in HTML rather than Markdown — richer structure and presentation for documents meant to be read by a human once, following the reasoning in "HTML is the new Markdown". Scope, refined during plan-writing: specs only, not plans — superpowers:subagent-driven-development's task-brief script mechanically parses plan files by Markdown ### Task N: headers (see skills/subagent-driven-development/scripts/task-brief), so plans stay Markdown to remain compatible with that tooling. The standards library itself (§ Structure & Storage) also stays plain Markdown — it's optimized for compact injection into subagent context, not visual review, and token cost there matters in a way it doesn't for a spec a human reads once.

Non-Goals

  • Not building the automatic call-site — this does not make every subagent dispatch automatically pull in standards. That's Tier 2's H (subagent-driven always). G produces the mechanism and the seam H will call; wiring H itself is out of scope here.
  • Not building E (the spine). G is usable standalone (invoked directly) until E exists to route to it automatically.
  • Not populating a comprehensive standards library. First-pass content is a dogfooding-scale seed (see Testing), not exhaustive documentation of every convention Jack has ever used.

Structure & Storage

DigiSmith/
├── skills/
│   ├── discover-standards/SKILL.md
│   ├── add-standards/SKILL.md
│   ├── index-standards/SKILL.md
│   ├── inject-standards/SKILL.md
│   └── ...
└── standards/
    ├── index.yml
    ├── global/
    │   └── *.md            # universal principles, any stack
    └── shopify/
        └── *.md             # Shopify/Liquid/Emma-theme layer

Everything lives inside the DigiSmith repo. global/ and shopify/ are plain folders (mirroring Agent OS's root/, api/, database/ convention) — not a profile-inheritance system. The shopify/ layer is pulled in only when the current working repo looks like a Shopify theme repo (see Detection Logic).

The Four Skills

Capture · from code

discover-standards

Analyze the codebase → 3–5 candidate areas → present findings → ask "why" per pattern → draft → confirm → write. One standard fully completes the loop before the next starts. Triggers index-standards at the end.

Capture · manual

add-standards

"Add a standard: always do X" → draft → confirm → write. No codebase analysis — the rule is dictated directly. Shares the overlap check (append vs. duplicate) with discover-standards. Also triggers index-standards.

Maintain

index-standards

Scans standards/, diffs against index.yml, prompts for a one-line description on new files, prunes entries for deleted files. root: sorts first, then folders and files alphabetically.

Use

inject-standards

The mechanism G exists to build — reads matched standards and folds them into context. Four scenarios, detailed below.

Both capture skills follow Agent OS's "writing concise standards" rules: lead with the rule, use code examples over prose, skip what the code already makes obvious, one standard per concept, bullets over paragraphs. Both write to standards/global/*.md or standards/shopify/*.md, folder confirmed at file-creation time.

inject-standards — four scenarios

#ScenarioTriggerFormat
1Conversation Regular chat / implementation work Reads matched standards into context, announces inline
2Creating a Skill Building a skills/*/SKILL.md file Asks: @-file references (stays in sync) or copied content (self-contained)
3Shaping/Planning Plan mode, brainstorming, writing-plans Same reference-vs-copy choice as above
4Dispatching a Subagent (new) About to fire an Agent tool call to build something Full content folded into the prompt under ## Standards — not references, since a fresh subagent has no guaranteed visibility into DigiSmith's plugin path. Auto-includes shopify/ via repo detection, no prompt.

Scenario detection: infer from context (plan mode or "spec"/"plan"/"shape" language → Shaping/Planning; editing a skills/*/SKILL.md → Creating a Skill; about to fire an Agent tool call → Dispatching a Subagent; otherwise → Conversation). If ambiguous, ask rather than guess — ported directly from Agent OS's rule.

Matching: read standards/index.yml, match descriptions against the current work context, present 2–5 suggestions for confirmation (skipped only for scenario 4's shopify/ auto-include). Explicit-mode invocation (naming a folder/file directly) skips suggestion but still validates the target exists.

Detection Logic

Scenario detection — see inject-standards above.

Shopify-repo detection — the current working repo qualifies for the shopify/ layer if either is true:

  • docs/development-workflow.md exists at the repo root, or
  • the repo name matches shopify-template-*

These are the same two signals Jack's global CLAUDE.md already uses to identify Emma theme repos (shopify-template-kr, -jp, -ca, etc.) — reusing an existing convention rather than inventing a new one.

Error Handling & Edge Cases

  • inject-standards finds no standards/index.yml → tells the user to run discover-standards or add-standards first (or index-standards if standards files exist without an index).
  • Explicit-mode inject-standards given a folder/file that doesn't exist → lists what's actually available, asks if one of those was meant.
  • discover-standards finds nothing notable in a chosen area → says so, offers another area or skip.
  • discover-standards / add-standards drafts a standard overlapping an existing file → offers to append instead of creating a duplicate.
  • Shopify detection fires but standards/shopify/ is empty or doesn't exist → silently skip, nothing to inject, not an error.
  • Scenario 4 (subagent dispatch) with zero standards captured anywhere (fresh install) → dispatch proceeds without a ## Standards section rather than blocking. G augments the brief; it doesn't gate dispatch — gating is H's future job, not G's.

Testing / Verification

These are instruction files (SKILL.md), not executable code — no automated test suite, consistent with the existing "no automated JS syntax validation, done manually" convention already in Jack's Emma workflow docs. Verification is a dogfooding pass after implementation:

  1. Run add-standards to manually capture a handful of rules already known today (e.g. pulled from the Emma CLAUDE.md conventions) as first real content in standards/shopify/.
  2. Run discover-standards against a real Emma repo on disk to validate the extraction loop end-to-end.
  3. Exercise all four inject-standards scenarios at least once each — plain conversation, building a new DigiSmith skill, a brainstorming/writing-plans pass, and an actual subagent dispatch — confirming standards appear correctly formatted in each.

Relationship to Other Map Items

  • H (subagent-driven always, Tier 2) will later call inject-standards scenario 4 automatically before every implementer dispatch. Until H exists, scenario 4 is invoked explicitly.
  • E (the spine, Tier 1) will eventually route to all four skills as part of enforcing stage order. G is designed to work standalone in the meantime.
