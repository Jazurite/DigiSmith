Problem & Goal

After a PR opens against an Emma Shopify theme repo, a GitHub Actions check (Continuous Integration / Ephemeral / Comment Ephemeral Information) deploys an ephemeral theme and the github-actions bot comments on the PR with a Shopify Preview URL and a Theme Editor URL. Today, getting those two URLs means manually watching the PR's checks and re-reading the bot comment by hand.

MEMORY.md's map originally filed this under I.1 — "capture Emma CI/CD's ephemeral URL → JIRA comment + status transition" — in Tier 5. Jack pulled it forward directly (same pattern as A being pulled ahead of E earlier) and, during brainstorming, scoped it down twice from the original ask: no automated JIRA status transition (kept permanently manual), and no JIRA comment write-back either (see Non-Goals). With the JIRA piece removed entirely, what's left — poll the check, extract both URLs, report them in-session — has no JIRA dependency at all, so it was split out into its own map item, M, rather than staying a narrower slice of I.1. I.1 itself still exists as a separate, later feature: JIRA comment write-back that consumes M's captured URLs as input.

Non-Goals

  • Not writing to JIRA. Posting the captured URLs as a JIRA comment is I.1, a separate later feature that consumes this one's output — not built now. This build's job ends at reporting the two URLs in the conversation.
  • Not transitioning JIRA ticket status. This is a permanent product decision, not a deferral — Jack changes ticket status manually. I.1, when it's eventually built, shouldn't add this either.
  • Not creating the PR. superpowers:finishing-a-development-branch already handles "push and create PR," following the repo's template and reporting the URL. Rebuilding that would violate DigiSmith's philosophy #2 ("duplicating a Superpowers capability is a bug, not a feature"). This skill picks up only once a PR already exists.
  • Not reading raw check/job logs. Considered as an alternative extraction method (more "source of truth" but slower to navigate and more fragile to parse than one purpose-built bot comment) and rejected in favor of parsing the bot's PR comment directly.
  • Not a webhook or event-driven listener. Would need a standing server and a public endpoint — infrastructure overkill for a personal, single-developer tool. Polling on demand, while the skill is actively running, is sufficient.

Architecture

New skill: digismith:capture-ephemeral-url. It doesn't hook into or modify finishing-a-development-branch — it triggers on its own description ("a PR was just created in an Emma theme repo, capture the ephemeral deploy URLs"), matched the same way any skill match works under superpowers:using-superpowers' discipline. In practice that means the same agent that just ran finishing-a-development-branch's "push and create PR" option recognizes and invokes this skill immediately after, with no explicit call wired into Superpowers' own file.

Step 1

Resolve Ticket Key

Parse <Key> from the current branch name (<Key>__<slug>, the convention using-digismith already establishes). If the branch doesn't match that shape, ask directly for the key instead of guessing.

Step 2

Identify the PR

gh pr view --json number for the current branch.

Step 3

Poll the Check

Poll gh pr checks <PR> --json name,state,conclusion (via a Monitor until-loop) watching specifically for Continuous Integration / Ephemeral / Comment Ephemeral Information to reach a terminal conclusion. ~30–60s interval, 20-minute timeout.

Step 4

Extract URLs

Once the check succeeds, fetch PR comments (gh pr view --json comments), find the github-actions bot's "Ephemeral Theme Deployed Successfully" comment, and regex out the Preview Theme: and Customize your Theme: URLs.

Step 5

Report

Tell Jack both URLs (and the resolved ticket key) in the conversation. No file write, no JIRA call.

Data Flow

branch name → ticket key → PR number → poll check → bot comment body → regex-extracted URLs → report to Jack

Error Handling & Edge Cases

  • Branch doesn't match <Key>__<slug> → ask directly for the ticket key rather than guessing.
  • Check never appears, or the 20-minute timeout elapses → stop and report clearly; don't hang indefinitely.
  • Check completes with a failure conclusion → stop and report the failure; don't attempt URL extraction (nothing to extract — the deploy didn't succeed).
  • Check succeeds but the bot comment isn't there yet (brief lag between check completion and the comment posting) → a short additional retry window before giving up and reporting "check passed but comment not found."
  • Comment found but the regex doesn't match either URL (format drift) → report the raw comment body so Jack can see what changed, rather than failing silently.

Testing / Verification

No automated test suite — consistent with every DigiSmith skill so far. Verification is a manual edge-case walkthrough against the written skill, same pattern used for using-digismith:

  1. Branch matches <Key>__<slug> → key resolves correctly.
  2. Branch doesn't match → falls back to asking for the key.
  3. Check succeeds, comment present and well-formed → both URLs extracted and reported.
  4. Check times out (simulate with a short timeout for the test) → clean timeout report, no hang.
  5. Check completes with failure → stops, reports failure, doesn't try to parse a comment.
  6. Check succeeds but the comment is missing or malformed → retry-then-report / raw-body-fallback behaves as specified.

Relationship to Other Map Items

  • I.1 is now a separate, later feature — JIRA comment write-back that consumes M's captured URLs as input: "detect a JIRA-capable tool at runtime (same principle jira-intake already uses); found → post comment, not found → draft it for Jack to paste." Backlogged, not abandoned, and buildable without changing anything shipped here.
  • D (delivery, Tier 5, not yet built) — PR creation itself lives in Superpowers' finishing-a-development-branch, not in DigiSmith's eventual D. This skill only ever consumes an already-created PR.
  • E (using-digismith) — unchanged; this skill isn't wired into its routing, since it triggers post-implementation, after E's own job (ticket → branch → brainstorming handoff) is long done.
