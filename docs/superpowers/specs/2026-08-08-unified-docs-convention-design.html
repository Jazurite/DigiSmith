Problem & Goal

DigiSmith currently uses two separate, inconsistent storage conventions. Its own self-development history lives in docs/superpowers/{specs,plans,reports}/ — organized by artifact type, so a single feature's design, plan, and report are three files scattered across three folders, linked together only by a shared date-slug prefix. Separately, jira-intake writes ticket content into a consumer repo (an Emma theme repo, say) at docs/<slug>/ticket.md, gitignored unconditionally — a different shape, in a different place, with no user choice in the matter.

Jack asked to replace both with one convention: everything DigiSmith writes about a single feature — its ticket, design spec, implementation plan, and implementation report — lives together in one folder, named for the feature, under a dot-prefixed .digismith/ root. This applies everywhere DigiSmith writes docs, not just its own repo, and makes commit-vs-gitignore an explicit per-repo choice instead of a hardcoded assumption.

Non-Goals

  • No map letter. This doesn't add a new gap to the SDLC pipeline map — it reorganizes how existing capabilities store their output. Recorded as a MEMORY.md Convention update and a history.html timeline entry, the same treatment the digismith→jazurite marketplace rename got.
  • Not touching standards/. A different content category — the coding-standards library, not tickets/specs/plans/reports — untouched by this change.
  • Not building PR-merge (Option 2) awareness for consumer-repo commit/gitignore detection beyond what's described here — the ask-once/detect mechanism is the whole of this change's consumer-repo scope.

Architecture

New convention, wherever DigiSmith writes docs — its own repo or any consumer repo:

.digismith/
  history.html                          (DigiSmith's own repo only — the living tracker)
  docs/
    <feature-slug>/
      ticket.md                         (from jira-intake, when a real ticket exists)
      design.html                       (from brainstorming)
      plan.md                           (from writing-plans)
      report.html                       (from report-implementation)

One folder per feature, named for its slug, holding every artifact about that feature together — no more date-prefixed filenames scattered across type-named folders. Files are renamed to their role only (ticket.md, design.html, plan.md, report.html) since the folder name and git history already carry the date/slug.

Consumer-repo commit-vs-gitignore is a per-repo, ask-once-then-remember choice. Before writing into .digismith/docs/ in a given repo for the first time, check that repo's own .gitignore for a .digismith/ entry:

  • Entry found → write gitignored, no question asked.
  • No entry, and .digismith/docs/ doesn't exist there yet → ask once via AskUserQuestion ("commit this repo's DigiSmith docs, or keep them local-only?"). Choosing gitignored appends the entry to that repo's .gitignore (creating the file if needed) — the entry's presence is the remembered answer for every future session, no separate state store needed. Choosing committed does nothing further; the entry's absence is itself the remembered "committed" signal.

Files are git mv'd, not copied, to preserve history. docs/history.html moves to .digismith/history.html. This spec's own design doc and the implementation plan that follows it move too, into .digismith/docs/unified-docs-convention/, as part of the same migration pass — they're subject to the convention they define.

Every cross-reference gets rewritten in the same pass:

  • .digismith/history.html's own links (currently superpowers/specs/…, superpowers/plans/…, superpowers/reports/…) → docs/<slug>/design.html etc.
  • Every spec/plan/report's internal links to its own siblings (e.g. "the design spec and the implementation plan", currently ../specs/… / ../plans/…) → same-folder links (design.html, plan.md).
  • MEMORY.md's Conventions section — rewritten to describe .digismith/docs/<slug>/ as the standard, for both DigiSmith itself and consumer repos.
  • skills/report-implementation/SKILL.md — Step 4's target path and the {{SPEC_RELATIVE_LINK}}/{{PLAN_RELATIVE_LINK}} derivation rules change from ../specs//../plans/ to same-folder (design.html, plan.md).
  • README.md's docs/history.html link becomes .digismith/history.html.

Consumer-Repo Changes

  • jira-intake: ticket path becomes .digismith/docs/<slug>/ticket.md. Applies the ask-once/detect logic from Architecture before writing there for the first time in a given repo.
  • using-digismith: updates the one place it reads ticket.md's path from to match.

Error Handling & Verification

  • Migration completeness check: after moving everything, grep the whole repo for the old path patterns (docs/superpowers/, superpowers/specs/, superpowers/plans/, superpowers/reports/) — zero hits required.
  • Broken-link check: for every link the migration touches, verify the target file actually exists on disk at its new path.
  • jira-intake's ask-once logic: dogfooded against a throwaway fixture repo (never DigiSmith's own), both branches — entry present (no ask) and entry absent (asks, then writes the entry back).
  • No automated test suite, consistent with every DigiSmith skill — verification is the grep/link-check pass plus the usual dogfooding for the two changed skills' new logic.

Relationship to Other Map Items

  • G, A, E, M, N — none of their shipped behavior changes; only where their already-written artifacts live on disk.
  • N (report-implementation) — most directly affected skill, since its whole job is writing into this structure. Its placeholder-derivation logic (already hardened in its own final review) gets simpler here: same-folder links instead of sibling-folder relative paths.
  • A (jira-intake) — gains the ask-once/detect commit-vs-gitignore logic; otherwise unchanged.
