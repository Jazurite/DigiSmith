Timeline

2026-08-05

Project memory established

MEMORY.md written: philosophy, the map (A-L), build order (6 tiers). Tier 1 chosen as G (standards injection) + E (the spine).

2026-08-05

G brainstormed and specced

Modeled on Agent OS's discover/index/inject-standards pattern, adapted for DigiSmith: skills instead of slash commands, no profile/inheritance system. Spec approved; implementation plan written.

2026-08-06

G built — 5 tasks, subagent-driven-development

Repo initialized (first commit). Plugin scaffold, then index-standards → add-standards → discover-standards → inject-standards, each dispatched to a fresh implementer subagent and independently reviewed.

2026-08-06

Final review found a real architecture gap

All four skills used bare relative paths to standards/ — broke the moment they'd be invoked from any repo other than DigiSmith itself. Fixed with an explicit "locate DigiSmith, ask if unknown" resolution rule, plus three Important findings (Scenario 4 contradiction, unqualified skill refs, no content-change refresh path). Re-reviewed clean, merged to main.

2026-08-06

Polish, restructure, and go live

  • Swept every deferred Minor finding from the build (typos, an inconsistent code example, unqualified references)
  • Split standards/team/ out of shopify/ — the original two-folder design conflated scope (universal vs. Emma-specific) with kind (code technique vs. process convention); real content made the seam obvious
  • Renamed the marketplace digismith → jazurite (matches the GitHub owner; the plugin itself is unaffected)
  • Pushed to github.com/Jazurite/DigiSmith so it installs from any machine
2026-08-06

Live validation

discover-standards captured snippet-render-vs-include.md in an actual session against a real Emma repo — not a dogfood simulation. First real proof the installed plugin works end to end.

2026-08-06

Explored and shelved: local standards cache + fetch-standards

Live testing surfaced friction — being asked to locate DigiSmith's repo path every time. Proposed fix: a local .digismith/ cache per consuming repo, refreshed by a new fetch-standards skill. Mid-brainstorm, self-corrected: this solves a multi-tenant sync/merge problem DigiSmith doesn't have. Shelved before any design was written — writes still go straight to canonical DigiSmith, unchanged.

2026-08-06

G closed

Map item G done. E (the spine) is next in Tier 1.

2026-08-06

A reprioritized ahead of E

Jack pulled A (intake/creation) ahead of E (the spine) by direct request, out of the Tier 1/Tier 3 build order — E was still open. Tier order in MEMORY.md is a plan, not a lock.

2026-08-06

A brainstormed and specced

Settled on a single skill with two doors: Door 1, a ticket already exists — ingest by key or paste; Door 2, a raw need with no ticket yet — shape one. Both converge on docs/<slug>/ticket.md. This resolved the open question logged in MEMORY.md — "A and L may be one skill, not two" — in favor of keeping them separate: A stops once the ticket exists, while L (grounding it in the actual codebase) stays a distinct future map item. Spec approved; implementation plan written.

skills/jira-intake/SKILL.md delivered: both doors' happy path first, then edge-case handling for existing-file branching (re-run, collision, Door 2 → Door 1 upgrade) and can't-proceed paths, each dispatched to a fresh implementer subagent and independently reviewed.

2026-08-07

A closed

Map item A done. Tier 3 ("Intake & estimation") moves to in progress (1/2) — J (estimation) is still outstanding.

2026-08-07

E pulled forward, specced as a first slice

Design spec approved for using-digismith, deliberately scoped to a first slice — intake → branch → brainstorming hand-off — rather than E's full future role enforcing stage order and routing to everything else. Implementation plan written (3 tasks).

2026-08-07

E first slice built — 3 tasks, subagent-driven-development

skills/using-digismith/SKILL.md delivered: Task 1 built the skill and dogfooded the happy path; Task 2 dogfooded three edge cases and found one real gap — the skill's native-worktree-tool branch-naming didn't guarantee the exact <Key>__<slug> name, fixed with a verify/rename step; Task 3 is this history.html update. Map item E stays in progress — only the first slice has shipped, not the spine's full future scope.

2026-08-08

M split out from I.1, brainstormed, and specced

Jack asked to build I.1's ephemeral-URL capture as a normal development task, no ticket. During brainstorming, the JIRA piece was scoped out entirely — no automated status transition (permanent), no JIRA comment write-back (backlogged). What remained had no JIRA dependency, so it was split into its own map item, M, rather than staying a slice of I.1. I.1 now names the separate, later JIRA write-back feature that will consume M's output. Design spec approved; implementation plan written (3 tasks).

2026-08-08

M built — 3 tasks, subagent-driven-development

skills/capture-ephemeral-url/SKILL.md delivered: Task 1 built the skill and dogfooded the happy-path decision logic against fixtures (ticket-key parsing, poll-to-success branching, URL extraction from a real example comment); Task 2 dogfooded four edge cases (no-match branch, check failure, timeout, missing/malformed comment). Live gh pr view/gh pr checks calls couldn't be dogfooded against a real PR — the authenticated gh account can't reach DigiSmith's own repo, and creating a scratch PR against a real Emma repo would be visible to teammates — so those get their first live verification the next time this skill runs for real. Task 3 is this history.html update. Map item M done.

2026-08-08

N brainstormed, specced, and built — 3 tasks, subagent-driven-development

Jack asked to formalize G's hand-written implementation report into a required step. Brainstorming surfaced a real sequencing problem: the ledger content that makes a report worth reading is deleted by subagent-driven-development's own Finish step before finishing-a-development-branch even runs — so report-implementation triggers earlier than "after merge," right before that deletion, relying on this repo's merges always being fast-forward so the commit range it records never changes afterward. Task 1's dogfood run reconstructed M's actual (already-deleted) ledger from this session's own record of it and generated M's real missing report against real git history — kept, not discarded as test scaffolding. Task 2 dogfooded four edge cases with no gaps found. Task 3 is this history.html update.

2026-08-08

Unified docs convention adopted — no map letter

Replaced two inconsistent storage conventions — docs/superpowers/{specs,plans,reports}/ (DigiSmith's own repo, organized by artifact type) and docs/<slug>/ticket.md (consumer repos, hardcoded gitignored) — with one: .digismith/docs/<feature-slug>/{ticket.md, design.html, plan.md, report.html}, wherever DigiSmith writes docs. Commit-vs-gitignore in a consumer repo is now an explicit ask-once-then-remember choice instead of a hardcoded assumption. All 13 existing files across G/A/E/M/N migrated in the same pass; this is a structural change, not a new pipeline capability, so it's recorded here and in MEMORY.md's Conventions section rather than added to the map table.

2026-08-11

O brainstormed, specced, and built — 4 tasks, subagent-driven-development

Jack asked to make DigiSmith's existing "everything on" Emma flow and a lighter Personal flow (no ticket, no ephemeral capture) a declared per-repo choice instead of an undocumented, ad hoc deviation from pillar 5's prescriptive stance. Two flat YAML profiles ship (emma, personal), read independently by using-digismith, inject-standards, capture-ephemeral-url, and report-implementation at each one's own trigger point — no central orchestrator, no inheritance system. A repo with no .digismith/profile file sees zero behavior change, including DigiSmith's own repo. Task 4 also closed a standing gap: report-implementation had never rendered a ticket-key field at all until this feature added one, gated by the same profile mechanism.
