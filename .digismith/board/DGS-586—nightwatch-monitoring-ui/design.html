Nightwatch monitoring UI

Ticket: DGS-586 (J.5, Nightwatch DGS-580)Date: 2026-10-22 (UTC+7)Status: spec approved at checkpoint 1, with changes applied

Layout mock for Jack: mock.html (static, fake data).

1. Goal

A read-only Nightwatch dashboard in the Nexus web app. Jack opens one site and sees every run, what waits for him, and how each run is going. It reads the files that DGS-581, 582, 583 and 486 write. It writes nothing.

Out of scope (later tickets): buttons to resolve an attention item or send a steer; a websocket; seat-window and token-burn numbers (see section 7).

2. How the API reads the data (decision 1)

Problem. The Nexus API runs from the depot copy (~/.digismith-depot/nexus-api/src/server.ts). That copy has no packages/ folder. DGS-587 showed the same limit for jobs: the depot clone has no node_modules, so the jobs run the built CLI.

Decision. The API does not import the readers. It runs the built CLI, the same way the job registry does. One new read-only command group is added to packages/cli:

node <MAIN_CHECKOUT>/packages/cli/dist/index.js nightwatch view <name> [--run ID] [--ticket KEY] [--since SEQ] --json

The names are overview, attention, runs, run, events, plan. Each prints one JSON document and exits 0. The command calls the existing readers: listRuns, showRun, tailEvents, classify, phaseOf (run), readOpen (attention), readJournal, readLock, readAway, readBreaker, readEvents (scan day files), findWorkspace and parseVerdictEntries (plan). There is no second parser.

  • Why not copy the readers into the depot. A copy drifts from the writers. The built CLI is the build the global dg already uses, and DGS-587 made the jobs use it.
  • Source rules. The new files in packages/cli/src/nightwatch/ run under node --experimental-strip-types (the DGS-587 smoke test strips every file): no parameter properties, no enums, no namespaces. Double quotes and semicolons, like the rest of packages/cli.
  • Safety. The API spawns with an argument array (no shell). Run ids and ticket keys must match ^[A-Za-z0-9][A-Za-z0-9._-]*$ (the isSafe rule of the run record) before they reach the command line. The command opens files read-only and never creates a folder.
  • Cost control. One in-flight call per view name (single flight) and a 5 s cache per view and argument set. Ten browser tabs polling every 10 s then cost at most one spawn per view per 5 s. Timeout 8 s per call.
  • Missing build. No dist/index.js: the route answers 503 {"error":"reader_unavailable"} and the page shows its error state. The fix is pnpm --filter @digismith/cli build, which the finish hooks already run.
  • Contract. The shapes live in scripts/nexus-shared/nightwatch.ts (zod, like life-calendar.ts). The CLI prints them, the API checks them before it answers, the web app parses them. Same file, three users. That file must not import from packages/cli.

3. API routes (read-only, GET only)

All under /api/v1/nightwatch/, in a new nightwatch-route.ts wired in app.ts the way the jobs routes are (deps.nightwatch). Same helpers: sendJson, Cache-Control: no-store, 405 for other methods, 400 for a bad query (no input echoed), error codes only, never a message.

RouteQueryServes
/overview-Top bar, Operations (phase table, active workers, last events)
/attention-Attention page
/runsstate, role, ticket, trigger, limit (default 100, max 500)Runs page
/runs/:id-Run detail: record, pipeline, budget, order text
/runs/:id/eventssince (line count already seen), kind = all | agent | system | errorsEvent stream and tail
/plan/:ticket-Plan page

Event cursor: the run record says order is file position and seq can repeat. So since is a line count, not a seq. The answer holds total (lines now) and the new lines. A follower sends since=total from the last answer.

What an event row shows. Only ts, seq, type and the small data fields the hooks write (tool, ok, kind, reason, source, phase). The hooks never store prompts or tool output, so the stream cannot show them. Kind groups: Agent = tool, turn_end; System = started, ended, phase, review_ready, merged, pushed, lost; Errors = blocked, lost, tool with ok=false.

Trigger of a run (manual / night scan / away): the run record has no trigger field. The reader derives it: a run whose ticket matches a scan claim event and whose order path sits in the autonomous orders folder is night scan (or away when away.json was on at the claim time); any other is manual. If this cannot be told, the value is unknown, shown as "-". The plan checks the rule with fixtures.

4. Listening and login (decision 4)

  • The API already binds 127.0.0.1:4300 and Caddy proxies /api/* to it. The new routes sit under that prefix. No Caddy change, no new port.
  • The web pages are static files. nuxt generate writes one folder per page, and Caddy's file_server serves /nightwatch/runs/ from runs/index.html. A run or plan id travels in the query string (/nightwatch/run/?id=...), because a static host cannot serve an unknown path. No Caddy rewrite is needed.
  • No login in v1 (Maestro decision, checkpoint 1). The door is tailnet-only, like the Life Calendar. scripts/caddy/Caddyfile has no login, and test-config.mjs checks that no basic_auth exists. DGS-458 adds a login for the whole site later. The dashboard shows ticket keys, run ids, branch names and phase times. It shows no prompts and no secrets. A login for this dashboard alone is not part of this ticket.

5. Screens

Pages are in scripts/nexus-web/app/pages/nightwatch/. This adds the Nuxt router; the Life Calendar page stays at /. A shell component holds the top bar and the nav (Operations, Attention, Runs, Plan). Every page polls its route every 10 s (section 6). Mobile: the nav collapses to a row, tables become row cards (Warren's own pattern).

Shared states. Loading: a skeleton of the final layout, no spinner text. Error: the existing StatePanel with the error code and a Retry button; the last good data stays on screen, dimmed, with "last update failed at HH:MM (UTC+7)". Empty: one line that says what is empty and why that is fine.

Operations - /overview

  • Tickets per phase. Table: phase (claimed, building, review, merge-ready, merged, released, lost), count, oldest (age of the oldest phaseStartedAt). The scan is single flight, so the lock holds one claimed ticket at a time. So: claimed to merge-ready come from lock.json (one ticket at most). Merged and released count the release events of the last 7 days. Lost counts open attention items of kind lost. The table footer states both limits on screen: "one claimed ticket at a time (scan lock)" and "window: 7 days".
  • Active workers. One row per open run: key, role, seat, phase (from phaseOf), health (classify: healthy / blocked / stalled / lost), elapsed since started. Tokens column: "-" in v1 (section 7). Row link: run detail.
  • Last events. The newest 20 events of all open runs, merged by time, plus scan events (claim, release, breaker). Link: run detail.
  • Empty: "No worker is running. The next scan starts at 00:00 (UTC+7)" (read from the registry window). Error: shared panel.

Attention (new) - /attention

  • Open items from attention.jsonl (readOpen), oldest first: age, ticket, kind (stalled, blocked prompt, refused merge, lost, failed, unknown), cause, cause class (transient / durable / unknown), retry-eligible mark, link to the run. Title: "Waiting on Jack". A count badge sits in the nav.
  • Below: the last 20 resolved items (who resolved, when, note).
  • Read-only: no resolve button (later ticket). Each row shows the CLI command Jack would run, as copy text (for example dg autonomous attention resolve ID, only if that command exists; the plan checks and drops the line if not).
  • Empty: "Nothing waits for you." Error: shared panel.

Runs - /runs

  • Table, newest first: state (running / blocked / stalled / lost / ended), key, role, seat + model, trigger, started (UTC+7), duration, tokens ("-" in v1), delivery (commits, merged, pushed; commits from the base_sha to the branch head are NOT read in v1: the cell shows merged and pushed from events only).
  • Filters: state, role, ticket key (text), trigger. They run in the API (query) so the 500-row cap applies after the filter. Filter values go in the URL query so a view can be shared.
  • Empty: "No run matches" (with the filter) or "No run yet" (no filter). Error: shared panel. A run whose files cannot be read is skipped by listRuns, so it never shows.

Run detail - /runs/:id, /runs/:id/events

  • Header: run id, state, role, ticket, branch, seat, model.
  • Phase pipeline: Claimed, Worktree ready, Building, Review, Merged, Pushed. Each step has a time or "-". Sources: Claimed = the journal claim line of the ticket; Worktree ready = created_at; Building = first started or phase building; Review = first phase review or review_ready; Merged and Pushed = the merged and pushed events. A lost event turns the current step red. A manual run with no claim shows Claimed as "-".
  • Event stream: filters All / Agent / System / Errors, and "Tail: on/off". Tail on = poll events?since=total every 10 s and append; the view sticks to the bottom until the user scrolls up. First load: the last 200 lines, with "show earlier" (loads 200 more by line count). Event count badge.
  • Budget card: the run's watchdog budgets (building / review / merge minutes, from nightwatch.budgets) with the elapsed time of the current phase and a bar. Not money. Token totals are out of scope in v1.
  • Run record card: the frozen run.json, shown field by field and as raw JSON (collapsed).
  • Order: the text of the order file (run.json.order). The reader reads only a path inside ~/.digismith-depot/sessions/ or the autonomous orders folder, up to 64 KB, after realpath. A path outside these folders or a missing file gives "order not available" (not an error).
  • Empty events: "No events yet." Unknown run id: 404 not_found, page says "This run does not exist."

Plan - /plan/:ticket

  • The reader finds the builder run of the ticket (newest builder run), takes its worktree, and calls findWorkspace. It reads progress.md (the SDD ledger) and the plan file named on its first line.
  • Shows: "Task n of m". m = count of ### Task N: headings in the plan. n = tasks with a Task N: complete line. A list of tasks with state (done / fix round R / waiting). Under it the Reviewer verdicts from parseVerdictEntries: scope, round, finding id, verdict (fixed / parked / rejected), reason.
  • A ledger line that does not parse: the verdict list shows "ledger unreadable" and the task list still shows.
  • Empty: "No plan yet for this ticket" (no builder run, no worktree, or no ledger). The Plan nav item opens the page for the ticket under lock; with no lock it shows a ticket picker built from the runs list.

6. Live updates (decision 3)

  • A composable useNightwatchPoll(route, intervalMs = 10000): fetch, then wait 10 s after the answer arrives (no overlap). It stops when the tab is hidden (visibilitychange) and fetches at once when the tab shows again. A failed fetch keeps the last data and backs off to 30 s; it returns to 10 s after one success.
  • The page announces changes in an aria-live="polite" region only for new attention items (so a screen reader is not flooded).
  • The API and the scheduler never push. No websocket in v1.

7. Token burn per hour and seat windows

Out of scope for v1 (Maestro decision, checkpoint 1): token burn per hour, tokens and seat windows. The token counter (DGS-214, dg tokens) counts one ticket by reading whole Claude transcripts. That is too slow for a 10 s poll and has no per-hour series. Seat 5h and weekly usage come from the Claude status line rate_limits probe that runs in a seat's own session; no file or API exposes it to Nexus. The UI keeps the slots ("burn -/h", seat windows, tokens columns) so the layout does not change later. A follow-up ticket should add (a) a small job that writes a per-run token snapshot and (b) a depot file with the last probe of each seat. The Maestro files that follow-up (Maestro decision, checkpoint 1); this ticket does not create it.

8. Visual design and gates

  • Look: Warren's operator console (see the layout mock): a left nav, a top status strip, dense tables, mono for ids and times, section labels in small caps, green for action and health. The mock shows all five screens.
  • Tokens: a new app/assets/nightwatch-tokens.scss with Warren's tokens.css values (colors, radii, fonts) under a .nw scope on the Nightwatch shell. The Life Calendar keeps its own tokens. The file starts with the MIT notice: Copyright (c) 2026 Jaymin West and the permission text, and a line naming github.com/jayminwest/warren docs/ui-revamp/tokens.css. No Warren component code is copied; the layout is rebuilt from the screenshots, so only the tokens carry the notice. Fonts: Inter and JetBrains Mono are NOT loaded from a CDN (the page requests nothing at load except the API). The stacks fall back to system-ui and ui-monospace.
  • Dark and light: dark default like Warren, light by prefers-color-scheme, same switch as the Life Calendar (data-theme). The a11y gate runs both. The plan checks contrast of every token pair with the existing contrast.test.ts pattern (WCAG AA, 4.5:1 text, 3:1 UI).
  • Gates, same as Life Calendar: (1) Storybook stories for each new component and each state (loading, empty, error, loaded) in light and dark; (2) visual baselines in tests/visual from those stories; (3) Playwright e2e in tests/e2e against the stub API server (fixtures, no real API); (4) axe in tests/a11y for each page, and the Storybook axe run; (5) Vitest unit tests for composables, utils and the story list test; (6) the built-page and built-storybook tests; Lighthouse config unchanged. New nuxt generate pages are added to the built-page test.

10. First use

  1. After the merge the conductor builds the CLI (pnpm --filter @digismith/cli build, a finish hook), runs scripts/nexus-api/install.sh (copies the new API files to the depot and restarts the API; the Builder does not run it) and scripts/nexus-web/build-www.sh (static files to DIGISMITH_WWW).
  2. Jack opens https://pazurite.com/nightwatch/. With no run yet, every screen shows its empty state; that proves the read path and the error-free empty case.
  3. The next night scan, or a manual dg run start run, fills Operations and Runs. The first real review is Jack's: he checks the five screens against that data. The ticket is done when he says yes.
