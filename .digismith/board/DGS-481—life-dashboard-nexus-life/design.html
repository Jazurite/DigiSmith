1. Goal and scope

Jack's private life dashboard is the home page of https://pazurite.com/. Version 1 has one widget, the Life Calendar: a life in weeks. The page draws a grid of 90 rows (one per year of age) of 52 boxes. Weeks lived are filled, this week uses the one accent colour, weeks ahead are outlined. Above the grid are weeks lived, weeks left and % lived. Each box has a tooltip with age, week number and date range. The look is black and white with one accent colour, and dark mode follows the device.

The data comes from GET /api/v1/life-calendar on the Nexus API. Access is tailnet only, with no login (login design: DGS-458). Stack: TypeScript on the API (Hono on Node, Jack's call) and on the page (Nuxt 4 with Vue 3, SCSS, generated as static files), one shared Zod schema and Hono's typed client between them, Storybook for the components, Vitest, Playwright, pnpm. This document is the architecture and solution design. It contains no code.

2. Privacy and the date-range decision

Decision A (Jack, 2026-10-16). The tooltips keep their date ranges. They reveal Jack's birth date to anyone who can see the page or the JSON (today only his devices on the tailnet). Jack accepts this.

Why it reveals the date: box 0 of row 0 starts on the birth date, and rows[0].start in the JSON is that date. The API still has no field named for a birth date, and the schema forbids one (section 6).

  • The birth date and the life length are secret. They never appear in the repo, ClickUp, a spec, a plan, a test, a log or a pane. Tests use a fake profile.
  • The real values exist in two places only: the private input file ~/.digismith-depot/nexus/profile.private.json (fields birthDate as YYYY-MM-DD and lifeYears as a number, mode 600), and, encrypted, in the database. The input file stays in plain text until Jack deletes it, so the at-rest protection is only complete after that.
  • Nobody in this work opens the private input file. Only the seed step reads it, when the build runs the step. The seed step never changes or deletes the file; deleting it is Jack's call.
  • FileVault is off on the Workbox and cannot be turned on (it breaks the headless auto-login). The encryption in section 8 is therefore the protection at rest.

3. First step: move the Nexus API onto Hono

The first ticket-sized step of version 1. It changes the framework and nothing else. No life-calendar code is in it. Hono runs on Node through @hono/node-server.

  • What must stay the same: GET /api/v1/power-metrics and its verdict answer the same JSON (same key order, so the body still starts with {"verdict":), the same 200 and 503 codes (no_reading, Retry-After: 5), the same 404 not_found and 405 method_not_allowed with Allow: GET, the same headers (application/json; charset=utf-8, Cache-Control: no-store). The server is still bound to 127.0.0.1:4300 only, and still started by the same LaunchAgent wrapper (nexus-api.sh.tmpl keeps running server.ts).
  • Shape: app.ts exports buildApp(getReading) and returns a Hono app. createApiServer(getReading) stays in server.ts and still returns a Node http.Server that has not started listening (it uses createAdaptorServer from @hono/node-server). The existing tests call server.listen(0, HOST) on it, so they keep working without change. The entry code reads the port and listens on HOST (127.0.0.1). HOST, parsePort, createDefaultReader and the version constant stay as they are.
  • Old behaviours that Hono changes by default, and are set back:
    • Hono answers HEAD with the GET handler. A first middleware on the known paths returns the old 405 with Allow: GET for any method that is not GET, HEAD included.
    • Hono's own 404 and error bodies differ. app.notFound and app.onError return the old JSON.
    • c.json() sends application/json without the charset. The power route sends its body with c.body(JSON.stringify(reading)) and the exact old headers, so the key order and the content type cannot change.
    • Trailing slash and letter case stay exact (Hono's strict default, same as the old code). A query string is ignored on the power route, as before.
  • Proof: the existing tests (server.test.ts and the rest) pass unchanged. One new test compares the bytes of the new response with the bytes the old server produced for the same fixture reading (stored as a fixture file). Another test checks that the server listens on 127.0.0.1 only and that HEAD, POST, an unknown path and a trailing slash behave as before.
  • Logging: a small own logger replaces the console.log start-up line (see section 10).
  • Dependencies: hono and @hono/node-server are new runtime dependencies. The plan pins exact versions (section 4). Checked 2026-10-16: hono 4.13.13, @hono/node-server 2.1.5, @hono/zod-validator 0.9.1 (peer: zod ^3.25.0 || ^4.0.0, so Zod 4 is supported), zod 4.6.7, @electric-sql/pglite 0.5.10. @hono/node-server needs Node 20 or newer; the Workbox has Node 24.

5. Counting rule (birthday-anchored)

  • All dates are date-only, in UTC+7. "Today" is the UTC+7 calendar day, never the UTC day.
  • Row k (age k) starts on the k-th birthday and ends the day before the next one. Box j (0 to 51) covers days 7j to 7j+6 after the row start. Box 51 absorbs the one or two leftover days.
  • A 29 February birthday counts as 1 March in non-leap years. The code and the tests state this rule.
  • Weeks lived are the boxes whose last day is before today. The current box holds today and counts as neither lived nor ahead. Weeks left = total − lived − (1 when a current box exists).
  • Before the birth date: lived is 0 and current is null. Past the last row: everything is lived, current is null and weeks left is 0.
  • The number of rows is lifeYears (version 1 expects 90). weeksTotal = rows × 52.

6. Shared schema and the API JSON

One Zod 4 schema in scripts/nexus-shared/life-calendar.ts describes the response. The inferred types come from it (z.infer). The API and the page both import this file. Zod is chosen for the best type inference and wide familiarity. On the API, @hono/zod-validator uses Zod for request validation. The route is built as one chained new Hono().get(...) expression and app.ts exports type AppType = typeof app. The page imports only that type (import type, so no API code enters the bundle) and calls the API with hc<AppType> from hono/client. The request and response types are then inferred end to end from the one schema.

{
  "readAt": "2026-10-16T14:00:00.000Z",
  "readAtUtc7": "2026-10-16 21:00:00",
  "today": "2026-10-16",
  "timezone": "UTC+7",
  "totals": { "weeksTotal": 4680, "weeksLived": 0, "weeksLeft": 0, "percentLived": 0.0 },
  "current": { "row": 0, "box": 0 },
  "rows": [ { "age": 0, "start": "YYYY-MM-DD", "end": "YYYY-MM-DD", "lived": 52 } ]
}
  • rows[i].lived is the number of filled boxes in row i (0 to 52). The box at current is this week. The remaining boxes are ahead. current is null before birth and after the last row. percentLived has one decimal.
  • The schema is strict: an unknown key, including any birth-date key, fails validation. The seed input schema (birthDate, lifeYears) lives only inside scripts/nexus-api/ and is never shared with the page.
  • API side: Hono does not check responses itself. The handler runs the result through the shared schema (parse) just before c.json(). A bad shape returns 503 internal_invalid and sends no body from the calculation. The route also uses zValidator with an empty strict query schema and a custom failure hook: any query string returns 400 bad_request, and the body never echoes the input. The handler gets its types from the schema, with no casts. c.json() is given the Content-Type: application/json; charset=utf-8 header explicitly; a test checks it.
  • Page side: the typed client gives compile-time types only, so the page also runs the same schema (parse) on the JSON it receives. A bad shape shows the plain error state (section 11).
  • The page draws what the API sends. For the tooltip it adds one thing: box j covers start + 7j days to start + 7j + 6 days, and box 51 ends on end. This is plain day addition, unit-tested.
  • Same headers as the power route: application/json; charset=utf-8 and Cache-Control: no-store. Only GET is allowed (405 with Allow: GET), other paths return 404.

  • Limit: one process owns the data folder. The seed step cannot run while the API runs. The order is: stop the API, seed, start the API. The API is restarted by hand anyway (no deploy pipeline, DGS-467).

8. Encryption at rest and the key

The blob

  • One JSON blob {birthDate, lifeYears} is encrypted with AES-256-GCM (Node crypto). The nonce is 12 random bytes, new on every seed. The 16-byte tag is stored with the ciphertext. The associated data is the fixed text nexus-profile:v1, so a blob cannot be reused for another purpose.
  • The API reads the key once at start and keeps it in memory. It decrypts on each request. It never caches the plaintext, never logs it and never writes it anywhere.

Key providers

A small interface getKey() with two implementations. One setting chooses between them: NEXUS_KEY_PROVIDER=file|keychain. The API defaults to file when the setting is absent, so the first deploy needs no wrapper change. The Keychain task adds the setting to the wrapper (written by install.sh). The code keeps both providers once that task is done.

  1. File (the provider for the first deploy). A 32-byte key in ~/.digismith-depot/nexus/profile.key, mode 600, checked at start. The seed step creates it if it is missing and never overwrites an existing key. The API refuses to start the calendar route if the file is not mode 600. Limit, stated plainly: the key file sits in the same folder as the database folder (nexus/db/), and if the whole depot is backed up, the key goes into the same backup as the data. The encryption then protects only against someone who gets the database folder without the key file. Mode 600 and mode 700 protect against other local users. This is the weaker option, and the Keychain ticket exists to replace it.
  2. Keychain (a later ticket). The service com.jazurite.digismith.nexus, account profile-key in the macOS login Keychain. The API runs security find-generic-password -s ... -a ... -w through execFile with a timeout. The key would be stored with security add-generic-password; the key is in a process argument for a moment while it is stored, so another local user could see it (a one-user machine; the ticket names the risk). Moving from the file to the Keychain means: store the key in the Keychain, switch the setting, restart the API, then Jack deletes the key file (a re-seed is not needed, the key is the same).

The Keychain probe is a separate, later ticket

From an SSH-like session, security answered "User interaction is not allowed". Before the Keychain provider is switched on, a probe script and a small probe LaunchAgent must prove that the LaunchAgent can read the item. The probe writes only ok or fail plus the key length to a log, never the key. Jack loads the probe LaunchAgent, so this ticket waits for him.

Risk the probe must settle. With automatic login the login Keychain may stay locked after a reboot, because nobody typed the password. The probe runs after a reboot too. If it fails, the file provider stays, by Jack's decision, with the backup limit above told to him.

If the key is not available (no key file, or later a locked Keychain), the API still starts. It returns 503 key_unavailable for the calendar route and serves everything else. It does not crash and it does not fall back silently.

9. Seed step

node --experimental-strip-types scripts/nexus-api/seed-profile.ts [--from <path>]. The deploy runs it (not Jack), with the API stopped. Jack can run it again later to change the profile.

  1. Read the input file (default ~/.digismith-depot/nexus/profile.private.json). Refuse if it is not mode 600.
  2. Validate with the private seed schema (birthDate a real YYYY-MM-DD date, lifeYears a whole number from 1 to 120).
  3. Get the key from the provider. With the file provider, create a new 32-byte key at ~/.digismith-depot/nexus/profile.key (mode 600) only when none exists yet, and never overwrite one.
  4. Encrypt. Upsert the single row in the database (created with mode 700).
  5. Print nothing on success (exit code 0). On failure print only the name of the invalid field or the failing step, and exit non-zero. It never prints a value, a key or a value inside an error. It never changes or deletes the input file; Jack decides about it.

Logging (an own small logger, no dependency)

Hono has no structured logger. hono/logger prints plain text and cannot carry an error code, and pino would be a second dependency for one route. The design uses about 20 lines in logger.ts: a middleware that writes one JSON line per request to stdout. The LaunchAgent already sends stdout to the Nexus log folder.

  • A log line has fixed fields only, written by this one function: time, level, method, path without the query string, status, duration in milliseconds, and an error code when there is one. The handler sets the code on the request context (c.set('errorCode', ...)). Nothing else can be added to a line.
  • No other code calls console.*. A test scans the API source files and fails on any console. call outside logger.ts.
  • No headers, no query string, no request or response body, no error message and no stack are logged. The crypto, key and storage modules throw errors with a code and no message built from data. app.onError logs the code only, never the error object.
  • The level is info. There is no debug logging in code that handles the profile. The start-up line (listening on 127.0.0.1:4300) goes through the same logger.

11. The page: Nuxt and Vue

The visual reference is the Designer's ui-design.md and mock.html in this board folder (all mock data is fake: born 1990-01-01, "today" 2026-10-16). This spec decides the structure. The look, tokens, states and wording come from the Designer's files.

Rendering mode: static generation

The page is a Nuxt 4 app built with nuxt generate (prerendered HTML plus JS), served by Caddy as files. The data is fetched in the browser through Hono's typed client. This adds no new server process and no new LaunchAgent.

  • Why not SSR (a running Nitro server): it needs a second always-on process and a LaunchAgent, and it adds nothing here. The data is private and live, so it must be fetched per visit anyway, and it must never be baked into HTML or cached. The prerendered HTML holds the header, the widget frame, the stat placeholders and the grid placeholder at their final size. Static files from Caddy have the fastest first byte. So the first paint does not wait for data, and Core Web Vitals do not give a reason for SSR (section 13). If a later widget needs server-rendered data, it gets its own decision.
  • The build never touches the API or the profile. nuxt generate runs with no access to the API. All data code runs on the client after mount. A test greps the built files for the fixture's fake values and for any API response shape, and fails if found.
  • Page content that depends on "now" (today's date in the header) is rendered on the client only, in a slot of fixed size, so the prerendered HTML is never stale and never shifts.
  • No Nuxt pages or router (one page), no Nitro server routes, no Nuxt modules except @nuxtjs/storybook. app/app.vue is the shell.
  • The API base is relative (/api/...), so the same build works on the tailnet host and in the test server.

Storybook

  • Choice: the @nuxtjs/storybook module (10.0.1) with Storybook 10.6.2. It reuses Nuxt's Vite config, so stories see the same auto-imports and aliases as the page. The plain @storybook/vue3-vite builder would need that setup repeated by hand.
  • Stories live next to the components (*.stories.ts). One story per widget state on LifeCalendarView: loaded, loading, error, key unavailable, empty, before birth, past 90 years. Plus one story per other component state (tooltip placements, the three stat forms, legend, buttons, panels, a small three-state grid).
  • Fake data only. A fixture module builds the data by calling the API's pure life-math function with the fake profile (born 1990-01-01, today 2026-10-16), so fixtures cannot drift from the real counting rule. The expected numbers match the Designer's mock: 1,913 lived, 2,766 left, 40.9%, this week at row 36, box 41. A decorator replaces fetch with a function that throws, so no story can reach the API.
  • Light and dark: the tokens follow prefers-color-scheme. A small toolbar item (device, light, dark) sets a data-theme attribute that the tokens also honour, so Jack can compare both on one device. The tests use browser colour-scheme emulation instead, which is how the real page behaves.
  • Hosting: a static Storybook build is served at https://pazurite.com/storybook/ through Caddy (section 14), tailnet only, no login. I see no reason against it. Conditions: stories use fake data only and cannot fetch (above), and the Storybook build is rebuilt by the same install step as the page. It is several megabytes, but it is a separate path and does not touch the page's Core Web Vitals.

12. Accessibility

Target: WCAG 2.2 level AA, in light and dark. The Designer's section 8 is the detailed pattern. This section sets what must be true and how it is checked.

  • Grid: role="grid" with a name that explains the keys, role="row" rows, a role="rowheader" per row ("Age 36") and role="gridcell" boxes. A column header row (role="columnheader") carries "Week 1", 13, 26, 39, 52, and every box's accessible name also holds its week number. The ruler is the visual form of the headers. (If the 4,680 cells cost too much in the measured render budget, the fallback order is in section 13.)
  • Labels on every box: "Age 36, week 42 of 52, 12 October 2026 to 18 October 2026, this week". A screen reader user gets the full text without the tooltip.
  • Tooltip by keyboard: when a box has focus, the tooltip shows over it and the box has aria-describedby pointing at the one tooltip element (role="tooltip"). Escape hides it (WCAG 1.4.13: dismissible, hoverable, persistent). The touch readout is a live status region.
  • Keyboard: the grid is one tab stop with a roving tabindex, starting on this week. Keys: arrows, Home, End, Ctrl+Home, Ctrl+End, Page Up, Page Down, Escape (Designer, section 8). A "Skip to the calendar" link is the first tab stop. Focus is visible (2 px ink ring, 3 px on this week) and never hidden by sticky content (WCAG 2.4.11).
  • Live regions: the stat area is a polite live region and has aria-busy while loading. The state panels use role="alert" (error, locked) and role="status" (empty). After Retry succeeds, focus moves to the grid. The skeleton boxes are aria-hidden.
  • Contrast and meaning: text 4.5:1 or more, ahead outlines and the accent box 3:1 or more against the page, in both themes (the vermilion accent #e8401c on white and #ff5a3c on near-black are checked by test, not by eye). Meaning is never colour alone: lived is filled, ahead is an outline, this week has a ring and a word in the legend and the tooltip.
  • Target size (WCAG 2.5.8): buttons are 44 px. The grid boxes are smaller than 24 px, so the grid uses the spec exception for an equivalent: the nearest-box selection on touch and the full keyboard control. The test notes this exception.
  • Other: forced colours (lived CanvasText, ahead GrayText, this week Highlight) and reduced motion (pulse and fades stop).

How it is checked

  • axe-core in Playwright (@axe-core/playwright) runs on the real page in the end-to-end tests and on every Storybook story, in light and dark, with the tags wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa. The run fails on any violation. There is no allow-list; an exception needs its own reason in the test file and Jack's sign-off.
  • Storybook a11y addon (@storybook/addon-a11y) shows the same axe results in the Storybook panel for Jack and the builder. The failing gate is the Playwright run over the built Storybook. It uses the same axe engine and the same rules. Failing from the addon itself would need @storybook/addon-vitest, which wants Vitest 3 or newer in browser mode and the repo root has Vitest 2; I do not do that in version 1.
  • Keyboard tests in Playwright press each key and assert focus and the tooltip text. A contrast test reads the computed token colours in both schemes and checks the ratios.
  • Automated checks do not find everything. A manual screen-reader pass (VoiceOver) is a step before release, done by Jack or by a note in the acceptance step for the Jack sign-off ticket.

13. Performance: Core Web Vitals

Budgets at Google's "good" thresholds for the dashboard page: LCP under 2.5 s, INP under 200 ms, CLS under 0.1. They hold on a desktop profile and on a phone profile (390 px wide, CPU slowed 4 times). All measurements stay local. There is no external analytics and no field monitoring service.

Measurement

  • Lighthouse CI (@lhci/cli) runs against the built page served locally by the test server (the same stub API server the end-to-end tests use), 3 runs, median, mobile and desktop presets. Assertions: LCP at most 2,500 ms, CLS at most 0.1, and Total Blocking Time at most 200 ms as the lab stand-in for INP (Lighthouse's navigation run does not measure INP). Results are written to a local folder, never uploaded.
  • web-vitals in a Playwright test measures LCP, CLS and INP on the real page with scripted interaction: pointer moves across many boxes, a click, tap, keyboard arrows through rows and Escape. The test fails over any budget. It runs with the desktop profile and the phone profile (CPU throttle through the browser protocol).
  • A render guard: the grid's render task is timed with the User Timing API. The budget is a guard value the plan sets after the first measure (starting point: under 100 ms desktop, under 400 ms on the 4 times slowed phone profile).

Design rules that keep the budgets

  • 4,680 boxes, render cost. The boxes are plain elements, not components. The rows render once and are marked static (v-once or v-memo) until the data signature changes (midnight refresh). Styles use classes only, with contain: layout paint on the grid. If the measured render budget fails, the fallbacks, in order: (1) the per-box aria-label is written on first hover or focus and the row carries the label until then, keeping the accessible names complete for the focused cell and the row; (2) render the grid in decade chunks with requestIdleCallback. The plan measures first and changes nothing before that.
  • Layout shift while data loads. The prerendered HTML, the client's first render and the skeleton all use the same markup and size. The skeleton is one element with the grid's exact height, computed from the same CSS variables as the grid (rows, box size, gap, decade spacing), with the boxes drawn by a CSS pattern. It keeps the prerendered HTML small and the DOM light before data arrives. The stat slots have fixed height and tabular figures. The state panel sits on top of the ghost grid and takes no space. The header date has a fixed slot. The system font stack means no font swap. Version 1 expects 90 rows; if the data has another row count, the grid height changes once, which is the only allowed shift (and the shift test uses 90).
  • LCP. The largest element is text (the title or the stat), so there is no image to wait for. It appears from the prerendered HTML without waiting for JS or data. No web fonts, no external requests, no analytics.
  • INP and a fast tooltip. One delegated pointermove listener. The handler finds the box from the event target (one DOM lookup), does no layout read while moving, updates the tooltip only when the box changes, and moves it with a transform inside one animation frame. Hover work stays under a few milliseconds even on the slowed phone profile.
  • Delivery. Caddy compresses (gzip and zstd) and sends hashed assets with a long immutable cache (section 14). No CDN in version 1.

14. Caddy: the page, Storybook, caching

  • caddy-run.sh exports DIGISMITH_WWW="$D/nexus/www".
  • In the pazurite.com block, the last handle becomes a file server with root * {env.DIGISMITH_WWW} instead of the 404. /api/* stays above it and still goes to 127.0.0.1:4300. Unknown files return 404.
  • Storybook is published into $DEPOT/nexus/www/storybook/. The same file server serves https://pazurite.com/storybook/ and redirects /storybook to /storybook/. No second route is needed.
  • Caching: index.html files (the page and Storybook) are sent with Cache-Control: no-cache. The hashed build assets (/_nuxt/* and Storybook's hashed files) are sent with public, max-age=31536000, immutable.
  • Compression: encode zstd gzip in the pazurite.com block (HTML, JS, CSS, JSON).
  • A change to a static file needs no restart. The Caddyfile change needs one Caddy restart.

15. Tests

Backend (Vitest, repo root, Vitest 2)

  • Hono move (step 1): the existing server tests, unchanged; a byte comparison of the power response against a stored fixture; 127.0.0.1 binding; HEAD, POST, unknown path and trailing slash as before; the 503 no_reading case.
  • Life math: fixed "now" values and a fake birth date. Cases: birthday today, the day before a birthday, the 29 February birthday, 52-box rows and the leftover days, before birth, past the last row, UTC+7 midnight edges, totals add up to rows times 52.
  • Crypto: a fixed fake key and a fake profile. Round trip, a changed ciphertext, a changed tag, a wrong key, a wrong associated-data text, a new nonce on each seed.
  • Key providers: the Keychain provider runs against an injected fake security runner (found, not found, locked, timeout). The file provider checks mode 600 and a missing file.
  • Storage and seed: PGlite in memory for most tests. One test uses a real data folder in a temp directory, checks mode 700 and checks that the files do not contain the fake birth date as plain text. Seed tests use a fake JSON file in a temp folder: mode check, invalid input, and a capture that shows no value or key in any output.
  • Life-calendar route: the 200 shape, the key list has no birth-date key, every 503 code, 400 for a query string, 405 and 404, a response failing the shared schema becomes 503 internal_invalid, and the charset header.
  • No secret in a log line: the app is built with a logger whose output function collects every line. A fake profile, a fake key and the matching fake ciphertext are loaded. The test runs a good request, then every error path (missing profile, key unavailable, a changed blob, a wrong key, a bad response, a query string, an Authorization header, an error thrown by a fake provider whose message holds the fake values). It asserts that the collected log text contains none of: the fake birth date (in any common format), the fake life length as a field, the key (hex and base64), the ciphertext and the nonce. The same test scans the API source files and fails on any console. call outside logger.ts.
  • Shared schema: a strict-key test (an extra key is rejected), the error-code schema, and a pattern check that no source file, fixture or snapshot outside the test folders holds a birth-date literal.

Page (Vitest in the page package, Vitest 5)

  • Units: the tooltip range math (box 51 ends on the row's end), the keyboard navigation rules (nextCell), the nearest-box rule, the tooltip placement, the error-code mapping, the date formats.
  • Components (@nuxt/test-utils with @vue/test-utils, happy-dom): each component and LifeCalendarView in every state: the roles, names and live regions, the roving tabindex and each key, the tooltip text and aria-describedby, the busy and retry behaviour of the panels, the three stats and their labels.
  • Type check, end to end: nuxt typecheck (vue-tsc) and tsc --noEmit over the API, the page and the shared file. A type test (expectTypeOf) checks that the type the page gets from hc<AppType> equals the type inferred from the shared schema.
  • Build checks: the generated files contain no fake profile value and no API response shape; the built page makes no request except to /api/.

Storybook as the state catalogue

  • Every widget state has a story (section 11). The static build is the input of the visual and accessibility runs below.

End to end (Playwright)

  • Against a throwaway server (tests/serve-stub.ts): the built page files plus a stub /api/v1/life-calendar that answers from a fake profile (born 1990-01-01, fixed "today"). It listens on a high port on 127.0.0.1 only. The same server is used by Lighthouse CI.
  • Checks: 90 rows of 52 boxes, the three states, the stats line, the tooltip text, dark mode (colorScheme: 'dark'), the error, locked and empty panels (the stub answers each 503 code on request), Retry, the keyboard keys, and the midnight refresh with a fake clock.

Visual regression (Playwright toHaveScreenshot)

  • Every story of the static Storybook build, in light and dark (colour-scheme emulation). The seven LifeCalendarView states run at two widths (390 px and 1,000 px); the other stories run at one width.
  • Baselines are committed (fake data only). No SaaS such as Chromatic: everything stays private.
  • Stability: animations disabled, reduced motion on, a fixed clock, web fonts absent, and a small allowed difference (maxDiffPixelRatio 0.001). The baselines depend on the OS and the Chromium build, because the page uses the system font stack. They are made on the Workbox, which is also where the tests run, with the pinned Playwright version. A Playwright or macOS update that changes pixels means a baseline update in its own ticket; a baseline change in a pull is always reviewed as an image diff.
  • Playwright downloads its own Chromium for this (playwright install chromium). That install is part of the build order, not of this order.

Accessibility and performance runs

Caddy

16. Deploy steps (the Maestro or the future Releaser; nothing is done in this order)

  1. Merge.
  2. Provider: the first deploy uses the file key (NEXUS_KEY_PROVIDER=file). The Keychain probe and the switch to the Keychain are a later ticket that needs Jack.
  3. From the repo checkout: pnpm install, then pnpm exec playwright install chromium (build order only), then the build: nuxt generate and the Storybook build. The page output and the Storybook output go into a new folder next to www/ and are swapped in with one rename, so the site is never half-updated.
  4. sh scripts/nexus-api/install.sh (copies the API source and nexus-shared, runs pnpm install --prod in the depot copy) and sh scripts/caddy/install.sh.
  5. Stop the API. The build runs the seed step once (it reads the private input file, creates the key file if missing, prints nothing). Start the API.
  6. Restart Caddy once (the Caddyfile changed). The Nexus API and Caddy are already installed as LaunchAgents and the Maestro restarts them; no new LaunchAgent is needed, because the page is static files.
  7. Health check: /api/v1/life-calendar returns 200, / returns the page, /storybook/ returns Storybook, and the totals are in a plausible range. The check never prints the birth date.
