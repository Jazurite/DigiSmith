1. Goal and scope

Jack's private life dashboard is the home page of https://pazurite.com/. Version 1 has one widget, the Life Calendar: a life in weeks. The page draws a grid of 90 rows (one per year of age) of 52 boxes. Weeks lived are filled, this week uses the one accent colour, weeks ahead are outlined. Above the grid are weeks lived, weeks left and % lived. Each box has a tooltip with age, week number and date range. The look is black and white with one accent colour, and dark mode follows the device.

The data comes from GET /api/v1/life-calendar on the Nexus API. Access is tailnet only, with no login (login design: DGS-458). Stack: TypeScript on the API (Fastify, a battle-tested backend framework, Jack's call) and on the page, SCSS, Vitest, Playwright, pnpm, no UI framework. This document is the architecture and solution design. It contains no code.

2. Privacy and the date-range decision

Decision A (Jack, 2026-10-16). The tooltips keep their date ranges. They reveal Jack's birth date to anyone who can see the page or the JSON (today only his devices on the tailnet). Jack accepts this.

Why it reveals the date: box 0 of row 0 starts on the birth date, and rows[0].start in the JSON is that date. The API still has no field named for a birth date, and the schema forbids one (section 6).

  • The birth date and the life length are secret. They never appear in the repo, ClickUp, a spec, a plan, a test, a log or a pane. Tests use a fake profile.
  • The real values exist in two places only: the private input file ~/.digismith-depot/nexus/profile.private.json (fields birthDate as YYYY-MM-DD and lifeYears as a number, mode 600), and, encrypted, in the database.
  • Nobody in this work opens the private input file. Only the seed step reads it, when Jack runs the step.
  • FileVault is off on the Workbox and cannot be turned on (it breaks the headless auto-login). The encryption in section 8 is therefore the protection at rest.

3. First step: move the Nexus API onto Fastify

The first ticket-sized step of version 1. It changes the framework and nothing else. No life-calendar code is in it.

  • What must stay the same: GET /api/v1/power-metrics and its verdict answer the same JSON (same key order, so the body still starts with {"verdict":), the same 200 and 503 codes (no_reading, Retry-After: 5), the same 404 not_found and 405 method_not_allowed with Allow: GET, the same headers (application/json; charset=utf-8, Cache-Control: no-store). The server is still bound to 127.0.0.1:4300 only, and still started by the same LaunchAgent wrapper (nexus-api.sh.tmpl keeps running server.ts).
  • Shape: app.ts exports buildApp(getReading) and returns a Fastify instance. server.ts stays the entry file: it reads the port, calls buildApp and listens on HOST (127.0.0.1). HOST, parsePort, createDefaultReader and the version constant stay as they are.
  • Old behaviours that Fastify changes by default, and are set back: Fastify answers HEAD for every GET route (set exposeHeadRoutes: false, so HEAD still gets 405); it answers an unregistered method with its own 404 (a catch-all for the known paths returns the old 405 with Allow: GET); its own 404 and error bodies differ (a custom not-found handler and error handler return the old JSON); trailing slash and letter case stay exact (the Fastify defaults, same as the old code). A query string is ignored on the power route, as before.
  • The power route has no response schema. The body is sent as the reading object serialized by JSON.stringify, so the key order cannot change.
  • Proof: the existing tests (server.test.ts and the rest) pass with only their start-up helper changed (it builds the app and listens on port 0 of 127.0.0.1). One new test compares the bytes of the new response with the bytes the old server produced for the same fixture reading (stored as a fixture file). Another test checks the listen address is 127.0.0.1 and that HEAD, POST and a trailing slash behave as before.
  • Logging: Fastify's built-in logger (pino) replaces the console.log start-up line. The LaunchAgent already writes stdout and stderr to the Nexus log folder. See section 10 for what a log line may carry.
  • Dependencies: fastify and fastify-type-provider-zod are new runtime dependencies. The plan pins exact versions and confirms that the provider version supports Zod 4 before anything is built on it.

5. Counting rule (birthday-anchored)

  • All dates are date-only, in UTC+7. "Today" is the UTC+7 calendar day, never the UTC day.
  • Row k (age k) starts on the k-th birthday and ends the day before the next one. Box j (0 to 51) covers days 7j to 7j+6 after the row start. Box 51 absorbs the one or two leftover days.
  • A 29 February birthday counts as 1 March in non-leap years. The code and the tests state this rule.
  • Weeks lived are the boxes whose last day is before today. The current box holds today and counts as neither lived nor ahead. Weeks left = total − lived − (1 when a current box exists).
  • Before the birth date: lived is 0 and current is null. Past the last row: everything is lived, current is null and weeks left is 0.
  • The number of rows is lifeYears (version 1 expects 90). weeksTotal = rows × 52.

6. Shared schema and the API JSON

One Zod 4 schema in scripts/nexus-shared/life-calendar.ts describes the response. The inferred types come from it (z.infer). The API and the page both import this file. Zod is chosen for the best type inference and wide familiarity. On the API, fastify-type-provider-zod connects the same schema to Fastify: it drives request validation, the response check and the route types.

{
  "readAt": "2026-10-16T14:00:00.000Z",
  "readAtUtc7": "2026-10-16 21:00:00",
  "today": "2026-10-16",
  "timezone": "UTC+7",
  "totals": { "weeksTotal": 4680, "weeksLived": 0, "weeksLeft": 0, "percentLived": 0.0 },
  "current": { "row": 0, "box": 0 },
  "rows": [ { "age": 0, "start": "YYYY-MM-DD", "end": "YYYY-MM-DD", "lived": 52 } ]
}
  • rows[i].lived is the number of filled boxes in row i (0 to 52). The box at current is this week. The remaining boxes are ahead. current is null before birth and after the last row. percentLived has one decimal.
  • The schema is strict: an unknown key, including any birth-date key, fails validation. The seed input schema (birthDate, lifeYears) lives only inside scripts/nexus-api/ and is never shared with the page.
  • API side: the life-calendar route declares the shared schema as its response schema. Fastify checks the response against it before it is sent. A bad shape returns 503 internal_invalid and sends no body from the calculation. The route also declares an empty strict query schema: any query string returns 400 bad_request. The route handler gets its types from the schema, with no casts.
  • Page side: the page validates what it receives. A bad shape shows the plain error state (section 11).
  • The page draws what the API sends. For the tooltip it adds one thing: box j covers start + 7j days to start + 7j + 6 days, and box 51 ends on end. This is plain day addition, unit-tested.
  • Same headers as the power route: application/json; charset=utf-8 and Cache-Control: no-store. Only GET is allowed (405 with Allow: GET), other paths return 404.

7. Database: PGlite

Jack's toolchain says PostgreSQL. The design uses PGlite, embedded PostgreSQL for Node (WebAssembly), with one pnpm dependency and no server.

Testsin-memory database, no setupa test database must exist
Data~/.digismith-depot/nexus/db/, mode 700the Postgres data directory
  • This Mac is Intel (x86_64). PGlite is WebAssembly, so the architecture does not matter.
  • It is still PostgreSQL, with the same SQL. A later move to a real server is a dump and restore. That would be its own ticket.
  • Limit: one process owns the data folder. The seed step cannot run while the API runs. The order is: stop the API, seed, start the API. The API is restarted by hand anyway (no deploy pipeline, DGS-467).
  • Cost: the API process holds the database in memory (roughly 100 MB or more). The storage ticket measures it.
  • Table: profile(id INTEGER PRIMARY KEY CHECK (id = 1), key_version INTEGER NOT NULL, nonce BYTEA NOT NULL, ciphertext BYTEA NOT NULL). One row. There is no plaintext column.
  • The API opens the database at start and checks that the data folder is mode 700. A wrong mode is the same failure as an invalid profile (503 profile_invalid).

8. Encryption at rest and the key

The blob

  • One JSON blob {birthDate, lifeYears} is encrypted with AES-256-GCM (Node crypto). The nonce is 12 random bytes, new on every seed. The 16-byte tag is stored with the ciphertext. The associated data is the fixed text nexus-profile:v1, so a blob cannot be reused for another purpose.
  • The API reads the key once at start and keeps it in memory. It decrypts on each request. It never caches the plaintext, never logs it and never writes it anywhere.

Key providers

A small interface getKey() with two implementations. One setting chooses between them: NEXUS_KEY_PROVIDER=keychain|file, written into the API wrapper by install.sh.

  1. Keychain (preferred). The service com.jazurite.digismith.nexus, account profile-key in the macOS login Keychain. The API runs security find-generic-password -s ... -a ... -w through execFile with a timeout. The seed step stores the key with security add-generic-password. The key is in a process argument for a moment while it is stored, so another local user could see it. This is a one-user machine, and the seed ticket names the risk.
  2. File (fallback, a deliberate setting only). ~/.digismith-depot/keys/nexus-profile.key, mode 600, checked at start. The data is in nexus/db/ and the key is in keys/, so the key is not next to the data. Limit: if the whole depot is backed up, the key file goes into the same backup as the data. The Keychain does not have that problem.

The Keychain probe comes first

From an SSH-like session, security answered "User interaction is not allowed". The build must therefore prove that the LaunchAgent can read the item before anything else depends on it. A probe script and a small probe LaunchAgent read the item and write only ok or fail plus the key length to a log. They never write the key. Jack loads the probe LaunchAgent.

Risk the probe must settle. With automatic login the login Keychain may stay locked after a reboot, because nobody typed the password. The probe runs after a reboot too. If it fails, the file provider is chosen on purpose, by Jack, and the backup limit above is told to him.

If the Keychain is locked while the API runs, the API still starts. It returns 503 key_unavailable for the calendar route and serves everything else. It does not crash and it does not fall back silently.

9. Seed step

node --experimental-strip-types scripts/nexus-api/seed-profile.ts [--from <path>], run by Jack with the API stopped.

  1. Read the input file (default ~/.digismith-depot/nexus/profile.private.json). Refuse if it is not mode 600.
  2. Validate with the private seed schema (birthDate a real YYYY-MM-DD date, lifeYears a whole number from 1 to 120).
  3. Get the key from the provider. Create a new 32-byte key only when none exists yet.
  4. Encrypt. Upsert the single row in the database (created with mode 700).
  5. Print only profile saved, or the name of the invalid field. It never prints a value, a key or a value inside an error. It never deletes the input file. It prints "you can delete the input file now" and Jack decides.

A 503 sends Retry-After: 5, as the power route does.

Logging (Fastify's built-in logger, pino)

  • No error message or log line carries a profile value, a key, a ciphertext or a response body. A log line carries a request id, the method, the path, the status, the timing and an error code.
  • Pino's request logs are kept, but with fixed serializers that print only the method, the path (without the query string) and the status. The Authorization header and all other headers are never logged. The pino redact option also lists the response body, headers and any profile or key field as a second guard.
  • The crypto, key and storage modules throw errors with a code and no message text built from data. The error handler logs the code only, never the error object (which would print its message and stack).
  • The log level is info. There is no debug or trace logging in code that handles the profile.

11. The page

  • Files in scripts/nexus-web/: index.html, main.ts, grid.ts, tooltip.ts, styles.scss. Plain TypeScript and the DOM, no framework.
  • The grid is a CSS grid of 4,680 divs with data-row and data-box, easy for Playwright to query.
  • States: lived is filled, current uses the accent colour, ahead is outlined.
  • Above the grid: weeks lived, weeks left, % lived.
  • One shared tooltip element follows the pointer and shows age, week number (1 to 52) and the date range. A tap shows it on touch.
  • Look: black and white, one accent colour, dark mode through prefers-color-scheme. Colour tokens on :root.
  • The page fetches with cache: 'no-store'. It refreshes once at the UTC+7 midnight so "this week" stays right if the tab stays open.
  • Phone access works only when the phone is on Tailscale.

12. Caddy route for /

  • caddy-run.sh exports DIGISMITH_WWW="$D/nexus/www".
  • In the pazurite.com block, the last handle becomes a file server with root * {env.DIGISMITH_WWW} instead of the 404. /api/* stays above it and still goes to 127.0.0.1:4300. Unknown files return 404. index.html is sent with Cache-Control: no-cache.
  • A change to a static file needs no restart. The Caddyfile change needs one Caddy restart.

13. Tests

  • Vitest, Fastify move (step 1): the existing server tests, unchanged except their start-up helper; a byte comparison of the power response against a stored fixture; 127.0.0.1 binding; HEAD, POST, unknown path and trailing slash as before; the 503 no_reading case.
  • Vitest, life math: fixed "now" values and a fake birth date. Cases: birthday today, the day before a birthday, the 29 February birthday, 52-box rows and the leftover days, before birth, past the last row, UTC+7 midnight edges, totals add up to rows × 52.
  • Vitest, crypto: a fixed fake key and a fake profile. Round trip, a changed ciphertext, a changed tag, a wrong key, a wrong associated-data text, a new nonce on each seed.
  • Vitest, key providers: the Keychain provider runs against an injected fake security runner (found, not found, locked, timeout). The file provider checks mode 600 and a missing file.
  • Vitest, storage and seed: PGlite in memory for most tests. One test uses a real data folder in a temp directory, checks mode 700 and checks that the files do not contain the fake birth date as plain text. Seed tests use a fake JSON file in a temp folder: mode check, invalid input, and a capture that shows no value or key in any output.
  • Vitest, life-calendar route: the 200 shape, the key list has no birth-date key, every 503 code, 400 for a query string, 405 and 404, and that a response failing the shared schema becomes 503 internal_invalid.
  • Vitest, no secret in a log line: the app is built with a pino stream that collects every line. A fake profile, a fake key and the matching fake ciphertext are loaded. The test runs a good request, then every error path (missing profile, key unavailable, a changed blob, a wrong key, a bad response, a query string, an Authorization header, an error thrown by a fake provider whose message holds the fake values). It then asserts that the collected log text contains none of: the fake birth date (in any common format), the fake life length as a field, the key (hex and base64), the ciphertext and the nonce. The test also runs once at debug level to catch a debug line added later.
  • Vitest, shared schema: a strict-key test (an extra key is rejected). The API and the page import the same file, so the types cannot drift.
  • Vitest, page units: the tooltip range math.
  • Playwright: against a throwaway server with a stub API on a high port. It checks 90 rows of 52 boxes, the three states, the stats line, the tooltip text, dark mode (colorScheme: 'dark') and the error state with Retry.
  • Caddy: extend scripts/caddy/test-config.mjs so / serves the index file, /other returns 404 and /api/* still proxies.
  • A pattern check that no source file, fixture or snapshot outside the test folders holds a birth-date literal. Tests use a fake date only.

14. Deploy steps (Jack or the future Releaser; nothing is done in this order)

  1. Merge.
  2. Prove the Keychain with the probe (load the probe LaunchAgent, also after a reboot). Choose the provider.
  3. sh scripts/nexus-api/install.sh (copies the API source and nexus-shared, runs pnpm install --prod in the depot copy, builds www/) and sh scripts/caddy/install.sh.
  4. Stop the API. Run the seed step once. Start the API.
  5. Restart Caddy once (the Caddyfile changed).
  6. Health check: /api/v1/life-calendar returns 200, / returns the page, and the totals are in a plausible range. The check never prints the birth date.
