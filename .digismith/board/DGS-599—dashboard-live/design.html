1. Goal

3. Subdomain, Caddy and DNS

How the front door works today (read 2026-10-24, nothing changed)

  • The Caddyfile source is scripts/caddy/Caddyfile; scripts/caddy/install.sh copies it to ~/.digismith-depot/caddy/Caddyfile (the two are the same today). bin/caddy-run starts Caddy with only CLOUDFLARE_API_TOKEN and DIGISMITH_WWW=$DEPOT/nexus/www. Caddy listens on 127.0.0.1:8443 only, admin off.
  • The tailnet-only door: Tailscale Serve forwards TCP 443 on the Workbox's tailnet addresses to 127.0.0.1:8443. Caddy picks the site by the TLS server name. Nothing is open outside the tailnet.
  • Two site blocks: opencode.pazurite.com (reverse proxy to 4198) and pazurite.com (/api/* to the Nexus API on 4300 without the Authorization header; everything else static files from {env.DIGISMITH_WWW}). Each gets its certificate by the Cloudflare DNS challenge.
  • DNS (DGS-325): Cloudflare DNS-only (grey cloud) A records to the Workbox's Tailscale address 100.108.1.19 for pazurite.com and opencode.

Decision: a second static build, its own web root, at base path /

Oculus is served at the root of its own host, so its router paths are /, /runs/, and so on. The Life Calendar already owns / on pazurite.com. One build cannot serve both at /, and a base path (app.baseURL: '/oculus/') with a Caddy rewrite would leave the browser URL and the router out of step. So:

  • The same Nuxt project builds two sites, chosen by NEXUS_SITE=life|oculus at build time. A pages:extend hook in nuxt.config.ts keeps only that site's pages: the Oculus pages live in app/pages/oculus/ and the hook maps /oculus/runs to /runs for the Oculus build; the Life build drops them. app.baseURL stays '/' for both. Each build has its own _nuxt/, so assets never mix.
  • build-www.sh builds both: the Life site to $DEPOT/nexus/www.d/<stamp>/ (unchanged, Storybook stays at pazurite.com/storybook/), the Oculus site to $DEPOT/nexus/oculus.d/<stamp>/, and switches the symlinks nexus/www and nexus/oculus, each with one rename, as today. The same dotfile and build-path checks run on both. Old build folders are kept.
  • caddy-run exports DIGISMITH_OCULUS_WWW=$DEPOT/nexus/oculus and, like today, points it at an empty placeholder build folder before the first build (fail closed: never an empty root).

Same origin for the API

Yes: oculus.pazurite.com proxies /api/* to the Nexus API exactly as pazurite.com does. The pages keep calling the relative path /api/v1/nightwatch/…, so there is no CORS and no new API setting. The proxy goes into one Caddy snippet that both blocks import, so the two cannot drift.

Decision: the /nightwatch/ redirect is a Caddy redirect

A Caddy redir on pazurite.com, not redirect pages in the Life build. It is one rule; it keeps the path and the query (/nightwatch/run/?id=x → https://oculus.pazurite.com/run/?id=x); it works without JavaScript; it answers before any file lookup, so no old page can be served. A redirect page could keep the query only with JavaScript and would keep a copy of the old pages in every Life build. The Caddy change is needed for the subdomain anyway. It is a 302 (temporary) for the first month, so a browser does not cache it while the setup is new; a later order can make it 301.

Order rule: the Caddy and DNS step (below) is done before the first build-www.sh run of this branch, because the new Life build no longer has /nightwatch/ pages.

The separate step: Caddy and DNS (guardrail change)

Nothing in Caddy or DNS changes before Jack approves this spec. The Builder changes only the repo files (scripts/caddy/Caddyfile, scripts/caddy/caddy-run.sh, their tests). Installing them into the depot, restarting Caddy, and adding the DNS record are guardrail changes: the conductor does them only on the Maestro's word, after the merge, as their own step.

Repo change, scripts/caddy/Caddyfile (new snippet, new block, two changes in the pazurite.com block):

(nexus_api) {
	# Nexus API (DGS-324): the whole /api/* space goes to the API, which names the version. Tailnet only, read-only.
	handle /api/* {
		reverse_proxy 127.0.0.1:4300 {
			header_up -Authorization
		}
	}
}

(static_site) {
	@hashed path /_nuxt/* /storybook/assets/* /storybook/_nuxt/*
	@notHashed not path /_nuxt/* /storybook/assets/* /storybook/_nuxt/*
	header @hashed Cache-Control "public, max-age=31536000, immutable"
	header @notHashed Cache-Control "no-cache"
	file_server
}

oculus.pazurite.com {
	tls {
		dns cloudflare {env.CLOUDFLARE_API_TOKEN}
	}
	encode zstd gzip
	import nexus_api
	# Oculus (DGS-599): its own static build at the root of this host.
	handle {
		root * {env.DIGISMITH_OCULUS_WWW}
		import static_site
	}
}

pazurite.com {
	tls {
		dns cloudflare {env.CLOUDFLARE_API_TOKEN}
	}
	encode zstd gzip
	import nexus_api
	# DGS-599: the old Nightwatch pages moved to Oculus; keep the page path and the query.
	redir /nightwatch https://oculus.pazurite.com/ 302
	handle_path /nightwatch/* {
		redir https://oculus.pazurite.com{uri} 302
	}
	handle {
		root * {env.DIGISMITH_WWW}
		import static_site
	}
}

The existing comments (no hide .*, why) stay in the snippet. handle_path strips /nightwatch, so {uri} is the rest of the path plus the query.

Repo change, scripts/caddy/caddy-run.sh: export DIGISMITH_OCULUS_WWW="$D/nexus/oculus", the same placeholder (oculus.d/empty) and the same fail-closed check as for DIGISMITH_WWW.

4. The Live panel

Live page (oculus.pazurite.com/live/)

One table, one row per herdr agent, all workspaces. Columns:

ColumnValue
AgentThe herdr agent name (for example dgs-599). An agent with no name shows "unnamed" and its pane id.
Rolemaestro, conductor, builder, reviewer, scout or other (the rule is below).
ProjectThe project folder name (for example DigiSmith, shoppable-video), or "-".
Statusworking, idle, blocked, done, or unknown. A dot and a word: the word carries the meaning, the color only helps. Blocked uses the "bad" tone; only working uses green.
WhereWorkspace and tab id (for example w2 · t5).
RunThe run id with a link to its run page, when a run matches; else "-".
  • Order: blocked first, then working, idle, done, unknown; then by workspace and name. The order is stable, so rows do not jump between polls.
  • Filters (in the URL, as on the Runs page): status, role, project, workspace.
  • On a phone the table becomes row cards. The cards keep the table ARIA roles (lesson from DGS-586).
  • A polite live region announces only changes, as sets of names: "Blocked: dgs-601. New: dgs-602. Gone: dgs-571." It never reads the whole table again (lesson from DGS-586).

Top-bar count

The top bar gets "Agents 17 · working 3 · blocked 1", a link to the Live page. The side nav gets a "Live" link; its badge shows the blocked count when it is above 0. The layout owns one Live poll (5 s) and shares it with the Live page, the same way it shares the overview poll today. The old "Workers" count (run-based) stays.

Role rule (same as DGS-598)

  • The agent name matches an identity card in ~/.digismith-depot/identities/ with role: maestro → maestro.
  • *-conductor → conductor; dgs-NNN (any key-NNN) → builder; a name with -rev → reviewer; a name with -scout or probe → scout; else other.
  • DGS-598 has the same rule. This ticket puts it in one small function; after DGS-598 merges, the last task uses DGS-598's function instead, so there is only one rule.

Project rule

From the agent's working folder: a path under ~/Workspace/<org>/<project>/… gives <project> (a worktree under .worktrees/ gives the same project). Any other folder gives "-". Only the project name leaves the reader; the folder path never does.

Run id

A run matches an agent when the run is not ended and its record has the same herdr pane id (DGS-581 records herdr.pane). If two runs match, the newest wins. After DGS-598, a run also matches by the Claude session id; that join is added in the last task.

5. Data source: herdr, read-only

Probe result (2026-10-24): herdr-ws agent list filters the list to one workspace (HERDR_WS, the DGS-198 guardrail), and herdr-ws has no way to list workspaces. The plain herdr agent list returns all workspaces (w2, w3, w4 today; 17 agents). Its fields: name, agent_status, workspace_id, tab_id, pane_id, cwd, agent_session, and terminal_title.

Decision (technical): herdr-ws stays unchanged. A new read-only view dg nightwatch view live (in packages/cli/src/nightwatch/) runs the herdr binary with one fixed argument list, --session default agent list, with XDG_CONFIG_HOME set the same way herdr-ws sets it. No input from the request reaches that argument list (a test checks the exact argv). It is the only herdr call in Oculus. It never calls agent read, prompt, send-keys or any other verb.
  • An allowlist keeps only: name, agent_status, workspace_id, tab_id, pane_id, the project name from cwd, and the session id (used only for the run join, never output). terminal_title is dropped: Claude sets it from the conversation, so it can hold message text.
  • The Nexus API serves it as GET /api/v1/nightwatch/live through the existing reader. The reader already gives a 5 s cache and a single flight per view, so ten open tabs still give one herdr call per 5 s. A strict zod schema in nexus-shared/nightwatch.ts checks the response.
  • The herdr call has a 3 s timeout.
  • The Nexus API reads packages/cli/dist/index.js of the main checkout. The CLI build after the merge (as for DGS-586) brings the live view in.

6. Runs page: role and project (after DGS-598)

  • The role filter gets maestro and conductor. A project filter is added (values from the runs that exist). Both live in the URL and go to the API as checked values.
  • Maestro and conductor runs show their state as "-" with no health dot and no stalled or lost flag (DGS-598 stops the watchdog from flagging them; the UI does not invent a flag either). They do not count in the attention count.
  • A Project column is added to the Runs table; the Live table links each project to the Runs page filtered by it.

7. Errors and privacy

  • herdr fails (not running, timeout, bad JSON): the view exits non-zero, the API answers 503 reader_unavailable, and nothing is cached. The Live page then shows the error panel "herdr is not reachable" with a retry button and hides the old list: no stale green. The top bar shows "Agents unknown" with the warn tone, not the last count.
  • Zero agents is a real answer: the page says "No herdr agents are running." This is different from the error.
  • Privacy: no pane text, no terminal title, no prompt, no message text; names, ids, statuses and counts only. A test greps the API response and the built page for the fake terminal title in the fixture.

8. Side bar edge fix

Jack's screenshot: the brand ("nightwatch") and the "WATCH" label touch the left window edge.

What the CSS does today

  • NwShell.vue: a grid, grid-template-columns: 200px 1fr, no padding. NwNav.vue: .nw-nav { padding: 16px 10px }, .brand { padding: 0 8px 16px }, h2 { margin: 16px 8px 6px }. So the text sits 10 + 8 = 18 px from the edge. The main column and the top bar sit 24 px in. There is no negative offset and no transform in the side bar.
  • Probe (2026-10-24, the live build in Chromium at 1440, 1280 and 390 px wide): the brand box starts at 10 px, its text at 18 px; no clipping. I could not reproduce the touch in Chromium.

Cause (to confirm in the first task)

  • The side bar has only 18 px of left inset, the smallest on the page, and no safe-area inset. In Safari with the window against a rounded screen corner, a notch, or a landscape phone, the edge eats into those 18 px, so the text looks like it touches the edge.
  • The first task reproduces Jack's view in WebKit (Playwright WebKit at his window size; landscape iPhone for the safe area) before the fix. If the cause is different, the task says so and fixes that cause; the target below stays the same.

Fix

  • .nw-nav: padding-inline-start: max(16px, env(safe-area-inset-left)). 16 px of nav padding plus the 8 px inner padding of the brand, the section label ("WATCH") and the links puts their text at 24 px from the edge, the same as the main column and the top bar. The hover and current-page fill keep their 8 px inner padding.
  • The phone layout (the nav row under 760 px) gets padding-inline: max(16px, env(safe-area-inset-left)) max(16px, env(safe-area-inset-right)), the 16 px gutter of the rest of the page.
  • The top bar and .main also take env(safe-area-inset-*) with max(). env() is 0 when there is no inset, so on a desktop only the side bar moves.
  • No viewport-fit=cover change: the viewport meta stays as it is.
