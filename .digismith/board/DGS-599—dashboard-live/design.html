1. Goal

Jack, 2026-10-24: the dashboard is DigiSmith's control room for the whole factory ("this is not a night watch"); "I want all those on the whole herdr panel". Jack named it Oculus (lineage J.5: Oculus). There is no Nightwatch dashboard any more, only Oculus. This ticket does five things:

  1. The dashboard surface is renamed Oculus everywhere (pages, API routes, CLI view, components, tokens, schema, tests) and served on its own subdomain oculus.pazurite.com, titled "DigiSmith Oculus".
  2. The index page oculus.pazurite.com/ shows every herdr agent on the Workbox, in all workspaces, as its main section, with the attention summary. The top bar carries the agent count.
  3. When herdr is unreachable, Oculus keeps the last good agent list, marked "Disconnected from herdr", from a snapshot the server keeps in the depot.
  4. The Runs page gets role and project filters. Maestro and conductor runs show without health flags.
  5. The side bar no longer touches the left window edge.

Out of scope: no backward compatibility (no redirect from the old /nightwatch/ pages, no old API routes); the B.6 engine names (appendix); new run data (DGS-598); pane text; any action on an agent (Oculus stays read-only); a login (DGS-458); moving the Life Calendar or Storybook.

3. Subdomain, Caddy and DNS

How the front door works today (read 2026-10-24, nothing changed)

  • The Caddyfile source is scripts/caddy/Caddyfile; scripts/caddy/install.sh copies it to ~/.digismith-depot/caddy/Caddyfile (the two are the same today). bin/caddy-run starts Caddy with only CLOUDFLARE_API_TOKEN and DIGISMITH_WWW=$DEPOT/nexus/www. Caddy listens on 127.0.0.1:8443 only, admin off.
  • The tailnet-only door: Tailscale Serve forwards TCP 443 on the Workbox's tailnet addresses to 127.0.0.1:8443. Caddy picks the site by the TLS server name. Nothing is open outside the tailnet.
  • Two site blocks: opencode.pazurite.com (reverse proxy to 4198) and pazurite.com (/api/* to the Nexus API on 4300 without the Authorization header; everything else static files from {env.DIGISMITH_WWW}). Each gets its certificate by the Cloudflare DNS challenge.
  • DNS (DGS-325): Cloudflare DNS-only (grey cloud) A records to the Workbox's Tailscale address 100.108.1.19 for pazurite.com and opencode.

Decision: a second static build, its own web root, at base path /

Oculus is served at the root of its own host, so its router paths are /, /runs/, and so on. The Life Calendar already owns / on pazurite.com. One build cannot serve both at /, and a base path (app.baseURL: '/oculus/') with a Caddy rewrite would leave the browser URL and the router out of step. So:

  • The same Nuxt project builds two sites, chosen by NEXUS_SITE=life|oculus at build time. A pages:extend hook in nuxt.config.ts keeps only that site's pages: the Oculus pages live in app/pages/oculus/ and the hook maps /oculus/runs to /runs for the Oculus build; the Life build drops them. app.baseURL stays '/' for both. Each build has its own _nuxt/, so assets never mix.
  • build-www.sh builds both: the Life site to $DEPOT/nexus/www.d/<stamp>/ (unchanged, Storybook stays at pazurite.com/storybook/), the Oculus site to $DEPOT/nexus/oculus.d/<stamp>/, and switches the symlinks nexus/www and nexus/oculus, each with one rename, as today. The same dotfile and build-path checks run on both. Old build folders are kept.
  • caddy-run exports DIGISMITH_OCULUS_WWW=$DEPOT/nexus/oculus and, like today, points it at an empty placeholder build folder before the first build (fail closed: never an empty root).

Same origin for the API

Yes: oculus.pazurite.com proxies /api/* to the Nexus API exactly as pazurite.com does. The pages call the relative path /api/v1/oculus/…, so there is no CORS and no new API setting. The proxy goes into one Caddy snippet that both blocks import, so the two cannot drift.

No redirect from the old pages

Jack's answer: no backward compatibility. pazurite.com/nightwatch/… gets no redirect; the old pages go away when the new Life build no longer has them (Caddy then answers 404). Order rule: the Caddy and DNS step (below) is done before the first build-www.sh run of this branch, so Oculus has its host before the old pages go.

The separate step: Caddy and DNS (guardrail change)

Nothing in Caddy or DNS changes before Jack approves this spec. The Builder changes only the repo files (scripts/caddy/Caddyfile, scripts/caddy/caddy-run.sh, their tests). Installing them into the depot, restarting Caddy, and adding the DNS record are guardrail changes: the conductor does them only on the Maestro's word, after the merge, as their own step.

(static_site) {

Top-bar count

The top bar gets "Agents 17 · working 3 · blocked 1", a link to /#agents. The layout owns one agents poll (5 s) and shares it with the index page, the same way it shares the overview poll today. The old "Workers" count (run-based) stays. The nav badge on "Oculus" shows the blocked count when it is above 0.

Role rule (same as DGS-598)

  • The agent name matches an identity card in ~/.digismith-depot/identities/ with role: maestro → maestro.
  • *-conductor → conductor; dgs-NNN (any key-NNN) → builder; a name with -rev → reviewer; a name with -scout or probe → scout; else other.
  • DGS-598 has the same rule. This ticket puts it in one small function; after DGS-598 merges, the last task uses DGS-598's function instead, so there is only one rule.

Project rule

From the agent's working folder: a path under ~/Workspace/<org>/<project>/… gives <project> (a worktree under .worktrees/ gives the same project). Any other folder gives "-". Only the project name leaves the reader; the folder path never does.

Run id

A run matches an agent when the run is not ended and its record has the same herdr pane id (DGS-581 records herdr.pane). If two runs match, the newest wins. After DGS-598, a run also matches by the Claude session id; that join is added in the last task.

5. Data source: herdr, read-only

Probe result (2026-10-24): herdr-ws agent list filters the list to one workspace (HERDR_WS, the DGS-198 guardrail), and herdr-ws has no way to list workspaces. The plain herdr agent list returns all workspaces (w2, w3, w4 today; 17 agents). Its fields: name, agent_status, workspace_id, tab_id, pane_id, cwd, agent_session, and terminal_title.

Decision (technical): herdr-ws stays unchanged. A new read-only view dg oculus view live (in packages/cli/src/oculus/) runs the herdr binary with one fixed argument list, --session default agent list, with XDG_CONFIG_HOME set the same way herdr-ws sets it. No input from the request reaches that argument list (a test checks the exact argv). It is the only herdr call in Oculus. It never calls agent read, prompt, send-keys or any other verb.
  • An allowlist keeps only: name, agent_status, workspace_id, tab_id, pane_id, the project name from cwd, and the session id (used only for the run join, never output). terminal_title is dropped: Claude sets it from the conversation, so it can hold message text.
  • The Nexus API serves it as GET /api/v1/oculus/live through the existing reader. The reader already gives a 5 s cache and a single flight per view, so ten open tabs still give one herdr call per 5 s. A strict zod schema in nexus-shared/oculus.ts checks the response.
  • The CLI view stays read-only: it prints { readAt, herdr: "ok" | "unreachable", agents } and writes nothing. The snapshot (section 7) is the API's job.
  • The herdr call has a 3 s timeout.
  • The Nexus API reads packages/cli/dist/index.js of the main checkout. The CLI build after the merge brings dg oculus view in.

7. herdr disconnected, errors and privacy

Last good snapshot (Jack's answer)

  • Each time the live view says herdr: "ok", the Nexus API writes the answer (allowlisted fields only) to $DEPOT/nexus/state/oculus-live-last.json, by a temp file and one rename, so a reader never sees half a file. The folder is outside every web root: nexus/oculus and nexus/www are the symlinks Caddy serves and build-www.sh switches, so a file there would be public and would be lost at the next build. The API makes nexus/state/ itself with mode 700 (the file 600). At most once per 5 s (the cache already limits it).
  • When herdr is unreachable (the view says "unreachable", times out, or fails), the API answers 200 with the snapshot's agents and herdr: { state: "disconnected", asOf: <snapshot time> }. A fresh page load during an outage gets the same answer, with its time. Connected answers carry herdr: { state: "connected", asOf: <now> }.
  • No snapshot yet (first start during an outage): agents: [], asOf: null; the page says "Disconnected from herdr. No agent list yet."
  • A snapshot file that cannot be read or parsed counts as no snapshot; a write that fails is logged as a code (never data) and the answer still goes out.

What the page shows when disconnected

  • The agents table stays, under a warn banner: "Disconnected from herdr, as of 15:20 (UTC+7)". Every status dot turns neutral grey (hollow); the status words stay, as they were at that time. No green anywhere in the table.
  • The page keeps polling every 5 s; the banner goes away on the first connected answer.
  • The top bar shows the last count with a "disconnected" marker (for example "Agents 17 · disconnected", warn tone), not "unknown".
  • Run data comes from the run files, not from herdr: the attention summary, tickets, workers and events keep showing as normal.
  • The Nexus API itself unreachable: the existing stale behaviour stays (the stale banner, the "Nexus unreachable" dot).

Zero agents and privacy

  • Zero agents with herdr connected is a real answer: "No herdr agents are running."
  • Privacy: no pane text, no terminal title, no prompt, no message text, no folder path; names, ids, statuses and counts only, in the API answer and in the snapshot file. A test greps the API answer, the snapshot file and the built page for the fake terminal title and folder path in the fixture.

8. Side bar edge fix

Jack's screenshot: the brand ("nightwatch", "Oculus" after this ticket) and the "WATCH" label touch the left window edge.

What the CSS does today

  • NwShell.vue (OcShell.vue after the rename): a grid, grid-template-columns: 200px 1fr, no padding. NwNav.vue: .nw-nav { padding: 16px 10px }, .brand { padding: 0 8px 16px }, h2 { margin: 16px 8px 6px }. So the text sits 10 + 8 = 18 px from the edge. The main column and the top bar sit 24 px in. There is no negative offset and no transform in the side bar.
  • Probe (2026-10-24, the live build in Chromium at 1440, 1280 and 390 px wide): the brand box starts at 10 px, its text at 18 px; no clipping. I could not reproduce the touch in Chromium.

Cause (to confirm in the first task)

  • The side bar has only 18 px of left inset, the smallest on the page, and no safe-area inset. In Safari with the window against a rounded screen corner, a notch, or a landscape phone, the edge eats into those 18 px, so the text looks like it touches the edge.
  • The first task reproduces Jack's view in WebKit (Playwright WebKit at his window size; landscape iPhone for the safe area) before the fix. If the cause is different, the task says so and fixes that cause; the target below stays the same.

Fix

  • .oc-nav: padding-inline-start: max(16px, env(safe-area-inset-left)). 16 px of nav padding plus the 8 px inner padding of the brand, the section label ("WATCH") and the links puts their text at 24 px from the edge, the same as the main column and the top bar. The hover and current-page fill keep their 8 px inner padding.
  • The phone layout (the nav row under 760 px) gets padding-inline: max(16px, env(safe-area-inset-left)) max(16px, env(safe-area-inset-right)), the 16 px gutter of the rest of the page.
  • The top bar and .main also take env(safe-area-inset-*) with max(). env() is 0 when there is no inset, so on a desktop only the side bar moves.
  • No viewport-fit=cover change: the viewport meta stays as it is.
