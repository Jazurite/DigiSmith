2. Decision (a): one field, not two

Fold. Today report-implementation carries two separate spans: {{MAP_ITEM}} (mandatory, derived from {{FEATURE_TITLE}}'s own parenthetical, e.g. Capture Ephemeral URL (M) → M) and {{TICKET_KEY_META}} (optional, empty string unless a ticket key survives the profile gate). Once {{MAP_ITEM}} stops being derived from a title parenthetical and instead just becomes the ticket key or n/a (per your item 2), the two fields hold the same value in every case a key exists, and {{TICKET_KEY_META}}'s only remaining job — rendering nothing when there's no key — is exactly what n/a now does instead. Keeping both would mean two spans both saying "DGS-123" (or one saying "n/a" and the other rendering empty, which reads as a contradiction). Folding costs nothing for old reports: they're static HTML, never regenerated, and the hook change (section 7) parses Map item: for those regardless of what new reports do.

Net: one mandatory field, replacing both. New name {{TICKET}} (the label changes from "Map item" to "Ticket" — keeping the old label on a field that now holds a ticket key, or the literal text "n/a", would read as a mismatch).

3. Decision (b): the new report markup

Replace this (report-implementation's template, inside .meta):

<span>Map item: <strong>{{MAP_ITEM}}</strong></span>
{{TICKET_KEY_META}}

with:

<span>Ticket: <strong>{{TICKET}}</strong></span>

Value: the ticket key from Step 1.5's existing derivation (ticket.md's Key: line, discarded if the active profile's ticket field is false) when one survives — e.g. <strong>DGS-123</strong> — otherwise the literal string <strong>n/a</strong>. Always rendered, never omitted (unlike the old {{TICKET_KEY_META}}, which vanished entirely when empty).

adopt's and brainstorming's design.html shells get the same label and value change, for consistency — a design doc saying "Map item: DGS-123" right after the hook starts expecting a report to say "Ticket: DGS-123" would read as two conventions, not one. Both shells currently render <span>Map item: {{MAP_ITEM}}</span> (no <strong> — neither file is hook-parsed, so this is cosmetic only). New: <span>Ticket: {{TICKET}}</span>, same value rule, for the keyed branch only — brainstorming's keyless branch keeps "Map item: {{MAP_ITEM}}" and its existing letter-or-reason derivation byte for byte, since "no change at all" for keyless is a decided rule (Part 3 design, section 8) and nothing here revisits it.

Correction (post-final-review): adopt has no keyless row at all. Unlike brainstorming, adopt never computed its own {{MAP_ITEM}} value — it only ever carried forward whatever the supplied spec already had (it adopts externally-authored specs; it has no map-letter-derivation machinery of its own to preserve). There is no "existing behavior" for a keyless adopt invocation to keep byte for byte, so the original ticket's own item 2 ("replace it with the ticket key, or n/a for keyless work") applies to adopt with no exception, exactly as it does to report-implementation — both branches render {{TICKET}}. The sentence above, read as applying to adopt too, was a misstatement caught by the final whole-branch review; it was only ever true of brainstorming.

4. Decision (c): brainstorming/writing-plans keyed path

brainstorming ("After the Design" → DigiSmith-tracked work, SKILL.md:119-251). Before the existing map-letter-or-_unlettered logic, insert a keyed branch:

  • A tracker key is in hand (passed in by bootstrap/adopt, or already evident from how the work was requested) → resolve the existing folder first, never reconstruct one: run board-path.ts --action find --slug <slug> against .digismith/board/. Found → that folder, <folder>/design.html. Not found (an ad hoc keyed call with no prior jira-intake run this session) → compute fresh with board-path.ts --action path --key <key> --title <title>.
  • No key → the existing logic, untouched: scan .digismith/docs/<Letter>/ for map-letter nesting, or .digismith/docs/_unlettered/<slug>/, exactly as today.

{{MAP_ITEM}} in the template (line 194) follows decision (b): the keyed branch renders Ticket: {{TICKET}} with the key (always present in this branch — a key that resolved a board folder is never absent); the keyless branch keeps Map item: {{MAP_ITEM}} with its current letter-or-"no map letter — reason" value, unchanged.

writing-plans (SKILL.md:18-40) mirrors this exactly, same "reuse the path brainstorming already resolved this session, never re-derive" rule it already states for the keyless case — now also covering the keyed resolved path. Standalone keyed call with nothing resolved yet this session → the same two-step (find by slug, then path --key --title) brainstorming just ran. No key, no resolved path → existing flat docs/<slug>/plan.md fallback, unchanged.

5. Decision (d): report-implementation's board-vs-docs read

Step 1's job is to find <target folder> from the plan file's own path. Today it only knows the docs/ shapes (flat, nested, lineage, or the docs/superpowers/plans/ filename fallback) and counts path segments to tell them apart. A board folder needs no such counting: whatever directory the plan file sits in is the target folder, flat or nested — this ticket's own worker folders (worker-dgs-159-paths/ beside worker-dgs-159-lifecycle/, etc., all under one DGS-159—… folder) are exactly that nested case, and update-history.ts's own error message already anticipates a <part> subfolder under a board ticket folder.

New Step 1 rule, checked first: plan path starts with .digismith/board/ → the folder segment right after board/ must parse as a real board folder name (board-path.ts --action parse --name <name> — confirms the key and em dash; a parse failure here is a real error, not a fallback case) and <target folder> is simply dirname(plan.md), nesting depth included. Otherwise, fall through to the existing docs/ segment-counting logic exactly as today — the two bases are mutually exclusive by construction (a plan lives in exactly one place), so there is no real "already exists under both" conflict to resolve; "legacy vs. new" just means "which one pattern this particular plan's path happens to match."

Step 1.5's ticket-key read (<target folder>/ticket.md, gated by the active profile's ticket field) and Step 4's write target + gitignore check both generalize to <target folder> the same way — the exact pattern adopt Step 6 already uses for this. Step 4's existing "ask before overwrite" check needs no change beyond that: it already treats "a file already exists at that path" as one case, regardless of which base the path happens to be under.

The Step 4 commit message ("docs: add <feature> (<map-item>) implementation report") also branches: board case → (<ticket-key>); docs case → unchanged, (<map-item>).

Correction (post-merge-review, a real bug, not a misstatement): the sentence above claiming Step 1.5's ticket-key read is "gated by the active profile's ticket field" for every case was wrong for the board branch. A board folder only exists under .digismith/board/ because a real key was already in hand (section 8 of the Part 3 design) — it is keyed by definition, so its key must never depend on ticket.md or on any profile's ticket field. Under the original text, DigiSmith's own ticket: false profile would have discarded a board folder's own key and rendered Ticket: n/a even for a clearly-keyed DGS-xxx folder. Shipped fix (commit d65a22c): for a board-folder plan, {{TICKET}} is the key Step 1's own --action parse call already printed, independent of ticket.md and the profile gate entirely. The profile-gated ticket.md read now applies only to the docs-folder case, which this bug never touched.

7. The history hook

parseReport's current rule: throw unless Map item: <strong>…</strong> is present. New rule: try Ticket: <strong>(.+?)</strong> first; if absent, try Map item: <strong>(.+?)</strong>; if neither is present, throw (error message names both forms). ParsedReport's mapItem: string field renames to ticket: string — nothing downstream reads its value today (it only gates presence), so the rename is a one-module, no-behavior-change cleanup, not a risk; test fixtures rename their mapItem override to ticket and gain a legacy flag choosing which label writeReportFixture emits.

New tests: a board-folder report with Ticket: <strong>DGS-…</strong> parses; a board-folder report with Ticket: <strong>n/a</strong> parses (keyless ticket:false profile); an old fixture with only Map item: still parses unchanged (regression guard); a report with neither line throws, naming both forms in the message.
