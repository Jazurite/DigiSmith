2. scripts/board-path.ts

Builds and parses the board folder name <KEY>—<slug> (section 2), per section 9's build/parse rules. No existing code implements the slug algorithm today — digismith:jira-intake describes it only in prose, for an LLM to follow by hand. This module is the first time it's codified.

export function slugify(title: string): string
// lowercase; drop whole-word fillers (a, an, the, on, to, of, for, in);
// collapse remaining non-alphanumeric runs to one ASCII hyphen;
// truncate to ~40 chars at a word boundary; never leave a trailing
// filler word or hyphen. Same algorithm jira-intake's prose already
// describes (Step 3.1) — codified here as the first real implementation,
// not a second one.

export function buildFolderName(key: string, title: string): string
// `${key.toUpperCase()}—${slugify(title)}`.normalize("NFC")
// (NFC is a no-op while slugify only ever emits ASCII — defensive per
// section 9, in case a future slugify revision keeps more of the title.)

export type ParsedFolderName = { key: string; slug: string }
export function parseFolderName(name: string): ParsedFolderName
// Split at the FIRST U+2014. No em dash found → throw (section 9: "fails
// loudly if no U+2014 is found, rather than silently guessing a
// different separator"). Key validated against /^[A-Z]+-\d+$/ after
// uppercasing; slug returned untouched (it can never itself contain an
// em dash, so first-occurrence splitting is unambiguous).

export function boardRelPath(key: string, title: string): string
// `.digismith/board/${buildFolderName(key, title)}`

No caller inside this unit — Parts 3/4/6 wire it into writing-plans, report-implementation, update-history.ts, and the file moves. Section 9's risk table also proposes a thin dg board path <key> <title> CLI command for a human copy-pasteable result. No board folder exists yet (Part 6 hasn't run), so nothing needs that command today — proposing to defer it to whichever part first creates a real board folder, rather than building a CLI surface with no caller. Flagging this as a scope call I'm making, not a Jack-level policy question — easy to revisit.

5. .git/info/exclude: a conflict with the spec, flagged for approval

Design section 10's bullet: "drop the old handoff.md/brief.md patterns, add .digismith/board/** ... and .digismith/sessions/**/note.md, .digismith/sessions/**/brief.md." Checked this repo's actual .git/info/exclude and found three problems with applying it literally, right now:

  • The sessions patterns are already redundant. .digismith/sessions/ is already excluded as a whole directory (one line, already in the file). Adding .digismith/sessions/**/note.md and .../brief.md on top does nothing new.
  • Dropping the old fallback patterns now is premature and unsafe. Six real handoff.md files are live fallback notes today (A/A.4, B, B/B.2, D/D.3, E/E.4, _unlettered). They're excluded by .digismith/docs/**/handoff.md right now. Dropping that pattern before Part 6 migrates or moves those six files would make them show up as untracked, "ready to add" content in the main checkout — a real risk, not a theoretical one, and squarely the kind of thing the brief tells me not to touch this unit ("do not move or edit .digismith/sessions/DigiSmith/note.md," and more generally the file moves are Part 6's job).
  • .digismith/board/** would silently change this repo's own commit choice. Confirmed live: git check-ignore -q .digismith/docs/_unlettered/... exits 1 — this repo does not gitignore its own docs folder; every ticket's design.html/plan.md/ report.html is committed. Section 2 says board/ keeps "the same mechanism as today (commit-vs-gitignore stays a per-repo choice)" — for DigiSmith's own repo, that choice is "commit it." Blanket-adding .digismith/board/** here would reverse that silently, and would land Part 6's own migrated files as gitignored by accident.

Recommendation: no change to .git/info/exclude in this unit. Revisit the old fallback patterns exactly when Part 6 migrates or removes the six handoff.md files (drop the pattern only once nothing needs it), and treat .digismith/board/** as something Part 6 decides per this repo's existing per-repo choice (committed, matching docs/ today) rather than something this unit adds pre-emptively. This is the one point in this design I'm flagging for explicit sign-off rather than just proceeding on — it reverses part of what section 10 literally says to do.

8. Checkpoint 3: three changes from the maestro

The maestro checked sections 2, 3 and 5 against the repo directly and approved them as written — section 5's recommendation (no .git/info/exclude change this unit) is confirmed correct and carries forward unchanged. Three corrections follow.

8.1 Section 4 reversed: the banner and the CLI listing now cover both conventions

The maestro's own check found the concrete evidence section 4 missed: skills/handoff/SKILL.md's own Overview table already says the script "still know[s] only [the old paths] until DGS-159 migrates them", and its own documented --action list behavior ("list the folders under .digismith/sessions/ that hold a note.md") has never matched what lineage-handoff.ts's listNotes actually scans (.digismith/docs/ only). Real risk if left as section 4 originally proposed: once Part 6 moves the six fallback notes away, listNotes returns [] and the SessionStart banner goes silent — a fresh maestro gets no pointer to its own sessions/<name>/note.md at all.

Built: session-path.ts gained listNoteSessionNames(mainRoot) — scans immediate subfolders of .digismith/sessions/ for ones holding a note.md directly, sorted, skipping dotfile folders. A worker's brief-only folder (dgs-161) and workbox-archive (a dated subfolder sits inside it, not a note, one level too deep) are both excluded by the same "has a note.md directly inside it" check — no special-casing needed for either. lineage-handoff.ts's main() (--action list) now prints the fallback keys followed by the session names. session-init.ts's buildLineagePointer now emits up to two clauses — "lineage handoff notes in ...: ..." and "session notes in ...: ..." — joined with "; " when both exist; the fallback-only wording is byte-for-byte what it printed before this change when no current-convention note exists yet, so every existing caller and test keeps working unmodified. skills/handoff/SKILL.md's own text is unchanged, per the maestro's instruction — its "lists only fallback notes" sentence is now stale prose the skill-text owner will reconcile separately, not something this unit edits.

8.2 Section 10 (new): update-history.ts gains board/ support — and a live bug it would have shipped with

.digismith/hooks/post-finish/scripts/update-history.ts finds changed reports with the git pathspec .digismith/docs/*/report.html and derives a slug with a docs-only regex; a report written to .digismith/board/ was invisible to it. Pulled into this unit per the maestro's instruction: findChangedReports now also matches .digismith/board/*/report.html (git's pathspec glob already crosses / on a single *, confirmed live, so this needed no ** magic); parseReport tries a board-shaped slug pattern first (<key>—<slug>[/<part>]) before falling back to the existing docs-shaped one, and returns a new base: "docs" | "board" field; buildReferenceLinks takes that base and builds both the on-disk folder and the history.html href under it instead of always assuming docs/.

Writing the board-shaped test surfaced a real, independent bug this change would otherwise have shipped live: a board folder name contains a real em dash (U+2014, section 9's own build/parse rules), and git's default core.quotepath=true octal-escapes any byte ≥0x80 in plain --name-only output — exactly the risk section 9's own table already named for this exact character, just not yet hit by any caller until this unit's own board-shaped path exercised it. findChangedReports's existing newline-split then could not turn "...DGS-159\342\200\224ticket.../report.html" back into a real path. Fixed the way section 9 itself prescribes as defense in depth regardless of the repo-level core.quotepath setting: git diff now runs with -z (NUL-terminated, unquoted, real UTF-8 bytes) and the result is split on "\0" instead of "\n". Verified live before writing the fix (see the test file's own board-shape cases, which failed without it and pass with it). .digismith/hooks/post-finish/03-history-update.md's own prose is updated to mention the board/ shape alongside docs/, since it was describing this exact pathspec.

Deliberately not touched: the Map item: <strong>...</strong> requirement in parseReport. A real board-based report.html template doesn't exist yet — Part 4/6 decide its header shape — so guessing at a second accepted format now would be speculative. DGS-158's own shipped report (still docs-based) already carries both a Map item span and a new Ticket: DGS-158 span side by side, which is the precedent this ticket's own report.html follows too (see this file's own header, above).
