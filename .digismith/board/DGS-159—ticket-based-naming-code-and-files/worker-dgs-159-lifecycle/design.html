1. Scope

DGS-159 applies the ticket-based naming convention (DGS-158) to the code and the files. This unit is Part 3: the four skills that start a ticket's work — skills/bootstrap, skills/adopt, skills/init, skills/jira-intake — today write .digismith/docs/<slug>/{ticket,plan,design.html} in any repo, keyed by nothing but a slug. This design moves a keyed ticket's files to .digismith/board/<KEY>—<slug>/, per the convention at .digismith/docs/E/E.3/worker-maestro-conventions/design.html (sections 2, 6, 9). A keyless ticket keeps using .digismith/docs/<slug>/ exactly as today — see section 2.

Out of scope: the nine skills that only mention the path in passing (Part 4), moving any of the ~70 existing .digismith/docs/ folders or the backlog/ files (other tickets), and MEMORY.md (another worker's ticket).

2. Decided: keyless work stays in docs/

Decided by Jack, 2026-10-04: the board is only for a ticket that has a key.

  • A key is in hand — always true for a ticket: true repo (profiles/emma.yml), and true for a ticket: false repo whenever one is supplied anyway (DigiSmith's own repo, profiles/digismith.yml, is ticket: false yet every one of its own tickets, this one included, carries a real DGS key) → .digismith/board/<KEY>—<slug>/.
  • No key — a ticket: false repo with genuinely none supplied (personal, jazurite, or DigiSmith's own repo for a slice of work with no tracker key at all) → .digismith/docs/<slug>/, exactly as today. No board folder, no new code path, nothing to migrate later.

Rejected by Jack: a keyless board folder (.digismith/board/<slug>/), so that every new ticket-related write — keyed or not — would land under one shared root. Simpler to state as a single rule, but it would move a working, unremarkable path (docs/<slug>/, already used by every keyless repo today) for no benefit to anyone, and it would hand Part 4's nine skills a second new shape to learn for a case that needs no change at all. Rejected: work with no key stays in docs/<slug>/, unchanged; the board is only for a ticket that has a key.

3. board-path.ts: unchanged, plus two additions

buildFolderName, boardRelPath and parseFolderName stay exactly as Part 1+2 shipped them — key is string, required; parseFolderName still throws loudly on any folder name with no em dash (U+2014), no exceptions. No signature change, no new guard, nothing to re-verify against the existing test file — it's untouched.

Two small additions, both only useful for a ticket that already has a key:

// For a caller that already has a final key and slug in hand (init, resolving one from a
// branch name) rather than a raw title — skips slugify, which an already-final slug must never
// go through again (re-truncation/re-filler-dropping on it is not guaranteed idempotent).
export function boardRelPathForSlug(key: string, slug: string): string {
  return `${BOARD_DIR_PATH}/${key.toUpperCase()}${EM_DASH}${slug}`.normalize("NFC");
}

// Finds a keyed ticket's board folder by slug alone — a folder's own key does not have to match
// whatever key (if any) the branch name carries. DigiSmith's own repo already has this today:
// branch "plugin-update-after-merge" (no key) against folder "DGS-161—plugin-update-after-merge"
// (keyed). Reconstructing the folder name from the branch's own key would miss that folder.
export function findBoardFolderBySlug(slug: string, mainRoot: string): string | undefined {
  const dir = path.join(mainRoot, ...BOARD_DIR_PATH.split("/"));
  let entries: string[];
  try {
    entries = fs.readdirSync(dir, { withFileTypes: true })
      .filter((e) => e.isDirectory()).map((e) => e.name);
  } catch (err) {
    if ((err as NodeJS.ErrnoException).code === "ENOENT") return undefined;
    throw err;
  }
  for (const name of entries) {
    let parsed: ParsedFolderName;
    try {
      parsed = parseFolderName(name);
    } catch {
      continue; // not a board-shaped folder name — skip it, don't fail the whole scan
    }
    if (parsed.slug === slug) return name;
  }
  return undefined;
}

Both land with tests in the plan, not here.

4. ticket: true with no key still stops

Unchanged — not new code. jira-intake already stops cleanly when Door 1 has neither a JIRA tool nor a pasted answer, and bootstrap Step 1 already stops when the result has no **Key:** line (a Door 2 draft never upgraded). Both checks run before any board folder is touched. This design does not add a new stop condition; it only confirms the existing ones still gate every path that would otherwise reach boardRelPath with no key for a ticket: true repo.

5. The real gap: a ticket:false repo throwing an available key away

Checked against the actual skill text, not just the profile schema. digismith:adopt Step 1 already asks for the ticket key unconditionally, every time, regardless of the active profile — then Step 3's own ticket: false branch throws it away: "skip straight to deriving the slug directly... No ticket.md gets written." The fix is narrow: Step 3's ticket: false branch gains one check — if Step 1 already confirmed a real key, invoke digismith:jira-intake Door 1 with it (same "already confirmed, don't ask again" call Step 3 already makes for a ticket: true repo) and use the board folder (boardRelPath); only when Step 1 found no key at all does the existing, unmodified docs/<slug>/ flow run — no edit needed on that branch at all.

digismith:bootstrap has no equivalent prior step that asks for a key at all under ticket: false — it jumps straight to deriving a slug. The same fix applies, moved earlier: before skipping jira-intake, check whether a real tracker key is already evident from how this work was requested — the user named one, or (DigiSmith's own case) the dispatching context supplied one directly, the way this very ticket's brief named DGS-159. If one is evident, invoke digismith:jira-intake Door 1 with it instead of skipping intake outright, and use the board folder. Otherwise: unchanged — it keeps writing to docs/<slug>/ exactly as today, no edit needed on this path either.

jira-intake itself needs no change to its own door logic — it has never read the ticket: field (confirmed by re-reading its SKILL.md: every "ticket" occurrence there is the English word, not the profile flag). It only needs its target path updated (section 6), and only for the half of its output that carries a real key — a key-less write keeps landing in docs/<slug>/, unchanged.

6. Per-skill changes — the keyed path only

Every change below fires only when a real tracker key is in hand. The keyless path in each of these four skills needs no edit at all — it is already exactly what section 2 decided should keep happening.

bootstrap

Step 1, Step 1.5, Step 2

Step 1: add the key-already-evident check (section 5) before the ticket: false skip — only on the branch where a key turns out to be evident. Step 1.5/telemetry marker: unchanged shape; slug is whichever slug ends up in play either way. Step 2: only the keyed branch's .digismith/docs/<slug>/... paths become boardRelPath(key, title)'s result, resolved once and carried forward. The no-key branch's existing docs/<slug>/ references are untouched. Branch naming (Step 2's <Key>__<slug> vs. <slug> rule) is untouched — tracked separately (section 7).

adopt

Step 3, Step 6

Step 3: the narrow fix in section 5. Step 6 ("Relocate the Docs") now branches on whether Step 3 resolved a real key: key in hand → target is the resolved board path, and the HTML shell's footer line updates to match; no key → Step 6 is completely unchanged, writing to .digismith/docs/<slug>/ with its existing footer line exactly as today.

init

Step 0, Step 1

Never reads ticket: itself — delegates entirely to bootstrap/adopt. Its resume check (Step 0 item 2, Step 1 rows 2–3) still derives <slug> from the branch name the same way as today. It does not reconstruct a board folder name from that derivation — a folder's own key does not have to match the branch's (section 3). Instead: call findBoardFolderBySlug(slug, mainRoot) first. Found → its plan.md. Not found → fall back to the existing, flat .digismith/docs/<slug>/plan.md check (today's exact mechanism, unchanged) — which is the permanent home for a genuinely keyless ticket, and (until DGS-164) also still the temporary home for an old keyed ticket not yet migrated. Neither exists → no plan anywhere, same as today.

jira-intake

Step 3, Handling Existing Files

Target path: boardRelPath(key, title) when the ticket being written has a real **Key:** (Door 1, or an upgraded Door 2 draft); the existing, unmodified .digismith/docs/<slug>/ticket.md path otherwise (a Door 2 draft with no key yet, or any ticket: false repo with none supplied) — docs/ is that ticket's real, permanent home, not a holding pen. The "Blank/absent → Door 1, now has a real key → Upgrade" row in Handling Existing Files changes from an in-place field edit to a folder move: the whole .digismith/docs/<slug>/ folder (ticket.md and anything already sitting beside it) moves to .digismith/board/<KEY>—<slug>/ — the same move-and-correct idiom digismith:adopt Step 3.2 already uses for its own branch-slug correction. Step 3.3's commit-vs-gitignore probe checks both ticket-file folders, never the repo-wide .digismith/ (that would count unrelated tracked files — config.yml, hooks, session notes — and call a repo "committed" without ever asking), since docs/ stays a live, permanent home, not just a migration remnant:

# ignored — either path already resolves to gitignored
git check-ignore -q .digismith/board/ || git check-ignore -q .digismith/docs/

# already tracked — either path has files git already knows about
git ls-files .digismith/board/ .digismith/docs/

This keeps an earlier docs/-era "committed"/"gitignored" decision valid for good, since docs/ doesn't go away, and never asks the gitignore question twice. The Handling Existing Files table's own existing-file check gets the same board-then-docs lookup order as init's plan lookup above.

8. Path rules (for Part 4)

  • A tracker key is in hand (always for ticket: true; for ticket: false, whenever one is supplied anyway) → .digismith/board/<KEY>—<slug>/, via boardRelPath(key, title), or boardRelPathForSlug(key, slug) when both are already final (e.g. adopt Step 3, which already confirmed both).
  • No tracker key (ticket: false, genuinely none supplied) → no change at all: .digismith/docs/<slug>/, exactly as today. This convention, and Part 4's nine skills, only ever change behavior for a keyed ticket.
  • Resolving an existing ticket's folder (a resume check, a collision check) — never reconstruct the folder name from a branch name or any other derived key. Call findBoardFolderBySlug(slug, mainRoot) against .digismith/board/ first, matching on slug alone; not found there → fall back to the flat .digismith/docs/<slug>/ check. That fallback serves two different tickets at once: it is the permanent home for a genuinely keyless ticket, and (until DGS-164 migrates it) the temporary home for an old keyed ticket not yet moved.
  • ticket.md exists only inside a folder jira-intake actually wrote one into — absent wherever intake was skipped outright (bootstrap's no-key, ticket: false fast path, which is itself unchanged).
  • design.html, plan.md, report.html all reuse the one resolved path — board or docs, whichever applies — carried forward from wherever it was first resolved, never re-derived from a bare slug partway through a skill chain.
  • A ticket: true repo with no resolvable key stops before any board folder work starts at all (section 4) — the pre-existing jira-intake/bootstrap stop conditions, unchanged.
  • buildFolderName, boardRelPath, parseFolderName stay exactly as Part 1+2 shipped them (key required, throws loudly on any no-em-dash name, no exceptions). The only additions are boardRelPathForSlug(key, slug) and findBoardFolderBySlug(slug, mainRoot), both for a ticket that already has a key.
  • The commit-vs-gitignore probe (jira-intake Step 3.3) checks both .digismith/board/ and .digismith/docs/ — never the repo-wide .digismith/ — per the exact commands in section 6.
