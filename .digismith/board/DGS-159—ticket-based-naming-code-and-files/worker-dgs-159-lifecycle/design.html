1. Scope

DGS-159 applies the ticket-based naming convention (DGS-158) to the code and the files. This unit is Part 3: the four skills that start a ticket's work — skills/bootstrap, skills/adopt, skills/init, skills/jira-intake — today write .digismith/docs/<slug>/{ticket,plan,design.html} in any repo, keyed by nothing but a slug. This design moves them to .digismith/board/<KEY>—<slug>/, per the convention at .digismith/docs/E/E.3/worker-maestro-conventions/design.html (sections 2, 6, 9).

Out of scope: the nine skills that only mention the path in passing (Part 4), moving any of the ~70 existing .digismith/docs/ folders or the backlog/ files (other tickets), and MEMORY.md (another worker's ticket).

2. The key is optional, not forbidden

Recommended by the maestro at checkpoint 1; Jack confirms at design approval: the board folder shape depends on whether a tracker key is actually in hand for this work, not on the repo's ticket: profile flag alone.

  • A key is available — always true for a ticket: true repo (profiles/emma.yml), and true for a ticket: false repo whenever one is supplied anyway (DigiSmith's own repo, profiles/digismith.yml, is ticket: false yet every one of its own tickets, this one included, carries a real DGS key) → the keyed folder, .digismith/board/<KEY>—<slug>/.
  • No key anywhere — a ticket: false repo with genuinely no tracker involved (personal, jazurite) → the keyless folder, .digismith/board/<slug>/.

Rejected alternative: the folder shape depends only on the profile, never on a supplied key. Simpler to state (one lookup, no runtime branching on key presence) — but its cost is exactly the case this ticket is run under: DigiSmith's own repo would mechanically derive a bare, keyless slug for every one of its own tickets and discard the real DGS key it already has in hand, even though the key is sitting right there in the request. The maestro's reasoning at checkpoint 1: the convention says the key comes from the tracker, so an available key should be used, not thrown away. Rejected for that reason, pending Jack's own confirmation of the split at design approval.

3. board-path.ts: a key that may be absent

No existing caller depends on buildFolderName/boardRelPath yet (Part 1+2 shipped the module with tests only). Widening key to string | undefined is therefore additive, not breaking — every existing call site passes a concrete string, which is still valid, and every existing test keeps passing unchanged (verified against scripts/board-path.test.ts line by line below).

export function formatFolderName(key: string | undefined, slug: string): string {
  if (slug === "") throw new Error(`cannot format a board folder name: slug is empty`);
  const prefix = key === undefined ? "" : `${key.toUpperCase()}${EM_DASH}`;
  return `${prefix}${slug}`.normalize("NFC");
}

export function buildFolderName(key: string | undefined, title: string): string {
  const slug = slugify(title);
  if (slug === "") {
    throw new Error(`cannot build a board folder name: title has no slug-able content: ${title}`);
  }
  return formatFolderName(key, slug);
}

export function boardRelPath(key: string | undefined, title: string): string {
  return `${BOARD_DIR_PATH}/${buildFolderName(key, title)}`;
}

// For a caller that already has a final slug in hand (init, resolving one from a branch name)
// rather than a raw title — skips slugify, which a branch-derived slug must never go through
// again (re-truncation/re-filler-dropping on an already-final slug is not guaranteed idempotent).
export function boardRelPathForSlug(key: string | undefined, slug: string): string {
  return `${BOARD_DIR_PATH}/${formatFolderName(key, slug)}`;
}

Parsing. A legitimate keyless folder name is always pure lowercase — slugify never emits an uppercase character. So an uppercase <PREFIX>-<number>-looking prefix followed by a plain hyphen or en dash, with no em dash anywhere in the name, can never be a real keyless folder — it can only be the exact mistake the convention's own section 9 already names (a human substituting the wrong dash for a keyed name). That is the one case parseFolderName must still fail loudly on; every other no-em-dash name is a legitimate keyless folder.

export type ParsedFolderName = { key: string | undefined; slug: string };

// Matches only an uppercase - prefix immediately followed by a plain hyphen or
// en dash — never a lowercase slug segment, since slugify can't produce one of those.
const KEY_LIKE_PREFIX = /^[A-Z]+-\d+[-–]/;

export function parseFolderName(name: string): ParsedFolderName {
  const dashIndex = name.indexOf(EM_DASH);
  if (dashIndex === -1) {
    if (KEY_LIKE_PREFIX.test(name)) {
      throw new Error(`no em dash (U+2014) found in board folder name: ${name}`);
    }
    return { key: undefined, slug: name };
  }
  const rawKey = name.slice(0, dashIndex).toUpperCase();
  if (!KEY_PATTERN.test(rawKey)) {
    throw new Error(`board folder name's key part is not -: ${name}`);
  }
  return { key: rawKey, slug: name.slice(dashIndex + EM_DASH.length) };
}

Checked against every existing test in scripts/board-path.test.ts: the two dash-substitution cases (DGS-159-ticket-based-naming, DGS-159–ticket-based-naming) both still throw — both match KEY_LIKE_PREFIX. not-a-key—some-slug still throws on the key-pattern check (it has an em dash, so it never reaches the new branch at all). Every keyed round-trip, case-insensitivity, and multi-em-dash case is untouched — none of them go through the new branch either. A slug such as fix-123-bug does not match KEY_LIKE_PREFIX (the prefix must be uppercase), so it correctly returns { key: undefined, slug: "fix-123-bug" } rather than a false-positive throw.

Finding a ticket's board folder by slug alone. A folder's own key does not have to match whatever key (if any) the branch name carries — DigiSmith's own repo already has this today: branch plugin-update-after-merge (no key) against folder DGS-161—plugin-update-after-merge (keyed). Deriving a key from the branch name and reconstructing the folder path from it (what section 6's first draft proposed for init) would miss that folder entirely. The fix is to resolve by slug, not by reconstructing the name:

export function findBoardFolderBySlug(slug: string, mainRoot: string): string | undefined {
  const dir = path.join(mainRoot, ...BOARD_DIR_PATH.split("/"));
  let entries: string[];
  try {
    entries = fs.readdirSync(dir, { withFileTypes: true })
      .filter((e) => e.isDirectory()).map((e) => e.name);
  } catch (err) {
    if ((err as NodeJS.ErrnoException).code === "ENOENT") return undefined;
    throw err;
  }
  for (const name of entries) {
    let parsed: ParsedFolderName;
    try {
      parsed = parseFolderName(name);
    } catch {
      continue; // not a board-shaped folder name — skip it, don't fail the whole scan
    }
    if (parsed.slug === slug) return name;
  }
  return undefined;
}

Lists .digismith/board/, parses every entry (keyed or keyless — one function, section 3 above), and matches on slug alone. Tests land with the plan, not here.

Considered and rejected: a separate keyless pair (buildKeylessFolderName/parseKeylessFolderName, fully split from the keyed functions) — avoids widening an already-shipped signature, but doubles the API every future consumer (Part 4, in particular) has to learn and pick between, for no behavioral difference. The optional-key form reads the same decision (is a key in hand or not) as a single branch inside one pair of functions, which is what Part 4 will need to apply across nine more skills without asking this ticket's worker again.

4. ticket: true with no key still stops

Unchanged — not new code. jira-intake already stops cleanly when Door 1 has neither a JIRA tool nor a pasted answer, and bootstrap Step 1 already stops when the result has no **Key:** line (a Door 2 draft never upgraded). Both checks run before any board folder is touched. This design does not add a new stop condition; it only confirms the existing ones still gate every path that would otherwise reach boardRelPath with no key for a ticket: true repo.

5. The real gap: a ticket:false repo throwing an available key away

Checked against the actual skill text, not just the profile schema. digismith:adopt Step 1 already asks for the ticket key unconditionally, every time, regardless of the active profile — then Step 3's own ticket: false branch throws it away: "skip straight to deriving the slug directly... No ticket.md gets written." That is precisely section 2's rejected alternative, already live in adopt today. The fix is narrow: Step 3's ticket: false branch gains one check — if Step 1 already confirmed a real key, invoke digismith:jira-intake Door 1 with it (same "already confirmed, don't ask again" call Step 3 already makes for a ticket: true repo) and use the keyed folder; only derive the slug directly and use the keyless folder when Step 1 found no key at all.

digismith:bootstrap has no equivalent prior step that asks for a key at all under ticket: false — it jumps straight to deriving a slug. The same fix applies, moved earlier: before skipping jira-intake, check whether a real tracker key is already evident from how this work was requested — the user named one, or (DigiSmith's own case) the dispatching context supplied one directly, the way this very ticket's brief named DGS-159. If one is evident, invoke digismith:jira-intake Door 1 with it instead of skipping intake outright; otherwise, unchanged.

jira-intake itself needs no change to its own door logic — it has never read the ticket: field (confirmed by re-reading its SKILL.md: every "ticket" occurrence there is the English word, not the profile flag). It only needs its target path updated (section 6) — which door ran, and whether that door's output carries a real key, already fully determines keyed-vs-keyless without jira-intake ever consulting the profile.

Step 2: every .digismith/docs/<slug>/... path becomes boardRelPath(key, title)'s result, resolved once and carried forward (never re-derived from a bare slug later). Branch naming (Step 2's <Key>__<slug> vs. <slug> rule) is untouched — flagged in section 7, not decided here.

adopt

Step 3, Step 6

Step 3: the narrow fix in section 5 — use the key Step 1 already confirmed instead of discarding it under ticket: false. Step 6 ("Relocate the Docs"): target path becomes the resolved board path instead of .digismith/docs/<slug>/; the HTML shell's footer line and Step 6's own embedded copy both need their literal .digismith/docs/<slug>/design.html string updated to match.

init

Step 0, Step 1

Never reads ticket: itself — delegates entirely to bootstrap/adopt. Its own branch-name-to-path check (Step 0 item 2, Step 1 rows 2–3) still derives <slug> from the branch name the same way as today (strip a leading <Key>__ prefix if present, else the whole branch name). It does not reconstruct a board folder name from that derivation — the folder's own key does not have to match the branch's (section 3's findBoardFolderBySlug note). Instead: call findBoardFolderBySlug(slug, mainRoot) against .digismith/board/; found → plan.md lives at .digismith/board/<that folder>/plan.md. Not found → fall back to the legacy, flat .digismith/docs/<slug>/plan.md check (today's exact mechanism, unchanged) until the historical folders move (DGS-164). Neither exists → no plan anywhere, same as today.

jira-intake

Step 3, Handling Existing Files

Target path: boardRelPath(key, title) when the ticket being written has a real **Key:** (Door 1, or an upgraded Door 2 draft), boardRelPath(undefined, title) otherwise (a Door 2 draft, or any ticket: false repo with none supplied). The "Blank/absent → Door 1, now has a real key → Upgrade" row in Handling Existing Files changes from an in-place field edit to a folder move: the whole .digismith/board/<slug>/ folder (ticket.md and anything already sitting beside it) moves to .digismith/board/<KEY>—<slug>/ — the same move-and-correct idiom digismith:adopt Step 3.2 already uses for its own branch-slug correction. Step 3.3's commit-vs-gitignore probe checks both ticket-file folders, never the repo-wide .digismith/ — that would count unrelated tracked files (config.yml, hooks, session notes) and call a repo "committed" without ever asking:

# ignored — either path already resolves to gitignored
git check-ignore -q .digismith/board/ || git check-ignore -q .digismith/docs/

# already tracked — either path has files git already knows about
git ls-files .digismith/board/ .digismith/docs/

This keeps an earlier docs/-era "committed"/"gitignored" decision valid until the historical folders move (DGS-164), and never asks the gitignore question twice. The Handling Existing Files table's own existing-file check (is there already a ticket.md at this slug) gets the same board-then-docs fallback order as init's plan lookup above — check boardRelPath's resolved path first, fall back to the legacy flat .digismith/docs/<slug>/ticket.md only if nothing is found under board/.

General read-vs-write rule, all four skills: every write this design touches goes to .digismith/board/ only — nothing new is ever written under .digismith/docs/ again. Every place that reads for an existing ticket folder — init's resume check above, jira-intake's Handling Existing Files table, adopt's relocation-collision check (Step 6), and bootstrap's own-session ticket.md check (Step 1) — checks board/ first and falls back to the legacy docs/ shape only if nothing is found there, until the historical folders move (DGS-164).

8. Path rules (for Part 4)

  • Writing: a tracker key is known (always for ticket: true; for ticket: false, whenever one is supplied anyway) → .digismith/board/<KEY>—<slug>/, via boardRelPath(key, title), or boardRelPathForSlug(key, slug) when both key and slug are already final (e.g. adopt Step 3, which already confirmed both). No tracker key is known (ticket: false, genuinely none supplied) → .digismith/board/<slug>/, via boardRelPath(undefined, title) / boardRelPathForSlug(undefined, slug). Nothing is ever newly written under .digismith/docs/ again.
  • Resolving an existing ticket's folder (a resume check, a collision check) — never reconstruct the folder name from a branch name or any other derived key: a folder's own key does not have to match the branch's (section 3). Call findBoardFolderBySlug(slug, mainRoot) against .digismith/board/ instead, and match on slug alone.
  • Reading, fallback order: check .digismith/board/ first (via findBoardFolderBySlug); nothing found there → fall back to the legacy, flat .digismith/docs/<slug>/ shape (today's unchanged mechanism) until the historical folders move (DGS-164). This applies everywhere an existing ticket folder is read: init's resume check, jira-intake's Handling Existing Files table, adopt's relocation-collision check, bootstrap's own-session ticket.md check.
  • ticket.md exists only inside a folder jira-intake actually wrote one into — absent wherever intake was skipped outright (bootstrap's no-key, ticket: false fast path).
  • design.html, plan.md, report.html all reuse the one resolved board path, carried forward from wherever it was first resolved — never re-derived from a bare slug partway through a skill chain.
  • A ticket: true repo with no resolvable key stops before any board folder work starts at all (section 4) — the pre-existing jira-intake/bootstrap stop conditions, unchanged.
  • parseFolderName(name) returns { key: string | undefined; slug } — undefined for a genuine keyless folder, never a thrown error for one. It still throws only when the name looks like a keyed name typed with the wrong dash (section 3). The commit-vs-gitignore probe (jira-intake Step 3.3) checks both .digismith/board/ and .digismith/docs/ — never the repo-wide .digismith/ — per the exact commands in section 6.
