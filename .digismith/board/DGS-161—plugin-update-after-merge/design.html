Problem

A merge to main should leave every live Claude Code session running DigiSmith's own plugin at the new version. Today it does not: the post-finish hooks (.digismith/hooks/post-finish/) that are supposed to handle this have five faults, found live during the Flux build 1 merge (DGS-154). ClickUp DGS-161 lists all five; the maestro has decided the fix direction for four of them and asked this ticket to find, document and wire the fifth (the reload step). This design covers hooks 01, 02 and 03 plus the runbook wording — it does not grow past that.

Hook 02: update command and cache flush

Command fix

claude plugin install digismith@jazurite --scope user only installs; once a version is already installed it reports "already installed, run update" and does nothing. The fix swaps the verb, keeping the same marketplace-refresh-first shape the hook already has:

claude plugin marketplace update jazurite && claude plugin update digismith@jazurite --scope user

Confirmed against the installed CLI (v2.1.283): claude plugin update --help takes --scope, and claude plugin marketplace update <name> takes the marketplace name (jazurite), unchanged from today's call.

Cache flush: skip it

The flush loop deletes every subdirectory of ~/.claude/plugins/cache/jazurite/digismith/ except the current version. A session that is still running on an older version loads its skills from that directory — deleting it out from under a live session is the unsafe case point 3 describes. There is no decided signal yet for "no session still uses the old version," so this design removes the flush entirely rather than guessing one. The whole flush block is deleted and replaced with one printed line:

Cache flush skipped (old versions stay in ~/.claude/plugins/cache/jazurite/digismith/
until there's a safe signal that no running session still uses them — see
backlog/auto-update-plugin-after-merge.md, point 3).

No automatic deletion happens anywhere in this hook after this change. Old version directories accumulate until someone clears them by hand or a later ticket defines the signal.

The reload step (point 2)

Research this ticket did (reading the installed Claude Code CLI binary, v2.1.283, directly, since there is no published doc for this) found two separate things that were being conflated in the backlog write-up:

  • The CLI has its own self-updater (claude binary/npm package) with a similar-looking banner, "Update installed · Restart to apply" — unrelated to plugins.
  • claude plugin update's own success message is different text: Plugin "X" updated from A to B ... for scope S. Restart to apply changes. This is the one workers actually saw. Its CLI help text literally says "(restart required to apply)".
  • A real, separate local command, /reload-plugins, exists: "Activate pending plugin changes in the current session." The binary's own notification system (plugin-reload-pending / needsRefresh) tracks marketplace-sourced plugins as one of its three categories (inline, synced, marketplace) — this is not limited to the dev-mode "mods" hot-reload feature that most of the /reload-plugins strings describe. /reload-plugins --force also exists, for re-reading when the normal path reports nothing pending.

What is not confirmed: whether /reload-plugins actually picks up a real marketplace-plugin version bump in a live session without a restart. The maestro's condition on this design is explicit: the hook text must not assert this as fact. Hook 02's closing reminder changes from

"Any other Claude Code sessions already running on this machine won't see this update until restarted."

to:

"Any other live session on this machine can try /reload-plugins to pick this up without restarting — if the skill text stays stale, restart that session instead. For a herdr worker pane: herdr agent prompt <agent> "/reload-plugins". Untested on the Desktop maestro — it is a remote session, and the CLI has a separate message, "/reload-plugins isn't available over a remote connection in this session," that may apply there; treat the maestro's own reload path as unverified until tested separately."

This wording is provisional. Once Jack runs the live test (below), hook 02's text is tightened to state whatever was actually observed.

Live test procedure for Jack

Jack runs this himself, from the maestro, using this worker's own pane (dgs-161) as the test subject — not a throwaway pane, since memory is tight. This pane's session started before this ticket's own merge bumps the plugin version, so it is a genuine stale-session test with no extra process.

Observable: invoking any skill prints Base directory for this skill: <...>/cache/jazurite/digismith/<version>/skills/<name> as the very first line of that skill's output. The version number in that path is a direct, unambiguous read of which cache directory this specific session is actually loading from right now — not what is merely installed on disk.

  1. Before. After this ticket's merge and hook 02's successful claude plugin update have both happened (so ~/.claude/plugins/cache/jazurite/digismith/ has a new version directory newer than what this pane loaded at its own start), run: 
    herdr --session DigiSmith agent prompt dgs-161 "Invoke any digismith skill (for example digismith:toolchain with a harmless read-only argument) and report only its first line."
    Read the pane's reply: the version number in Base directory for this skill: .../digismith/<version>/skills/... should be the old version (this pane's own session-start version) — if it already shows the new version, this pane already picked it up some other way and is not a valid test subject; stop and say so rather than continuing.
  2. Reload. Confirm the pane is idle (not mid-turn) — a plugin change applies only when the current response finishes, per the CLI's own messaging — then send: 
    herdr --session DigiSmith agent prompt dgs-161 "/reload-plugins"
    Read whatever the pane prints in response (it may be a short status line, or nothing visible if it queues silently).
  3. After. Repeat the exact same skill-invocation prompt from step 1: 
    herdr --session DigiSmith agent prompt dgs-161 "Invoke any digismith skill (for example digismith:toolchain with a harmless read-only argument) and report only its first line."
    Read the version number again.
  4. Pass / fail.
    • Pass — the "after" version is the new version and the "before" version was the old one. /reload-plugins genuinely updates a live session without a restart.
    • Fail — the "after" version is unchanged. Try herdr --session DigiSmith agent prompt dgs-161 "/reload-plugins --force" once, then repeat step 3. Still unchanged → /reload-plugins does not apply a marketplace plugin version bump in this setup; a restart (closing and reopening the agent) is the only path, same as before this ticket.
    • Inconclusive — the pane's reply to either command contains wording like "not available over a remote connection" or similar refusal text. Record the exact wording; it means herdr's own pane is being treated as a remote connection by the CLI, which would change this design's assumption that only the Desktop maestro is affected.
  5. Report back (pass/fail/inconclusive, and the exact wording of anything unusual) so hook 02's reminder text can be tightened from "try, and restart if stale" to a confirmed statement either way, before this worker's pane closes.

Hooks 01/03: dropping the ssh_key read

Full list of live ssh_key consumers found by grepping the main checkout (historical docs under .digismith/docs/, backlog/, and tests are excluded — they are records of what shipped, not live behavior):

FileRoleChanged by this ticket?
.digismith/hooks/post-finish/01-version-bump.md Reads ssh_key before pushing the version-bump commit. Yes — the fault this ticket fixes.
.digismith/hooks/post-finish/03-history-update.md Reads ssh_key before pushing the history-update commit. Yes — same fault, same fix.
skills/finishing-a-development-branch/SKILL.md (Option 1 and Option 2) Resolves ssh_key via digismith:preferences' get and builds SSH_KEY_PREFIX for the merge-time push and the PR-branch push. No. Not reported as blocked by the classifier; out of scope per the maestro's instruction.
skills/bootstrap/SKILL.md Step 0.6 Asks once per repo which key file to use, stores the answer. No.
skills/adopt/SKILL.md Step 2 Runs bootstrap's Step 0.6 verbatim as part of its own profile/credential resolution. No.
skills/preferences/SKILL.md Documents ssh_key as an example preference key. Not a consumer — no get/set call of its own. No.
MEMORY.md (H row, H.2 entry) Historical record of what shipped 2026-09-19: lists the two hooks and finishing-a-development-branch as consumers. No — a shipped-history entry is not rewritten after the fact; it will read as slightly stale for the two hooks once this ticket merges, same as any other historical entry whose consumer list changes later. Out of scope for this ticket to edit.

Only the two post-finish hooks change. In each, the whole SSH_KEY=$(... preferences.ts --key ssh_key --action get) line and the if/else around the push are deleted, replaced with a plain, unconditional push:

git add <files> && \
git commit -m "<message>" -- <files> && \
git push origin <base-branch>

Each hook file already carries prose immediately below its code block that says what to do if the push is rejected: "stop, report the rejection plainly, and investigate — do not force-push automatically." That prose already satisfies "say plainly and stop if git push fails" — it needs no new wording, since it already covers a failed/rejected push for an agent following these instructions as a skill. One new sentence is added to each hook, directly under the push line, making the behavior change explicit for a future reader:

"This push always uses the environment's default git/SSH config now, never a configured ssh_key preference. A repo whose default config can't reach the remote will have this push fail here — loudly, per the rejection handling above — rather than silently succeeding through a preference this hook no longer reads."

This repo's own default config already pushes fine with no key override (confirmed: this is exactly what the worker who hand-ran these hooks after the Flux merge already did, successfully, with a plain git push origin main).

Runbook wording (point 5)

The maestro writes this into .digismith/sessions/workbox.md directly (it is untracked; this ticket never edits it). Wording for the worker-merge-order step:

"After a worker merges to main (Option 1 or 2 of finishing-a-development-branch, or a maestro-ordered hand merge), the merge order must say: fire the post-finish hooks (fire-lifecycle-hook.md). A hand merge that skipped Option 1 needs the merge-range pins set by hand first (same doc, 'Merge-range pins') before the hooks can read a range."

Out of scope

  • A safe signal for when the cache flush can run (point 3's open half) — stays a manual/TODO step, tracked in the existing backlog item.
  • A confirmed, automated reload mechanism for the Desktop maestro's own (remote) session — the live test above only covers a herdr worker pane. If the test comes back needing maestro-specific work, that is a separate ticket, not an expansion of this one.
  • Any change to finishing-a-development-branch, bootstrap, or adopt's own ssh_key handling.
  • Editing MEMORY.md's historical H.2 entry.
