DGS-332 Add status command — Implementation Report

Ticket: DGS-332Date: 2026-10-13

Summary

dg clickup add-status adds a status to a space's status set through Frontdoor. The PUT replaces the whole set, so it reads the current set, sends every status back plus the new one, and verifies the set after the PUT. Dry run unless --yes; space level only. Whole suite passes (1881).

What was built

dg clickup add-status --space <id> --name <n> --type custom|done|open|closed [--color #rrggbb] [--yes] (Frontdoor). Dry run unless --yes.

  • Client methods getSpaceStatuses and putSpaceStatuses.
  • The PUT replaces the whole set, so the body is every current status untouched plus the new one (no id), before the closed status, orderindex re-numbered.
  • Dry run prints the planned set with the new status marked and "a real add replaces the whole status set: needs Jack's yes".
  • --yes prints the full previous set, sends one PUT, reads the set again, and exits 1 naming any status that is lost or changed.
  • A conflict prints ClickUp's message and exits 1.

Not built

--folder and --list wait for a capture (Jack). A pure add has no capture: status_change_map is omitted; the first real add will show if ClickUp accepts that.

Tests

26 new in add-status.test.ts (planStatusAdd 11, add-status 9, verification 6), 3 new in frontdoor.test.ts (FrontdoorClient 18 → 21). Full run: 133 files, 1881 tests pass (base 1852). Mocks only, no write.

Review

Claude whole-branch review: NOT READY, 9 findings, all fixed test first. Main one: an empty or missing status read could have wiped the space's set; the read now throws and the plan refuses an empty set. Also: relative order kept, id-less or unordered statuses refused, full post-PUT verification (id, name, type, colour, order, count), digits-only --space, clear messages for a failed read-back and a conflict, and the dry run says the position of a custom status is assumed.

First use

Dry run only on the DigiSmith space 1301150000001271. A real add needs Jack.
