1. Goal and scope

Today to do is the only starter, and the night scan takes every ticket in it. Jack cannot keep a ticket for himself, and cannot plan a ticket for a later day. This spec adds two starters and one clock.

DGS-600

ready, scheduled, Mode

New statuses ready and scheduled. New field Mode. The scan claims ready only. to do becomes attended. The Steward knows the new flow.

DGS-601

Scheduled at, schedule-release, Schedule view

New date field Scheduled at. A Nexus job schedule-release moves a due scheduled ticket by its Mode. A ClickUp view "Schedule".

Not in this work: the Oculus view (DGS-602); the pickup loop, caps and the day/night dial (later in DGS-434); the Refiner role (Definition of Ready, Sign-off and Mode proposal, rank); a better name for ready. Pickup timing, the night window and the away switch do not change.

No migration. Tickets in to do today stay in to do and are now attended.

2. Status flow

refinement --(Jack approves)--> to do       attended: Jack starts and observes it; never picked up automatically
refinement --(Jack approves)--> ready       unattended: autonomous-scan claims it (Mode must be Autonomous)
refinement --(Jack approves)--> scheduled   parked until "Scheduled at"
scheduled  --(schedule-release, Scheduled at is past)--> ready  (Mode Autonomous)
scheduled  --(schedule-release, Scheduled at is past)--> to do  (Mode Manual)
to do      --(Jack starts it)--> in progress
ready      --(autonomous-scan claims it)--> in progress

Space order after the change: backlog, concept, discovery, refinement, scheduled, to do, ready, in progress, review, acceptance, release, done, documented, discarded, Closed. Both new statuses are type custom. Colours: scheduled #0091ff, ready #2ecd6f.

Jack can also move scheduled to to do or ready by hand at any time. Nothing stops that; schedule-release only reads tickets that are still scheduled.

3. Custom fields

Scheduled atdate, with timean instant (ms). Shown and entered in UTC+7.DGS-601

Mode says who carries a ticket through (AI on its own, or Jack). Sign-off says who accepts. Every ticket can hold Mode; it is set in refinement (proposed by the Refiner later, approved by Jack). No "Then" field.

Where the fields live. Both fields go to the same location as the existing Sign-off field (id 9f85d93c-…), so every list that shows Sign-off also shows Mode and Scheduled at. The reads of DGS-600, DGS-457 and DGS-586 show Sign-off in clans B, C and J; DGS-548 (another folder) does not have it, so Sign-off is not workspace-wide. The exact location (space or a set of folders) is read first, with a new read command (section 6).

The scan reads Mode the same way it reads Sign-off today: the dropdown value is an orderindex; the option name is found in type_config.options. Any other value, or no value, reads as null.

5. The scan after DGS-600

Only the starter changes. The order of steps, the night window, the away switch, the lock, the breaker, the guardrails, rank order and "claim one and stop" stay as they are.

  1. Step 3: hasStatus("ready"). Missing → event no-starter-status, one comment on DGS-548: "the status "ready" is missing, so no ticket can be picked up".
  2. Step 4: listByStatus("ready"). Only Task and Bug (unchanged).
  3. Step 5: checkReady now has five checks, in this order: spec and plan, Sign-off, milestone, blocked, Mode. Mode passes only when it is Autonomous. A failure is a skip with one comment, posted again only when the reasons change (the existing notes.json hash).
  4. A claim that fails writes ready back.

A ready ticket with Mode Manual stays in ready with the comment. Jack moves it to to do or sets Mode to Autonomous; the scan does not move it.

7. schedule-release (DGS-601)

Command

dg autonomous schedule-release [--dry-run]. Code in packages/cli/src/autonomous/schedule-release.ts (pure core with injected tracker and clock) and its command in autonomous/index.ts. It uses the same Tracker, state folder (autonomousDir()) and clock helpers as the scan. No model tokens.

Nexus job

defineJob({
  name: 'schedule-release',
  description: 'Scheduling: move each scheduled ticket whose Scheduled at is past to ready (Mode Autonomous) or to do (Mode Manual). No model tokens.',
  schedule: { atUtc7: '00:00', windowEndUtc7: '23:59', everyMinutes: 5 },
  command: { file: process.execPath, args: [...DG, 'autonomous', 'schedule-release'] },
  timeoutMs: 2 * 60 * 1000, catchUp: 'skip', order: 45, notify: 'failures', manualOutsideWindow: 'allowed',
})

Order 45 puts it before autonomous-scan (50) in the same slot, so a ticket released to ready can be claimed in the same 5-minute slot. The Nexus engine runs one job at a time, so the two never run together.

Rules, per run

  1. listByStatus("scheduled"), any task type. The team search gets an optional status filter (statuses[]), used by both jobs, so a run reads only the tickets it needs.
  2. For each ticket, in "Scheduled at" order:
    • Scheduled at missing or not a number → skip; comment once: "Scheduled at is empty or not a date. Set it (UTC+7) and the ticket moves at that time."
    • Mode missing → skip; comment once: "Mode is empty. Set Autonomous (moves to ready) or Manual (moves to to do)."
    • Scheduled at later than now → nothing.
    • Else move: Autonomous → ready, Manual → to do. Read the status back. Equal → event schedule-move (ticket, to, mode, scheduledAtUtc7). Not equal or an error → event schedule-move-failed (ticket, to, error); comment once with the error; the ticket is still scheduled, so the next run tries again.
  3. No other write. No comment on a normal move (the event is the journal; ClickUp's own history shows the status change).

Journal. The move goes into events.jsonl in the autonomous folder (the Nightwatch event tail shows it). It does not use the ticket-phase journal (journal.jsonl), which belongs to the locked ticket's controller.

Comment once. A separate file schedule-notes.json (ticket key → hash of the reason). A comment is posted only when the hash changes, and the entry is removed when the ticket leaves scheduled (so a later scheduling problem comments again). Separate from the scan's notes.json, so the two jobs never overwrite each other's notes.

Idempotent. The only input is the set of tickets still in scheduled. A moved ticket is no longer listed. A run that dies halfway leaves each ticket either moved or still scheduled; the next run finishes. catchUp: 'skip': after a Nexus restart the next 5-minute slot moves everything that came due meanwhile.

Dry run. --dry-run prints one line per scheduled ticket (key, Scheduled at UTC+7, Mode, verdict) and writes nothing.

Exit code. 0 when the run finished (even with skips or a failed move, which are events); non-zero only when the tracker cannot list tickets. Nexus then notifies on failure, as for the other jobs.

8. Schedule view and the DGS-488 text

View. One List view named Schedule at the DigiSmith space (1301150000001271): status scheduled, sorted by Scheduled at, ascending, with the Scheduled at and Mode columns. A Calendar view is not used: it places tasks by start and due date, not by a custom date field.

DGS-488. The status table gets: a row scheduled (parked until Scheduled at; schedule-release moves it by Mode), the to do row (attended: Jack starts and observes; never picked up automatically), a row ready (unattended: autonomous-scan claims it in rank order; Mode Autonomous), refinement leaves "Jack approves -> to do, ready or scheduled", and the Lights-Out role "picks ready tickets". The Definition of Ready gains "Mode set". The write: read the current Markdown with dg clickup get-task DGS-488 --markdown, change only those lines, write with dg clickup update-task --task DGS-488 --markdown-description-file <file>, read back.

9. Errors and edge cases

  • ready missing in a list with its own status set: hasStatus passes when any list has it; a ticket in a list without it cannot reach ready. The setup lists such lists (read only) and reports them; no change to them.
  • schedule-release cannot set ready or to do (status missing in that list): schedule-move-failed, one comment, retried each run; the comment says what is missing.
  • Scheduled at in the past at approval: moves on the next run (at most 5 minutes).
  • Mode changed while scheduled: the value at the due run decides.
  • A ready ticket with Sign-off Jack: allowed; it runs to acceptance, as today.
  • Jack moves a locked (claimed) ticket to to do: the controller no longer writes in progress back; the watchdog's existing rules handle the stalled run.

10. Testing

  • Test first. Fakes only: the existing fake tracker and fake ClickUpClient / FrontdoorClient objects; no real ClickUp, no herdr prompt, no live API, DIGISMITH_DEPOT_DIR in a temp folder.
  • Scan: ready claimed, to do never claimed (a fake with one of each); Mode Manual and missing skipped with one comment, again only on a changed reason; claim failure writes ready; missing ready status.
  • Advance: ready repaired to in progress; to do left alone.
  • Steward: approved --into each target and a bad one; started from ready.
  • schedule-release: due Autonomous → ready; due Manual → to do; future → nothing; missing date, invalid date, missing Mode → one comment each, not repeated; read-back mismatch → failed event and retry next run; second run after success does nothing; dry run writes nothing.
  • Commands: get-field, create-field --location, create-field --type date, --field date value, create-view: body and path in the dry run, the sent call with --yes, the refusals.
  • Registry: the job validates (name, interval, order); registry.test.ts pins its fields.
  • Code in packages/cli/src/ runs under node --experimental-strip-types (no parameter properties, enums or namespaces).
