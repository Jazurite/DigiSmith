1. Goal and non-goals

Count the tokens of every ticket, exactly, from the native usage data of the tool that did the work. Phase 1 has one reader: Claude Code transcripts.

  • Counts only. No prices, no dollars, no price table read, at any level. Analysis (dollars, meaning, comparison) is a separate plan, not filed yet.
  • Transcripts are read for numbers only: usage, model, ids, timestamps. No message text is copied out.
  • Not in phase 1: OpenCode, Codex, TokenReply, footprint measure, ClickUp comment, DGS-204 database, levels 3 and 4.
  • Not decided here: where the registry lives (DGS-220).

4. Record shape and readers

One record per API response, the same for every source:

UsageRecord {
  source:      "claude-code"            // reader name; later "opencode", "codex", ...
  session_id:  string                   // the session the response belongs to
  agent_id:    string | null            // subagent id, null for the main thread
  response_id: string                   // dedupe key (Claude Code: message.id + requestId)
  model:       string
  ts:          ISO-8601 UTC
  input:       number
  output:      number
  cache_read:  number
  cache_write_5m: number
  cache_write_1h: number
}

A reader is one function: read(sessionRef) -> UsageRecord[], already deduped. The grouping code (steps, tickets, levels) never sees a transcript, only records. Adding Codex or OpenCode later means adding a reader, nothing else.

The Claude Code reader maps usage.input_tokens, output_tokens, cache_read_input_tokens and usage.cache_creation.{ephemeral_5m,ephemeral_1h}_input_tokens. If cache_creation is missing, all of cache_creation_input_tokens goes to cache_write_5m and the record is marked write_split: unknown. Fields such as service_tier, speed, iterations, fallback_credit are kept in a free-form raw_flags object so a later analysis can use them; this plan does not interpret them.

5. Counting right

  • Dedupe. One response appears on several transcript lines with the same message.id and requestId. Checked on this session's own transcript: 109 assistant lines, 60 unique pairs. Group by the pair, take one record per pair. Where lines differ, keep the line with the highest output_tokens (streaming lines can carry a partial output). The plan must pin this with a fixture.
  • Subagents. Their transcripts are in <session>/subagents/agent-<id>.jsonl with a .meta.json. Each line carries the parent sessionId and an agentId. So a parent session in the registry covers its subagents; no write is needed at subagent dispatch.
  • Session id changes. A worker's session id changes on /clear or resume. The registry therefore lists every session id of a ticket, and the init write must be repeated when a resumed session continues the ticket (the resume path of init appends a line too).
  • Transcript location. A transcript is re-homed to the project folder of its current cwd. Find it by session id with the three-step lookup already in skills/telemetry/SKILL.md Step 2 (recorded path, current-cwd folder, a search under ~/.claude/projects).
  • Compaction, refusal fallbacks, iterations. Not assumed. The plan opens real transcripts that contain each case and checks that the per-response sum is right. If iterations carries extra billed work not in the top-level counts, the reader adds it and the fixture proves it.
  • Cross-check. At build time and when a Claude Code version changes the format, compare per-session totals against pnpm dlx ccusage session --json. A mismatch is a bug in one of the two. ccusage is never a dependency.

6. The registry

Interface

Registry {
  append(entry: RegistryEntry): void   // append-only
  read(ticket: string): RegistryEntry[]
}

RegistryEntry =
  | { kind: "session",    ticket, session_id, source, role, ts }
  | { kind: "step_start", ticket, step, session_id, ts }
  | { kind: "step_end",   ticket, step, session_id, ts }
// role: worker | maestro | reviewer | other   (subagents are found through their parent session)
// step: brainstorming | writing-plans | implementation | finishing | other

Everything else in DGS-214 uses only these two calls. The location behind them is not picked.

Location: open, owned by DGS-220

  • Option 1, depot per ticket: ~/.digismith-depot/token-registry/<ticket>.jsonl. Outside every worktree, so no copy step. Stays on one machine.
  • Option 2, board folder: .digismith/board/<ticket>/registry.jsonl. Travels with the ticket. Untracked in a worktree, lost on cleanup unless committed, puts session ids into git.
  • Option 3, one global registry split by month and year: registry/<yyyy>/<mm>.jsonl. One place to scan. A ticket that spans a month boundary spans two files.

The plan for DGS-214 ships a default implementation behind the interface only so the feature works; DGS-220 may replace it. The default must be chosen at plan time and is marked interim.

Why not reuse .digismith/telemetry-marker. It is written only when the profile has logging: true (the digismith profile has false). It is one untracked file per checkout, deleted and rewritten at each ticket start, and it holds one session id. Only its start point and its transcript lookup are reused.

Fallback tagging

For sessions with no registry line: the customTitle (custom-title.json in the session folder, such as DGS-214 ⚚ Token counter), the gitBranch (<Key>__<slug>) and the cwd (worktree path) are matched to a ticket key. A match is marked attribution: inferred in the output. No match goes to the unattributed bucket. The maestro's and the Master's turns are never split by ticket in phase 1: they are a maestro session of their own, counted per session.

7. Levels and steps

LevelSum ofPhase 1?Where it lives
1 TaskThe records of the task's subagents: implementer, reviewers, fix dispatchesYesA row in the SDD progress.md ledger
2 TicketIts tasks plus the non-SDD steps; with a total per stepYestokens.json and dg tokens <ticket>
3 EpicIts tickets' tokens.jsonNo, waits for DGS-220Read-only roll-up
4 EverythingAll epicsNo, waits for DGS-220Read-only roll-up

Only level 1 reads transcripts. Each level above reads the output of the level below, so a roll-up never touches a transcript.

Step boundaries

A record belongs to the step whose step_start / step_end window (in the same session) contains its timestamp. A record inside no window goes to step other. Subagent records take the step of their parent session at that time. A step may have several windows (resumed work). The SDD task rows split the implementation step further, by task.

8. tokens.json and dg tokens

{
  "schema_version": 1,
  "ticket": "DGS-214",
  "generated_at": "...",
  "reader_versions": { "claude-code": "1" },
  "steps": {
    "brainstorming": {
      "claude-opus-5-5": { "input": 0, "output": 0, "cache_read": 0,
                           "cache_write_5m": 0, "cache_write_1h": 0, "responses": 0 }
    }
  },
  "tasks": { "task-1": { "...": "same shape as a step" } },
  "sessions": [ { "session_id": "...", "role": "worker", "attribution": "registry" } ],
  "unattributed": { "...": "same shape" }
}

Counts only. Versioned and self-describing so DGS-220 can ingest it unchanged. Written once at finish by the command below; rewritten if the command is run again.

dg tokens <ticket>: read the registry, run the readers, dedupe, group by step, print a table (steps by model by token class) and a per-session list. --json prints the snapshot. --write saves it into the board folder. Code location is not fixed by this design (proposed: a new module next to scripts/token-counter/, with the command in packages/cli); the plan decides.

9. The DGS-220 boundary

DGS-220 (Imperium epic, backlog/telemetry-and-data-collection-plan.md) is the future home of the store. DGS-214 keeps its storage small so it moves in:

  • The registry interface (append, read) and its entry types are the contract. DGS-220 replaces the implementation behind it.
  • The tokens.json schema (schema_version) and the UsageRecord shape are the migration format. DGS-220 ingests existing files unchanged.
  • DGS-220 decides: the registry location (the three options above), one record shape across all telemetry, who collects, retention and privacy, and levels 3 and 4.
  • A separate Analysis plan (name open, not filed) owns prices, dollars and comparisons. DGS-214 emits nothing it needs beyond counts.

10. Phase 2 and later readers

Phase 2 (named, bounded, not designed)

More readers behind the same UsageRecord: OpenCode (its own session store, for Sol), Codex (its native logs), TokenReply (its request log, for Kimi and luna), and the runners' ParsedResult. Each needs its own look at what that tool records, and whether its numbers are comparable (for example, how it reports cache). Nothing in phase 1 blocks them.

Footprint measure (claudecheck.py), later

The colleague's script measures what we would send each turn (system prompt, tool schemas, a sample tool payload) with the free count_tokens endpoint, subtracting a baseline call. dg tokens measures what was billed. Together they explain a bill: footprint times turns is most of the input and cache tokens.

  • Not phase 1. It needs an API key, which the Workbox rules forbid reading. Its model claude-3-5-sonnet-latest has an older tokenizer than 5.x. The baseline subtraction leaves a few tokens of error per measure. It uses pip.
  • Where it would sit: a dg footprint command beside dg tokens, as its own reader with kind: footprint records. Subjects: our skills list, CLAUDE.md, MEMORY.md, MCP tool definitions. It would use a 5.x model, pnpm and a key held the way Jack approves.
  • Free partial view now: the first response of a session shows the real fixed prefix (turn-1 cache creation). Phase 1 can print it as observed_prefix per session at no API cost. Optional; the plan decides.

11. Testing and rules

  • Fixtures: small synthetic transcripts (no real message text) for: duplicate lines, a subagent file, missing cache_creation, a resumed session, a record outside every step window.
  • Reader contract test: every reader returns the same UsageRecord shape.
  • Oracle check: per-session totals against ccusage, run by hand or in a manual test; not a CI dependency.
  • Real run: count DGS-214's own session and compare with a hand count of one transcript.
  • Rules: pnpm only. No token or .env read. No message text copied. Skill changes (init, step skills, SDD, finishing) follow digismith:writing-skills.
