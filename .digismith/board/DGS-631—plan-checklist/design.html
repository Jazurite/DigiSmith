Goal

A ticket's plan tasks show as a ClickUp checklist on that ticket, one item per plan task, ticked as each task passes. One branch, two tickets: DGS-632 builds the dg command (tool side), DGS-631 hooks it into three skills (skills side). A checklist, not subtasks: DGS-563 spike Q4 (one write per task, no new keys, no status flow).

DGS-632: dg clickup checklist sync

dg clickup checklist sync --task <KEY|id> --plan <plan.md>
    [--done <n,n,...> | --ledger <progress.md>] [--name "Plan"] [--yes]
  • Plan parse. Every line ### Task N: <title> outside fenced code blocks gives item number N, name Task N: <title>. No task headings, or a number twice: exit 1.
  • Done set. --done lists task numbers; a number not in the plan exits 1. --ledger (an addition to decision 1, so the skills read the ledger, not memory) takes every Task N: complete line of an SDD or inline-execution ledger; ledger numbers not in the plan are ignored and listed in the output. Both flags: exit 1. Neither: no item is done.
  • Read. getTaskByRef returns the task's checklists. The target is the first checklist named --name (default Plan); a second one of that name is left alone and reported.
  • Diff by task number. Each checklist item whose name starts Task N: is matched to plan task N. Missing → add. Name differs → rename. Number not in plan, or a second item for the same number → remove. resolved differs from the done set → tick or untick (in the same PUT as a rename). Items with any other name are someone else's: left alone, counted as foreign. No checklist → create it, then add every item.
  • Dry run (no --yes): reads the task only, writes nothing, prints the planned operations.
  • With --yes: create, remove, rename/tick, add (then tick the added done items), then read the task back and check the checklist equals the plan. A failed write or a read-back mismatch exits 1 with clickup checklist sync: <message> on stderr, naming the step that failed. A second run with no change makes no write (idempotent).
  • Output. One JSON line on stdout: {"task":"DGS-631","checklist_id":"…","dry_run":false,"ops":{"create":0,"add":1,"rename":0,"remove":0,"tick":2,"untick":0}, "items":[{"n":1,"name":"Task 1: …","resolved":true}],"foreign":0,"ignored_done":[]}.

Code

  • packages/clickup-client/src/types.ts: ClickUpChecklist, ClickUpChecklistItem; ClickUpTask.checklists typed with them.
  • packages/clickup-client/src/client.ts: createChecklist(taskId, name) (POST /task/{id}/checklist), createChecklistItem(checklistId, name) (POST /checklist/{id}/checklist_item), editChecklistItem(checklistId, itemId, {name?, resolved?}) (PUT /checklist/{id}/checklist_item/{item}), deleteChecklistItem(checklistId, itemId) (DELETE same path).
  • packages/cli/src/clickup/checklist/: plan.ts (pure parse of plan and ledger), diff.ts (pure diff: current checklist + plan + done set → operations), sync.ts (the yargs command, client factory injected like add-comment.ts), index.ts (the checklist group, registered in clickup/index.ts). No low-level checklist commands: the sync covers recovery.
  • Tests: Vitest, mocks only. Pure tests for parse and diff; command tests with a fake client (dry run writes nothing, create path, add/rename/remove/tick, idempotent second run, failed write exits 1, read-back mismatch exits 1). No live ClickUp write.

DGS-631: skill hooks

Each hook is one small step titled Plan checklist (DGS-631), so the Hallmark (DGS-546) rebase stays easy. Key rule: the key the build runs under (board folder, else branch/worktree name, same regex the skills already use). Only DGS-<n> keys run the sync; any other key or none prints one line Plan checklist: skipped (no ClickUp key).

SkillWhenCommand
writing-plansAfter the plan is written and committeddg clickup checklist sync --task <Key> --plan <plan> --yes
subagent-driven-developmentStep 5, after the completion line (role mode reaches step 5 on "review clean"); after a plan revision; once after the final review is clean, before Finish… --ledger <workspace>/progress.md --yes
executing-plansAfter each task's ledger line (step 6); after a plan revision; once in Step 3 before the report… --ledger <workspace>/progress.md --yes

Never blocks. A non-zero exit prints a warning and appends Checklist sync: failed (<first stderr line>) to the ledger (writing-plans has no ledger: warning only); the build goes on. The next sync recomputes the whole list and heals a missed one.

Allowlist. If the classifier blocks dg clickup checklist sync, the worker tells its conductor; the runbook gets the rule, never edited by the worker.

Out of scope

  • Item order repair (a task added back later sits at the end; the numbers still say the order).
  • Assignees, nested items, deleting a whole checklist.
  • Ticket status changes (the conductor owns them).
