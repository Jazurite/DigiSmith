Goal

A ticket's plan shows as a ClickUp checklist on that ticket and moves with the build. One branch, three tickets (order main-13 changes main-12): DGS-632 builds the dg command, DGS-631 makes writing-plans create the checklist, DGS-634 makes SDD and executing-plans tick it. A checklist, not subtasks: DGS-563 spike Q4 (no new keys, no status flow).

Layout and item keys

One checklist named Plan. ClickUp v2 nests items: Create Checklist Item takes only name, Edit Checklist Item takes parent ("to nest a checklist item under another checklist item, include the other item's checklist_item_id"; verified on developer.clickup.com 2026-10-25). So a child is created, then edited with its parent. The flat fallback is not built: nesting is documented, and the read-back catches a server that ignores it.

Item N is ticked when its three children are ticked (or when N itself is in the done set). Any other item is someone else's: left alone, counted as foreign.

DGS-632: dg clickup checklist sync

dg clickup checklist sync --task <KEY|id> --plan <plan.md>
    [--done <key,key,...> | --ledger <progress.md>] [--name "Plan"] [--yes]
  • Plan parse. Every ### Task N: <title> line outside fenced code blocks is a task. No task, or a number twice: exit 1.
  • Done set. --done takes item keys: N, N.implement, N.review, N.fix, N.fix:none, final.review, final.fix, final.fix:none. The :none form ticks the fix item and names it Fix (none needed) / Whole-branch fixes (none needed). A key for a task not in the plan, or a bad key: exit 1. --ledger derives the same keys (next section); ledger keys for tasks not in the plan are ignored and listed. Both flags: exit 1. Neither: nothing done.
  • Read. getTaskByRef returns checklists. Items are flattened (nested children objects or flat items with parent, both read). Target: the first checklist named --name; others of that name are left alone and reported.
  • Diff by key. Missing → add (children: add, then one edit with parent and the tick). Name differs → rename. Resolved differs → tick or untick (same PUT). Key of a task not in the plan, a second item for one key, a known child under a removed task → remove, children before parents. No checklist → create it, then add everything.
  • Dry run without --yes: reads only. With --yes: create, removes, edits, adds, then read back and check the checklist equals the wanted state. A failed write or a read-back mismatch exits 1 with clickup checklist sync: <message>, naming the failed step and how many writes were made. A run with no change makes no write.
  • Output. One JSON line: {"task","checklist_id","dry_run","ops":{"create","add","rename","remove","tick","untick"}, "items":[{"key","name","resolved"}],"foreign","ignored_done","same_name_skipped"}.

Code

  • clickup-client: ClickUpChecklist, ClickUpChecklistItem types; createChecklist, createChecklistItem, editChecklistItem(id, item, {name?, resolved?, parent?}), deleteChecklistItem.
  • packages/cli/src/clickup/checklist/: plan.ts (plan, --done keys, ledger → keys), want.ts (plan + done → wanted items), diff.ts (current + wanted → ops), sync.ts (command), index.ts (the checklist group). Vitest, mocks only.

Ledger to keys (DGS-634)

State always comes from the ledger. Existing lines carry most of it; the DGS-634 hook adds three lines where none exists today.

Key done when the ledger hasLineNew?
N.implementTask N: implemented, Task N: review requested or Task N: completeimplemented is new
N.reviewTask N: reviewed (...) or Task N: completereviewed is new
N.fixTask N: complete; named Fix (none needed) when the ledger has no Task N: fix round lineno
final.reviewTask final: reviewed (...) or Task final: completeboth new
final.fixTask final: complete; (none needed) when Task final: reviewed (clean)new

"Review" ticks when the task review returns its verdict, like "Whole-branch review when it returns"; with findings, Fix stays open until the task's complete line (fixes verified). With a clean review, Review and Fix (none needed) tick together. executing-plans writes Task N: complete after its self-check, so its three children tick together with Fix (none needed); its whole-branch items tick only if a Task final: line is written.

Skill hooks

Small, named steps, so the Hallmark (DGS-546) rebase stays easy. Only DGS-<n> keys sync; other keys or none: one line Plan checklist: skipped (no ClickUp key). The key is the one the build runs under.

HookSkillWhat
Plan checklist (DGS-631)writing-plansAfter the plan commit (and after a plan revision): dg clickup checklist sync --task <Key> --plan <plan> --yes (creates).
Plan checklist (DGS-634)subagent-driven-developmentOne section: the ledger lines above and the command … --ledger <workspace>/progress.md --yes. Run after: implementer DONE (append Task N: implemented), task review verdict (append Task N: reviewed (clean|K findings)), task complete, plan revision, final review verdict (append Task final: reviewed (clean|K findings)), final review clean (append Task final: complete). Role mode: the Builder appends the same lines when its parent's verdict arrives.
Plan checklist (DGS-634)executing-plansAfter each task's ledger line, after a plan revision, once in Step 3.

Never blocks. A non-zero exit prints a warning and appends Checklist sync: failed (<first stderr line>) to the ledger (writing-plans: warning only). The next sync recomputes everything. If the classifier blocks the command, the worker tells its conductor.

Out of scope

  • The flat fallback layout (only if nesting proves broken live).
  • Item order repair, assignees, deleting a whole checklist, ticket status changes.
