1. Goal and scope

Today the reviews are subagents inside the Builder. They share its context, its seat and its blind spots. On the first Lights-Out night (DGS-483) the 21 task reviews and the 2 whole-branch reviews found real faults, one of them a leak: the Storybook build would have published file paths from the Mac. The Builder paid for all of it in its own context.

This spec makes the Reviewer one role with its own card, its own context pack for each type and its own start. The input is Jack's pitch on DGS-529 (ClickUp comment 1301150000116983). The pitch is a decision, not a proposal. This spec does not reopen it.

Settled by the pitch and not repeated as questions:

  • The Reviewer only judges. The Builder fixes. The Reviewer re-checks. The Reviewer never fixes and never merges.
  • One role, one field reviewer type: task or ticket. The ledger role final-reviewer becomes ticket.
  • Every role is its own agent with a defined context pack. It never gets the Builder's context.
  • Roles use primitives. The primitives stay the source of truth and are not merged into the role.
  • SDD decides when a review happens. It calls the Reviewer role at that step.
  • The ticket Reviewer prepares the preview for "Sign-off: Jack" tickets until a Releaser exists (DGS-467).
  • The report is a findings table on the ticket with a reviewer-type column.

Out of scope here: the call inside SDD (DGS-129), more tiers and the cross-model reviewer (DGS-127), the rename task to step (DGS-554), the Steward wiring (DGS-551), the Releaser (DGS-467), the nightly audit.

2. The role card

The role is one skill: skills/reviewer/SKILL.md, called digismith:reviewer. It is the Reviewer card. A task subagent and a ticket worker both load the same file, so the rules cannot drift between the two types. A skill is the right place because the repo already holds its roles' text in skills, and a herdr worker can read a skill from the brief.

The card holds, and only holds:

  • Authority. Read the target. Write one report. Return findings and a verdict. Nothing else. This is the Reviewer ceiling of DGS-404 (section 4 of that design). The one change is the preview step (section 8).
  • The type table (section 3) and the pack each type reads (section 4).
  • Which primitive to follow for which job, by reference, never by copy (section 3).
  • The output addendum: the findings block (section 7). The primitives do not have it.
  • Who "your human partner" is for each type: the Builder's orchestrator for task, the Maestro for ticket. The Maestro sends taste questions to Jack.
  • How the role is started (section 5) and which Steward events it maps to (section 9).

The card holds no review criteria. Severity, what to check, the fix loop and the output format stay in the primitives.

The session card fields (DGS-404, section 5)

A ticket Reviewer is a herdr worker, so it has a session card. The card uses role: reviewer and adds two fields for every worker:

  • reviewer_type: ticket (only on a Reviewer's card).
  • seat: dev0 or jack. This field is new. The conductor needs it to find the Builder's seat when it picks the Reviewer's seat. Today the seat is only in the pane's environment. The field is read from claude-account status at the start.

A task Reviewer is a subagent. It has no card of its own. The Builder's card stands for it.

Owner header on each primitive

Each primitive file gets one first line after its title: Used by the Reviewer role (DGS-529): not dispatched directly by a Builder. The files are:

  • skills/subagent-driven-development/task-reviewer-prompt.md
  • skills/subagent-driven-development/re-review-prompt.md
  • skills/requesting-code-review/code-reviewer.md

These files are vendored from Superpowers (vendored/PROVENANCE.md). The header is a local change. It gets a "Further diverged by DGS-529" line in PROVENANCE.md, and scripts/check_vendored_skills.ts must still report it as local divergence, not upstream drift. requesting-code-review stays callable by hand.

4. Context packs

A pack is the complete input of one review. It is a folder with a manifest, built by code, not assembled from memory. A new command builds it: dg reviewer pack --type task|ticket --plan <plan.md> .... It calls the existing review-package script for the diff, so the attribution check still runs before any pack is written. A hit stops the pack and the review.

Location: <sdd workspace>/reviews/<type>-<id>-r<round>/. The workspace is the plan's git-ignored .sdd-workspace (the SDD script sdd-workspace prints it). The manifest is pack.md. It lists each file with an absolute path and a one-line role, and it carries the values that fill the primitive's placeholders: base, head, diff file, model, brief file.

Two points where the pack lists something the pitch's short list does not, both because a primitive demands it. See section 14.

  • The implementer's report is in the task pack. task-reviewer-prompt.md requires it as a file of claims to check. It is marked unverified.
  • carry-over.md is in the ticket pack. SKILL.md of SDD tells the final reviewer to triage the deferred Minors and parked findings. Without that list the triage cannot happen. The file has one-line entries only, not review transcripts.

Standards are not matched by the pack command. The matching is a judgment (standards/index.yml holds descriptions). The Builder already picked the standards for its tasks and named them in the brief. The pack only copies those paths.

5. How each type runs

Type task: a subagent of the Builder

  1. SDD finishes a task and runs dg reviewer pack --type task.
  2. SDD dispatches a subagent with an explicit model. The prompt is short: read the card, read pack.md, follow the primitive named there.
  3. The subagent returns its report as its final message, as the primitive says. SDD saves it to <pack>/report.md and adds the ledger line Task N: dispatch task-reviewer ... as today.
  4. The fix loop is the primitive's: up to 5 rounds, the Builder fixes, a scoped re-review checks. The Reviewer subagent never edits.

Because this step lives in SDD, DGS-129 builds the call. This ticket defines what the call passes (type and pack path) and what it gets back (report and verdict).

Type ticket: its own worker

A Builder is a worker. A worker may not start another agent (DGS-404, authority ladder). So the Builder cannot start the Reviewer worker itself. A conductor or the Maestro starts it. The Builder stops at a checkpoint, as it did at STOP-1 and STOP-2 on the Lights-Out night.

  1. Request. The Builder finishes the last task, runs dg reviewer pack --type ticket, writes the ledger line Task final: review requested, and reports the marker STOP: ticket-review-ready <pack path>. It does not start anything. It waits.
  2. Start. The conductor starts the Reviewer with the runbook's "Start of a ticket" steps (S0 to S6), with these values:
    • Brief: skills/reviewer/ticket-brief.md, a template. It names the pack and the card. It says: judge only, write one report, never edit, never merge.
    • Agent: <key>-rev, for example dgs-529-rev. Label: <KEY> ⚚ Review. The Names block of the runbook allows a short word when one ticket has two workers.
    • Working folder: the Builder's worktree, read only. The Builder is stopped, so nothing changes under the Reviewer. During a fix wave the Reviewer is idle.
    • Model: Opus 5.5. Seat: see below.
    • The session card gets role: reviewer, reviewer_type: ticket, under: <the conductor or Maestro that started it>, seat.
  3. Review. The Reviewer follows code-reviewer.md against its pack, writes <pack>/report.md with the findings block, and ends with one pane line: done: <path> verdict: <approved|needs-fixes>.
  4. Verify and relay. The conductor verifies each finding (the skill digismith:receiving-code-review), then sends the verified findings to the Builder. A finding the conductor cannot verify goes to the Maestro, not into a fix.
  5. Fix wave. The Builder dispatches ONE fix subagent with the whole list (the SDD rule). Then it asks for the re-review.
  6. Re-review. The same Reviewer worker gets a round 2 pack (open findings, fix-wave diff) by herdr agent prompt. It follows re-review-prompt.md. If the worker is gone, a new one starts with the round 1 report in its pack.
  7. Residual. Any finding still open after the one re-review is adjudicated by the Maestro, as the primitive says: park with a ruling, or stop on a load-bearing one.
  8. Close. After an approved verdict (and the preview, when it applies) the conductor closes the Reviewer worker. Its record is the report and the table row. The merge follows the merge order. The Reviewer does not merge.

The seat

The pitch says "the other seat". The seat rule in force (Jack, 2026-10-17) puts every worker on dev0 until Wed 21 Oct 12:00 UTC+7. Until then the ticket Reviewer runs on dev0, like the Builder. The separation then rests on the separate context and the separate model, not on the seat. After that date the conductor picks the seat with "The rule" of the runbook and excludes the Builder's seat when the other seat has headroom. If no other seat has headroom, the Reviewer runs on the Builder's seat. A limit stop on the Reviewer's seat is reported to Jack. The conductor does not move the Reviewer on its own.

6. Findings, blocking, adjudication

All of it is as the primitives say. The card only names who decides.

  • Severity. Critical, Important, Minor, as in task-reviewer-prompt.md and code-reviewer.md. A hit from check-attribution is an automatic Critical.
  • What blocks. A verified Critical or Important finding, or a confirmed ⚠️ item, or spec ❌. For task it blocks the next task. For ticket it blocks the merge. Minor findings go to the ledger as deferred and never block. The ticket Reviewer triages the deferred ones and says which must be fixed before merge.
  • Loop. task: five fix rounds, then the breaker. ticket: one fix wave, one scoped re-review, then adjudication. There is no second wave.
  • Who adjudicates. The human partner: the Builder's orchestrator for task, the Maestro for ticket. A load-bearing finding that survives goes up to the Maestro and stays a blocker. A finding that conflicts with the plan text, and a finding that is taste, goes from the Maestro to Jack.
  • Who may override a block. Only the human partner, with a written ruling. The Reviewer cannot clear its own finding. The Builder cannot clear a finding either.
  • No fix, no merge. While a blocking finding is open, the ticket stays in review. The Steward gets no merged event. A night run does not retry it on its own (the failed-ticket status is DGS-490).

7. The findings table

The findings block (the card's addendum)

The primitives return free text. A table cannot be built from free text without guessing. So the card adds one rule to every Reviewer prompt: end the report with one fenced json block named findings.

[
  { "id": "F1", "path": "src/a.ts", "line": 42, "severity": "Important",
    "what": "fileNames leak the Mac home path",
    "scenario": "run the Storybook build; the output lists /Users/..." }
]

An approved review with no findings has []. The block is the only machine-read part. The rest of the report stays as the primitive writes it.

The verdict lines (the human partner writes them)

The Reviewer judges only, so the verdict on a finding is not the Reviewer's. The human partner writes one ledger line per finding at the moment it is decided:

Review ticket final r1: F1 -> fixed (commit a7f3c2d)
Review task 7 r2: F2 -> parked (reviewer wrong: the test asserts the cap)
Review task 3 r1: F1 -> rejected (out of scope per plan line 40)

The three verdicts are fixed, parked (real but deferred, or the code stands), and rejected (not a defect, with the reason). A reason is required for parked and rejected.

The table

A new command, dg reviewer table, joins the report files and the verdict lines into <board folder>/findings.md. One row per finding. Reviews with no findings give one summary row each, so the table shows that the review ran.

Reviewer typeRoundPath:lineSeverityWhat is wrongFailing scenarioVerdict

A finding with no verdict line makes the command fail with the finding's id. An unjudged finding must not ship in a table.

When it runs: in digismith:report-implementation, after the final review and before the Finish step deletes the SDD workspace. The report files live in that workspace, so the table must be built first. The conductor attaches findings.md to the ticket with dg clickup upload-attachment (a worker has no ClickUp write). This is the Provenance record (DGS-534). The report skill also links the table from report.html.

8. Preview for "Sign-off: Jack" tickets

For a ticket with the mark Sign-off: Jack, the ticket Reviewer has one last step after an approved verdict: it prepares what Jack needs to say yes or no. The output is <pack>/preview.md: what to look at, how to open it, and what changed in plain words. If the project has a preview recipe, the Reviewer also runs it and writes the URL.

A recipe is named in the profile as a new optional field preview (a skill or a command, for example the skill capture-ephemeral-url for an Emma theme). With no recipe, preview.md holds the local run steps and no URL. This ticket does not invent a deploy path.

Limits that keep the role narrow:

  • The preview step runs only the named recipe, only to a preview target, never to production.
  • It changes nothing in the repo and nothing in ClickUp.
  • It runs only when the ticket's mark is Jack and the verdict is approved.

This raises the Reviewer's ceiling in DGS-404 by this one permission (run the profile's preview recipe). DGS-404 says "raising any ceiling needs Jack". Jack's approval of this spec is that approval, and DGS-404's ladder gets the row change (section 10). When the Releaser exists (DGS-467), the step moves there.

11. Errors

  • Attribution found in the commit range. No pack is written. The review does not run. The Builder removes the attribution first.
  • Pack file missing (no plan, no spec, no ticket file). dg reviewer pack exits non-zero and names the file. A review without its input does not start.
  • Report without a findings block, or with invalid JSON. The human partner treats the review as not done and re-dispatches once. A second failure goes to the Maestro.
  • The Reviewer worker stalls. The conductor follows the Builder's time box rule (DGS-528): after about 30 minutes without output it reports and does not retry on its own. A whole-branch review took about 9 minutes on the cross-model proof of concept (DGS-78), so 30 minutes is a real stall.
  • The Reviewer wants to change something. It reports the need as a finding. It does not edit. A Reviewer that edited a file produces a Critical process finding in the next review.
  • The Reviewer cannot verify a claim. It marks it as ⚠️, as the primitive says. The human partner checks it.
  • The Reviewer's seat hits a limit. Report to Jack and wait (the seat rule in force).

12. Testing

  • dg reviewer pack, Vitest with a temporary git repo: a task pack holds exactly the listed files; a ticket pack holds no ledger text beyond carry-over.md; attribution in a commit stops the pack; a missing file gives a named error; pack.md has every placeholder value of the primitive.
  • dg reviewer table: findings plus verdict lines give the exact rows; a clean review gives a summary row; a finding without a verdict fails; a bad JSON block fails with the report path.
  • The card: a test checks that the type table in SKILL.md matches REVIEWER_TYPES, and that each of the three primitive files has the owner header (this guards drift). The existing check_vendored_skills.ts test still passes with the divergence recorded.
  • The brief template: a test that every placeholder in ticket-brief.md has a value in the start recipe.
  • First use, live and read only: pack a finished ticket (for example the DGS-481 branch) as a ticket pack, run one real ticket Reviewer worker on it, and check that its findings block parses and the table builds. No ticket is written to by a test.

13. Not in version 1

  • The call inside SDD, the STOP marker and the automatic start (DGS-129 and the Lights-Out engine). Until then the conductor starts the Reviewer by hand with the recipe in section 5.
  • More reviewer types (design, security, cross-model) and a second field for scope or focus. They come when a real ticket needs one.
  • The cross-model Reviewer (Sol, paused since 2026-10-11) and the review tiers (DGS-127).
  • The Releaser (DGS-467) and the nightly audit.
  • A faster tier for the task model (the Haiku spike, DGS-537).
  • Reviewing a design or a plan. The role judges code against a spec and a plan.

14. For Jack to confirm

The pitch settles the design. These five points are consequences the pitch did not state. Each one has a default in this spec. A "no" on any of them changes only that point.

  1. The task pack keeps the implementer's report, as unverified claims. The pitch lists diff, task text and standards. The primitive requires the report. Default: keep it.
  2. The ticket pack keeps one file of one-line carry-over entries (deferred Minors, parked rulings), and no review transcripts. The pitch says "not the task-review history". The primitive needs the list to triage. Default: keep the list only.
  3. The "other seat" waits until Wed 21 Oct 12:00 UTC+7. Your seat order says every worker on dev0 until then. Default: your seat order wins. The ticket Reviewer runs on dev0 until then.
  4. The preview step raises the Reviewer's ceiling by one permission (run the profile's preview recipe, preview target only). Your pitch says the Reviewer prepares the preview, and the DGS-404 ceiling says read only. Default: the narrow permission, until the Releaser exists.
  5. The Builder stops and a conductor starts the ticket Reviewer. A worker cannot start an agent (DGS-404). So the call from SDD is a stop-and-start, not a function call. The Lights-Out engine and DGS-129 can later automate the start. Default: stop-and-start.
