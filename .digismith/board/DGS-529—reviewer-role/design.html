1. Goal and scope

Today the reviews are subagents inside the Builder. They share its context, its seat and its blind spots, and the Builder starts and runs them. On the first Lights-Out night (DGS-483) the 21 task reviews and the 2 whole-branch reviews found real faults, one of them a leak: the Storybook build would have published file paths from the Mac. The Builder paid for all of it in its own context.

This spec makes the Reviewer one role with its own card, its own context pack for each type and its own start. The input is Jack's pitch on DGS-529 (ClickUp comment 1301150000116983). The pitch is a decision, not a proposal. This spec does not reopen it.

Settled by the pitch and not repeated as questions:

  • The Reviewer only judges. The Builder fixes. The Reviewer re-checks. The Reviewer never fixes and never merges.
  • The Builder never starts or runs a review, task reviews included (Jack: "The builder should never review."). Only a conductor or a Maestro starts a review. The Builder reports up and waits.
  • One role, one field reviewer type: task or ticket. The ledger role final-reviewer becomes ticket.
  • Every role is its own agent with a defined context pack. It never gets the Builder's context.
  • Roles use primitives. The primitives stay the source of truth and are not merged into the role.
  • SDD decides when a review is due. In role mode it stops with a marker and reports up. A conductor or a Maestro starts the Reviewer.
  • The ticket Reviewer prepares the preview for "Sign-off: Jack" tickets until a Releaser exists (DGS-467).
  • The report is a findings table on the ticket with a reviewer-type column.
  • The existing primitives keep working by hand. The role path is added beside the old path, never in place of it (section 15).

Out of scope here: the automatic start by the Lights-Out engine (DGS-129), more tiers and the cross-model reviewer (DGS-127), the rename task to step (DGS-554), the Steward wiring (DGS-551), the Releaser (DGS-467), the nightly audit.

2. The role card

The role is one skill: skills/reviewer/SKILL.md, called digismith:reviewer. It is the Reviewer card. A task worker and a ticket worker both load the same file, so the rules cannot drift between the two types. A skill is the right place because the repo already holds its roles' text in skills, and a herdr worker can read a skill from the brief.

The card holds, and only holds:

  • Authority. Read the target. Write one report file (report.md, ending with the findings block), in scratch. Return findings and a verdict. Nothing else. This is the Reviewer ceiling of DGS-404 (section 4 of that design). The one change is the preview step (section 8).
  • The type table (section 3) and the pack each type reads (section 4).
  • The type to model policy (section 5, "The model"). The role sets the model when a review starts. Neither the conductor nor the Builder picks it.
  • Which primitive to follow for which job, by reference, never by copy (section 3).
  • The output addendum: the findings block (section 7). The primitives do not have it.
  • Who "your human partner" is for each type: the Builder's orchestrator (the SDD controller) for task, the Maestro for ticket. The Maestro sends taste questions to Jack.
  • The rule: a Builder never starts or runs a review. In role mode a conductor or a Maestro starts every review (section 5). By hand, outside role mode, the old path stays (section 15).
  • How the role is started (section 5) and which Steward events it maps to (section 9).

The card holds no review criteria. Severity, what to check, the fix loop and the output format stay in the primitives.

The session card fields (DGS-404, section 5)

Both Reviewer types are herdr workers, so each has a session card. The card uses role: reviewer and adds two fields:

  • reviewer_type: task or ticket (only on a Reviewer's card).
  • seat: dev0 or jack. This field is new for every worker. The conductor needs it to find the Builder's seat when it picks the Reviewer's seat with the runbook's rule. Today the seat is only in the pane's environment. The field is read from claude-account status at the start.

Owner header on each primitive

Each primitive file gets one first line after its title. The text is true in both modes:

The files are:

  • skills/subagent-driven-development/task-reviewer-prompt.md
  • skills/subagent-driven-development/re-review-prompt.md
  • skills/requesting-code-review/code-reviewer.md

These files are vendored from Superpowers (vendored/PROVENANCE.md). The header and the additive sections are local changes. They get a "Further diverged by DGS-529" line in PROVENANCE.md, and scripts/check_vendored_skills.ts must still report them as local divergence, not upstream drift. requesting-code-review stays callable by hand.

4. Context packs

A pack is the complete input of one review. It is a folder with a manifest, built by code, not assembled from memory. A new command builds it: dg reviewer pack --type task|ticket --plan <plan.md> .... It takes the diff file that the existing review-package script wrote, and refuses any file that does not start with the package header. The attribution check runs inside review-package, so a hit stops the diff file and with it the pack and the review. (The depot clone that dg runs from holds only packages/, so the command cannot call a skill script itself. The Builder runs the script and passes the file.)

Location: <sdd workspace>/reviews/<type>-<id>-r<round>/. The workspace is the plan's git-ignored .sdd-workspace (the SDD script sdd-workspace prints it). The manifest is pack.md. It lists each file with an absolute path and a one-line role, and it carries the values that fill the primitive's placeholders: base, head, diff file, model, brief file. The model comes from the role's model policy (section 5), so the conductor reads it from the pack and does not choose it.

Two points where the pack lists something the pitch's short list does not, both because a primitive demands it. Jack approved both (section 14).

  • carry-over.md is in the ticket pack (approved default 2, section 14). SKILL.md of SDD tells the final reviewer to triage the deferred Minors and parked findings. Without that list the triage cannot happen. The file has one-line entries only, not review transcripts.

Standards are not matched by the pack command. The matching is a judgment (standards/index.yml holds descriptions). The Builder already picked the standards for its tasks and named them in the brief. The pack only copies those paths.

5. How each type runs

This section describes role mode: the mode a herdr Builder runs in. The conductor turns it on when it starts the Builder (section 15). By hand, outside role mode, nothing here applies and SDD runs as today.

A Builder is a worker. A worker may not start another agent (DGS-404, authority ladder), and Jack's rule is stronger: a Builder never starts or runs a review. So after each review point the Builder runs a pack, reports a marker line and waits. Its parent decides. The Lights-Out night used the same shape at STOP-1 and STOP-2.

Type task: one worker per ticket

  1. Request. The SDD controller finishes a task and its implementer. It runs dg reviewer pack --type task --task N, appends the ledger line Task N: review requested, and reports STOP: task-review-ready <pack path>. It does not dispatch a reviewer. It waits.
  2. Start or reuse. The conductor (or the Maestro) looks for the ticket's task Reviewer. None exists: it starts one with the runbook's "Start of a ticket" steps (S0 to S6), brief skills/reviewer/brief.md, agent <key>-rev-task, label <KEY> ⚚ Review task. One exists and is idle: it sends /clear, then the prompt. The prompt is short: Read <pack>/pack.md and follow the Reviewer card. The conductor reads the pane with --format ansi first and sends only when the input box is empty.
  3. Review. The Reviewer follows the primitive named in pack.md. It writes <pack>/report.md, ending with the findings block, and ends with one pane line: done: <pack> verdict: <Approved|Needs fixes>.
  4. Relay. The conductor prompts the Builder with the report path and the verdict, and does not filter the findings. The SDD controller verifies the ⚠️ items itself (it holds the plan and the cross-task context) and adjudicates, as SDD says.
  5. Fix loop. The primitive's loop stays: up to 5 rounds. The Builder's implementer fixes (rounds 1 to 3 resumed, rounds 4 and 5 fresh on a stronger model). The controller runs dg reviewer pack --type task --task N --round R for the scoped re-review and reports STOP: task-review-ready <pack> again. The same Reviewer worker takes it after /clear, with re-review-prompt.md.
  6. Breaker. After round 5 the SDD controller adjudicates the open findings, as the primitive says: park with a ruling, or BLOCKED to the parent.
  7. Clean. The conductor tells the Builder "task N review clean". The Builder moves to the next task.
  8. Close. After the last task review is clean, the conductor closes the task Reviewer worker.

SDD's rule "do not pause between tasks" gets one exception in role mode: the Builder waits at each STOP: ...-review-ready. This costs wall time at every task. The conductor watches for the marker and answers it, as it does for the other STOP markers. The Lights-Out engine can take this over later (DGS-129).

Type ticket: its own worker

  1. Request. The Builder finishes the last task, runs dg reviewer pack --type ticket, appends Task final: review requested, and reports STOP: ticket-review-ready <pack path>. It waits.
  2. Start. The conductor starts the Reviewer with S0 to S6, with these values:
    • Brief: skills/reviewer/brief.md, a template with the type as a placeholder. It names the pack and the card. It says: judge only, write one report, never edit, never merge.
    • Agent: <key>-rev, for example dgs-529-rev. Label: <KEY> ⚚ Review. The runbook's Names block allows a short word when one ticket has two workers.
    • Working folder: the Builder's worktree, read only. The Builder is stopped, so nothing changes under the Reviewer. During a fix wave the Reviewer is idle.
    • Model: Opus 5.5. Seat: see below.
    • The session card gets role: reviewer, reviewer_type: ticket, under: <the conductor or Maestro that started it>, seat.
    • The Reviewer registers its session for the ticket's token count (entry.ts session --ticket <KEY> --role reviewer, written in the brief), so its tokens count with the ticket.
  3. Review. The Reviewer follows code-reviewer.md against its pack, writes <pack>/report.md, ending with the findings block, and ends with one pane line: done: <path> verdict: <approved|needs-fixes>.
  4. Verify and relay. The conductor verifies each finding (the skill digismith:receiving-code-review), then sends the verified findings to the Builder. A finding the conductor cannot verify goes to the Maestro, not into a fix.
  5. Fix wave. The Builder dispatches ONE fix subagent with the whole list (the SDD rule), runs the re-review pack and reports STOP: ticket-review-ready <pack> again.
  6. Re-review. The same Reviewer worker gets the round 2 pack by herdr agent prompt and follows re-review-prompt.md. If the worker is gone, a new one starts with the round 1 report in its pack.
  7. Residual. Any finding still open after the one re-review is adjudicated by the Maestro, as the primitive says: park with a ruling, or stop on a load-bearing one.
  8. Close. After an approved verdict (and the preview, when it applies) the conductor tells the Builder "ticket review clean" and closes the Reviewer worker. The merge follows the merge order. The Reviewer does not merge.

The model

The role picks the model for each review. The card holds a type to model policy, and the code behind dg reviewer pack applies it and writes the result into pack.md as model. The conductor and the Builder never pick a model. They pass on what pack.md says.

TypePolicy
taskThe primitive's mid-tier floor: Sonnet 5.5 (claude-sonnet-5-5) today. Scaled to the diff: a diff above 800 changed lines gets Opus 5.5 (claude-opus-5-5). The limit is one constant, TASK_ESCALATE_LINES. DGS-537 (the Haiku spike) may change the floor.

The two model ids and the line limit are constants in one place in the code. How the model is set:

  • A worker that starts (the ticket Reviewer, and the task Reviewer at its first pack): the conductor starts it with the model from pack.md (herdr agent start ... -- --model <model>).
  • The task worker that is reused: after /clear and before the review prompt the conductor sends /model <model> when the pack's model differs from the worker's current one. The conductor reads the model from the pack and does not judge the diff.

The seat

The conductor picks the seat with "The rule" of the runbook (usage probe, headroom, workers in use), inside Jack's seat order in force. The order in force (Jack, 2026-10-17) puts every worker on dev0 until Wed 21 Oct 12:00 UTC+7. Until then both Reviewer types run on dev0. The separation then rests on the separate context and the separate model, not on the seat.

After that date the rule applies again. For the ticket Reviewer the conductor excludes the Builder's seat first, because a review on the other seat does not share the Builder's quota or its blind spots. If the other seat has no headroom, the Reviewer runs on the Builder's seat. A limit stop on the Reviewer's seat is reported to Jack. The conductor does not move the Reviewer on its own.

6. Findings, blocking, adjudication

All of it is as the primitives say. The card only names who decides.

  • Severity. Critical, Important, Minor, as in task-reviewer-prompt.md and code-reviewer.md. A hit from check-attribution is an automatic Critical.
  • What blocks. A verified Critical or Important finding, or a confirmed ⚠️ item, or spec ❌. For task it blocks the next task. For ticket it blocks the merge. Minor findings go to the ledger as deferred and never block. The ticket Reviewer triages the deferred ones and says which must be fixed before merge.
  • Loop. task: five fix rounds, then the breaker. ticket: one fix wave, one scoped re-review, then adjudication. There is no second wave.
  • Who adjudicates. The human partner: the Builder's orchestrator (the SDD controller) for task, the Maestro for ticket. Adjudicating is not reviewing: the Builder rules on findings and fixes them, and never judges its own work. A load-bearing finding that survives goes up to the Maestro and stays a blocker. A finding that conflicts with the plan text, and a finding that is taste, goes from the Maestro to Jack.
  • Who may override a block. Only the human partner, with a written ruling. The Reviewer cannot clear its own finding. The conductor relays and verifies and does not rule.
  • No fix, no merge. While a blocking finding is open, the ticket stays in review. The Steward gets no merged event. A night run does not retry it on its own (the failed-ticket status is DGS-490).

7. The findings table

The findings block (the card's addendum)

The primitives return free text. A table cannot be built from free text without guessing. So the card adds one rule to every Reviewer prompt: end the report with one fenced json block named findings.

[
  { "id": "F1", "path": "src/a.ts", "line": 42, "severity": "Important",
    "what": "fileNames leak the Mac home path",
    "scenario": "run the Storybook build; the output lists /Users/..." }
]

An approved review with no findings has []. The block is the only machine-read part. The rest of the report stays as the primitive writes it.

The verdict lines (the human partner writes them)

The Reviewer judges only, so the verdict on a finding is not the Reviewer's. The human partner writes one ledger line per finding at the moment it is decided. The ledger is the Builder's file, so a ruling that comes from the Maestro reaches the Builder in the conductor's message and the Builder appends it as written:

Review ticket final r1: F1 -> fixed (commit a7f3c2d)
Review task 7 r2: F2 -> parked (reviewer wrong: the test asserts the cap)
Review task 3 r1: F1 -> rejected (out of scope per plan line 40)

The three verdicts are fixed, parked (real but deferred, or the code stands), and rejected (not a defect, with the reason). A reason is required for parked and rejected.

The table

A new command, dg reviewer table, joins the report files and the verdict lines into <board folder>/findings.md. One row per finding. Reviews with no findings give one summary row each, so the table shows that the review ran.

Reviewer typeRoundPath:lineSeverityWhat is wrongFailing scenarioVerdict

A finding with no verdict line makes the command fail with the finding's id. An unjudged finding must not ship in a table.

When it runs: in digismith:report-implementation, after the final review and before the Finish step deletes the SDD workspace. By hand, where no review pack exists, the command finds nothing, says so and writes no file (section 15). The report files live in that workspace, so the table must be built first. The conductor attaches findings.md to the ticket with dg clickup upload-attachment (a worker has no ClickUp write). This is the Provenance record (DGS-534). The report skill also links the table from report.html.

8. Preview for "Sign-off: Jack" tickets

For a ticket with the mark Sign-off: Jack, the ticket Reviewer has one last step after an approved verdict: it prepares what Jack needs to say yes or no. The output is <pack>/preview.md: what to look at, how to open it, and what changed in plain words. If the project has a preview recipe, the Reviewer also runs it and writes the URL.

A recipe is named in the profile as a new optional field preview (a skill or a command, for example the skill capture-ephemeral-url for an Emma theme). With no recipe, preview.md holds the local run steps and no URL. This ticket does not invent a deploy path.

Limits that keep the role narrow:

  • The preview step runs only the named recipe, only to a preview target, never to production.
  • It changes nothing in the repo and nothing in ClickUp.
  • It runs only when the ticket's mark is Jack and the verdict is approved.

This raises the Reviewer's ceiling in DGS-404 by this one permission (run the profile's preview recipe). DGS-404 says "raising any ceiling needs Jack". Jack's approval of this spec is that approval, and DGS-404's ladder gets the row change (section 10). When the Releaser exists (DGS-467), the step moves there.

11. Errors

  • Attribution found in the commit range. No pack is written. The review does not run. The Builder removes the attribution first.
  • Pack file missing (no plan, no spec, no ticket file). dg reviewer pack exits non-zero and names the file. A review without its input does not start.
  • Report without a findings block, or with invalid JSON. The human partner treats the review as not done and re-dispatches once. A second failure goes to the Maestro.
  • The Reviewer worker stalls. The conductor applies the time box proposed in DGS-528: after about 30 minutes without output it reports and does not retry on its own. A whole-branch review took about 9 minutes on the cross-model proof of concept (DGS-78), so 30 minutes is a real stall.
  • The Reviewer wants to change something. It reports the need as a finding. It does not edit.
  • The Reviewer cannot verify a claim. It marks it as ⚠️, as the primitive says. The human partner checks it.
  • The Reviewer's seat hits a limit. Report to Jack and wait (the seat rule in force).
  • The Builder's STOP is not answered. The Builder waits. The conductor treats a STOP: ...-review-ready marker like the other STOP markers and answers it. A Builder never falls back to reviewing itself in role mode.
  • The task Reviewer worker is gone or stuck after a /clear. The conductor starts a new one. The pack holds the full input of a review, so nothing is lost.
  • Role mode is on but dg reviewer pack fails. The Builder reports the error up and waits. It does not review without a pack.

12. Testing

  • dg reviewer pack, Vitest with a temporary git repo: a task pack holds exactly the listed files; a ticket pack holds no ledger text beyond carry-over.md; attribution in a commit stops the pack; a missing file gives a named error; pack.md has every placeholder value of the primitive.
  • dg reviewer table: findings plus verdict lines give the exact rows; a clean review gives a summary row; a finding without a verdict fails; a bad JSON block fails with the report path.
  • The card: a test checks that the type table in SKILL.md matches REVIEWER_TYPES, and that each of the three primitive files has the owner header (this guards drift). The existing check_vendored_skills.ts test still passes with the divergence recorded.
  • The brief template: a test that every placeholder in skills/reviewer/brief.md has a value in the start recipe, for both types.
  • The model policy: task gives Sonnet 5.5 at 800 changed lines or fewer and Opus 5.5 above; ticket gives Opus 5.5; pack.md carries the model; the two ids and the limit are single constants.
  • Both paths (section 15): tests for the mode switch, for the old text that must stay, and for the by-hand behaviour of dg reviewer table.
  • First use, live and read only: pack a finished ticket (for example the DGS-481 branch) as a ticket pack, run one real ticket Reviewer worker on it, and check that its findings block parses and the table builds. No ticket is written to by a test.

15. Compatibility

Requirement: SDD and requesting-code-review run exactly as today when used by hand, outside a herdr Builder. The role path is added beside the old path. It never replaces it. check_vendored_skills passes with the divergence recorded. Tests prove both paths.

The switch

The mode is role mode when the environment variable DIGISMITH_REVIEW_MODE is exactly role. The conductor sets it in the Builder's pane when it starts the Builder (the S3 step, next to claude-account). Any other value, and an unset variable, is hand mode. A script skills/subagent-driven-development/scripts/review-mode prints role or hand. SDD runs it at setup and records the result in the ledger as Review mode: role or Review mode: hand. The script is the one place that reads the variable. A resumed session reads the ledger line first.

Rules for the edits

  • Edits to the three primitives and to SDD are additive: new lines and new sections. No existing line is deleted or rewritten. The role-mode text is a separate section that starts with "In role mode".
  • The old dispatch instructions stay in place. The role-mode section says that when the mode is role it replaces those steps, and it names each one.
  • The owner header is true in both modes (section 2).
  • PROVENANCE.md gets one "Further diverged by DGS-529" line that names the files. check_vendored_skills.ts must report them as local divergence and must not report upstream drift.

Tests for both paths

  • The switch. review-mode prints hand when the variable is unset, empty, Role, 1 or role , and role only for exactly role.
  • The old path stays. A text test lists anchor phrases of the old dispatch text (for example "Dispatch final code reviewer", "Generate review package, dispatch task reviewer", "Never dispatch a task reviewer without a diff file") and asserts that each is still in SKILL.md. The same test checks that the primitive prompts keep their original placeholders and that the findings section is the only addition besides the owner header.
  • The new path exists. A text test asserts that SDD has the role-mode section, the two marker names (STOP: task-review-ready, STOP: ticket-review-ready) and the ledger lines.
  • By hand, the table. dg reviewer table on a workspace with no reviews/ folder exits 0, writes no file and says "no reviews found".
  • The vendored check. The existing check_vendored_skills.ts test still passes, and a run on the branch reports the changes as local divergence only.
