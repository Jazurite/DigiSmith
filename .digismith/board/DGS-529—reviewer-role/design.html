1. Goal and version 1 scope

Today the per-task reviews and the final whole-branch review run as subagents of the Builder, through subagent-driven-development (SDD). They work. On the first Lights-Out night (DGS-483) the 21 task reviews and 2 whole-branch reviews found real faults, one of them a leak: the Storybook build would have published file paths from the Mac.

Jack's decision at checkpoint 1: "To make sure that the current primitive workflow doesn't interrupt, I want to keep the current primitives workflow for the reviewer. Just now, we would put it into a role and it's connected to ClickUp."

So version 1 names today's reviews as one role, the Reviewer, and connects them to ClickUp. It changes no review flow. The input is Jack's pitch on DGS-529 (ClickUp comment 1301150000116983), cut to this scope.

Version 1 is four things:

  1. The card. skills/reviewer/SKILL.md documents today's reviews: the types task and ticket, the primitive each already uses, the human partner for each.
  2. The findings block and the table. Each review report ends with a findings block (additive only). dg reviewer table builds findings.md in report-implementation. The conductor attaches it to the ticket.
  3. The Steward moments. The spec names the two moments that map to review-started and merged. The wiring stays DGS-551.
  4. The role rows. The Reviewer rows of DGS-488 and DGS-404 say: judges only, never fixes, never merges.

Settled by the pitch and not repeated as questions: the Reviewer only judges; the Builder fixes; the Reviewer re-checks; one role with one field reviewer type (task or ticket); the ledger role final-reviewer becomes ticket; roles use primitives and the primitives stay the source of truth; the report is a findings table with a reviewer-type column.

Moved to DGS-556 by Jack's decision (section 12): the ticket Reviewer as its own herdr worker, dg reviewer pack, the other seat, the preview step. Out of scope here too: the call from SDD (DGS-129), more tiers (DGS-127), the rename task to step (DGS-554), the Steward wiring (DGS-551), the Releaser (DGS-467).

2. The role card

The role is one skill file: skills/reviewer/SKILL.md, digismith:reviewer. In version 1 it is documentation of the reviews that already run. SDD does not call it. It sits in the repo so that a reader, a conductor or a later ticket finds one place that says what the Reviewer is.

The card holds, and only holds:

  • Authority. Read the target. Write findings and a verdict. Never fix, never merge, never change anything. This is the Reviewer ceiling of DGS-404, unchanged.
  • The type table (section 3): which primitive, which model rule, which human partner, what it blocks.
  • The findings block every report ends with (section 4), and the verdict lines (section 5).
  • The Steward moments (section 7).
  • What is later: a pointer to DGS-556.

The card holds no review criteria. Severity, what to check, the fix loop and the report format stay in the primitives. The card does not copy them.

The primitives get no owner header line. A header such as "not dispatched directly by a Builder" would be false in version 1, because the Builder's SDD does dispatch them. The primitives change only by the additive findings block (section 4).

4. The findings block

The primitives return free text. A table cannot be built from free text without guessing. So each of the three primitive prompts gets one additive section: end the report with one fenced json block, and also write the same array to a findings file.

[
  { "id": "F1", "path": "src/a.ts", "line": 42, "severity": "Important",
    "what": "fileNames leak the Mac home path",
    "scenario": "run the Storybook build; the output lists /Users/..." }
]
  • An approved review with no findings writes [].
  • The id is F<n>, numbered within one review. A re-review lists only new findings from the fix diff and continues the numbering after the ids of the findings it received.
  • severity is Critical, Important or Minor, as the primitive defines it. A ⚠️ item that the controller confirms is written as Important.
  • The findings file is [FINDINGS_FILE], a new placeholder. The dispatch fills it with <sdd workspace>/reviews/<kind>-<id>-r<round>.findings.json. The workspace is the plan's git-ignored .sdd-workspace. This is the one file the Reviewer writes, in scratch, as DGS-404 allows ("write one report file in its own scratch folder"). The rest of the review stays read only on the checkout.
  • The report text stays exactly as the primitive writes it. The block is the only machine-read part.

Why both the block and the file: the block makes the report self-contained for a reader. The file lets dg reviewer table read the findings without the controller copying text. The controller's context does not grow.

5. Verdict lines and the findings table

The verdict lines

The Reviewer judges only, so the verdict on a finding is not the Reviewer's. The human partner writes one ledger line per finding when it is decided. These are additive lines in SDD's existing adjudication steps, not a new step:

Review ticket final r1: F1 -> fixed (commit a7f3c2d)
Review task 7 r2: F2 -> parked (reviewer wrong: the test asserts the cap)
Review task 3 r1: F1 -> rejected (out of scope per plan line 40)

The verdicts are fixed, parked (real but deferred, or the code stands) and rejected (not a defect). A reason is required for parked and rejected. A Minor finding that SDD records as deferred gets the line -> parked (deferred minor).

The table

A new command, dg reviewer table --workspace <dir> --out <board folder>/findings.md, joins the findings files and the verdict lines. One row per finding. A review with no findings gives one summary row, so the table shows that the review ran.

Reviewer typeRoundPath:lineSeverityWhat is wrongFailing scenarioVerdict
ticket1src/a.ts:42ImportantfileNames leak the Mac home pathrun the Storybook build; the output lists /Users/...fixed (a7f3c2d)

task 91--approved, no findings--

A finding with no verdict line makes the command fail with the finding's id. An unjudged finding must not ship in a table.

When it runs: in digismith:report-implementation, after the final review and before the Finish step deletes the SDD workspace. The findings files live in that workspace, so the table is built first. report.html links the table. The conductor attaches findings.md to the ticket with dg clickup upload-attachment (a worker has no ClickUp write). This is the Provenance record (DGS-534), and it is the connection of the Reviewer to ClickUp.

6. Findings, blocking, adjudication

All of it stays as the primitives and SDD say today. The card only names who decides.

  • Severity. Critical, Important, Minor. A hit from check-attribution is an automatic Critical.
  • What blocks. Spec ❌, a Critical or Important finding, or a ⚠️ item the controller confirmed. For task it blocks the next task. For ticket it blocks the merge. Minor findings are deferred in the ledger and never block. The final review triages the deferred ones.
  • Loop. task: five fix rounds, then the breaker. ticket: one fix wave, one scoped re-review, then adjudication. No second wave.
  • Who adjudicates. The human partner (section 3). A finding that conflicts with the plan text, and a finding that is taste, goes up to the Maestro and from there to Jack.
  • Who may override a block. Only the human partner, with a written ruling in the ledger. The Reviewer cannot clear its own finding. The Builder cannot clear a finding either.
  • No fix, no merge. While a blocking finding is open, the ticket stays in review and the Steward gets no merged event.

9. Errors

  • The report has no findings block, or the block is invalid JSON. The SDD controller treats the review as not done and re-dispatches once. A second failure goes to the Maestro.
  • The findings file is missing when the table runs. dg reviewer table exits non-zero and names the review.
  • A finding has no verdict line. The command exits non-zero and names the finding id.
  • The workspace is already gone. The table cannot be built. report-implementation says so in the report and the ticket gets no findings.md. It never invents rows.
  • The Reviewer wants to change something. It reports the need as a finding. It does not edit.
  • The Reviewer cannot verify a claim. It marks a ⚠️ item, as the primitive says. The human partner checks it.

10. Testing

  • dg reviewer table, Vitest with a temporary workspace: findings files plus verdict lines give the exact rows; a clean review gives a summary row; a finding without a verdict fails with its id; a bad JSON file fails with its path; a missing findings file fails with the review name; row order is stable (type, then round, then id).
  • The primitives: a test checks that each of the three files has the findings section and the [FINDINGS_FILE] placeholder, and that the example block in the text parses with the same parser the table uses.
  • The card: a test checks that the type table in SKILL.md matches REVIEWER_TYPES, and that the card names each primitive file that exists on disk.
  • The existing check_vendored_skills.ts test still passes, with the divergence recorded in PROVENANCE.md.
  • First use, live and read only: run dg reviewer table on the workspace of the next real SDD ticket before its Finish step, and check the table has a row for every review in the ledger. No ticket is written to by a test.

  • The call from SDD into the role, and the rename of the ledger role to ticket (DGS-129).

12. Later: DGS-556

DGS-556 (backlog) keeps the parts of the first spec that change how reviews run. The full first text is in the commit 69feccb of the branch DGS-529__reviewer-role. In short:

  • The ticket Reviewer as its own herdr worker. A worker cannot start an agent (DGS-404), so the Builder stops with STOP: ticket-review-ready <pack> and a conductor starts the Reviewer with the runbook's "Start of a ticket" steps. Model Opus 5.5. After an approved verdict the conductor closes it.
  • dg reviewer pack. Each review's input is a folder with a manifest, built by code, for task and ticket, round 1 and re-review. The ticket pack holds the ticket, the approved spec, the plan, the full diff against main and the standards. Never the Builder's conversation. Two defaults wait for Jack: the implementer's report stays in the task pack as unverified claims, and the ticket pack gets one carry-over file of one-line entries (deferred Minors and parked rulings).
  • The other seat. The ticket Reviewer runs on the seat the Builder does not use. Until Wed 21 Oct 12:00 UTC+7 the seat order puts every worker on dev0. The card gets reviewer_type and seat.
  • The preview step. For "Sign-off: Jack" tickets, after an approved verdict, the ticket Reviewer writes preview.md and runs the profile's preview recipe, preview target only. It raises the DGS-404 ceiling by one permission, which needs Jack's approval. It moves to the Releaser (DGS-467) later.

Version 1 leaves room for all of it: the findings block, the verdict lines and the table do not depend on how a review runs.
