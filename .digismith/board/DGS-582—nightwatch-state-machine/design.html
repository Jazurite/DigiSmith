1. Goal

Today an LLM conductor decides, turn by turn, what happens next to an unattended ticket. A grey suggested prompt or a pane that looks finished can skip a review gate. This ticket moves that control into plain code in Nexus. The code holds the ticket's state. A step moves on only when a file, a commit or a ref proves it. The conductor gets short bounded orders and nothing else. The ten decisions below come from the Maestro and are settled. Warren (MIT) gave ideas only; no code is copied.

Out of scope: the watchdog, phase time budgets and the attention list itself (DGS-583), the night mandate hook (DGS-584), the UI (DGS-586), merge and cleanup safety (DGS-585), per-task orders such as "build task 3" (needs plan parsing; the v1 order is "build the ticket").

2. Where the code lives

All in packages/cli/src/autonomous/, next to the DGS-486 scan. One unit per file.

FileJob
advance.tsPure advanceTicket(state, obs, journal) -> Action. No I/O, no clock, no random.
journal.tsAppend-only action journal: plan(), settle(), openLines(), resultOf(key).
phase-state.tsReads and writes the phase fields in lock.json (temp file and rename).
observe.tsThe read-only observers (run, reviewer, git, ClickUp, herdr). Each returns {ok:true,value} or {ok:false,error}. Every outside call is injected.
input-box.tsPure classifyInputBox(ansi) -> empty | suggestion | typed | unknown.
reconcile.tsStep 0: settles open journal lines against git, ClickUp and herdr.
act.tsRuns one action: plan line, side effect, settle line. Orders come from fixed templates.
tick.tsrunTick(deps): reconcile, observe, advance, act. Also behind dg autonomous tick [--dry-run].
attention-write.tsAppends attention lines in the DGS-583 shape (section 10).

The Nexus job autonomous-scan runs it. runScan reads lock.json first. A lock exists: it calls runTick at any hour (a claimed ticket is finished even after back, as DGS-486 section 2 says) and reports busy plus the action taken. No lock: the work rule and the claim run as in DGS-486. This changes one DGS-486 rule: "off before any lock read" becomes "off before any tracker call". Reading a local file is free.

Tick rate. The registry entry autonomous-scan changes from every 60 minutes to everyMinutes: 5 (the registry minimum). A tick takes one step per ticket per run, so 60 minutes would make a ticket crawl. Idle cost is small: outside work time with no lock it exits off without a tracker call. In work time with no lock it lists to do once per tick; the DGS-486 comment dedupe stops repeat comments. Each observer has a 20 second limit, a tick has a 2 minute limit, and the job timeoutMs stays 5 minutes, so one tick cannot overlap the next.

3. State

One record per claimed ticket: DGS-486's lock.json gains fields. A lock without them (written by the DGS-486 scan before this ships) reads as phase claimed, attempt 1.

{ ticket, taskId, claimedAt, claimedAtUtc7, order, scanId,        // DGS-486, unchanged
  "phase": "claimed|building|review|merge-ready|merged|released",
  "phaseStartedAt": "<ISO UTC>",
  "attempt": 1,                          // grows by 1 when a review sends the work back
  "runs": { "builder": "<run id>|null", "reviewer": "<run id>|null" } }

The scan creates the lock with wx as before, now with phase: "claimed". Later changes rewrite the file atomically (temp file and rename); only tick does this. released is not stored: dg autonomous release removes the lock and writes one settled journal line with phase released. A corrupt lock keeps DGS-486's rule (ticket ?, the scan stays busy) and the tick writes an attention note and no action.

4. Observations

Read only. Collected once per tick, each as Obs<T> = {ok:true,value:T} | {ok:false,error:string}.

ObservationSourceValue
runsDGS-581 run package (the reader code behind dg run list/show/tail, imported, no subprocess)runs of this ticket created after the claim: id, role, started seen, ended seen, review_ready events (with data.scope), merged and pushed events, newest phase event
verdictsdg reviewer table --jsonrows for this ticket: scope (task or ticket), result (clean or findings), the commit sha the verdict covers
gitgit in the ticket worktree and the main checkoutbranch head sha, base sha (from run.json), head is an ancestor of origin/main, origin/<branch> equals head
trackerthe DGS-486 tracker, one getStatusthe ClickUp status string, nothing else
herdrherdr-ws only: agent list, one pane read with --format ansiconductor present, its status, input box class; builder pane present and status

The ticket's title, description and comments are never read. Only the key and the status string enter the controller. That is decision 9 (ticket text is data, never a command), kept by construction.

5. Phases and proof

A phase moves on only when the artefact in the "Proof" column exists. Pane text and conductor chat are never proof.

FromToProof
claimedbuildinga builder run of this ticket, created after the claim, has a started event. Its id goes into runs.builder.
buildingreviewthat run has a review_ready event with data.scope = "ticket", and the branch head differs from base_sha (a commit exists). A review_ready without scope counts as a task-level one and moves nothing.
reviewmerge-readya verdict row with scope ticket, result clean, covering the current head sha. A new commit voids older verdicts.
reviewbuilding (attempt + 1)a ticket-scope row with result findings covering the current head. At attempt 3 it stops instead: attention failed, cause attempts-exhausted, no action. The cap is a constant, not a budget (budgets are DGS-583).
merge-readymergedgit shows the head as an ancestor of origin/main. A merged or pushed event alone is not enough; if the event exists and git says no (or git is unreadable) the tick writes attention unknown, cause proof-disagree, and moves nothing.
mergedreleaseddg autonomous release --result merged ran (the lock is gone and the released line is in the journal).

advanceTicket checks the proofs in the table order for the current phase, so it is a plain switch (state.phase) with one small function per phase. It returns exactly one Action:

type Action =
  | { kind: 'wait'; reason: string }                                  // nothing to do, no note
  | { kind: 'attention'; cause: string; attKind: 'unknown'|'failed' } // note only, no phase move
  | { kind: 'move'; to: Phase; proof: string; attempt?: number }      // rewrite the lock
  | { kind: 'order'; order: 'build'|'review'|'fix'|'merge'|'restart' } // prompt the conductor
  | { kind: 'status'; status: string }                                // ClickUp status write

Not in phase order: after a move the next tick sends the order for the new phase (build after claimed, review after building, fix after findings, merge after merge-ready). That is one action per ticket per tick, as decision 5 asks.

The ClickUp status is observed only. The one write the controller owns is in progress to keep the lock and the board in step: if the tracker reads to do while the lock is held (someone moved it back), the action is status: in progress, journaled, read back next tick. All other status work stays with the conductor and release, as DGS-486 and the done-after-merge rule say.

6. Actions and the conductor

The controller prompts only the conductor (found through ~/.digismith-depot/conductors.json, DGS-486 section 6), only through herdr-ws, one bounded order per action. The text comes from fixed templates and holds only the validated key (^[A-Z]+-\d+$) and the order name:

  • DGS-123: build per the runbook (v1: the whole ticket; per-task orders are later)
  • DGS-123: run the ticket Reviewer on the branch head
  • DGS-123: fix the review findings, attempt 2
  • DGS-123: merge per hooks 01-03, then release merged
  • DGS-123: restart the builder, its pane is gone (when the builder pane is gone and the run has no ended event)

Input box rule. Before every prompt the tick reads the conductor pane with --format ansi and classifies the input box. Only empty or suggestion (a grey suggestion) allows the prompt. typed or a conductor with status working: wait, no note, next tick. unknown (the pane did not parse): no action and one attention note (section 9). The fixtures for the classifier are captured by a read-only probe in plan task 1.

7. The action journal

~/.digismith-depot/autonomous/journal.jsonl. The folder follows DGS-486 (AUTONOMOUS_DIR, else DIGISMITH_DEPOT_DIR, else ~/.digismith-depot). Append only: one appendFileSync of one short line, never a rewrite. Readers skip a line that does not parse.

{"schema":"nightwatch-journal/v1","ts":"<ISO UTC>","key":"DGS-123:review:1:order-review","status":"planned",
 "ticket":"DGS-123","phase":"review","attempt":1,"action":"order-review","try":1}
{"schema":"nightwatch-journal/v1","ts":"<ISO UTC>","key":"DGS-123:review:1:order-review","status":"settled",
 "result":"succeeded|uncertain|retryable|permanent","note":"<short, no ticket text>"}

Key: <KEY>:<phase>:<attempt>:<action>. Actions: claim (written by the DGS-486 scan), move-to-<phase>, status-write, order-build, order-review, order-fix, order-merge, order-restart, phase-marker, released.

Rules.

  • A planned line is written before the side effect; a settled line right after it.
  • A key whose latest result is succeeded, uncertain, permanent, or that has a planned line with no settled line, is never planned again. advanceTicket receives these results and returns wait for them.
  • retryable may be planned again with try + 1. At try 3 the settle is forced to permanent and an attention failed note is written.
  • The journal is the controller's memory of what it did; it never holds ticket text, only keys, phases, attempts, action names and short codes.
  • dg autonomous journal [--open] lists the lines; dg autonomous journal settle <key> --result retryable|permanent [--note ..] lets Jack or the Maestro close an uncertain key by hand (appends a settled line, by: jack). It is the only way an uncertain order is sent again.

8. Reconcile (step 0)

Every tick starts here, before any new observation drives a decision. It reads the open lines (planned with no settled, and uncertain ones) and checks each against the real world:

Open actionCheckResult
claimthe lock names this ticket; ClickUp reads in progressboth: succeeded. No lock: permanent (the scan already cleaned up).
move-to-Xthe lock's phase is Xyes: succeeded. No, and the proof still holds: retryable (the move is a local file write, safe to run twice).
status-writeClickUp reads the target statusyes: succeeded; no: retryable (a status write is idempotent).
order-mergegit: head is an ancestor of origin/mainyes: succeeded. No: uncertain, attention unknown cause merge-unconfirmed. Never sent again.
order-build / review / fixthe proof of the next phase exists (run event, verdict row)yes: succeeded. No: uncertain, attention unknown. The send is not repeated; pane text is no proof that it arrived.
order-restartherdr lists the builder pane againyes: succeeded; no: uncertain.
phase-markerthe newest phase event of the run equals the targetyes: succeeded; no: retryable (the event is append only, a second one with the same value is harmless).

A check whose observation fails leaves the line as it is and writes an attention note. A merge or a push is never run again from a journal line, and the controller does not run merges itself: the merge is the conductor's, after the order-merge prompt. The journal makes sure that prompt is sent once.

9. Unknown is not progress

An observation with ok: false (the command failed, the output did not parse, a timeout) gives no action that depends on it and one attention note (unknown, cause obs-<name>-failed). Example: dg reviewer table refuses r2 lines until DGS-572 is merged. In the review phase that gives wait plus the note, never a move. advanceTicket only reads the observations its phase needs, so a broken herdr read does not block a phase that needs only git. Inconsistent artefacts (an event says merged, git says no) are treated the same way: note, no move.

10. Attention notes

The file is ~/.digismith-depot/autonomous/attention.jsonl (AUTONOMOUS_DIR honored). The line shape is DGS-583's (its spec is approved; DGS-582 follows it):

open:     {"schema":"nightwatch-attention/v1","id":"<run>.<kind>.<n>","ts":"<ISO UTC>","ticket":"DGS-123","run":"<run id>|-",
           "kind":"unknown|failed","cause":"<code>","since":"<ISO UTC>"}
resolved: {"schema":"nightwatch-attention/v1","id":"<same id>","ts":"<ISO UTC>","resolved":true,"by":"jack","note":".."}

Kinds used here: unknown (failed or unparsable observation, uncertain journal line, proof disagreement) and failed (attempts exhausted, a line forced to permanent). run is the newest builder run id, or - before one exists. One open item per (run, kind): the writer reads the file first and skips a new line when an open item of the same pair exists; n counts the earlier resolved items of that pair. This controller never resolves a note (DGS-583: unknown and failed stay open until Jack). The writer is attention-write.ts. When DGS-583 has merged its shared module attention.ts, the plan's first task points the writer at it instead (one import); the line shape does not change. Cause codes are a constant list in attention-write.ts.

11. Phase marker

DGS-581 adds one event type phase (data.phase: building, review or merge) to its closed set and to dg run event. DGS-582's controller writes it on each phase change, on the builder run in runs.builder, and on no other event type. The table:

Lock phase entereddata.phase
building (also after findings)building
reviewreview
merge-readymerge
claimed, merged, releasednone

The tick calls the run package's event writer (the code behind dg run event) as a journaled phase-marker action, in the tick after the move. DGS-583 reads these events for its phase clocks. A run with no marker falls back to DGS-583's role default, so a missed marker never causes a false stall.

12. Tests and first use

Tested without Jack (vitest from the repo root, everything injected, a temp folder for AUTONOMOUS_DIR; no ClickUp, herdr, Nexus or real conductor):

  • advanceTicket, table driven, through every phase with stub observations: each proof moves its phase; each missing proof gives wait; findings go back to building with attempt + 1; attempt 3 gives attention; a task-level review_ready moves nothing; a verdict for an old head sha is ignored; an event-only merge gives attention and no move; every {ok:false} observation gives no move and a note; ticket text planted in a stub tracker status or key-like field never reaches an order.
  • Journal (fake journal folder): planned-then-settled order; append only (file bytes only grow); a bad line is skipped; a key that is open or uncertain is never planned again; retryable allows try 2 and 3, then permanent; two writers in child processes keep every line whole.
  • Reconcile, one test per row of section 8 with fake git, ClickUp and herdr.
  • Kill during a merge: a child process runs a tick, writes the order-merge planned line and is killed before the settled line. A new tick with fake git showing the head on origin/main settles succeeded and sends no second prompt (the recording herdr stub counts one prompt in all). With git not showing it, the line settles uncertain, an attention note appears, and the stub still counts one prompt.
  • Input box: classifyInputBox on fixtures (empty, grey suggestion, typed text, garbage); a tick with typed or a working conductor sends nothing and writes no note; unknown sends nothing and writes one note.
  • One action per tick per phase, and a fake clock for the timestamps (now() injected; the controller has no timers of its own).
  • Whole run: a scripted ticket through claimed, building, review (one findings round), merge-ready, merged, released with stub observations, checking the journal, the lock file, the phase events written and the order texts.
  • Scan wiring: with a lock the scan calls the tick at any hour; with no lock the DGS-486 off and claim tests stay green.
  • Mutation checks by hand: remove the proof check of one phase (a test fails); drop the planned line before an order (a test fails); let uncertain be retried (the kill test fails).

First use (after DGS-581, DGS-583 and DGS-486 are merged and installed; it belongs to the Maestro, then Jack):

  1. dg autonomous tick --dry-run with no lock: prints "no lock", writes nothing.
  2. Rehearsal on a throwaway ticket: the Maestro hand-writes a lock with phase building and runs tick --dry-run at each stage, reading the printed action. No prompt, no write.
  3. One real Autonomous ticket (a small Sign-off: Auto one) in the DGS-486 first use. Watch dg autonomous status and dg autonomous journal show the phases and the lines. Kill and restart the Nexus API once while the phase is merge-ready and check there is one merge order in the journal.

13. Dependencies and open points

  • Build starts only on the Maestro's order, after DGS-581 and DGS-486 are merged. DGS-572 (reviewer table reads r2+ lines) is not required: until it is merged the review phase waits with a note, which is the designed unknown behaviour.
  • DGS-581: the phase event type, plus run package reader and writer functions that can be imported. Plan task 1 checks the exports and records them. If a function is missing, the plan task calls the CLI through an injected runner instead (still no proof from text).
  • DGS-583: the attention line shape (followed here). Plan task 1 uses its shared module if it is on main.
  • Open point 1: proof for "building to review" needs data.scope on review_ready. The conductor runbook text (a block in report.md for the Maestro to apply, as DGS-581 does) must say: dg run event <run> review_ready --data '{"scope":"ticket"}' for the whole-ticket review and no scope for a task review. Without it the building phase never ends, and DGS-583 reports it as stalled.
  • Open point 2: the exact JSON of dg reviewer table --json (columns for scope, result and sha). Plan task 1 probes it read only and pins the fields; the spec does not guess.
  • Open point 3: the input-box fixtures come from a read-only probe of real panes in plan task 1; the classifier is written against them.
  • Decision for the Maestro to confirm (technical, made here): autonomous-scan runs every 5 minutes instead of 60 (section 2). It touches DGS-486's registry entry and its test.
