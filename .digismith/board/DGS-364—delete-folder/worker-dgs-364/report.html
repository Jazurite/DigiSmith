DGS-364 dg clickup delete-folder on the public API — Implementation Report

Ticket: DGS-364Date: 2026-10-11

Summary

Added dg clickup delete-folder on the public ClickUp API: DELETE /folder/{id}. It deletes only a folder with no lists (archived included). Built and committed on branch dgs-364; not merged. No real delete and no ClickUp write was made.

Built

  • ClickUpClient.deleteFolder(id) and getFolderLists(id): two reads (archived=false and archived=true) merged by list id. A body without a lists array throws, so the gate fails closed.
  • delete-folder --folder <id> [--yes]: reads the lists first. The dry run prints "would delete" or "would refuse" with each list id and name, exit 0, no DELETE. With --yes, any list means a refusal and exit 1; none means the DELETE.
  • No allow rule: every real delete prompts.
  • Tests: client 65, CLI 514 pass with FORCE_COLOR=1; the build is clean. Lists found only by the active read, or only by the archived read, both refuse.
  • Dry run on the old O folder 1301150000001877 (read only): refused, 5 lists.

ClickUp docs: non-empty folder

The Delete Folder page says only "Delete a Folder from your Workspace." It does not say if a non-empty folder is refused or deleted with its contents.

Accepted risks

  • Race: a list added between the read and the DELETE is not guarded.
  • Nested folders: the gate reads direct lists only; a folder holding only child folders would pass. Not verified against ClickUp. Check before deleting such a folder.

First use

First use pending (DGS-363): Jack runs the first real delete. The branch carries no allow rule for delete-folder; main has ask rules for every delete command.

Review
