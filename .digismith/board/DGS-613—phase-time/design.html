1. Goal

Jack, 2026-10-24 ~17:5x UTC+7, from two Oculus screenshots: "we should see the running build time here and here".

  • Runs table: a running run shows its current phase and the time in that phase, for example building 0:14, in a new Phase column next to Duration.
  • Run page: each cell of the phase strip (Claimed, Worktree ready, Building, Review, Merged, Pushed) shows how long that phase took. The current phase shows a counter that keeps counting.

All clock times are UTC+7. Durations are h:mm, the same as the budget bar ("building 0:15 of 45 min").

Not in scope: forecasts (DGS-614); the Workers table on the index page; a new event type; any change to the budget bar's look.

Depends on DGS-599 (Oculus rename). This spec uses the names after that merge. The build starts after DGS-599 merges, on a rebase on main.

2. Where the times come from

No new event type. The phase markers already in the run events give every time this ticket needs:

  • The run view's phase strip already has one start time per step (pipelineOf in packages/cli/src/oculus/derive.ts): claim journal, run.created_at, started or phase: building, review_ready or phase: review, merged, pushed.
  • The watchdog's phaseOf() (packages/cli/src/autonomous/watchdog.ts) already returns the current phase and the time it started (since). The Runs table uses the same clock that the watchdog checks against the budget.

Two new fields (CLI view and shared zod schema)

FieldValue
RunRow.phaseSince (ISO or null)phaseOf().since when the row has a phase; null when phase is null (ended run, or no phase).
PipelineStep.durationSec (count or null)For a step that is done: the time from its at to the at of the next step that has a time. For the last step that was reached on an ended run: to the run's endedAt. Null for a current, waiting or lost step, for a step with no at, for Pushed (it is the end mark), and when the gap is below zero (times out of order).

The web counts the current step and the Runs table phase time itself, from at or phaseSince and the page clock (useNow, every 30 s). A done step never counts on the page; its number comes from the CLI.

One fix in the budget bar's number

Today the budget's elapsedMin counts from the newest phase event, else from the run start. The watchdog counts from phaseOf().since, which also restarts the building clock on the first tool after review_ready (a fix wave). The two can differ during a fix wave. After this ticket, elapsedMin comes from row.phaseSince, so the Runs table, the budget bar and the watchdog show one number. The budget bar's look does not change.

Each cell keeps its label and start time (UTC+7) and gets a second line: the time spent in that step. The current step shows its counter in the info color with the word "now". The budget card below does not change.

The Review step reads its start from the first review_ready or phase: review. Its duration ends at Merged. The watchdog's merge phase has no own cell; it is inside Review's time. This is today's strip; this ticket does not add a cell.

7. Tests without Jack

Fakes only: no real ClickUp, no herdr prompt, no live API, no real depot (DIGISMITH_DEPOT_DIR in a temp folder), a fixed clock.

  • CLI unit (derive.test.ts): phaseSince for a builder, a reviewer, a fix wave, an ended run; durationSec for done steps, the last step of an ended run, Pushed, a manual run with no claim, times out of order, a lost run.
  • CLI view (views.test.ts, temp depot with fixture events): the run view's strip and budget, and the runs view's rows, carry the new fields; the budget number equals the row's phase time during a fix wave.
  • Schema: the API test's fixtures pass the strict schema with the new fields; an answer without them fails (no silent drift between CLI and web).
  • Web unit: phaseTime and stepTime for every row of section 5; OcRunsTable and OcPipelineBar render with a fixed nowMs.
  • Storybook and visual baselines, desktop and phone, light and dark: Runs table with running, no-phase, lost and ended rows; strip running, ended, manual, lost.
  • e2e (stub server): the Runs page shows building 0:14 for the fixture run; the run page shows now 0:14 on Building and durations on done steps.
  • axe on both pages; the strip's hidden text is checked.
  • packages/cli/src/ code runs under node --experimental-strip-types (the existing smoke test).

8. First use

After the merge, the conductor runs the usual Oculus publish: CLI build in the main checkout, a restart of the existing Nexus API LaunchAgent, build-www.sh. No Caddy, DNS or LaunchAgent change.

Then, while a Builder runs: open oculus.pazurite.com/runs/. The Builder's row shows building h:mm, and that number equals the budget bar on its run page. The run page's strip shows durations on done steps and now h:mm on the current one. An ended run's strip shows all its durations. The first use is verified when both screens show this on a real run.
