Problem

Spike DGS-563 (DGS-529 build, 2026-10-17) found that tokens.json tasks holds 5% (DGS-560), 6% (DGS-562) and 34% (DGS-559) of the implementation step's output. DGS-561 was built without SDD and has no step lines. The spike's advice: keep per-task counts in the ledger, not in ClickUp subtasks. So the ledger must tag every plan task, and a non-SDD build must still write step lines.

Causes found

Counts only, from the three tokens.json files, the registry files and the session transcripts (no message text read).

#CauseEvidence
1The parser drops dispatch lines that carry a note. parseTaskAgents (ledger.ts) needs the line to end at the agent id: ^Task (\S+): dispatch \S+ agent=(\S+)\s*$. The Builder wrote Task 2: dispatch implementer agent=a99f… (base 47badfb). The SKILL.md rule names no note, but real ledgers carry one.DGS-560 session: 15 dispatch lines for tasks 1 to 6 and final. Only the lines with no note matched: the task 1 reviewer and the final reviewer. Tasks 2 to 6 (10 agents) all had (base …) or (head …). That is why tokens.json has task 1 and final only.
2The controller's own output has no agent id, so no task can claim it. Tagging is by agent_id only. The main thread (controller) writes most of the output: it reads reports, builds packs, writes ledger lines.DGS-560: main thread 35,868 output, 15 subagents 5,130. DGS-559: main 31,748, subagents 13,716. With cause 1 fixed, DGS-560 tags at most 5,130 of ~40,998 (13%) and DGS-559 at most 13,716 of 45,464 (30%). So the id-only rule cannot reach full coverage.
3A build that skips the build skill writes no step lines. Steps come from step-start blocks inside brainstorming, writing-plans, SDD and executing-plans. A Builder that starts from a plan pointer and codes directly runs none of them.DGS-561 session: skills used were init, bootstrap, report-implementation only. Registry: one session line and one step_end finishing. All 36 responses sit in other.

Design

A. Parser accepts a trailing note (cause 1)

parseTaskAgents reads agent=<id> and ignores any text after the id. The id pattern is [A-Za-z0-9_-]+. A line with no agent= still gives nothing. The SDD dispatch bullet says that a short note in parentheses may follow the id.

B. Task windows for the controller's turns (cause 2)

Two new registry entry kinds, written like step marks: task_start and task_end, each with ticket, task, session_id, ts. Two new commands: entry.ts task-start --ticket K --task N and entry.ts task-end --ticket K --task N, with the same session-id rule, the same "never blocks" rule, and a skip when the same start is already open.

In buildSnapshot, a record in a registered or inferred session is tagged with a task by this order, one task at most:

  1. Its agent_id is in the ledger map: that task (the ledger wins).
  2. Otherwise the task whose window holds the record's time, in the record's own session. A window opens at task_start and closes at the matching task_end, the next task_start, or a step_end implementation. Same instant rule as stepForRecord. This covers the controller and any subagent the ledger lacks.
  3. Otherwise no task (setup, report, merge prep stay in their step).

The tasks shape does not change (task → model → counts), so task-tokens, tokens.json readers and schema_version: 1 stay valid. The final task id gets its own window.

The skills write the marks:

  • SDD: task-start before recording BASE for a task; task-end right after the "complete" ledger line; task-start --task final at the start of "Final Review" (role mode runs the same opening line; it replaces only the dispatch); task-end --task final with the step-end implementation block.
  • executing-plans: the same pair around each task.

C. Non-SDD builds still write step lines (cause 3)

  • At the source: when digismith:init (or adopt) finds a plan for the ticket already in the board folder (a plan.md, or a plan pointer), the registry step is implementation, not brainstorming: init runs step-start --step implementation. Then a Builder that never opens SDD or executing-plans still has the step open.
  • Safety net in code: when a worker session has records but no step_start at all, and its first mark is a step_end finishing, the records before that mark count as implementation (not other). The snapshot gets one added field, inferred_steps: ["implementation"], so a reader can tell the step was inferred. This turns the DGS-561 shape (36 responses in other) into an implementation step.

Assumptions

The ticket's evidence settles these. The Maestro can overrule any of them.

  • Fix by the controller's time window, not by asking the controller to log more. A time window needs no new skill behaviour beyond two commands per task, and it gives full coverage.
  • New registry kinds, not timestamps in the ledger. The ledger is a deleted-at-finish workspace file; the registry is the durable store the steps already use.
  • The ledger tag beats the window. A record is never counted in two tasks.
  • tokens.json stays at schema_version: 1. inferred_steps is optional and added only when set. No reader is known to reject an extra key.
  • Reviewer-role sessions (role mode) stay out of tasks. They are their own registered sessions with role reviewer.
  • No backfill of the old tokens.json files (DGS-559, 560, 562). Their transcripts exist, but the windows do not.
  • No new dg command. The two new subcommands live in entry.ts beside step-start.
  • No ClickUp field, no ClickUp write, nothing the user sees in ClickUp.

Out of scope

  • Reviewer tokens per task (a Reviewer session would need the task id from the pack). A follow-up ticket if wanted.
  • Maestro and conductor windows for a parent ticket (spike Q2). Another ticket.
  • Price table and cache-write prices (DGS-545/546).
  • ClickUp subtasks per plan task. The spike said no.

Testing and first use

  • Unit tests (vitest, existing files): ledger.test.ts (a note after the id parses; no agent= gives nothing; the DGS-560 shapes), snapshot.test.ts (a main-thread record in a window tags the task; the ledger wins over the window; a window closes on task_end, on the next task_start and on step_end implementation; a record outside any window stays untagged; the inferred-step case), entry.test.ts (task-start and task-end write entries; a repeated open start is skipped; a bad task id fails with a usage error), registry.test.ts if the entry union needs a case.
  • Replay check: run dg tokens over the DGS-560 and DGS-559 transcripts with the new parser and report the task share. The build gives the share it reached; no number is promised, because those two runs wrote no windows. The parser fix alone must lift DGS-560 from 5% to its 13% ceiling.
  • First use after the merge: the next SDD build in role mode. Check its tokens.json: every plan task present, and the tagged share of the implementation step well above 34%.
