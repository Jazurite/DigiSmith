1. What goes wrong

Two tickets (DGS-561, DGS-562) had a ClickUp start date of 2026-10-18 after dg steward event started ran on the 17th at 22:44 UTC+7. At merged the Steward set due 2026-10-17 and ClickUp refused with ITEM_238 (start after due). The move to done stayed pending.

2. What the code and data show (read-only)

  • todayUtc7 and parseDateFlag are correct (tests in the repo; manual write gives 04:00 UTC+7 on the right day).
  • In event.ts, pendingOf writes a start only when the snapshot has none. write() sets the status first, then the dates, then reads back. It never checks that the start it leaves in ClickUp is a sane date. Nothing in write() compares start with due.
  • A queued (pending) write is replayed unchanged. A write that failed on ITEM_238 fails the same way at every retry, so the ticket stays stuck.
  • rebuildState sets start_written from the ClickUp snapshot. The by-hand dg steward rebuild on DGS-561 can therefore have changed the "start_written: null" evidence. That evidence is weak.
  • Log times: DGS-560 started 15:17Z and has the right date. DGS-561 and DGS-562 started 15:44Z. DGS-566 started 17:59Z (00:59 on the 18th UTC+7) and got 2026-10-18, which is right.
  • The writer of the 18th is not proven. Jack confirmed (2026-10-18): the ClickUp time zone is Hanoi, UTC+7, and no automation is running. Time zone and automations are ruled out. Most likely cause (unverified): the ClickUp space setting Dependencies, Reschedule dependencies. Evidence: only tickets with dependencies got the 18th (DGS-561 and DGS-562 wait on DGS-560; DGS-559 waits on DGS-560 and DGS-562); DGS-560, with none, was right. DGS-560 got due 2026-10-17 when it went to done at 15:34Z; ClickUp then moved the start of its dependents to the next day, the 18th. That happened before the dependents started (15:44Z), so the snapshot at started already held a start date. pendingOf skipped its own write, which also explains start_written: null. A start date that the Steward did not write is therefore expected, and the existing rule never repairs it. dg has no command that reads automations or the workspace time zone, and the public ClickUp API has no automations endpoint.

3. Question for Jack (a ClickUp setting, so only Jack)

Answered: time zone is UTC+7 and no automation runs. Decision for Jack, not me: the space setting Dependencies, Reschedule dependencies. Switching it off would stop ClickUp from moving the start dates of dependents; it also stops the automatic shift of a late chain, which Jack may want. I change nothing. The code fix below does not depend on his choice. The code fix below does not wait for the answer.

4. Design (works whatever the cause)

The Steward owns the dates. It does not trust that ClickUp left them alone.

  1. Check after the write. After the status write and the date write, write() reads the ticket back. On a started move: if the start is missing or later than today (UTC+7), write start = today. One extra read; one write only when needed.
  2. Repair at every event. At the start of apply, on a ticket in progress or later: a start date later than today is overwritten with today. This catches an automation that fires after the read-back.
  3. Merged never meets ITEM_238. When the move sets due = today, send start = min(start, today) in the same date write if the snapshot start is later than today. If ClickUp still answers ITEM_238, retry once with start = due. A queued write is recomputed from a fresh snapshot at retry, not replayed unchanged.
  4. Stuck tickets heal. A pending merged from before the fix completes at the next event, by rule 3.
  5. Dependents: rule 1 also runs with the start already set. A start date later than today is replaced even when the snapshot had one, so a rescheduled dependent gets the right date at started.
  6. Not in scope: changing the Reschedule dependencies setting (Jack's call, section 3); a new dg command to read automations (a gap; ticket it only if Jack wants it).

5. Tests

  • Fake tracker whose setStatus sets start to tomorrow: a started event ends with start = today.
  • Fake tracker that refuses dates with ITEM_238: merged ends in done with start = due.
  • A pending write with a stale start completes after a fresh snapshot.
  • Fake tracker where the snapshot already has start = tomorrow (a rescheduled dependent): started ends with start = today and start_written = today.
  • Existing 560-style case (no start at snapshot) unchanged.

6. Open

  • Cause of the 18th: most likely Reschedule dependencies, unverified. A check Jack can do: look at the setting, or move one test ticket that has a dependency. The setting change is his call; the code fix stands either way.
