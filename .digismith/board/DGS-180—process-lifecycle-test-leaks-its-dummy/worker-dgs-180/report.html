DGS-180 fixed a real process leak in ensureProcess (packages/cli/src/depot/process-lifecycle.ts): when it spawned a detached child and then threw — because it could not confirm, via netstat, which PID actually owned the port the child reported — the already-spawned child was left running with no parent and no tracking file pointing at it. On this VPS, every run of the test exercising this path left one orphan behind, matching the 76 found live on the box. The fix kills the exact PID it spawned before rethrowing, so no failure after the spawn (for any reason) can strand a child. A new, platform-agnostic test drives ensureProcess into that failure deterministically (a reported port nobody binds, so no platform's netstat can find an owner) and asserts the spawned PID is dead afterward, using only process.kill(pid, 0) — no pgrep, no process-name matching. No sibling test shares this leak shape.

2. Reproduction and root cause

Baseline pgrep -fc 'dummy listenin[g]' was 0. Running process-lifecycle.test.ts once left exactly 1 orphan (parent PID 1), matching the shape of the 76 found on the VPS. The leaking test is ensureProcess / stopProcess against a real child process > starts a real process, tracks its confirmed PID and port, reuses it, then stops it. It throws could not confirm a PID listening on port <N> via netstat — after the child is already spawned and detached, but before writeTracking runs, so the test's own afterEach (which only removes the temp dir) never learns the child exists.

This was not the maestro's original guess (a failed expect before stopProcess) — ensureProcess itself throws, before any expect runs. Same failure shape though: any throw after the spawn, for any reason, strands the child.

Why the file fails in this checkout: by design, not a bug — .digismith/docs/depot-cli-command-group/plan.md states "Windows is the real target platform... Use only tasklist, taskkill, netstat." On this Linux VPS, tasklist/taskkill are absent entirely, and netstat exists but its Linux output (tcp/LISTEN, no PID column) doesn't match the Windows-shaped parser. This cross-platform gap is out of scope for this ticket and is now tracked separately as DGS-181.

3. The fix

ensureProcess now captures child.pid into a local const pid right after the spawn, wraps the rest of the function (the listening-port wait, the netstat confirmation, writeTracking) in a try/catch, and on any throw calls process.kill(pid, "SIGKILL") (swallowing the error if the child is already gone) before rethrowing the original error. This covers both post-spawn throw points (the 5s "no listening line" timeout and the netstat-confirmation failure) with one wrap, and needs no platform-specific tooling.

4. Proof (TDD, red/green/sanity)

A new test, kills the process it spawned when it cannot confirm the pid and throws, drives the failure deterministically on any platform: the dummy script reports a listening port of 1, a port nothing ever binds, so netstat's PID confirmation legitimately finds no owner regardless of parser format or host OS. The child writes its own PID to a file at startup (no process-name matching needed), and liveness is checked with process.kill(pid, 0) only.

One implementation wrinkle found along the way: a killed process is a zombie — still "alive" to kill(pid, 0) — until Node's event loop runs and reaps it. An Atomics.wait-based synchronous sleep blocks that same event loop, so the first version of the liveness poll never went green even with the fix applied. The test's it callback was made async and the poll uses a real await new Promise(r => setTimeout(r, 20)), which actually yields and lets the reap happen. The production fix itself needed no change for this.

5. Sibling-test check

grep -rn "spawn\|setInterval(()=>{}" --include=*.test.ts packages scripts .digismith — every other hit across the repo is spawnSync (git, node, bash), synchronous and run to completion before the test continues. Only this one test used spawn(..., {detached:true}) + unref() plus a script kept alive with setInterval. No sibling leak found; nothing else needed fixing for this shape.

6. Open items carried forward

Filed to DGS-181 (the maestro is tracking it), found while investigating this ticket, not fixed here: (1) tasklist and taskkill are entirely absent on this VPS, affecting ensureProcess's reuse-check branch and all of stopProcess. (2) stopProcess's taskkill call failing with ENOENT is indistinguishable from "the process already exited" (the tasklist fallback check is also missing), so stopProcess can report {stopped: true} on Linux without having actually killed anything.
