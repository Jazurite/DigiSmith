1. Goal and version 1 scope

The Steward keeps the work, the Claude sessions and ClickUp in step. It is not a session. It is a set of dg steward commands. Each call loads one ticket's state file, acts, saves and ends. It holds no context between calls.

Version 1 is:

  1. The event engine with the whole status map of DGS-488. It knows every status, the event that moves a ticket into each one, the two gates, and the done rules by Sign-off mark. It applies any event it receives: dg steward event <event> --ticket <KEY>.
  2. Filing and typing new ideas into the backlog at once.

Tracker: ClickUp, for the DigiSmith profile. JIRA (Emma) later, behind the same adapter interface.

Out of scope here: which skill or step sends which event, and when. That wiring, including the SDD and merge hooks, is DGS-551 (A.3: Lifecycle Hooks), which waits on this ticket. This spec defines the event contract that DGS-551 calls.
Settled by Jack and the Maestro and not repeated here: events not polling; deterministic engine, a small model only for filing; one depot state file per open ticket; ClickUp writes go through dg only; the Steward never moves a ticket through the two gates (refinement to to do, and acceptance) on its own. It applies a gate move only when the event carries Jack's own answer, which is stored as the record of his decision.

2. Architecture

New command family dg steward in packages/cli/src/steward/, next to clickup/, tokens/ and sessions/. Five units, each with one job:

UnitDoesDepends on
rules.tsPure function: (ticket state, status now, event) gives a list of moves. No I/O. Holds the gate rule: no move has to do as target, and none has refinement or acceptance as source.nothing
state.tsReads, writes (temp file plus rename) and locks ~/.digismith-depot/steward/<KEY>.json. Rebuilds a missing file from the tracker and the token registry.depot dir, tracker adapter, token registry
tracker.tsInterface: getTicket, setStatus, setDates, createTicket, searchTitles, listLists. clickup-tracker.ts implements it over the existing @digismith/clickup-client calls that dg clickup uses. Every write is read back.clickup-client
event.tsThe dg steward event command: load state, run rules, apply moves through the adapter, save.rules, state, tracker
file.tsThe dg steward file command: duplicate check, clan and type pick (the only model call), create in backlog.tracker, model call

The tracker comes from a new profile field tracker: clickup | jira | none. Absent means none: every dg steward call then ends silently with exit 0. The DigiSmith profile gets tracker: clickup. A second new field, release_stage, is described in section 3.

3. Events and rules

Command: dg steward event <event> --ticket <KEY> [--by <role>] [--sha <sha>] [--quote "<Jack's words>"] [--dry-run]. --by is a free label kept in state, for the record only. The engine does not trust it.

The status map

Statuses in the space: backlog, concept, discovery, refinement, to do, in progress, review, acceptance, release, done, documented, discarded, Closed (DGS-488, DGS-493). Every status has an entry event. An event is valid only from the statuses in its "from" column. Any other status gives a refusal, never a move.

The failed-ticket status is undecided (DGS-490). The engine has no event for it. A failed ticket is never retried on its own.

The two gates

  • The two gates are refinement to to do and the acceptance status. Both are Jack's.
  • The only events that cross a gate are approved and accepted. Both are refused without a non-empty --quote. The quote is stored in state with the time and the --by label. The Steward cannot check that the quote is Jack's: it is a record of what the caller says he said. The caller's duty to relay only Jack's own words belongs to DGS-551.
  • No other event has to do as target, or refinement or acceptance as source. A test checks this over the whole table.
  • discard and close also need Jack's quote, because only Jack drops or closes a ticket.

The done rules by Sign-off mark

The mark is a ClickUp drop-down field Sign-off with the values Auto and Jack. It exists on all ten clan folders (DGS-552, done) and is set by name with dg clickup update-task --field "Sign-off=Auto". The Steward only reads it. A ticket with no value is unmarked. What merged does:

MarkAfter mergedReaches done by
Autodone at once, due date todaythe merge itself. No verified.
Jackacceptance (entering the gate)Jack's accepted yes only. verified is refused for these tickets.
unmarkedstays in reviewverified from the Maestro or a conductor

The release stage. The map has release, but the Releaser (DGS-467) does not exist. A profile flag release_stage (default false) says whether the stage is in use. While it is false, the rows above go straight to done as written, and accepted yes goes to done. When it is true, merged for Auto and accepted yes go to release, and released then moves to done. The events release-started and released are valid in both cases, so the map is complete before the Releaser exists.

General rules

  • Any other status now: no move. The command prints one plain line saying why, exits 0, and records the refused event in state.
  • Already at the target status: no write. Events are idempotent. State keeps the ids of applied events (name:sha-or-date).
  • Dates are date-only, in UTC+7. Start date is set once, at started. Due date is set at every move into done.
  • Out of order: verified before merged is refused. A merged that finds the ticket in in progress (the review-started event was missed) is refused and reported, not repaired. Repair is the audit's job, later.
  • Closing: after a move into done, discarded or Closed, state gets closed_at. The file is removed only when two checks pass: Hallmark's roll-up (DGS-545) and the analytics store (DGS-220) both hold the ticket. Neither exists yet, so in version 1 the check function returns false and the file stays with closed_at set. A later ticket turns the check on. documented after done only changes the status.

4. State file

~/.digismith-depot/steward/DGS-549.json
{
  "schema_version": 1,
  "ticket": "DGS-549",
  "tracker": "clickup",
  "status_written": "in progress",   // last status the Steward wrote and read back
  "status_seen": "in progress",      // last status read from the tracker
  "start_written": "2026-10-17",
  "due_written": null,
  "signoff": "Auto",                 // Auto | Jack | null, read from the tracker at each event
  "gates": [],                       // [{ "event": "approved", "quote": "...", "by": "maestro", "at": "..." }]
  "merged": { "sha": "abc1234", "at": "2026-10-17T05:10:00Z" },
  "applied": ["started:2026-10-17"],
  "pending": [],                      // writes that failed, retried first at the next event
  "sessions": [],                     // reserved: filled when session ties come (DGS-531)
  "closed_at": null
}
  • Created when the ticket is filed by dg steward file, or at the first event for a ticket that has no file.
  • The state file also keeps a short log of every event received, applied or refused, with its --by label and time.
  • Rebuild: dg steward rebuild <KEY>, also run automatically when an event finds no file. It reads status, dates and the Sign-off field from ClickUp and the sessions from the token registry. ClickUp stays the source of truth: where state and ClickUp disagree, ClickUp wins and the difference is reported.
  • Concurrency: a conductor and a worker can fire for one ticket at the same time. The command takes a lock file (<KEY>.json.lock, created with exclusive open). It waits up to 5 seconds, then proceeds without the write and puts the event in pending of the next call. A lock older than 60 seconds is stale and is taken over.
  • The Steward writes only its own folder in the depot.

5. Filing new ideas

Command: dg steward file "<idea>" [--type Task|Bug|Spike|Epic|Initiative]. A Maestro or conductor calls it. It prints the new key, the list and the type, or the key of the duplicate it found.

  1. Gather (code): the list names and descriptions of the space (listLists), and open tickets whose title shares words with the idea (searchTitles, top 10).
  2. One model call (small model, no tools, JSON out): from the idea, the list descriptions and the candidates, return { duplicate_of: KEY or null, list: id, type, title }. Rules in the prompt: no lineage fits means the clan's .0 Pavilion; agentic spikes go to clan B; a subtask needs --parent and is a Task. Prompt and schema live in the repo, with a test that the output is parsed strictly.
  3. Create (code): if duplicate_of is set, create nothing and print the existing key. Otherwise create the ticket in backlog, with the chosen type, priority Normal, and read it back. Write the state file.

The model is called with claude -p --model claude-haiku-5-5 and a JSON schema. The model id sits in one constant. If the call fails or returns output that does not parse, the idea is filed in clan B's .0 Pavilion as a Task with a ticket comment "filed unsorted: model call failed". Nothing is lost and a human can re-sort it. A fill of Kind and milestone link is left to the Maestro in version 1; the nightly audit takes it later.

6. Callers: DGS-551

Nothing in this spec edits a skill, a hook or a runbook. The skills' step markers, the session hooks and the Maestro runbook stay as they are. DGS-551 (A.3: Lifecycle Hooks, waits on this ticket) decides which skill or step sends which event and when, including the SDD and merge hooks.

What DGS-551 can rely on from this spec:

  • The command line, the event names and the "from" rules in section 3.
  • The ticket key is always given with --ticket. The Steward does not derive a key from a branch or a folder.
  • A non-zero exit means a usage error only (unknown event name, missing --ticket, a gate event without --quote). Tracker and state failures exit 0 with a stderr line, so a hook that calls the Steward never blocks a flow.
  • With tracker: none (the profile default) every call ends silently with exit 0.

7. Errors

  • ClickUp write fails (network, 4xx, 5xx): the move goes to pending, a warning goes to stderr, exit 0. The next event for that ticket retries pending first, in order.
  • Read-back differs from the write: same as a failed write. The Steward never reports a move as done without reading it back.
  • Status not on the ticket's list: the move is refused with the list's status names printed. No guess.
  • Ticket not found, or no key: one stderr line, exit 0, nothing written.
  • Frontdoor session expired: dg already renews it (DGS-491). If renewal fails, the failure is the same as a failed write.
  • State file unreadable or schema mismatch: moved aside as <KEY>.json.bad (never deleted), then rebuilt.

8. Testing

  • rules.ts: table-driven Vitest cases: every event against every status, including all refusals. One test asserts the gate rule holds for the whole table. One test checks that every status in the map has an entry event.
  • state.ts: temp depot dir: create, atomic write, lock wait and stale takeover, bad file moved aside, rebuild from a fake tracker and a fake registry.
  • clickup-tracker.ts: a fake ClickUpClient (the same factory pattern the dg clickup tests use): write then read-back, mismatch, missing status.
  • event.ts: end to end with a fake tracker: the whole map in order, filed to documented; the three done paths (Auto ends done at merged; Jack ends in acceptance, then accepted yes or accepted no, with verified refused; unmarked stays in review until verified); both values of release_stage; gate events refused without a quote; idempotent repeat; pending retry after a failed write.
  • file.ts: a stubbed model: duplicate found, clean create, malformed output, model failure falls back to the Pavilion.
  • Command wiring: one test in the style of index.e2e.test.ts: dg steward --help and a --dry-run event. No test touches a skill, because no skill changes.
  • First use (live): a dry run against DGS-549 itself, read-only. No ticket is written to by a test.

9. Not in version 1

  • Hooks and wiring: which skill or step sends which event (DGS-551).
  • The nightly audit. When it comes, its rule (Jack): fix the safe gaps (priority Normal, dates on done tickets, milestone links) and report the rest.
  • Session-to-ticket ties (shared with Hallmark, DGS-531). The state field sessions is reserved for it.
  • The status for a failed ticket (DGS-490).
  • The email or message to Jack when an Auto ticket goes done (Jack's call: a separate backlog ticket).
  • The Releaser itself (DGS-467). The engine only carries the release status and a flag.
  • JIRA (Emma).

10. Gaps that become D.3 tasks in the plan

  • Read ClickUp Time in Status. dg cannot read it. A new dg clickup command, with a test, is a plan item. The Steward does not need it in version 1; it feeds the refinement-time report.
  • The tracker and release_stage profile fields and their loader change, with tests.
