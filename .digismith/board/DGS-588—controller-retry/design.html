Nightwatch controller retry

DGS-588, J.5 Nightwatch. Maestro decisions of 2026-10-22 (UTC+7). Spec only: no build before the Maestro orders it.

1. Goal

DGS-583 (watchdog) records on an attention item retryEligible and causeClass and sends nothing. DGS-582 (controller) has no retry. This ticket adds the one automatic retry: the existing restart order, sent once per ticket, journaled, and proved by a new run.

Out of scope: the watchdog (watchdog.ts, watch.ts, causes.ts do not change), a second retry, a retry of a durable or unknown cause, a retry of blocked or stalled (a person looks).

2. Decisions

  1. The retry is the restart order. It uses the text ORDER_TEXTS.restart and the same gate (the conductor input box is empty or a suggestion). It is journaled: a planned line, then a settled line. At most one per ticket. The count is read from the journal, so a controller restart never gives a second retry.
  2. Trigger. An open attention item of this ticket with retryEligible: true and kind lost or failed, and 0 restarts in the journal for the ticket. The next tick plans and sends the order once. It resolves the attention item when a new run starts (a new builder run id with a started event).
  3. Files. advance.ts, act.ts, journal.ts, reconcile.ts. Small edits are also needed in phase-types.ts (types), observe.ts and observers-real.ts (one new observation) and attention-write.ts (the resolver name controller).
  4. Tests use fakes only. See section 7.
  5. The watchdog stays as merged. The tick reads the attention item shape of DGS-583 (OpenItem: id, ticket, run, kind, cause, retryEligible, causeClass) and writes only a resolved line.

3. Design

3.1 Observation

A new observation attention: Obs<AttentionView[]> in Observations. AttentionView = { id, ticket, kind, retryEligible }. The real observer calls readOpen(dir) and keeps the items of the lock's ticket. A failed read gives ok: false: no retry, one obs-attention-failed note. Unknown is not progress.

3.2 Journal count

journal.ts gains restartsOf(results, ticket). It counts the keys of the ticket whose action is retry or order-restart (the pane-gone restart of the building phase) and whose state is not retryable. A retryable key means the prompt was never delivered, so it is not a restart. The count is ticket wide: a phase move cannot reset it. Lines are never deleted; closeOpen at release only settles.

3.3 Advance (pure)

New action { kind: "retry", item: string, head: string, run: string }. advanceTicket checks it after the status rule and before the phase function, in the phases claimed, building, review, merge-ready:

  1. Take the open items with retryEligible === true and kind lost or failed. None: go on as before.
  2. restartsOf > 0: go on as before. The item stays open and Jack sees it (attention only).
  3. Otherwise send the retry through gate(obs) (same wait or note as every order). Journal key <KEY>:<phase>:<attempt>:retry, detail { item, run } where run is the lock's builder run (the old run).

The pane-gone restart in building stays, but it now also waits (wait: restart-used) when restartsOf > 0. So a ticket gets one restart order in total, whichever rule fires first.

After the retry, when the retry key is succeeded and a builder run exists that is not the lock's builder, has started and a later createdAt: return { kind: "adopt", run, item }. A merged or released ticket never retries.

3.4 Act

retry: run("retry", {item, run}, prompt(orderText("restart", ...))). A delivered prompt is not proof that the builder restarted, so on success the line is settled uncertain with note "order delivered, waiting for a new run" (not succeeded). A PromptError with delivered: "no" settles retryable (one more try, capped by MAX_TRIES); anything else uncertain. An uncertain key is never planned again.

adopt: journaled as adopt-retry. It writes runs.builder = <new run> to the lock, then writes the resolved line for the attention item (by: "controller", note "new run <id> started"). appendResolved returns false when the item is already closed, so the step can repeat safely.

3.5 Reconcile (proof)

New check for the action retry, following the DGS-582 rules: unknown is not progress, proof is an artefact.

ObservationResult
runs not observedunknown: the line is left as it is
a builder run of the ticket, id not equal to detail.run, started, createdAt later than the planned linesucceeded ("new run started")
no such run, the planned line is younger than 15 minutes (RETRY_PROOF_WAIT_MS)unknown: no note, the new worker is starting
no such run after 15 minutesuncertain: one journal-uncertain-retry note (the item stays open)

The check never returns retryable: the order may have been delivered, so the key must not be freed. A new check for adopt-retry: lock builder equals detail.run gives succeeded, otherwise retryable (a lock write is safe to repeat).

Crash cases: (a) crash after planned, before the prompt: the key is open, openLines lists it, order-style handling holds it (wait), reconcile settles it only on proof; the order is never sent twice, at the price that a lost prompt needs a person (the 15 minute note). (b) crash after the prompt, before settled: same. (c) crash after settled uncertain: the key is used, no second order.

4. Known limit

dg autonomous release --result failed clears the lock and the scan ticks only while a lock is held. So the retry covers a ticket whose lock is still held, which is the lost run case and any failed or retry-eligible item written while the lock is held. A transient failed release (lock already cleared) keeps its attention item for Jack; there is no builder or phase left to restart. A re-claim after a transient release is a possible follow-up ticket, not part of this one.

5. Code rules

Code in packages/cli/src/ runs under node --experimental-strip-types (the DGS-587 smoke test strips every file): no parameter properties, no enums, no namespaces. Nexus jobs run the built dist/index.js, so a new import must be a relative .ts path the build resolves like the existing ones. Ticket text is never read or journaled; only the validated key, the attention id and run ids enter the order and the journal.

7. Tests without Jack, and first use

Vitest from the repo root, pnpm vitest run packages/cli/src/autonomous. Fakes only: mkdtempSync state folder, fake observers, fake prompt, fake clock. No real ClickUp, herdr, depot, Nexus (4300) or live API.

  • advance: a transient failed item or a lost item with 0 restarts gives one retry; retryEligible: false, kind blocked, stalled or no item gives none; a used or open retry key gives wait; the gate (conductor working, input typed) gives wait; merged and released never retry.
  • a second failure (new item after a retry) gives attention only: no second order.
  • a durable or unknown cause (retryEligible: false) never retries, through the tick, and writes no journal line.
  • a pane-gone restart already sent blocks the retry, and the retry blocks the pane-gone restart.
  • a controller restart between plan and settle (journal has planned only; a new tick) sends no second order, and reconcile settles the line on proof only.
  • act: a delivered prompt settles uncertain; PromptError no settles retryable; the order text is the restart text with a valid key only.
  • reconcile: each row of 3.5, including the 15 minute edge (14:59 and 15:00) and a failed runs read.
  • adopt: after a new started run, the lock builder is the new run, the item has a resolved line, and a repeat writes nothing.
  • tick end to end with fakes: lost run, one order, new run appears, item resolved, a later failure gives attention only.
  • source test: the changed files contain no enum, namespace or parameter property (the same check as DGS-587).

First use (after merge and install, the Nexus API restarted once, both by the Maestro): a throwaway ticket, with a live lock, runs a builder whose pane is closed. The watchdog marks the run lost (retry eligible). The next tick sends one restart order to the conductor, dg autonomous journal shows the retry line, the conductor restarts the builder, the new run starts, the item resolves. Closing the new pane again gives an open item and no second order. The conductor reports the three journal lines.
