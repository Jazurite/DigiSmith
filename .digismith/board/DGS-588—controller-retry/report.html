Summary

The controller (DGS-582) sends the existing restart order once per ticket when an open attention item of the ticket is retry-eligible. The order is journaled, proved by a new started builder run, and the item is resolved when that run starts. The change is a set of small edits to the pure advanceTicket, act, journal and reconcile of packages/cli/src/autonomous/, plus one new observation (attention) that reads the open items. There is no new service and no watchdog change. Followed the full Superpowers process: brainstorming → spec → writing-plans → digismith:subagent-driven-development (8 tasks, each dispatched to a fresh implementer subagent and independently reviewed) → a final whole-branch review, plus 1 fix round before merge.

Reference documents: the design spec and the implementation plan.

What Was Delivered

Task 1: Types, journal count, constant

AttentionView, the retry and adopt actions, RETRY_PROOF_WAIT_MS, and restartsOf and retrySucceeded in the journal.

Task 2: The controller resolver

The attention writer lets the controller resolve an item (by: "controller").

Task 3: The attention observation

Observers.attention reads the open items of the ticket in observeAll, the real observers and the fakes.

Task 4: Advance decides the retry and the adopt

One retry per ticket for a lost or failed item, the adopt of a new started run, the building restart guard and the attention note.

Task 5: Act sends the retry and adopts the new run

The retry sends the restart text and settles uncertain; adopt writes the new builder into the lock and resolves the item.

Task 6: Reconcile proves the retry

A new started builder run after the planned line settles the retry succeeded; no run after 15 minutes gives one note.

Task 7: Tick tests with fakes

Seven tick tests cover the one restart order, a second failure, a crash between plan and settle, and the end-to-end adopt.

Task 8: Runbook line

runbook-text.md holds the text the Maestro applies to the conductor runbook, with the first-use steps.
