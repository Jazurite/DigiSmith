Problem

dg clickup has no command to create a ClickUp List or Folder. This was discovered live during the V-clan ClickUp backfill (2026-09-25) — the V.0/V.2/V.3 Lists had to be created via a one-off script calling ClickUpClient directly, the same workaround used for the original V.1 test task before create-task existed. Tracked as ClickUp task DGS-17 (D.3: ClickUp Channel) — no JIRA ticket, this is DigiSmith's own self-development.

Explicitly out of scope: wrapping ClickUp's private "frontdoor" API for moving a folder into another folder after creation. That needs a completely different session-cookie/bearer/x-csrf credential than the stored CLICKUP_API_TOKEN, and already has its own separate backlog ticket ("Wrap ClickUp's frontdoor API for list/folder moves").

Architecture

New ClickUpClient methods for folder/list creation, a new generic Space convenience class, and two new CLI commands — all following the existing create-task/get-lists pattern already in this codebase: same file layout, same try/catch → console.error + process.exitCode = 1 on failure, same console.log(JSON.stringify(result, null, 2)) on success. No new HTTP library — ClickUpClient already wraps axios internally, so the new methods just call the existing this.post().

Client methods

New methods on ClickUpClient (packages/clickup-client/src/client.ts), each taking just a name — no content/due_date/priority/etc., since nothing in the ticket or its real-world trigger ever needed more than a name:

MethodEndpointReturns
createFolder(spaceId, name)POST /space/{spaceId}/folderClickUpFolder
createListInFolder(folderId, name)POST /folder/{folderId}/listClickUpListSummary
createListInSpace(spaceId, name)POST /space/{spaceId}/listClickUpListSummary

Three separate methods rather than one union-typed method — following the existing precedent of getSpaceFolders/getFolderlessLists already being two separate methods rather than one. createListInFolder stays a plain client method taking an explicit folderId: a Folder isn't a fixed, single-instance concept the way the Space is (there are many folders per space), so it doesn't belong on the Space wrapper below.

The Space object

In practice, DigiSmith only ever works against one ClickUp space (id 1301150000001271, named "DigiSmith"). Rather than threading a spaceId through every call site, a small Space class (packages/clickup-client/src/space.ts) binds a client + a specific space id once: 

export class Space {
  constructor(private readonly client: ClickUpClient, readonly id: string) {}

  createFolder(name: string): Promise<ClickUpFolder> {
    return this.client.createFolder(this.id, name);
  }

  createList(name: string): Promise<ClickUpListSummary> {
    return this.client.createListInSpace(this.id, name);
  }
}

Space stays generic — it takes any client and any space id, no DigiSmith-specific knowledge — consistent with this package's own positioning ("Generic ClickUp API client") and with the pending Soveron cutover (backlog/clickup-soveron-cutover.md), which will consume this same package for a different workspace entirely.

The DigiSmith-specific constant lives in the CLI package instead, alongside the existing createClient() (packages/cli/src/clickup/lib.ts): 

export const DIGISMITH_SPACE_ID = "1301150000001271"; // the "DigiSmith" space

export function createDigiSmithSpace(client: ClickUpClient = createClient()): Space {
  return new Space(client, DIGISMITH_SPACE_ID);
}

CLI commands

create-folder

dg clickup create-folder --name <name>

No --space flag — always uses createDigiSmithSpace(). Calls space.createFolder(name).

create-list

dg clickup create-list --name <name> [--folder <id>]

--folder given → client.createListInFolder(folder, name). Omitted → folderless list via createDigiSmithSpace().createList(name). No --space flag — there's only ever one space to default to.

Both registered in packages/cli/src/clickup/index.ts alongside the existing commands. get-lists (the existing read command) is untouched — it keeps its explicit, required --space, out of scope for this ticket.

Testing

  • Unit tests for the three new client methods in client.test.ts, same request-mock pattern already used for createTask.
  • Unit tests for Space in a new space.test.ts — verifying it delegates to the client methods above with its bound id.
  • create-folder.test.ts / create-list.test.ts in the CLI package, same fake-client-factory pattern as create-task.test.ts — success case and thrown-error case each, plus create-list's two branches (with and without --folder).

Out of scope

  • Wrapping ClickUp's private "frontdoor" API for post-creation folder-nesting/moves — separate backlog ticket, different credential type entirely.
  • Changing get-lists to default its own --space — existing command, untouched by this ticket.
  • Any fields beyond name on the new create endpoints (content, due dates, priority, assignees, status) — nothing in the ticket's own trigger case ever needed them.
