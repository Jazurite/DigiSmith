Background & scope

Jack is moving DigiSmith's own task/backlog tracking to ClickUp going forward (reverses a prior standing decision that ClickUp was out of scope for DigiSmith — see the global memory update this brainstorm triggers). This build is the foundation for that: a generic @digismith/clickup-client package, moved and generalized from Jack's existing, working ClickUp client in his separate Soveron repo, plus a dg clickup CLI surface.

Scope is deliberately narrow: only the connector package and its CLI commands. Four related efforts are explicitly deferred and filed as backlog items rather than designed here:

  • backlog/clickup-backlog-map-flow-wiring.md — wiring DigiSmith's own backlog/map creation flow to actually call the connector
  • backlog/clickup-ticket-writeback-i1-analog.md — ticket-level ClickUp write-back (I.1/JIRA analog) for consuming-repo work
  • backlog/clickup-soveron-cutover.md — Soveron's own packages cutting over from their local copy to this one
  • backlog/clickup-historical-backfill.md — bulk-importing existing backlog/map history into ClickUp

Decisions settled

Scope

Both consumption modes

Direct TS library import (mirroring jira-client via Depot's sparse clone) and dg clickup CLI subcommands — each future call site picks whichever fits.

Move boundary

Generic client only

Only the generic ClickUp API client moves. Soveron's sprint-resolver.ts, factory.ts, and workspace-specific custom-field types stay in Soveron.

Style

Keep the working shape

Class-based, axios, existing RateLimiter — not rewritten to jira-client's functional/zero-dep style. Credential handling is adopted from jira-client for consistency.

Day one CLI

Read-only

check-credentials, list-tasks, get-task, get-lists. Write operations (create/update task, add comment) deferred until a real consumer needs them.

Publishing

clickup-client is published, unlike jira-client

jira-client stays workspace-private (nothing published depends on it). clickup-client must be a real npm package because the published @digismith/cli depends on it for dg clickup.

Deferred

Historical migration, letter-scheme question

No bulk-import of existing backlog/map history. Whether DigiSmith letters keep getting assigned once ClickUp replaces MEMORY.md's map table is explicitly deferred to the map-flow-wiring backlog item — not answered here.

Architecture

New package packages/clickup-client (@digismith/clickup-client), sibling to packages/jira-client in the DigiSmith monorepo. Two consumption paths:

  • Direct TS import — for future consumers (Soveron's cutover, DigiSmith's own map-flow wiring), the same way packages/jira-client is consumed today via Depot's sparse clone.
  • dg clickup <command> — a new command-group bucket in @digismith/cli, following the same bucket-of-leaves shape as the existing depot and vps buckets (packages/cli/src/depot/index.ts composing clone/opencode/bridge sub-buckets via yargs .command()).
Publishing fork: packages/jira-client is "private": true — nothing published depends on it, so it never needs to be on npm. @digismith/cli, however, is published (currently 0.2.0-beta), and a published package cannot depend on an unpublished workspace package. So @digismith/clickup-client ships as a real, published npm package ("private": false, same publishConfig.access: "public" as cli), and @digismith/cli takes it as a normal dependencies entry. This is a new precedent for packages/cli — it currently has zero dependencies on other workspace packages — mirroring how U.1 already reversed V.4's original "zero runtime dependencies" stance for yargs/picocolors. Direct-TS-import consumers can still use either the published package or Depot's clone; publishing doesn't remove that option.

Data flow

A dg clickup leaf command parses its argv (yargs options, matching the existing depot bridge ensure --repo pattern) → calls checkCredentials() → constructs new ClickUpClient(creds) → calls the relevant method → prints the result (formatted JSON) to stdout, non-zero exit code and a clickup <subcommand>: <message> line to stderr on failure — the same shape as depot bridge ensure's existing error handling.

Direct-import consumers skip the CLI layer entirely: import { ClickUpClient, checkCredentials } from "@digismith/clickup-client", then use the class directly.

Error handling

  • CredentialsError on a missing ~/.digismith-depot/.env or incomplete CLICKUP_API_TOKEN/CLICKUP_TEAM_ID fields — caught at the CLI layer, printed, exit 1.
  • HTTP/API errors thrown by axios inside ClickUpClient bubble up unchanged; CLI leaf commands catch generically and print err.message, exit 1.
  • The existing RateLimiter already throttles to ClickUp's 100 req/60s internally — inherited for free, no new rate-limit handling needed.
  • No new Windows entry-point guard needed — clickup commands run inside packages/cli's dispatcher, which already uses the realpath-based isDirectRun() check that closed map item I.5's bug (jira-client's own separate cli.ts entry point isn't reused here since clickup goes through the yargs framework instead).

Testing

  • Port clickup.client.spec.ts and rate-limiter.spec.ts from Jest/ts-jest to Vitest, per the standing toolchain default (map item G.2).
  • Drop factory.spec.ts and sprint-resolver.spec.ts — those test Soveron-only code that isn't moving.
  • New CLI leaf-command tests follow whatever pattern the existing depot/vps leaf commands already use.
  • Live ClickUp API calls stay credentials-gated and live-verify-only — not exercised in CI, the same caveat map item V.3's SSH/tmux logic carries.

Explicitly out of scope

  • Write operations in the day-one CLI (create-task, update-task, add-comment, set-custom-field) — the library methods exist on the moved class, but no CLI subcommand wraps them yet.
  • Wiring any real consumer (DigiSmith's own map-flow, ticket write-back, Soveron's cutover) — see the four backlog items filed alongside this design.
  • Historical backfill of existing backlog/map data into ClickUp.
  • Deciding whether DigiSmith letters keep getting assigned once ClickUp replaces MEMORY.md's map table for new entries — deferred to whenever the map-flow-wiring backlog item is actually brainstormed.
  • Choosing the ClickUp workspace/team DigiSmith's own future backlog/map would live under — deferred, not blocking this connector build (the client takes team ID as config either way).
