Background & scope

V.6 (shipped 2026-09-24) built the @digismith/clickup-client package and a read-only dg clickup CLI surface, deliberately deferring write operations and any real consumer wiring to backlog — see backlog/clickup-backlog-map-flow-wiring.md. This build closes part of that gap: it adds the write primitives (create, update, attach) so DigiSmith's own map/backlog history can actually be pushed into ClickUp — but deliberately not the fuller "auto-wire brainstorming/writing-plans/report-implementation to call ClickUp automatically" vision that backlog item originally sketched. Jack's explicit call during this brainstorm: this is a "one time job" per letter, not a recurring workflow — so it gets no new skill and no lifecycle-hook trigger, only reusable low-level write commands that an agent drives ad hoc.

The real ClickUp structure was clarified live during this brainstorm (Jack's own workspace, inspected via the API since it isn't public): the DigiSmith space has a Clans folder containing one List per DigiSmith letter (e.g. the "V" list), and each sub-item becomes its own task, a sibling within that letter's list — not nested as subtasks, and not distinguished via ClickUp's Custom Task Type feature (considered, explicitly rejected; see the Decisions section).

The whole field-mapping shape below was validated live: a real task was created for V.1 in the actual "V" list (https://app.clickup.com/t/14zcebru1dg) using the client directly, before this design was finalized. Jack confirmed it read well.

Rollout is a reversal of V.6's original "no historical migration" stance, but only via a manual, gradual process: the V clan (V.1–V.6) is backfilled first and validated, then the remaining ~39 clans follow one at a time, at Jack's own pace — never a single bulk migration.

Decisions settled

Trigger

Manual, ad hoc — no new skill

Every sync is a live, agent-assisted task using the new CLI primitives directly — not a skill, not a script, not a lifecycle hook. Jack's call: this is a one-time-per-letter job, not a recurring workflow.

Structure

Clans folder → one List per letter

Sub-items are sibling tasks within that letter's List. ClickUp's Custom Task Type feature was considered for representing letters and explicitly rejected ("No special task type").

Backfill scope

V clan first, then gradual

Reverses V.6's "no bulk migration" stance, but stays manual and incremental — one clan at a time, never an automated batch-all.

Field sourcing

Mixed judgment + mechanical

Title/description are agent-drafted from MEMORY.md's prose. Due date and status are read mechanically from the same prose. Start date comes from git history. Priority is a fixed default. See the Field mapping reference.

Report attachment

PDF, not inline text

A shipped sub-item's report.html is exported to PDF via Playwright's page.pdf() and attached to its task — ClickUp's task description is limited rich text and can't render the styled HTML report as-is.

Frontdoor API (noted, unused)

ClickUp's private Task-Type-creation endpoint

Captured live during this brainstorm as a sibling to the already-vendored FrontdoorFieldPutBody pattern (POST .../customItem, session-cookie auth, not the public API). Moot for this build since Task Types were rejected for letters — kept here only so the knowledge isn't lost for a future need.

Architecture

No new package and no new skill. This extends the existing packages/clickup-client and the existing dg clickup bucket (packages/cli/src/clickup/) that V.6 shipped. createTask and updateTask already exist on ClickUpClient — V.6 built them but never CLI-wrapped them. This build adds that CLI wrapping, plus the one genuinely new client capability, attachment upload.

No orchestration layer. There is deliberately no "sync a whole letter" command. Each create-task/update-task/upload-attachment call is a discrete, low-level primitive; the agent issues one call per sub-item per field group, driven by reading MEMORY.md live in the conversation — the same shape as the V.1 test, just through the real CLI instead of a scratch script.

Data flow

For a given letter's sub-item, the ad hoc flow is:

  1. Find the letter's List inside the Clans folder — existing get-lists, matched by name. No separate ID-mapping file; looked up live each time.
  2. List that List's existing tasks — existing list-tasks — and check by name whether this sub-item already has a task, to decide create vs. update (safe to re-run).
  3. Draft name/description from the sub-item's MEMORY.md prose.
  4. Derive status/due_date from the prose, start_date from git history, fix priority to normal.
  5. Call create-task (or update-task if it already exists) with those fields.
  6. If the sub-item has a report.html, export it to PDF and call upload-attachment against the resulting task.

Error handling

  • Same CredentialsError/generic-catch shape as V.6's read commands — missing or incomplete ~/.digismith-depot/.env fields caught at the CLI layer, printed, exit 1.
  • upload-attachment: a missing local file is checked before the request is made, with a clear stderr message rather than surfacing a raw ClickUp API error.
  • No dedicated "find task by name" primitive — the create-vs-update decision (Data flow step 2) is a judgment step using the existing list-tasks output, not a new mechanized lookup.
  • The existing RateLimiter (100 req/60s) already covers the new write calls, same as every other client method.

Testing

  • Vitest unit tests for uploadAttachment (mocked multipart request, asserting the body/field shape — mirroring packages/jira-client/src/client.test.ts's existing uploadAttachment describe block).
  • Vitest unit tests for the three new CLI leaf commands, following the existing check-credentials/get-lists/etc. test pattern.
  • No test for the ad hoc sync judgment itself (title/description drafting, git-history date lookup) — that stays a manual, conversational process, not code under test.

Explicitly out of scope

  • Any new skill, script, or lifecycle-hook trigger — every sync run is manual and ad hoc, per Jack's explicit call.
  • A mechanical/regex parser for MEMORY.md — title/description extraction stays agent judgment; the prose is too unstructured for reliable parsing (confirmed by inspecting several existing rows during this brainstorm).
  • A "find task by name" or other idempotency-search CLI primitive — the create-vs-update decision is a judgment step over existing list-tasks output.
  • A "sync this whole letter" single command — each create/update/attach call is issued individually by the agent.
  • backlog/*.md items (ideas not yet promoted to a shipped map letter) — this design covers only MEMORY.md's lettered/sub-lettered rows.
  • Bidirectional sync — ClickUp never writes back into MEMORY.md.
  • Wrapping ClickUp's private "frontdoor" customItem-creation endpoint — noted for future reference only (see Decisions), not built here.
  • Real prioritization logic beyond the fixed normal default.
