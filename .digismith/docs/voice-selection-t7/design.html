Overview

T.1 (technical_voice — ASD-STE100 artifact-writing style) and T.5 (conversation_voice — live-conversation response shape) both already exist as content in standards/global/, but nothing lets Jack deliberately turn either one on or off for a given repo the way a consumer app lets you pick a voice. Today inject-standards only suggests them contextually, per its own Scenario 1 matching — there's no persistent, explicit "this repo's voice is X" decision.

T.7 adds that: two independently selectable on/off switches, persisted per repo, with a dedicated skill to view and change them and an immediate, felt effect when toggled on.

Storage

No new store. Two new keys in the existing H-lineage preference store (.digismith/preferences.yml, read/written via digismith:preferences get/set — same mechanism H.1/H.2 already use):

technical_voice: on
conversation_voice: on

A missing key is treated as on — both axes default on for a repo with no saved preference yet, same missing-key-defaults-safely pattern H.1/H.2 established. Values are on/off only; no named-voice registry. Exactly one real standard exists per axis today (ste100-writing for technical_voice, ai-voice-conversational for conversation_voice) — building a picker for options that don't exist yet is deferred until a second real voice shows up per axis.

The digismith:voice skill

New skill, two modes:

InvocationBehavior
digismith:voice (no args)View mode — reports effective state for both axes, e.g. technical-voice: ON (ste100-writing) / conversation-voice: ON (ai-voice-conversational). Reads via digismith:preferences get, defaulting to on when a key is unset.
digismith:voice technical off / digismith:voice conversation on Set mode — writes the key via digismith:preferences set. Switching an axis ON also immediately reads and announces that standard inline in the current session, in the same format inject-standards Scenario 1 already uses — the toggle has a felt effect right away, not just at the next bootstrap/inject-standards trigger.

Integration with existing triggers

inject-standards gains a Voice Gate alongside its existing Profile Gate (Step 0): before matching/suggesting, read the two preference keys. Whichever axis is on gets its standard auto-included unconditionally in Scenario 1 (Conversation) — no suggestion prompt, since the repo already made this choice explicitly via digismith:voice. Scenario 4 (Dispatching a Subagent) is unaffected: it already excludes every kind: prose entry regardless of this gate, so neither voice ever leaks into a subagent-dispatch prompt.

bootstrap and adopt gain the same auto-inject at their existing Step 0 preference-resolution point, mirroring how H.2 resolves the per-repo SSH-key preference there — whichever axis is on gets announced at ticket start, same as an explicit digismith:voice toggle would.

Error handling

  • Missing or malformed .digismith/preferences.yml → both keys treated as unset → default on (existing store's own established fallback, not a new behavior).
  • digismith:voice given an invalid axis name or value → error listing the two valid axes and on/off, same style as inject-standards' existing "Standard not found" message.

Scope boundary and dependency (resolved)

Update, same day: W-lineage shipped W.10 (the real Claude Code SessionStart hook to init DigiSmith) while this design was in flight — hooks/hooks.json + scripts/session-init.ts, already on main. It fires on every session startup/resume/clear/compact/fork, reads .digismith/profile, and looks for a sibling scripts/voice-init.ts exporting default (): Promise<string | null> — missing file or a null return both mean "no voice segment," a thrown error is caught non-blockingly. This closes the gap this design originally deferred: T.7 now adds scripts/voice-init.ts directly (see the skill task list), giving every session a voice-aware banner (DigiSmith: profile=<name>, voices=<summary>), not just the ticket/coding-path triggers below.

bootstrap/adopt (ticket start) and inject-standards (coding, skill-building, planning, subagent dispatch) still each get their own auto-inclusion — W.10's banner is a terse one-line summary at session start, not a substitute for inject-standards actually injecting the full standard content where it's needed.

Out of scope

  • A named-voice registry or multi-option picker — deferred until a second real voice exists per axis.
  • Any change to scripts/session-init.ts itself, or to hooks/hooks.json — W.10 shipped both already; this design only adds the voice-init.ts file W.10's own contract expects.
  • T.2 (wiring generated artifacts to the standard), T.3 (consuming-repo propagation), T.4 (portable output-style + linter), T.6 (audience-filtering voice) — untouched by this design.
