Overview & Relationship

Two related map items, designed together. H (Preferences) is new, general-purpose infrastructure: a per-repo settings store any DigiSmith skill can read from or write to, wrapped in a skill (digismith:preferences) the same way digismith:depot wraps shared runtime-resource management. W.8 (Saved Finish Option) is the first consumer of it: finishing-a-development-branch's Step 4 menu (Merge locally / Push+PR / Keep as-is) stops asking fresh every time once a repo's answer is known, using H for storage.

H is being built now, not backlogged, because — unlike the deliberately-deferred lifecycle-hooks idea (map item Y, same session, same "one concrete use case isn't enough" reasoning that applied there) — this generalization was explicitly requested: build the general mechanism now rather than a one-off file for finish_option alone.

H: Problem

No general mechanism exists today for a skill to persist a small per-repo setting decided through live interaction. profiles/<name>.yml (inside DigiSmith's own repo) is the closest existing thing, but it's a hand-authored template applied to a class of repos (e.g. every Shopify theme repo uses the emma profile) — not a place for one specific repo's own, dynamically-set answer to something. .digismith/profile (inside each consumer repo) is the closest per-repo file, but it holds exactly one thing (which profile name applies) and isn't structured for arbitrary key/value settings.

H: Storage

A new file, .digismith/preferences.yml, sibling to the existing .digismith/profile, one per consumer repo (DigiSmith's own repo included — no special-casing). Flat key/value pairs, no nesting until a real need for it shows up: 

# DigiSmith-managed. Settings decided through live interaction, not hand-authored.
finish_option: merge_locally

Scope is per-repo only (not per-profile, not a separate global-to-you tier) — matches the grain already settled on for finish_option itself, and keeps the read/write logic to one tier instead of two with a precedence rule between them. Same commit disposition as .digismith/profile: where a consumer repo's .digismith/ isn't gitignored, committing this file is fine and makes it durable; where it is gitignored, it's written but never force-added — matching a choice the repo already made.

H: The digismith:preferences skill

Wraps read/write access to .digismith/preferences.yml, invoked two ways, same pattern as digismith:depot:

  • Automatically, by any consuming skill that needs to read or write a preference — starting with finishing-a-development-branch (W.8). A consuming skill never parses the YAML itself; it goes through this skill's read/write operations.
  • Directly, on explicit user request — "what's my preference for X in this repo", "set my preference for X to Y", "clear my preference for X". This is the only path that changes a preference outside of a consuming skill's own first-time "remember this?" flow (W.8's own mechanism, not a new one H needs to invent).

Interface (exact operation names and signatures are for the implementation plan, not this design): get(key) → value or unset; set(key, value); clear(key). No enumeration/listing of arbitrary keys is required by either known use case yet — add it only if a real need shows up (YAGNI).

H: Worktree propagation

.digismith/profile already needs explicit copy-forward into a freshly-created worktree (bootstrap Step 2.6) because a gitignored .digismith/ won't carry it automatically. .digismith/preferences.yml needs the exact same treatment, added alongside that existing copy step in both digismith:bootstrap and digismith:adopt — skipping it would silently make every fresh worktree look like "no preferences set," defeating the entire point of persisting them across many worktrees over time.

H: Error handling

  • File missing — every key reads as unset; not an error. A consuming skill falls back to its own default behavior (W.8: ask the menu as normal).
  • File present but malformed/unparseable — treat as unset, same as missing. Never crash a caller over a corrupt preferences file.
  • Key requested that was never set — returns unset, not an error.
  • Target path gitignored in this repo — write succeeds, commit is skipped, same disposition already established for .digismith/profile and this pipeline's generated docs. Never force with -f.

W.8: Problem

finishing-a-development-branch's Step 4 menu asks the same three-option question every single time a branch finishes, even though the answer is usually predictable per repo — DigiSmith's own self-work and most personal repos want Option 1 (merge locally); ticket work against a client repo almost always wants Option 2 (PR).

W.8: Behavior

First run in a repo (no finish_option set)

Step 4's menu is presented exactly as it is today, unchanged — this preserves the skill's existing "wait for their answer, the integration decision is theirs" rule untouched. Once the user answers with Option 1 or Option 2, one lightweight follow-up: "Remember [option] as this repo's default, so I stop asking?" Yes → write finish_option via digismith:preferences. No → proceed normally this run; ask again next time. Option 3 (keep as-is) never gets this follow-up — it's a one-off deferral, never a repeatable default, and is never itself a stored value.

Subsequent runs (finish_option already set)

Skip the menu. Announce the saved default plainly (e.g. "Using saved default for this repo: merge locally. Say 'show the menu' to override once.") and proceed straight to executing that option — unless the user's own message for this specific run already stated an explicit override ("push this as a PR instead"), mirroring the same "explicit user request for this specific run" pattern writing-plans' Execution Handoff already uses for inline vs. subagent-driven. An override changes only this run; the saved value is untouched.

Changing the saved default permanently

Only in response to the user explicitly saying so for this repo going forward (e.g. "always PR this repo from now on") — never inferred from context or from a single override. This overwrites finish_option via digismith:preferences, the same write path the first-run "remember this?" flow uses.

Applies uniformly

DigiSmith's own repo goes through the exact same mechanism as any consumer repo — no IS_DIGISMITH-based hardcoding. Every DigiSmith self-finish so far (W.4.1, W.7) has picked Option 1 anyway, so it will settle there naturally on first use and stay consistent with everything else built this way.

W.8: Scope

In scope: the normal-repo / named-branch-worktree three-option menu only. Out of scope: the detached-HEAD reduced two-option menu (Push+PR / Keep as-is) — only one option there is ever repeatable (Push+PR), so there is nothing meaningful to remember or skip.

Testing

H's read/get/set/clear operations against .digismith/preferences.yml are ordinary, independently-testable logic (parsing, writing, missing-file and malformed-file fallback) and should get real unit tests, following this repo's existing pattern (real file fixtures in a temp directory, no mocking — same shape as scripts/bump-plugin-version.test.ts). W.8's own behavior (menu-skip decision, override detection, the first-run follow-up prompt) is skill prose with no automated test harness, same as every other finishing-a-development-branch divergence so far (W.4, W.4.1) — verification there is a careful manual read-through plus a real end-to-end run.

Out of Scope

  • A global-to-you preference tier spanning all repos (considered, explicitly declined in favor of per-repo-only for now).
  • Enumerating/listing all preferences set for a repo (no concrete need yet).
  • Migrating any existing profiles/*.yml field into this store — those remain DigiSmith-repo-side, hand-authored, per-profile-class config; this store is per-individual-repo, dynamically written through live interaction. Different mechanisms for different jobs.
