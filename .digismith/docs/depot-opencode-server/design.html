Overview

K.2 (digismith:offload-implementer) shipped 2026-08-27 and passed a real end-to-end smoke test 2026-08-28: a live linked worktree, a real seeded bug, a real Chutes dispatch, a real commit, independently verified. Its server-lifecycle logic — start-if-not-running, resolve the Windows PID, track it, stop it — was written entirely inline in its own SKILL.md, scoped to one opencode serve process per subagent-driven-development plan.

V (digismith:depot), shipped the same day, already owns a different machine-wide runtime resource — a sparse clone of packages/ at ~/.digismith/repo — via the same shape of idea: provision once, reuse everywhere, independent of any single repo or ticket.

The structural rhyme between the two was noticed directly: Depot's ensure ("does the resource exist? no → provision it, yes → no-op") is the same shape as offload-implementer's own "locate or start the server" step, just applied to a process instead of a git clone. This design moves the OpenCode server under Depot's ownership as a second resource type, and — per explicit discussion — changes its scope in the process: from one server per plan to one shared server for the whole machine.

Scope Change: One Shared Server, Machine-Wide

Today: each subagent-driven-development plan that uses offload gets its own opencode serve process, tracked in that plan's own .superpowers/sdd/<plan-basename>/opencode-server.json, stopped when that plan's offloaded work is done.

Going forward: one shared server for the entire machine, tracked at ~/.digismith/opencode-server.json — sibling to Depot's existing ~/.digismith/repo, same machine-wide scope. Every concurrent plan, in every repo, dispatches through the same process. This is safe because OpenCode sessions are already proven isolated from each other (verified live, twice: during K.2's original spike and again in the 2026-08-28 smoke test) — a fresh dispatch with no --session flag always gets a new, context-free session regardless of what else is running on the server, and --dir is a per-run flag, not a per-server one, so one server instance correctly serves dispatches against different worktrees.

This is a deliberate behavior change, not a pure refactor — see Concurrent Plans and Accepted Risk below for what it actually changes and what it costs.

New Depot Operations

Two new operations, named and scoped like the existing pair rather than folded into a generalized "resource" abstraction — a git clone and a live process don't share mechanics, only the shape of "provision once, reuse everywhere." Depot ends up with two resources, each with its own concrete verbs:

ResourceProvisionTeardown
packages/ cloneensure — clone if missing refresh — fetch + hard reset (never deletes)
OpenCode serverensure-opencode-server — start if not alive stop-opencode-server — explicit only

ensure-opencode-server

Check ~/.digismith/opencode-server.json for a tracked {"pid": ..., "port": ...}. Alive (Windows: tasklist //FI "PID eq <pid>" actually lists it, not just exits 0) → return the tracked port, done. Absent or stale → start fresh exactly as offload-implementer does today: let the OS pick a free port (--port 0), read the log for the real assigned port, resolve the real Windows PID (ps -W/awk first, netstat -ano fallback if empty, per the WINPID gotcha already documented and proven in K.2), write the tracking file, return the port.

stop-opencode-server

Explicit only — never automatic, never tied to any single plan finishing. Invoked directly ("stop the OpenCode server", mirroring how refresh is invoked directly for the clone). taskkill //PID <pid> //F, delete the tracking file. Absent tracking file → nothing to stop, report that plainly (same disposition K.2's own Stop the Server section already has).

Unlike the clone's ensure, ensure-opencode-server is not auto-invoked by bootstrap/adopt. The server is a real background process (346-556MB observed in the 2026-08-28 smoke test) that exists only to serve K.2's explicit, opt-in offload dispatches — most tickets never touch it. Only offload-implementer itself calls ensure-opencode-server, the first time a task is actually offloaded. No refresh-opencode-server either — "refresh" for a process is just stop-then-ensure, not a distinct operation worth naming.

The One Credential Depot Now Touches

Depot's clone side is explicitly credential-free (~/.digismith/.env may sit alongside ~/.digismith/repo, but Depot never creates, reads, or references it). ensure-opencode-server breaks that pattern narrowly: starting the server needs CHUTES_API_KEY in its process environment (confirmed — opencode.json's provider block resolves {env:CHUTES_API_KEY} against whichever process is handling the actual model calls, which is the server, not the per-dispatch run client). So ensure-opencode-server fetches the key the same way offload-implementer already does today (manage_credentials.py get --field api_key) and passes it only as an environment variable at server-launch time.

This is look-don't-touch, same boundary Depot already keeps elsewhere: it reads one credential value to hand to a subprocess's environment, and stores, inspects, or manages nothing about it afterward. It stays completely agnostic about models, prompts, and opencode.json's own provider configuration — that remains entirely offload-implementer's concern, resolved per-dispatch, not at server-start.

What Moves Out of offload-implementer

skills/offload-implementer/SKILL.md's Step 2 ("Locate or Start the OpenCode Server") and its "Stop the Server" section are removed entirely. In their place: Step 2 becomes a single call out — invoke digismith:depot's ensure-opencode-server operation, use the port it returns. The "Stop the Server" section is deleted outright, not replaced — offload-implementer no longer stops anything; that responsibility belongs entirely to Depot now, invoked directly by you, independent of any specific plan's lifecycle.

What Stays in offload-implementer

Everything else is untouched — this is the part that was just proven working end-to-end and nothing here has reason to change it:

  • Step 1 — opencode.json per-worktree config, ignored via the resolved git rev-parse --git-path info/exclude (the exact fix verified live in a real linked worktree during the smoke test)
  • Step 3 — task-brief extraction, digismith:inject-standards invocation, the report contract
  • Step 4 — heredoc-captured dispatch, the long-timeout guidance
  • Step 5 — .part.text status extraction, per-plan sessionID capture
  • Step 6 — independent verification before trusting DONE, hand-back to the normal review/fix-loop flow

Session Tracking Is Unchanged

Only the server process becomes shared. Each dispatch still creates its own isolated OpenCode session, and opencode-sessions.jsonl still lives in the plan's own SDD workspace, tracking only that plan's tasks — exactly as today. Depot has no concept of sessions at all; it only ever sees one process and one port.

Concurrent Plans Sharing the Server

This is the actual payoff of the scope change: plan A (one repo, one worktree) and plan B (a different repo, a different worktree) can each dispatch offloaded tasks through the same server process at the same time, each getting its own isolated session, without either spinning up a second opencode serve instance. This has already happened for real, unplanned, during this project's own development (multiple concurrent Claude Code sessions building I.1, K.2, and V on the same day) — the shared-server model fits that reality instead of fighting it.

Within a single plan, this changes nothing: subagent-driven-development never dispatches more than one implementer at a time regardless (its own no-parallel-implementers rule, to avoid conflicts), so a plan never needs more than one active session at once whether the server is shared or not.

Accepted Risk: A Shared Stop Can Break Another Plan

Sharing the server introduces one real, disclosed risk that owning one per plan never had: if you stop the server while a different plan still has an in-progress offloaded task or an unresolved fix-round session on it, that other plan's session stops resolving — surfacing as the existing "captured sessionID no longer resolves" error case (already documented in K.2's Error Handling), just now reachable by a cause outside that plan's own control instead of only a machine restart.

This is accepted, not mitigated — per the explicit decision behind this design (mirror the clone: no reference-counting, no are-other-plans-using-this check before stopping). Building real multi-consumer safety for a personal, single-operator tool is solving a problem that doesn't exist yet; the cost of getting it wrong is "the other plan's next fix-round dispatch reports plainly that its session is gone, you re-run ensure-opencode-server and resume with a fresh one" — annoying, not destructive, and already the documented disposition for the pre-existing machine-restart case.

Error Handling

Server-lifecycle cases move to Depot, since it now owns that lifecycle. offload-implementer's own Error Handling section keeps only the cases genuinely specific to dispatching and resuming a task.

CaseOwned byDisposition
opencode not on PATHDepot Stop, point at the correct install command (pnpm add -g --allow-build=opencode-ai opencode-ai). Never install silently.
Server fails to start (no "listening on" line) DepotStop, show the log content, don't retry silently.
Tracked PID no longer running (stale)Depot Treat as absent, start fresh, overwrite the tracking file.
WINPID unresolvable (both ps -W and netstat come back empty)Depot Never persist an empty PID — report the failure plainly rather than writing an unusable tracking file.
opencode run itself errors, times out, or lies about successoffload-implementer Unchanged from K.2's existing Error Handling — these are dispatch concerns, not server-lifecycle ones.
Captured sessionID no longer resolves offload-implementer Unchanged, but now reachable via the shared-stop risk above in addition to a machine restart.

Backward Compatibility

No plan currently has an in-flight offloaded task sitting mid-fix-loop (K.2 shipped 2026-08-27, the smoke test's own server was stopped and its scratch worktree removed at the end of that test) — there is no live opencode-server.json anywhere to migrate. This ships as a clean cutover: old per-plan tracking format is simply no longer written; any plan workspace still holding one from before this change is inert leftover, not read by anything after this ships.

Out of Scope

  • A DigiSmith CLI entry point — raised during discussion, explicitly deferred to its own future feature. This design changes only how Depot and offload-implementer talk to each other as Claude Code skills; it does not add any way to trigger either from outside a Claude Code session.
  • Reference-counted or multi-consumer-safe stop — see Accepted Risk. Explicit-only stop, same as the clone.
  • Model or provider abstraction — Depot's new operations know nothing about Kimi, Chutes routing, or opencode.json's provider block. Still entirely offload-implementer's concern, unchanged from K.2.
  • A generalized multi-resource interface inside Depot — two concrete resources, two concrete operation pairs. Not generalized until a third real resource actually needs the same shape.
