Background & Feasibility Spike

MEMORY.md's Open Questions section flagged that map item K's feasibility was unverified, and explicitly called for a feasibility spike before speccing — not during. That spike ran first and settled the question:

No per-subagent non-Anthropic model routing exists. Verified against the official Agent SDK docs: AgentDefinition.model (and Claude Code's agent frontmatter model: field) accept only Anthropic model aliases or full Anthropic model IDs — no custom baseURL, no OpenAI-compatible endpoint, no per-agent provider override. The only global escape hatch, ANTHROPIC_BASE_URL, repoints the entire session at once, not individual subagents.

Chutes.ai — the open-weight provider named in the original roadmap note — was checked directly too. It's a plain OpenAI-compatible HTTP inference API (llm.chutes.ai/v1/chat/completions); nothing on its side plugs into Claude Code's subagent dispatch either. Its own routing/pooling (comma-separated model lists, :latency/:throughput failover, model-alias packs) only spans Chutes-hosted models — it can't reach across to Claude, since Claude isn't hosted there. A unified frontier-to-open-weight routing layer can't live entirely on Chutes' side; DigiSmith itself has to be the thing deciding which call goes where.

This also surfaced that superpowers:subagent-driven-development already does cost-aware model selection today — its own "Model Selection" section instructs the controller to pick the least powerful Anthropic tier (haiku/sonnet/opus) per task role, and explicitly warns that cheaper models taking more turns can cost more overall than a mid-tier model would have. So the real, previously-unaddressed gap in K was never "model tiering" in general — it's specifically the open-weight extension, and that extension cannot take the form of literal subagent dispatch with today's tooling.

Scope: K.1 vs. the Rest of the Initiative

Given the above, three narrower directions were considered instead of a literal subagent-model-swap: (1) offload specific mechanical subtasks within real implementer tasks via an MCP tool call, (2) formalize the existing Anthropic-tier routing convention into something enforceable, or (3) target DigiSmith's own internal mechanical text-generation steps — places where the acting Claude session produces well-specified HTML output with no code-correctness risk at stake, since a human or a downstream skill reviews the result either way. Option 3 was chosen as the lowest-risk, most concretely valuable first slice, and doesn't touch the implementer/reviewer/fix-loop machinery that real code changes depend on at all.

Model tiering is understood to be a larger, multi-phase initiative — this document specs only its first slice, designated K.1 following the same sub-item convention the map already uses for other large items (I.1/I.2/I.3, L.1/L.2, E.1/E.2). Everything beyond K.1 — including the implementer-task offload and multi-provider directions raised and set aside during this brainstorm — is deliberately left undesigned; see Future Phases.

Architecture & Components

  • New profile field model_offload_provider in profiles/*.yml — a string naming the provider (chutes for now), absent/omitted meaning the feature is off. Structured as a single named value, not a list, since only one provider is implemented; adding a second provider later means adding its implementation, not redesigning the config. Only the digismith profile sets it initially — other profiles stay off until this is proven out.
  • New shared script scripts/model-offload.py at the repo root. Takes a prompt (and a target-format hint) as input; reads the active profile's model_offload_provider; reads the Chutes API key from the credential store the chutes-ai skill already manages (~/.chutes/config — no new secret storage); calls POST https://llm.chutes.ai/v1/chat/completions with a fixed cheap-fast model suited to formatting/drafting (e.g. google/gemma-4-31B-turbo-TEE, not a reasoning model); validates the response is non-empty and roughly matches the expected shape; prints either the generated content or a clear failure marker. One script, one credential path, one validation/fallback rule, reused by both call sites below (and any future one).
  • Two call sites, both existing DigiSmith skills modified to use the script for one specific step each:
    enforcer · map item Q

    Step 2 rewrap

    When brainstorming's output lands in the wrong place/format, enforcer rewraps it into the HTML shell. This rewrap becomes the offloaded call.

    report-implementation · map item N

    Step 3 HTML render

    Rendering report.html from Step 2's already-derived placeholder values (summary paragraph, per-task rows, final-review rows, delivered cards, commit list) into the fixed template becomes the offloaded call — not Step 2's own derivation, which stays mechanical/deterministic and runs in-session either way.

Profile Schema Change

Adds one optional field to the existing profile shape (see profiles/digismith.yml today: name, standards, ticket, ephemeral, reporting, publish_artifact, logging):

model_offload_provider: chutes   # optional; absent = feature off

A missing field, or a value naming a provider the script doesn't implement, is treated identically to "feature off" — same disposition DigiSmith's other profile-driven gates already use for an absent or stale value.

Data Flow

  • enforcer's rewrap case: has the misplaced content brainstorming actually wrote, plus the target HTML shell. It builds a prompt ("wrap this body content into this exact shell, fill these placeholders") and pipes it to scripts/model-offload.py. On success, writes the returned HTML to .digismith/docs/<slug>/design.html. On failure, performs the rewrap itself, exactly as it does today.
  • report-implementation's Step 3 render: Step 2 has already mechanically derived every placeholder value (header fields, per-task rows, final-review rows, delivered cards, oldest-first commit list) — that derivation itself stays in-session, unchanged. Step 3 builds a prompt containing those derived values plus the fixed HTML template and pipes it to the same script. On success, writes report.html. On failure, renders the template in-session as today.
  • Both call sites report which path was taken ("generated via Chutes" vs. "generated in-session, offload unavailable/off") so the choice is visible after the fact, never silent either way.

Error Handling

  • Failure modes the script treats as "fail → let the caller fall back": no model_offload_provider in profile, no Chutes credentials found, network/timeout error, non-2xx response, empty or clearly truncated response.
  • No retries — one attempt, then fall back. This is a cost-saving optimization, not a critical path; retry complexity isn't worth it for a personal tool's nice-to-have.
  • Fallback is always silent-to-the-pipeline (never blocks) but never silent-to-the-user: the calling skill states plainly that it fell back and generated the content itself.

Testing

This hits a real external API, so verification is manual rather than automated: toggle model_offload_provider: chutes on this repo's own (digismith) profile, trigger both call sites for real, and confirm output quality. Separately verify the fallback path by temporarily pointing the script at a bad credential or URL and confirming both skills still complete, using in-session generation, with the fallback stated plainly. Consistent with this project's existing "no automated JS syntax validation, done manually" convention — there is no existing test harness for DigiSmith's own skills to extend, and this script has no internal logic complex enough to warrant one.

Future Phases (K.2+, Not Designed Here)

Raised during this brainstorm and deliberately left unscoped, each a candidate for its own future brainstorm once K.1 has proven the mechanism out:

  • Implementer-task offload. Offloading qualifying mechanical CODE subtasks within real subagent-driven-development plans — closer to the roadmap's original literal wording, but carries real code-quality risk and interacts with the existing review/fix-loop machinery. Considered and set aside for K.1 specifically because of that risk.
  • Multi-provider selection. A list/fallback-order mechanism across several third-party compute providers, each end-user- configurable, rather than the single named provider K.1 implements. Set aside until a second provider actually exists to design against.
  • A custom dispatch shim bypassing the Agent tool entirely for whole mechanical tasks (not just DigiSmith's own internal steps) — raised as an option during the feasibility discussion, explicitly flagged there as a much bigger scope (a new dependency class, not a skill tweak) likely deserving its own separate roadmap item rather than living under K at all.

Open Questions

  • Exact Chutes model choice for scripts/model-offload.py (google/gemma-4-31B-turbo-TEE proposed above as a reasonable default) is not pinned down by user decision — it's a swappable implementation detail the script can adjust if output quality disappoints, not a load-bearing design choice.
