Overview

G.3.1 is the content backbone of G.3, the ASD-STE100 (Simplified Technical English) writing standard. It adds three new content-only files to DigiSmith's existing standards/ library, indexed the same way every other standard already is. Nothing about digismith:inject-standards changes — it already knows how to find, suggest, and inject anything listed in standards/index.yml. G.3.1 supplies the content; wiring specific consumers (generate-comment, report-implementation) to proactively pull it in is G.3.2's job, deferred (see backlog/ste100-artifact-integration-g3-2.md).

The standard targets one specific kind of writing: prose DigiSmith generates for a reader other than Jack in the moment — PR descriptions, JIRA/Teams comments, report prose, and (per this design) DigiSmith's own SKILL.md authoring. It explicitly does not apply to code, code comments (G.1's territory), or live conversation with Jack.

Sources, decided earlier this session: danyuchn/asd-ste100-skill (MIT) is the content backbone, STE-flavored mode only — no Strict/agent-facing mode. AminBlg/SimpleEnglish (MIT) contributes the word-swap table (adopted whole) and the use-cases pattern guide (adapted). Both cloned to D:/Workspace/Library/ for reference. Toppa's output-style gist contributes only a packaging mechanism, deferred to G.3.4 — not part of this design.

Placement & file layout

Three new files under standards/global/, following G.1's existing one-topic-per-file convention (e.g. pr-descriptions.md, commit-style.md):

Core

ste100-writing.md

The rule content: structural rules, lexical rules (advisory), hedge-preservation, Scan Checklist, Boundaries.

Reference

ste100-word-swaps.md

Slop-word → plain-word substitution table, adopted whole from AminBlg (52 rows, unchanged).

Reference

ste100-use-cases.md

Per-genre writing patterns, adapted from AminBlg's 9-genre guide with DigiSmith-specific notes where a real consumer exists today.

A three-file split rather than one comprehensive file: the rules travel together as a unit and always apply, while the word-swap table (a lookup, not prose) and the use-cases guide (picked by genre, not read start-to-finish) are naturally separate references — consistent with how inject-standards already lets a caller pull in only what's relevant.

Core file: ste100-writing.md

Adapted from danyuchn's SKILL.md, STE-flavored only — no mode-picking, since Jack already decided Strict mode (agent-facing tool descriptions, inter-agent instructions) has no DigiSmith use case.

Kept, close to verbatim

SectionContent
Structural rulesActive voice, no phrasal verbs, one instruction per sentence, sentence-length caps (≤20-25 words), no semicolons, noun-cluster limit (≤3 words), no ellipsis, paragraph limits (≤6 sentences, one topic), lists for 3+ step sequences
Lexical rulesFramed explicitly as advisory / "direction of travel" — one word one meaning, verb not noun, domain terms defined once. Never claims verified dictionary compliance (DigiSmith doesn't have and won't redistribute ASD's actual ~900-word dictionary, same reasoning danyuchn's source already documents)
Hedge-preservation principleNonnegotiable. Never upgrade a hedge ("may have failed", "could be caused by") into a stated fact. A rewrite that removes a hedge is a different claim, not a simplification. This rule overrides AminBlg's own incident-report example (which drops a hedge for punchier prose) — where the two sources conflict, danyuchn's stricter position wins, per Jack's backbone choice
Scan ChecklistSynonym rotation, hedge stacking, nominalization, marketing adjectives, run-on sentences, soft phrasal verbs — repurposed here as a self-check to run before finalizing any drafted paragraph, not as a post-hoc rewrite pass
Boundaries (trimmed)Not for creative/marketing copy; never fabricate a certainty the source material didn't state; don't polish a hollow paragraph into looking substantive — if there's nothing to say, say that instead

Dropped

  • Modes section (Strict vs. STE-flavored) — this file simply is the STE-flavored ruleset; no mode question needed.
  • Process section (pick mode → read input → walk sentence-by-sentence → run linter) — this describes a rewrite-tool's own operating steps when invoked directly on existing text. G.3.1 is ambient guidance consulted while drafting new prose, not a rewrite pass, so this doesn't apply.
  • Output Format section (rewritten text alone, no preamble) — same reasoning; that's a rewrite-skill's response contract, not relevant to a standards file.

Word-swaps file

Adopted whole from AminBlg's references/word-swaps.md — all 52 rows (leverage→use, in order to→to, seamlessly→delete, robust/powerful→delete or give the measurable property, etc.), no changes. Already generic English with nothing aerospace-specific to strip and nothing DigiSmith-specific to add.

Growing this table further (e.g. from slop phrases observed in DigiSmith's own generated artifacts over time) is captured separately as backlog/ste100-word-swaps-expansion.md — out of scope for this initial ship.

Use-cases file

Adapted from AminBlg's references/use-cases.md. Per Jack's explicit call, keeps the full 9-genre spread rather than trimming to only what DigiSmith generates today — future consumers get pattern guidance ready and waiting rather than needing a second brainstorm later.

GenreDigiSmith fit
Error messages / CLI outputReal current home: @digismith/cli's own output
Commit messages & PR descriptionsCross-references G.1's existing commit-style.md / pr-descriptions.md rather than restating them — STE100 tightens the same surface for a second, compounding reason (reader clarity), doesn't compete with the existing rule
Instructions for AI agents (prompts / SKILL.md / AGENTS.md)Real current home: writing any DigiSmith SKILL.md is exactly this genre
Runbooks / SOPs, incident reports, API changelogs, support macros, translation prep, UI copyNo current DigiSmith consumer — kept close to AminBlg's original text as forward-looking reference, flagged inline as such so the content's purpose is clear

Index entries

Three new entries under global: in standards/index.yml, written so inject-standards' relevance-matching can distinguish these from G.1's code/commit standards:

global:
  ste100-writing:
    description: Writing style for AI-generated prose artifacts (PR descriptions, comments, reports, SKILL.md) — concise, unambiguous, hedge-preserving; not for code or live conversation
  ste100-word-swaps:
    description: Slop-word to plain-word substitution table for AI-generated prose
  ste100-use-cases:
    description: Per-genre writing patterns (errors, PR descriptions, changelogs, agent instructions, etc.) for applying the ASD-STE100 writing standard

Out of scope

  • Propagating this standard into consuming repos' own CLAUDE.md — G.3.3, deferred (backlog/ste100-consuming-repo-propagation-g3-3.md)
  • Portable output-style packaging and a mechanical linter — G.3.4, deferred (backlog/ste100-portable-packaging-g3-4.md)
  • Expanding the word-swaps table beyond AminBlg's original list — deferred (backlog/ste100-word-swaps-expansion.md)
  • Retroactively rewriting any existing DigiSmith prose (SKILL.md files, past PR descriptions) to comply — this design ships the standard, not a cleanup pass

Validation

No code changes — three markdown content files plus a YAML index update. Validation is: standards/index.yml still parses as valid YAML after the edit, the three new files exist at their stated paths, and digismith:inject-standards' existing Step 1 (read the index) picks up the new entries with no changes needed on its side.
