Vitest Worktree Contamination Fix

Problem

No vitest.config.ts exists at the repo root, so vitest run (via package.json's test script) uses its own default file discovery, which has no exclusion for nested worktree directories. Every worktree lives physically inside main's own working tree under .claude/worktrees/<name>/, so vitest globs straight into each one and runs its test files too, as if they belonged to main's own suite.

Confirmed live (2026-09-18, filed by another session): a completely unrelated worktree's failing test surfaced as a false failure while finishing an unrelated, already-correct change. Reconfirmed today (2026-09-19) with two different concurrent worktrees present: 1155 tests at the repo root vs. 385 in an isolated run — the same order of contamination, different worktrees, same root cause. Silent double-counting is the same bug's flip side: a sibling worktree's passing tests get counted as if they were part of main's own coverage, with no signal anything unusual happened.

Fix

Add vitest.config.ts at the repo root:

import { configDefaults, defineConfig } from 'vitest/config'

export default defineConfig({
  test: {
    exclude: [
      ...configDefaults.exclude,
      '**/.claude/worktrees/**',
      '**/.worktrees/**',
      '**/worktrees/**',
    ],
  },
})

Covers all three worktree-path conventions using-git-worktrees documents, not only the one currently in use (.claude/worktrees/) — the other two aren't exercised by any live worktree today, but the config should be correct for whichever convention gets used. No package.json change needed — vitest run picks up a root vitest.config.ts automatically.

Why configDefaults, not a bare array

Verified against Vitest's own current documentation: setting test.exclude directly to a plain array replaces the built-in default excludes (node_modules, dist, etc.) rather than extending them — exactly the pitfall the original finding flagged as a risk. The documented way to extend rather than replace is spreading configDefaults.exclude from vitest/config before adding new patterns, which is what the fix above does. (This differs from the CLI --exclude flag used to confirm the bug, which the same docs note is additive — a config-file array and a CLI flag do not behave the same way here.)

Scope

Repo-wide: this repo has a single package.json with one test script (vitest run) and no existing per-package test configs — one root vitest.config.ts covers everything. No nested packages/* config is needed or exists to reconcile.

Verification

Run pnpm test after adding the file, with at least one concurrent worktree present, and confirm the count matches an isolated run (currently ~385 tests) rather than the inflated count including worktree contents. No unit test applies to a config file itself; verification is this live before/after comparison.
