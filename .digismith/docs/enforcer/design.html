Problem & Goal

DigiSmith's unified docs convention says every feature's spec and plan live together at .digismith/docs/<feature-slug>/, with the spec authored in HTML. Nothing today actually tells superpowers:brainstorming or superpowers:writing-plans that this convention exists — they are third-party Superpowers skills with their own defaults (docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md, plain Markdown). This was a known open question in MEMORY.md ("design.html/plan.md have no enforcement mechanism") that went from hypothetical to actually blocking Jack on 2026-08-15: a real hand-off produced a plain Markdown spec in the wrong location.

Goal: a standing mechanism that makes any Superpowers skill DigiSmith calls honor DigiSmith's own conventions at the hand-off point — named Enforcer because the job is general (today: doc location and format; later: other convention gaps of the same shape, e.g. the already-logged backlog/review-time-standards-injection-gap.md item), even though this first slice implements only the doc-location/format rule.

Non-Goals

  • Scoped to doc-location/format only. Explicitly deferred: folding in the review-time standards-injection gap, or any other future enforcement rule. Enforcer is architected so a second rule can be added later without re-architecting, but only one rule ships now.
  • Not modifying Superpowers' own skill files. Per DigiSmith's philosophy (augment, never replace), Enforcer never patches superpowers:brainstorming/superpowers:writing-plans themselves. It works entirely by (a) what it tells them at invocation time and (b) what it checks/fixes after they finish — both hooks those skills already expose ("user preferences override the default").
  • Not a generic interception framework. Enforcer does not wrap every Superpowers skill DigiSmith might ever call — only the two hand-offs this feature is scoped to (brainstorming, writing-plans).

Architecture

A new standalone skill, digismith:enforcer — not a new scenario on inject-standards, which governs coding-standard content for implementers, a different concern from artifact location/format for doc-producing skills. Same detection pattern inject-standards and using-digismith already use: current working directory is DigiSmith's own repo (.claude-plugin/plugin.json name "digismith"), or a consumer repo with .digismith/profile present.

Job 1 — Advisory

Before the hand-off

Tell brainstorming explicitly: write the spec to .digismith/docs/<slug>/design.html, in HTML, matching the existing house template (see HTML Template Requirement). Tell writing-plans explicitly: write the plan to .digismith/docs/<slug>/plan.md — same Markdown format it already defaults to, just relocated.

Job 2 — Verified

After the hand-off

Check the file actually landed at the expected path in the expected format. If it landed at the wrong path (today's actual failure mode), move/rewrap it into place — the content was just produced in this same session, so re-packaging it is low-risk, not a blind automated transform of opaque output. Report what it corrected; never silently no-op on a mismatch.

Advisory alone was already tried, implicitly, and failed silently — nobody told brainstorming the override existed at all. Verified alone would catch the failure after the fact but do nothing to prevent it recurring on every call. Both together: the advisory step minimizes how often the verify step has to intervene, and the verify step is the actual guarantee — a mismatch gets caught and fixed in the same run, not discovered later as a stray file no one notices.

Convention amendment, not a third job. Once Verified confirms an HTML artifact is correctly placed, it gets published via the Artifact tool and the link is reported back — a local .html file nobody can comfortably open is still a failure, even when it's in the right place. This isn't Enforcer-specific behavior bolted on as a "Job 3" — it's an amendment to the unified docs convention itself (MEMORY.md's Conventions section gains a clause: any HTML doc DigiSmith writes gets published for readability), so it applies wherever it's suitable, not only where Enforcer happens to be watching. Concretely, two touchpoints ship under this same change: Enforcer performs it for design.html as the tail end of its Verified step, and report-implementation (map item N) gets a matching one-line addition to publish report.html the same way after it writes it. plan.md and ticket.md are unaffected — they're working documents meant to be read as files/parsed by tooling, not presented.

Trigger Wiring

Two paths reach brainstorming/writing-plans, so Enforcer needs two triggers:

  • Explicit call. using-digismith Step 3 gets a line: invoke digismith:enforcer immediately before superpowers:brainstorming — the same explicit-call pattern subagent-driven-development already uses for digismith:report-implementation once its final review passes.
  • Implicit backstop. digismith:enforcer's own skill description mirrors inject-standards' Scenario 3 trigger wording ("running brainstorming/writing-plans") so it self-triggers even when brainstorming is invoked directly for DigiSmith's own self-development, with no ticket and no using-digismith in the loop at all — exactly the path that produced this feature's own design spec, and the gap a Step-3-only fix would have missed entirely.

HTML Template Requirement

The advisory instruction Enforcer gives brainstorming doesn't just say "write HTML" — it points at the existing house style so new specs stay visually consistent with old ones: the CSS-variable light/dark palette, the nav.toc table of contents, the .card grid for parallel options, the .callout block, the standard section set (Problem & Goal, Non-Goals, Architecture, Error Handling & Verification, Relationship to Other Map Items). This document is itself built from that template, reusing the same CSS block verbatim from unified-docs-convention/design.html — Enforcer's own advisory instruction to brainstorming should tell it to do the same: copy the CSS block from the most recent existing design.html rather than inventing new styling per feature.

Error Handling & Verification

  • Wrong location, right format (the failure this feature fixes): Enforcer moves the file into .digismith/docs/<slug>/ under its correct role name (design.html / plan.md) and reports the move.
  • Right location, wrong format (e.g. Markdown written where HTML was expected): Enforcer rewraps the content into the house HTML template in place — same re-packaging logic as the location fix, just also converting structure.
  • Nothing found at either the expected or a plausible default location: stop and flag it rather than guessing — this means the upstream skill produced no artifact at all, a different failure than a misplaced one.
  • No automated test suite, consistent with every DigiSmith skill — verification is dogfooding Enforcer against this very feature's own build (its plan and eventual implementation report must land at .digismith/docs/enforcer/ in the correct formats) plus a repo-wide grep for stray docs/superpowers/specs/ or docs/superpowers/plans/ paths after rollout — zero hits expected going forward.

Relationship to Other Map Items

  • E (the spine) / using-digismith — Step 3 gains one explicit call to digismith:enforcer; nothing else about the hand-off changes.
  • G (standards injection) / inject-standards — sibling mechanism, not a dependency. Both fire around the same "brainstorming/planning" moment but inject different things (coding standards vs. doc location/format) and stay architecturally separate.
  • N (implementation reporting) / report-implementation — gets the one-line publish-as-artifact addition described above for report.html, under the same convention amendment as design.html; otherwise unchanged, and it already writes to the same .digismith/docs/<slug>/ convention Enforcer is protecting for the two artifacts upstream of it.
  • Unified docs convention (no map letter) — Enforcer is this convention's missing enforcement mechanism, called out as an explicit open question when that feature shipped.

Open Questions

  • Second enforcement rule's shape is undecided. The review-time standards-injection gap is thematically identical (a Superpowers hand-off DigiSmith's conventions don't reach) but explicitly out of scope for this slice. Decide whether it becomes Enforcer's second rule or its own separate mechanism when it's actually picked up, not preemptively.
  • Rewrap-on-format-mismatch fidelity is unverified. The location-fix case (move a file) is mechanical and safe. The format-fix case (Markdown → house-template HTML) asks the same agent to restructure its own just-written content into the template — should work in the common case since the content is still in context, but hasn't been exercised against a real mismatch yet. Watch for this during Enforcer's own dogfooding.
