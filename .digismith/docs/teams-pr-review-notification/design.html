Overview

A new skill, digismith:teams-pr-review-notification, that generates a ready-to-paste Microsoft Teams message asking reviewers to look at one or more open pull requests — replacing the ad-hoc manual drafting Jack currently does for this every time. DigiSmith never connects to Teams itself: it only produces the message text, in Jack's own established voice and format, for him to paste in himself.

Why I.4, Not Y

This was initially considered as a new Y-lineage lifecycle hook (parallel to Y.1's post-finish), since it could fire right after a PR opens. That's wrong: Y's hooks so far are internal DigiSmith self-development mechanics (version bump, plugin cache reinstall) — genuinely technical, gated to DigiSmith's own repo. This is a reporting/communication concern instead, which is exactly what map item I was broadened to cover on 2026-09-08 (renamed from "QA handoff" to plain "Reporting", explicitly naming other reporting channels as plausible future sub-items). The trigger timing can still mirror Y.1's shape conceptually, but the capability itself belongs to I.

Mechanism: Text Generation Only

Two real delivery mechanisms were considered and ruled out during brainstorming:

Ruled out

Microsoft Graph API (REST client)

Would mirror packages/jira-client's real-API precedent, but sending a channel message via application permissions requires the ChannelMessage.Send application permission, which needs tenant admin consent — Jack's Teams tenant is his organization's, not one he administers. Blocked regardless of preference.

Ruled out

Browser automation (Claude in Chrome)

Would use Jack's own logged-in session with no admin approval needed, but requires several fragile UI steps (compose box, @-mention autocomplete dropdown, send) that break when Teams' UI changes, and only works attended with the browser pane open. Made moot once text-generation-only was chosen — there is no send step to automate at all.

Decision: DigiSmith generates the message text only. Nothing is sent, posted, or connected to Teams by DigiSmith at any point — Jack copies the generated text and pastes it into Teams himself, doing the real @-mention selection in Teams' own UI at that point. This eliminates every failure mode above: no credentials, no admin approval, no live API, no browser dependency.

Trigger Points

Two invocation paths, covering both a single PR and a multi-repo epic:

PathWhenHow PR links are gathered
Auto-offered Right after finishing-a-development-branch's Option 2 (Push and Create PR) reports the new PR's URL — a lightweight yes/no ask ("Draft a Teams review-request message for this PR?"), same low-friction pattern as Option 1's existing "remember as default?" follow-up. Already known from the just-created PR: title, URL, current ticket key if any.
On-demand Jack asks directly ("draft a Teams review request for these PRs"), independent of just having created a PR — covers both a single PR and the multi-repo epic case (e.g. the real EMKT-756 example: one ticket, four market-repo PRs). Resolve the current branch's open PR via the forge CLI (e.g. gh pr view) when only one is meant; for multiple repos/markets, ask Jack directly for the ticket key/title and each PR link — I.2 (multi-repo distribution) doesn't exist yet to automate this gathering, so it's a direct ask for now, revisited once I.2 ships.

Reviewer Resolution

Reviewer names are resolved via digismith:preferences (H.1's saved-default mechanism), not a new profile field as the original backlog note guessed (map item O) — a per-repo saved default that changes over time and gets overridden in the moment is exactly the shape H already established ("saved choice, asked once, reusable"), not a structural on/off toggle like ticket/ephemeral.

  • First invocation in a repo with nothing saved yet: prompt via AskUserQuestion for the reviewer name(s) to tag, offer to save as the default via digismith:preferences' set operation — proceed with just this run's answer if declined, never nag again on a decline.
  • A saved default can always be overridden in the moment for a specific message.

Message Template

One unified template for both the single-PR and multi-repo-epic cases — the only difference is how many link lines it has. Matches Jack's own real, existing style exactly (verified against a real message he shared), deliberately plain rather than the emoji-heavy convention jira-progress-write-back (I.1) uses for JIRA — Teams and JIRA warrant different voices, and matching Jack's actual voice here is the point, not a generic DigiSmith-authored tone (same lesson already flagged in the backlog's tentative map item T, content-voice). 

Hello 500 ae (<Reviewer1>, <Reviewer2>, ...) -- <ask, e.g. "Phụ review dùm các PRs này cho <feature/epic>">

<TICKET-KEY>: <Ticket title>

🔗 <market1> PR: <link>
🔗 <market2> PR: <link>
  • Hello 500 ae is a fixed, literal greeting phrase — reused verbatim every time, not derived or computed.
  • The reviewer list is comma-separated inside parentheses, resolved per Reviewer Resolution above.
  • The ask line after -- is short, free-text, and may be in Vietnamese (as in Jack's real usage) or English — generated to match whatever Jack says when asked, never auto-translated.
  • Ticket key/title line is omitted entirely when there's no real ticket context (e.g. an ad-hoc PR with no tracked key).
  • Each link line is 🔗 <market> PR: <link> — the market label (e.g. the repo's directory-name-derived label, same convention I.1 already uses: shopify-template-<code> → <code> uppercased, otherwise the repo directory name as-is) makes each link scannable without needing to read the raw URL.

Data Flow

  1. Determine invocation path (auto-offered vs. on-demand) per Trigger Points.
  2. Gather PR link(s), ticket key/title if any, per the path's own resolution above.
  3. Resolve reviewer name(s) via digismith:preferences, prompting on first use per repo.
  4. Ask Jack for the short free-text "ask" line (what to say after --) — never fabricate one.
  5. Render the template, present it as plain text ready to copy.
  6. Done. No write, no send, no state persisted beyond the reviewer default.

Error Handling

  • On-demand, no PR found for the current branch (forge CLI returns nothing) → ask directly for the PR link(s) rather than guessing.
  • No reviewer default saved, and Jack declines to save one at first use → proceed with just this run's typed-in answer; ask again next time rather than treating the decline as "never ask."
  • No ticket key/context available → omit the ticket line entirely rather than inventing a placeholder.

Testing

Nothing here calls a live API, drives a browser, or writes to any external system — the entire skill is deterministic text templating plus a couple of `AskUserQuestion` prompts. Testing is manual verification that generated messages match the template exactly across both invocation paths (single PR, multi-repo epic, missing-ticket case), the same verification approach as any other DigiSmith SKILL.md — no automated test suite is warranted for markdown-instruction content with no executable logic of its own.

Out of Scope

  • Any live Teams connection — Graph API and browser automation were both considered and explicitly ruled out; see Mechanism.
  • Automating multi-repo PR discovery — on-demand multi-repo gathering is a direct ask to Jack for now; automatic gathering across market repos belongs to I.2 (multi-repo distribution) once that ships, not duplicated here.
  • Message templates for channels other than Teams (Slack, email) — named as plausible future I-lineage sub-items when map item I was broadened, not built here.
  • Editing or updating a previously-sent message — unlike I.1's JIRA comment update logic, there is nothing to update: DigiSmith never sends anything, so there is no message to find and edit later.
