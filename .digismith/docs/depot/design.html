Overview

A small utility skill that maintains a local, minimal, refreshable clone of DigiSmith's shared packages/ code at a fixed machine-wide location — ~/.digismith/repo — so any consumer repo can run a shared package (starting with jira-client) without a local DigiSmith development checkout, and without ever needing to know or pass around where one happens to live on a given machine.

Discovered as a prerequisite while designing the Jira REST migration, but deliberately generic: it knows nothing about Jira. Any future package added under packages/ is available through the same clone automatically, with no changes needed here.

Two Operations

Ensure

Idempotent, clone-if-missing

Provisions ~/.digismith/repo only if it doesn't already exist; a no-op otherwise. Called automatically by bootstrap/adopt at the start of any ticket's work.

Refresh

Explicit, on demand

Fetches and hard-resets to origin/main. Never runs automatically — invoked conversationally, any time ("update my DigiSmith clone"), mirroring the update-on-request pattern the company's own developer-toolbox already uses.

Location & Scope

A machine already carries at least two other copies of DigiSmith by the time this runs: Jack's own active development checkout, and Claude Code's own plugin-install cache (explicitly called out as a stale, version-locked snapshot in jira-progress-write-back's own Step 0). A third full clone would triple up on content this skill has no reason to duplicate — backlog/, standards/, MEMORY.md, every skill's own source. The runtime clone only ever needs packages/.

A blobless, sparse, cone-mode clone keeps exactly that scope — content outside packages/ is never even downloaded, not just hidden from the working tree: 

# ensure (clone-if-missing)
git clone --filter=blob:none --no-checkout --sparse \
  git@github.com:Jazurite/DigiSmith.git ~/.digismith/repo
git -C ~/.digismith/repo sparse-checkout set packages
git -C ~/.digismith/repo checkout main

# refresh
git -C ~/.digismith/repo fetch --all --prune --tags -q
git -C ~/.digismith/repo checkout main
git -C ~/.digismith/repo reset --hard origin/main

Same SSH remote (git@github.com:Jazurite/DigiSmith.git) as Jack's own development checkout — no separate auth path to set up. The sparse-checkout pattern is set once at clone time and persists across every subsequent reset --hard; refresh never needs to reapply it.

Relationship to Credentials

~/.digismith/.env lives alongside ~/.digismith/repo — same parent folder, for tidiness — but Depot never creates, reads, or manages it. That file is a Jira-specific concern owned entirely by the Jira client migration, including its own first-use bootstrap prompt. Keeping this boundary strict means Depot stays reusable by any future package that has nothing to do with Jira and needs no credentials of its own.

Invocation

  • bootstrap, new Step 0.5 — right after Step 0 resolves .digismith/profile, invoke Depot's ensure operation. Unlike .digismith/profile/telemetry-marker, this needs no per-worktree copy step (2.6/2.7-style) — the clone lives outside every repo and worktree, shared machine-wide, so it only ever needs provisioning once per machine, not once per ticket.
  • adopt — reuses Step 0.5 by reference, the same way it already reuses Step 0/2.6 for the profile, per MEMORY.md's existing convention. No second implementation.
  • Standalone — invoked directly, any time, for a refresh (e.g. "update my DigiSmith clone" after pushing a change to a shared package).

Error Handling

CaseDisposition
No SSH access / key not authorized for the repo Report the actual git error plainly. No retry, no fallback to an unauthenticated clone attempt.
Network unreachable / GitHub unreachable Report the actual git error plainly.
ensure fails during bootstrap/adopt Step 0.5 Fail the whole ticket-start flow. Jira write-back (and any other package-dependent stage) would be broken for this ticket regardless, so surfacing it at ticket-start beats a confusing failure later, deep inside a consuming skill.
refresh invoked standalone and it fails Same disposition — report the error, leave the existing clone exactly as it was (a failed fetch never reaches the reset --hard step).

Out of Scope

  • Credential management — entirely the Jira client migration's concern; see Relationship to Credentials.
  • Auto-refresh on every invocation — deliberately not done. Matches the company developer-toolbox's own precedent (clone once, refresh only on explicit request) and avoids a network round-trip on every package call.
  • Per-package logic — Depot has no awareness of what's inside packages/; it clones the whole directory as one sparse scope. A consumer picks its own package's path underneath (e.g. packages/jira-client/).
  • Publishing to an npm registry — considered and rejected for the Jira client specifically (see that spec's Architecture section); Depot is the chosen alternative to a real package-registry publish step.
