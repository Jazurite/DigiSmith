Background & Trigger

Triggered by a real-world gap: upstream superpowers:finishing-a-development-branch's Option 1 ("Merge Locally") never pushes the base branch to origin — confirmed by reading its SKILL.md directly (its own Quick Reference table marks Push: - for that option). This is exactly what let DigiSmith's own main silently accumulate 65 unpushed commits before anyone noticed (logged as backlog/no-push-after-local-merge.md).

DigiSmith already has a no-fork interception pattern for narrow behavior changes — subagent-driven-always (map item H) and enforcer (map item Q) both redirect behavior at a specific decision point inside an upstream skill's flow without duplicating any of its content. That pattern could likely fix the push gap on its own.

But the actual ask goes further: Jack wants deeper, ongoing divergence — not just patching isolated gaps, but eventually replacing core Superpowers primitives outright (starting candidate: finishing-a-development-branch) and assimilating other agent methodologies (e.g. Hermes agent, spec-driven development) over time. That scale of change needs DigiSmith to actually own copies of the primitives it intends to evolve, not just intercept them.

Scope: R.1 vs. the Rest of the Initiative

"Replace Superpowers' core primitives outright" is not one project — it's at least six (one per primitive DigiSmith currently calls into: brainstorming, writing-plans, subagent-driven-development, finishing-a-development-branch, executing-plans, requesting-code-review), each with its own risk profile and worth its own brainstorm. subagent-driven-development alone is load-bearing for nearly everything DigiSmith does today (map item H makes it the default execution path for every plan) — redesigning it carelessly would be far more disruptive than redesigning, say, finishing-a-development-branch.

This document specs only the first slice, designated R.1 following the map's existing sub-item convention (I.1/I.2/I.3, K.1/K.2+, L.1/L.2, E.1/E.2): a pure, mechanical, verbatim clone of every Superpowers skill into DigiSmith's own repo. No primitive is redesigned or replaced in this slice — cloning only establishes the baseline DigiSmith will own and evolve from. Deciding which primitive to actually replace, and how, is deliberately deferred to R.2+ (see Future Phases); finishing-a-development-branch is the leading candidate given the confirmed, scoped gap that triggered this whole initiative, but that choice is not locked in by this document.

Relationship to Philosophy #2

MEMORY.md's philosophy #2 currently reads: "It augments, never replaces... Duplicating a Superpowers capability is a bug, not a feature." Map item R is a deliberate, scoped exception to that rule, not a quiet violation of it — the principle stays the default for every DigiSmith skill that isn't map item R; R is called out by name as the one place ownership (not augmentation) is the intended relationship. This document's own build includes editing philosophy #2 in MEMORY.md to say so explicitly, and adding map item R itself to the map and build-order tables.

Architecture & Components

Correction made during planning (2026-08-20): this section originally specced a nested skills/vendored/<name>/ subfolder. Verified against Claude Code's own skill-discovery docs: plugin skills must be direct children of skills/ — no recursive subdirectory scanning — and the invocable name is taken from the SKILL.md frontmatter's name: field, not the folder name. A verbatim clone keeps that frontmatter untouched (still name: brainstorming, etc.), so the folder name is free to differ without changing the invocable skill name at all. The architecture below reflects the corrected, verified structure.
  • Flat, name-prefixed skill folders: skills/vendored-<name>/ — direct children of skills/, as required, but the vendored- prefix keeps them visually grouped and distinguishable from DigiSmith's own hand-authored skills/<name>/ folders (frozen, upstream-sourced, no organic edits expected until activated). Because the frontmatter name: field is untouched by a verbatim clone, each still becomes addressable as the clean digismith:<name> — e.g. skills/vendored-brainstorming/SKILL.md (frontmatter name: brainstorming) resolves to digismith:brainstorming, not digismith:vendored-brainstorming. This also means a future R.2+ activation never needs to touch the name: field — only content and DigiSmith's own call sites change.
  • All 14 Superpowers skills, cloned verbatim: brainstorming, dispatching-parallel-agents, executing-plans, finishing-a-development-branch, receiving-code-review, requesting-code-review, subagent-driven-development, systematic-debugging, test-driven-development, using-git-worktrees, using-superpowers, verification-before-completion, writing-plans, writing-skills. Every file (SKILL.md plus any supporting scripts/prompts each skill folder contains, e.g. subagent-driven-development's scripts/ and prompt files) is copied byte-for-byte — zero content edits in this slice.
  • New top-level vendored/ folder (repo root, sibling to skills/, not inside it) holds metadata only — kept out of skills/ so nothing there is ever mistaken for a skill folder during discovery:
    vendored/LICENSE

    A single copy of Superpowers' MIT license (Jesse Vincent, 2025), satisfying the license's own requirement that the notice travel with copies. One copy covers all 14 clones; no per-skill license files.

    vendored/PROVENANCE.md

    Records the source plugin version/commit and clone date, giving any future "diverge this one" decision a clear baseline to diff against. One file for the whole batch, not per-skill.

Data Flow

This is a one-time, one-directional copy — there is no ongoing data flow to design. The clone runs once: read each of the 14 skill directories from the installed Superpowers plugin cache, write an identical copy under skills/vendored-<name>/, write vendored/LICENSE and vendored/PROVENANCE.md, commit.

No sync tooling. This is explicitly a snapshot, not a mirror — consistent with keeping DigiSmith simple as a personal tool (no multi-source merge/sync machinery). Future upstream Superpowers improvements are pulled in manually, if and when noticed and wanted; nothing automated tracks or diffs against upstream after this initial clone.

DigiSmith's existing internal call sites — every place a DigiSmith skill currently invokes superpowers:<name> (subagent-driven-always, enforcer, using-digismith, bootstrap, adopt, etc.) — are left unchanged in this slice. They keep calling the live upstream skills exactly as today. The vendored clones sit dormant until a future R.2+ brainstorm activates one.

Error Handling & Known Limitations

  • Internal cross-references are not rewritten. Several vendored skills reference each other by name — e.g. subagent-driven-development's file literally says "Use superpowers:finishing-a-development-branch." A verbatim clone leaves those references untouched, so a vendored skill can still silently chain back to a live upstream skill when it calls out to another one. Rewriting those references is a content change, and is explicitly out of scope for a byte-identical clone — it gets resolved skill-by-skill, at each one's own future activation (R.2+), not here. This is a known, accepted limitation of R.1, not an oversight: until a given vendored skill is activated, it should not be treated as "fully owned."
  • Clone integrity. If a file fails to copy or comes back non-identical to its source, that's a hard stop for this slice — fix and re-copy before considering R.1 done. There's no partial-success mode; either all 14 skills are cloned cleanly or the slice isn't finished.

Testing / Verification

  • Diff every file under skills/vendored-<name>/ against its source in the installed Superpowers plugin cache — must be byte-identical.
  • Confirm vendored/LICENSE and vendored/PROVENANCE.md are present and correctly filled in (source version/commit, clone date).
  • Confirm at least two sampled vendored skills (e.g. digismith:brainstorming, digismith:finishing-a-development-branch) are recognized as invocable skills in a fresh session's skill listing.
  • Confirm no existing DigiSmith skill file was modified as a side effect — this slice is additive only.

Future Phases (R.2+, Not Designed Here)

Deliberately left unscoped, each a candidate for its own future brainstorm once R.1 has landed:

  • Activate finishing-a-development-branch. The leading candidate, given the confirmed Option-1-no-push gap that triggered this whole initiative. "Activating" means: edit the vendored copy to add the missing push step (and whatever else diverges), update DigiSmith's own internal call sites that reference superpowers:finishing-a-development-branch to reference digismith:finishing-a-development-branch instead, and record the switch in MEMORY.md.
  • Activate other primitives — subagent-driven-development, brainstorming, writing-plans, executing-plans, requesting-code-review — one at a time, each its own brainstorm, in whatever order future need dictates.
  • Assimilating outside methodologies (Hermes agent, spec-driven development, etc.) into activated primitives, or as entirely new DigiSmith skills alongside them. Not scoped at all yet — raised as motivation for this initiative, not designed here.
  • Cross-reference cleanup across vendored skills as each one activates (see Error Handling) — handled per-skill during its own activation, not as a standalone project.

Open Questions

  • None blocking R.1. The order in which R.2+ primitives get activated, and how outside methodologies actually get assimilated, are open by design — deferred to their own future brainstorms rather than decided speculatively here.
