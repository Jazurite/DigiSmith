Overview

packages/jira-client/src/cli.ts has a get-attachment subcommand for downloading an attachment, but nothing for uploading one — the missing half needed to get a screenshot into a Jira comment at all. Found live during EMKT-711 (shopify-hub, 2026-09-18); filed as backlog/jira-client-attachment-upload-subcommand.md and backlog/jira-media-platform-inline-images.md. Originally scoped together with I.5's Windows entry-point-guard fix, then split out (different domain: new capability vs. bugfix) once I.5's own scope was confirmed — I.5 shipped 2026-09-18.

This is deliberately narrow: it adds the upload capability to packages/jira-client only. It does not touch the Progress Update template's Screenshots/Videos section (that stays Q.1's deferred work, per Jack's own split: "the attachment-upload capability belongs to I... the template-section change stays under Q.1, deferred until real attachments exist") and does not wire anything into generate-comment or jira-progress-write-back.

Architecture

One new function in client.ts, one new CLI subcommand wrapping it — same shape every existing operation in this file already follows.

Real inline image embedding needs a Jira Media Platform UUID, a completely separate ID namespace from classic attachments, obtained (per confirmed research) via an undocumented technique: upload via the classic endpoint, then read the Location header of a manual-redirect request to that attachment's content URL — the UUID appears in api.media.atlassian.com/file/{UUID}/binary. This is not an officially documented flow (Atlassian's own bug tracker confirms inline images via REST are broken/unsupported for non-Forge integrations — JRACLOUD-97869), and community reports say it has gotten less reliable over time. Per the earlier brainstorm's explicit decision: build it with a graceful fallback, never a hard requirement.

Components

packages/jira-client/src/client.ts (modified)

export interface AttachmentUploadResult {
  id: string;
  filename: string;
  contentUrl: string;
  mediaId?: string;
}

export async function uploadAttachment(
  key: string,
  filePath: string,
  creds: Credentials
): Promise<AttachmentUploadResult>
  • Reads the file via readFileSync, wraps it in a native Blob/ FormData (no library — Node ≥18 globals), POSTs to /issue/{key}/attachments with header X-Atlassian-Token: no-check.
  • Jira's classic endpoint returns an array of attachment objects even for a single file — takes the first.
  • contentUrl is built manually as ${baseUrl(creds)}/attachment/content/${id}, the same pattern getAttachmentContent already uses — never trusts whatever URL shape Jira's own response includes.
  • Then attempts the UUID extraction via a small internal (non-exported) helper, tryGetMediaPlatformId(attachmentId, creds): a single fetch with redirect: "manual" against /attachment/content/{id}, reads the Location header, regexes out the UUID (api.media.atlassian.com/file/([^/]+)/binary). Any miss — non-3xx response, missing header, non-matching URL shape — returns undefined silently; never throws. Mirrors the existing fetchFollowingRedirectsSameOriginAuthOnly helper's manual-redirect pattern but stops at reading the header instead of following it.
  • The upload itself is not best-effort — a failed POST throws via the existing jiraFetch helper, same as every other function here. Only the UUID lookup is allowed to fail quietly.

packages/jira-client/src/cli.ts (modified)

case "upload-attachment": {
  requireArgs(args, ["key", "file"]);
  const creds = checkCredentials();
  const result = await uploadAttachment(args.key, args.file, creds);
  console.log(JSON.stringify(result));
  break;
}

Same shape as every existing subcommand — no new patterns introduced.

Error Handling

CaseDisposition
Upload POST fails (bad key, network error, auth)Throws via jiraFetch, same as every other write op — reported plainly by the CLI's existing catch block
File doesn't exist at --file pathreadFileSync throws a real ENOENT — no special handling needed, the CLI's catch already reports it
Media UUID lookup gets a non-3xx response, missing Location, or a Location that doesn't match the expected URL shapemediaId simply absent from the result — never thrown, never logged as an error; this is the confirmed-undocumented technique's expected failure mode

Testing

New describe("uploadAttachment", ...) block in client.test.ts, mocking fetch per test (matching every existing block's style):

  • Successful upload + successful UUID match: asserts the POST's URL/headers/multipart body shape, and that a mocked redirect: manual response with a matching Location header produces the right mediaId.
  • Successful upload, UUID lookup returns a non-matching Location (e.g. a different host) → mediaId absent, no throw.
  • Successful upload, UUID lookup gets a non-redirect (200) response → mediaId absent, no throw.
  • Upload itself fails (non-ok response) → throws, matching every other write function's existing failure test.

No CLI-level subprocess test needed here — I.5 already added that regression coverage for the entry guard itself; this subcommand just needs to exist and delegate correctly, which the client.ts tests already cover at the level that matters.

Out of Scope

  • Getting real image bytes onto disk from a screenshot Jack pastes in chat — that's the calling skill's job, whenever this gets wired up, not jira-client's concern.
  • The Progress Update template's Screenshots/Videos section — Q.1's deferred work.
  • Wiring uploadAttachment into generate-comment or jira-progress-write-back — a future consumer-integration task, not this one.
  • Actually constructing or posting a comment containing the mediaSingle/media ADF node — this item only discovers the UUID; using it is the future consumer's job.
