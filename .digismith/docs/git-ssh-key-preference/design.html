Per-Repo SSH Key Preference

Problem

Jack works across repos that need different SSH identities (e.g. personal projects vs. a different GitHub account/organization). Nothing today records which key a given repo expects, so a DigiSmith session running a git command on Jack's behalf (push, fetch, clone) has no way to know which key applies before trying — and picking the wrong one either fails outright or, worse, could succeed against the wrong remote identity.

Surfaced live 2026-09-19 while moving a project into the devkit monorepo — in that specific incident SSH already happened to work correctly and only the unrelated gh CLI account was mismatched, but the underlying gap (no recorded per-repo SSH identity) is real and worth closing proactively rather than only after it actually causes a failed push. See backlog/per-repo-git-credential-preference-h2.md for the original incident.

Storage

No new store. This reuses H's existing per-repo settings mechanism exactly as-is: one key, ssh_key, in that repo's own .digismith/preferences.yml, value the absolute path to an SSH private key file: 

# DigiSmith-managed. Settings decided through live interaction, not hand-authored.
ssh_key: C:\Users\jazurite\.ssh\id_ed25519_personal

Read and written exclusively through digismith:preferences' existing get/set operations — nothing here parses or writes .digismith/preferences.yml directly. No new skill, no new global file, no named registry: the same raw path is stored once per repo and reused for that repo only. Per-repo scope only, matching the grain H's own design already settled on for finish_option — no per-subfolder granularity even for a monorepo, since the actual need is "one key per remote," not per-package.

Trigger: bootstrap/adopt

Checked at the same moment digismith:bootstrap/digismith:adopt already resolve .digismith/profile on first use in a repo. If this repo's ssh_key preference is unset, ask once, plainly:

"Which SSH key file should I use on this computer for this repo?"

Store the answer verbatim via digismith:preferences' set operation. If it's already set, skip the question entirely — no re-asking, no "remember this?" follow-up needed (unlike H.1's menu-skip case, there's no competing "fresh answer" to distinguish from a reused one; this is a plain first-use-only prompt). Because .digismith/preferences.yml already propagates into freshly created worktrees via H's own bootstrap/adopt copy step, this preference carries forward automatically — no new propagation code needed here.

Usage: scoped per-invocation, no persistent config writes

DigiSmith never writes to ~/.gitconfig, ~/.ssh/config, or any file outside the repo's own .digismith/ folder. This was explicitly decided against a materializing-real-git-config approach considered earlier in this brainstorm — too invasive for what the actual problem needs.

Instead, whenever a DigiSmith skill runs a git command that needs network access on Jack's behalf within that repo (push, fetch, clone, pull) — finishing-a-development-branch being the main caller today — it resolves this repo's ssh_key preference first and, if set, scopes the key to that one command only: 

GIT_SSH_COMMAND="ssh -i <ssh_key>" git push origin <branch>

If unset (a repo where the question was never asked or was declined — see Error Handling), the command runs exactly as it does today, with no GIT_SSH_COMMAND override — identical to current behavior, so this is purely additive.

This covers the commands DigiSmith runs against the repo currently being worked in. digismith:depot's own clone of a fixed, separate DigiSmith remote is out of scope — it targets a different repo entirely, not the one this preference is set for.

Error Handling

  • Preference unset — not an error. Run the git command with no GIT_SSH_COMMAND override, exactly as today.
  • Stored key file doesn't exist on this machine (e.g. the same .digismith/preferences.yml checked out on a second machine with different key paths) — warn plainly before running the command ("This repo's saved SSH key, <path>, doesn't exist on this machine") and ask whether to proceed without the override, or supply a different path for this machine. Never silently fall through to a wrong or missing key without saying so.
  • File present but malformed preferences.yml — already covered by digismith:preferences' own existing contract: reads as unset, never crashes the caller.

Testing

The bootstrap/adopt prompt-and-store logic and the git-command scoping are skill prose with no new code to unit test — digismith:preferences' own get/set already have real-fixture tests from H's own build, and this feature only calls those existing, already-tested operations. Verification here is a careful manual read-through plus a real end-to-end run the next time a DigiSmith-driven push happens in a repo with this preference set.

Out of Scope

  • The gh CLI account mismatch — the actual trigger for this backlog item, deliberately excluded per Jack's explicit call ("prefer to avoid gh"). No per-directory auto-switch exists upstream (gh auth switch is a global, manual step); if this becomes worth solving later it's a separate, future item.
  • Writing real git/SSH config (~/.gitconfig includeIf blocks, ~/.ssh/config Host aliases) — considered and explicitly declined; DigiSmith only ever scopes the key to its own command invocations, never edits persistent config.
  • Named/reusable identity registry — considered (a global, toolchain.yml-shaped file mapping names to key paths) and explicitly declined in favor of a plain per-repo raw path with a direct prompt.
  • Per-subfolder granularity for monorepos — considered (the originating devkit incident is a monorepo) and explicitly declined; per-repo-root only.
  • The auto-mode credential-materialization classifier blocking read-only gh auth status — flagged in the original backlog item as likely deserving its own separate entry (possibly related to backlog/offload-blocked-by-permission-classifier-k.md, a different-context classifier complaint) — not investigated or addressed here.
