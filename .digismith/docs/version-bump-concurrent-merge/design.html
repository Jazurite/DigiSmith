Background

Every post-finish hook that reasons about "what did this merge bring in" derives its range from mutable global state: 01-version-bump.md and Y.1.3's 03-history-update.md both run BASE_SHA=$(git rev-parse ORIG_HEAD), and their scripts compare against the live working tree (versionChangedSince) or scan ${base}..HEAD (findChangedReports). Both hook files assert, in identical words, that ORIG_HEAD is "still valid here since nothing between the merge and this hook firing changes it." That assumption held for every merge whose hooks fired immediately — and broke the first time a hook was delayed.

The real instance (2026-09-11/12). Z's session merged (ac1b451, base de7ac6b) and deliberately paused its post-finish to avoid colliding with Y.1.3, which then merged on top (bd67ecc) and bumped 0.41.0-beta → 0.42.0-beta (058212f). Two merges, one bump. When Z's paused hooks eventually run on the shared checkout: ORIG_HEAD now reads Y's base (ac1b451), not Z's, and live HEAD includes Y's commits. Hook 01 reports SKIPPED already changed by incoming branch — a false reason (Z's branch never touched plugin.json). Hook 03 scans the wrong range and would either append Y.1.3's history entry a second time or miss Z's own. (Filed as backlog/bump-plugin-version-concurrent-merge-gap.md by the Y session.)

What this does and does not fix — the corrected premise. Content never strands in the version-keyed plugin cache: on this repo's single shared main checkout, Option 1 merges are sequential, so a later merge is always a descendant of an earlier one, a later bump+reinstall always covers earlier content, and the last merge in any burst always bumps (nothing lands after it to move the version). The earlier owning-lineage verdict's "stale cache on a coin flip" claim was wrong and is withdrawn here. The defect that remains is real but narrower: the hooks' stated contract (SKIPPED "means the incoming branch's own commits already changed the version") is not what the code checks, and a delayed hook reads another merge's base and range. For hook 01 that is a lying message and an extra or missing bump; for hook 03 it is a duplicated or missing history entry.

Why a naive fix doesn't work. Checking git log <base>..HEAD -- plugin.json still uses live HEAD, which has moved too. And any single shared "latest merge" slot — ORIG_HEAD, or a lone refs/digismith/post-finish/base — is clobbered by the very next merge on the shared checkout, reproducing the bug one level up. The pin must be keyed per merge. The durable per-merge key already threaded through Option 1's bash blocks is <feature-branch> (hook 01's own git push origin <base-branch> works this way today), and it outlives git branch -d.

Section 1 — Pinning the merge in Option 1

skills/finishing-a-development-branch/SKILL.md, Option 1, around git merge <feature-branch> and before the test run — pinning only when the merge actually moved HEAD, so a conflicted merge or an Already up to date re-run never writes a wrong pin:

PRE_MERGE=$(git rev-parse HEAD)      # recorded in the same block, before the merge
git merge <feature-branch>
if [ "$(git rev-parse HEAD)" != "$PRE_MERGE" ]; then
  git update-ref refs/digismith/post-finish/<feature-branch>/base "$PRE_MERGE"
  git update-ref refs/digismith/post-finish/<feature-branch>/head HEAD
fi

Pinning before the tests is deliberate: the merge commit is the thing being pinned, and if tests fail Option 1 stops anyway — the two refs are inert leftovers, harmless (see Section 5). A conflicted merge leaves HEAD unmoved and therefore pins nothing; Option 1 tells the agent to resolve, commit, and pin by hand from the merge commit's first parent (HEAD^1). After the post-finish hooks have all fired, Option 1 deletes both:

git update-ref -d refs/digismith/post-finish/<feature-branch>/base
git update-ref -d refs/digismith/post-finish/<feature-branch>/head

Why a git ref and not the alternatives. A shell variable cannot survive across the separate bash blocks the hooks run in — the exact cross-block-state-loss bug W.4.1 already hit once (e7ca1a7). A file in the working tree lands on the shared main checkout every concurrent session reads, needs a gitignore entry, and shows up in other sessions' git status. A ref is atomic, invisible to the working tree, cannot be accidentally committed, survives branch deletion, and — keyed by branch — is never clobbered by another merge. No custom-ref precedent exists in this repo; that is fine, this is the git primitive for "remember a SHA."

Section 2 — The firing contract

skills/finishing-a-development-branch/fire-lifecycle-hook.md today passes only the point name. It gains one documented contract clause, phrased point-agnostically: the firing skill pins the merge range for the point at refs/digismith/<point>/<feature-branch>/{base,head} before firing, and any hook that reasons about "what this merge brought in" resolves its range from those refs — never from ORIG_HEAD or live HEAD. The firing skill substitutes <feature-branch> into hook blocks from its own context, the same way it already substitutes <base-branch>.

Recovery when the branch name is not in context (a hook resumed after compaction, or run by hand): git for-each-ref refs/digismith/<point>/ lists every pending pin. Exactly one pin → it is yours. Several → several delayed sessions are pending; stop and ask which branch is being finished rather than guess. None → see Section 5.

Section 3 — Hooks 01 and 03 read the pin

Both 01-version-bump.md and 03-history-update.md replace BASE_SHA=$(git rev-parse ORIG_HEAD) with:

BASE_SHA=$(git rev-parse --verify refs/digismith/post-finish/<feature-branch>/base) || exit 1
HEAD_SHA=$(git rev-parse --verify refs/digismith/post-finish/<feature-branch>/head) || exit 1

and pass --base "$BASE_SHA" --head "$HEAD_SHA" to their scripts. Each hook's "ORIG_HEAD is still valid here" paragraph is replaced with one stating the pinned-ref mechanism and the recovery rule from Section 2. Hook 01's SKIPPED semantics paragraph is corrected to what is now actually checked: a SKIPPED result means this merge's own commits (base..head) changed plugin.json themselves — do nothing further. Hook 03's NOTHING (no report in range) semantics are unchanged in wording; the range it refers to is now the pinned one.

Section 4 — Scripts: pinned range, one invariant

bump-plugin-version.ts. versionChangedSince(baseSha, headSha, pluginJsonRelPath, cwd) compares git show <base>:plugin.json against git show <head>:plugin.json — never the live working tree. bumpTypeSince(baseSha, headSha, cwd) scans base..head. main() requires --head whenever --base is given (both or neither; one alone is a usage error, rejected through the shared requireArgs helper with a non-zero exit — the same path update-history.ts already takes for a missing --base). The bump itself still edits the live working tree and reads the current version to increment — the next version is "one past whatever main is at now," which is what a fresh cache key needs. The SKIPPED line becomes SKIPPED this merge's own commits already changed plugin.json (base..head).

update-history.ts. findChangedReports(baseSha, headSha, cwd) diffs base..head; main() requires --head alongside the already-required --base.

The invariant this buys: every merge bumps exactly once unless its own commits already bumped, and every merge records exactly its own reports — regardless of when its hooks fire or what else has landed on the shared checkout since. A delayed hook now produces the same result it would have produced immediately. In the real instance above, Z's delayed hook 01 would BUMP (its range never touched plugin.json) — one more bump than today's accidental SKIP, which is harmless (a monotonic cache key incremented once more) and, unlike today, predictable.

Section 5 — Error handling

CaseDisposition
Pin refs missing when a hook runs (fired by hand outside Option 1, or already deleted) git rev-parse --verify fails → the hook stops with a clear message: no post-finish pin for <feature-branch>; hooks must be fired from finishing-a-development-branch Option 1, or pin by hand with the two update-ref lines. Fail loud — never fall back to ORIG_HEAD.
Script gets --base without --head (or vice versa) Usage error — the shared requireArgs helper rejects it with a non-zero exit, the same path update-history.ts already takes for a missing --base.
Several pins present at once (several delayed sessions) No ambiguity when <feature-branch> is known — each hook reads its own. When it isn't (Section 2 recovery), stop and ask; never pick one.
Tests fail after the merge, Option 1 stops Refs remain, inert — nothing reads them until a hook for that branch fires. A re-run that reports Already up to date pins nothing and continues from them. If the fix needs new commits on the branch, Option 1 says to undo the local merge first (git reset --hard to the base pin) — guarded on HEAD still equalling the head pin, so another session's merge on top is never reset away.
git merge stops on conflicts HEAD did not move, so nothing was pinned. Resolve, git commit, then pin by hand: base = HEAD^1, head = HEAD.
git merge reports Already up to date An earlier run already merged this branch and stopped partway. Nothing is pinned now; that run's pins stand and are correct. Continue from where it stopped — never re-pin, since ORIG_HEAD now reflects the git pull, not this merge.
A hook fails partway, firing halts before cleanup Same as above — refs left in place, inert, visible via for-each-ref.

Testing

  • bump-plugin-version.test.ts (real git fixtures, no mocking — existing style, existing initVersionFixtureRepo/commitMessage helpers): versionChangedSince(base, head) → false when plugin.json is identical at both; true when a commit inside base..head changed it; false when a commit after head changed it — the delayed-hook case, the test that proves the fix; bumpTypeSince(base, head) ignores commits after head; main() rejects --base without --head.
  • update-history.test.ts: findChangedReports(base, head) ignores a report added after head; main() rejects a missing --head.
  • Option 1, the firing contract, and both hook files are agentic prose — verified by reading the diff, as every prior prose-only task in this lineage was.
  • Live: this branch's own finish is the first end-to-end run of the new path — Option 1 pins, both hooks read the pins, bump and history entry land, refs are deleted afterward (git for-each-ref refs/digismith/ empty at the end).

Out of scope

  • Direct-to-main pushes (no merge, no pin) — stays with backlog/post-finish-hooks-direct-push-gap.md; this pass only makes that case fail loudly instead of silently.
  • Any lifecycle point other than post-finish, and cross-repo hook sharing (Y2) — the contract clause is written point-agnostically so a second point can reuse it, but none is added.
  • The version-keyed cache mechanism itself, and how claude plugin install behaves on an already-present version dir — irrelevant once every merge with new content gets its own bump.
  • 02-plugin-reinstall.md — reads no range, unchanged.
