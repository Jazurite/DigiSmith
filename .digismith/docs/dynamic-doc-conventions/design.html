Overview

Two confirmed live gaps turned out to be the same underlying decision. First, 2026-09-19 during U.1's own report-implementation run: Jack wants docs nested by map letter (.digismith/docs/<Letter>/<Letter.N>-<slug>/, piloted at U/U.1-formatstructure/), but report-implementation's slug-derivation and update-history.ts's parseReport() both only understood the old flat shape and broke on the new one. Second, 2026-09-18 shipping a Screenshots/Videos addendum under Q.1: the addendum reused an already-occupied slug, and both writing-plans and report-implementation nearly wrote over an existing build's plan.md/ report.html.

Both resolve the same way: give every distinct build — a first pass or a later addendum, it doesn't matter which — its own permanent <Letter.N> sub-item and thus its own folder. No shared filename ever exists to collide over, and the nested shape Jack wants falls out of the same rule for free.

Folder shape

.digismith/docs/<Letter>/<Letter.N>-<slug>/{design.html,plan.md,report.html} — the full triplet lives together in one folder per build. An addendum gets its own complete set, not a patch to the original's design.html: today's in-place "Addendum" section pattern is retired in favor of full consistency across all three files.

.digismith/docs/
  G/
    G.1-standards-injection/
      design.html  plan.md  report.html
    G.3-dynamic-doc-conventions/
      design.html  plan.md  report.html
  Q/
    Q.1-generate-comment/
      design.html  plan.md  report.html
    Q.3-screenshots-section/              (addendum — own full set, not a patch to Q.1)
      design.html  plan.md  report.html

The trailing slug segment stays full-length (matching U.1's own pilot, U.1-formatstructure) — no reason to shorten it now that a numeric prefix already disambiguates; the slug still earns its keep for search/grep.

Numbering trigger and resolution point

Trigger: any distinct build gets the next unused <Letter.N> under its letter — a first pass and a later addendum are both "distinct builds." An addendum never reuses its parent's number. This is mechanical, not a judgment call: there is no case where two separate design/plan/report cycles share one folder.

Resolution point: the number is assigned once, the first time this build's design.html is about to be written — i.e. inside brainstorming's own "After the Design" documentation step, computed by scanning .digismith/docs/<Letter>/ on disk for existing <Letter>.M-* folders and taking max(M)+1. No new state to maintain — the filesystem is the source of truth. writing-plans and report-implementation both reuse that same already-resolved <Letter>/<Letter.N>-<slug> path rather than re-deriving anything, extending the existing "reuse the slug the caller already resolved" convention both skills already follow.

Unlettered builds

A structural change with no map letter (like the original unified-docs-convention work itself) has no natural key to nest under. These go to .digismith/docs/_unlettered/<slug>/ — its own bucket, flat inside (no .N numbering), keeping every letterless build grouped together rather than scattered in the top-level namespace with everything else. No historical case has ever needed a second build under the same letterless slug; if one ever does, it's caught the same way any other unexpected collision is — report-implementation's existing overwrite-ask — rather than a numbering scheme designed ahead of a real need.

Compatibility and lookup

Existing flat folders (V.4, V.5, I.6, and everything else shipped before this) are frozen historical record, exactly like a shipped design.html is never edited after the fact. They are never migrated into the nested shape.

Because old folders never move, any call site that reads .digismith/docs/<slug>/ needs to check both shapes permanently, not just during a transition window: try the nested shape first (.digismith/docs/*/<Letter>.*-<slug>/-style match), fall back to the flat shape second. There is no cutover date after which the flat fallback can be deleted.

Out of scope

  • Consumer repos — this build covers DigiSmith's own repo only (map-letter grouping). What the "grouping key" is for a repo with no map letters (a ticket key, or something else) is deliberately deferred until a real consumer-repo case forces the decision, rather than designed speculatively now.
  • Migrating any existing flat folder into the nested shape — frozen historical record, permanent, not touched by this build.
  • A numbering scheme for repeat builds under the same unlettered slug — no historical case has needed one; the existing overwrite-ask catches it if it ever happens.
  • A per-repo on/off toggle's storage location (a new profiles/<name>.yml field vs. preferences.yml-adjacent config) — moot for this build since it's scoped to DigiSmith's own repo only; revisit once the consumer-repo question above is actually being answered.

Validation

No behavior changes to any already-shipped, already-flat build — verified by the compatibility rule itself (old folders untouched, dual-shape lookup added rather than a shape swap). For new work: the next real DigiSmith build after this ships should land in the nested shape end-to-end (design → plan → report → history entry), the same way U.1 already validated the nested shape by hand before this convention existed to formalize it.
