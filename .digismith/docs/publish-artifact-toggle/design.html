Problem & Goal

Map item Q (Enforcer) shipped an unconditional "publish HTML docs via the Artifact tool" step in both digismith:enforcer (for design.html) and report-implementation (for report.html), gated only by the existing reporting profile field — the same flag that decides whether a report gets generated at all. There is no way to generate a report or spec locally without also publishing it externally. This was flagged mid-build (2026-08-15) as conflicting with the Emma theme-repo convention that progress reports stay private/gitignored, and shipped anyway as a deliberate, tracked risk — this feature is the committed fast-follow (see backlog/artifact-publish-opt-out.md).

Goal: a new profile field, publish_artifact, that decouples "generate this HTML doc" from "publish it externally," so a profile can keep doing the former without the latter.

Non-Goals

  • Not auto-cleanup. Deleting/unpublishing an already-published artifact automatically after some approval event was considered and closed as infeasible (2026-08-16) — the Artifact tool has no per-artifact delete, only whole-conversation deletion. This feature is a publish-time gate, not a post-hoc cleanup mechanism.
  • Not changing today's behavior. All four shipped profiles default publish_artifact: true — per Jack's explicit call, nothing publishes differently the day this ships. The field exists so a profile can be flipped later, not to change any profile's behavior now.
  • Not a new gate on report/spec generation itself. reporting: false already controls whether report-implementation runs at all; this field only governs the publish step within a run that's already happening.

Architecture

One new boolean field, publish_artifact, added to all four profiles/*.yml files (digismith, emma, jazurite, personal), all set to true. Same resolution mechanism every other profile field already uses — .digismith/profile → profile name → profiles/<name>.yml — no new lookup machinery.

report-implementation

Step 4, item 5 (Publish as an artifact)

Reuses the same profile already resolved for the reporting gate in Prerequisites — no re-locating or re-asking. Checks publish_artifact immediately before the Artifact tool call.

digismith:enforcer

Step 3 (Publish — HTML Artifact)

Same profile-resolution rule inject-standards and using-digismith already use. Checks publish_artifact immediately before the Artifact tool call.

No central orchestrator relaying the decision — each of the two consuming skills performs this check independently, at its own trigger point, matching the precedent O's own design established for ticket/ephemeral/reporting.

Behavior When False

Skip the Artifact tool call only. The HTML doc itself (design.html or report.html) is still written and committed exactly as it is today — generation and publishing stay fully decoupled. State the outcome plainly rather than silently omitting the publish step: "Not published — publish_artifact: false in this repo's profile."

Error Handling & Verification

  • Missing .digismith/profile → unchanged existing behavior: publish proceeds (same as reporting's own missing-file case).
  • Profile exists but predates this field (an older profiles/<name>.yml written before publish_artifact existed, or a stale .digismith/profile pointer with no matching file) → treat the field as absent, default to true — same absent-field convention already used for reporting: true, or the field absent → proceed as today.
  • No automated test suite, consistent with every DigiSmith skill. Verification is dogfooding: flip one profile's publish_artifact to false in a fixture, confirm the HTML doc still gets written/committed but the Artifact call is skipped and reported plainly; flip back.
