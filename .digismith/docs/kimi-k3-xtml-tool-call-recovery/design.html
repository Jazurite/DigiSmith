Problem

TokenReply's kimi-k3 route returns raw, unconverted tool-call text instead of a real tool-use response. Confirmed live, reproducing identically across both the claude-code and opencode runners — ruling out a client-protocol-specific cause. Today this silently reports as a successful dispatch (is_error: false, subtype: "success") while nothing was actually executed — exactly the "a status reply can lie" failure mode offload-implementer's own docs already warn about, just from a new source. Full investigation trail: backlog/tokenreply-kimi-k3-tool-calling-failure.md.

Root cause recap

Kimi K3 emits tool calls in its own documented "XTML" format (<|open|>tools<|sep|> <|open|>call tool="..." index="1"<|sep|>...), not a hallucination or garbage output. vLLM ships a dedicated KimiK3ToolParser specifically to convert this into standard tool calls (vllm/tool_parsers/kimi_k3_tool_parser.py, cloned for reference to D:/Workspace/Library/vllm). TokenReply is almost certainly not running this conversion step for this route. kimi-k2.7 through the identical pipeline works correctly and remains the shipped default; this feature exists to make kimi-k3 usable too, without waiting on TokenReply to fix their own server config.

Architecture

No standing proxy server, no new orchestrator loop, no LLM-based guessing at the decode step. The existing controller (digismith:offload-implementer, driven by whichever Claude Code session is running a subagent-driven-development plan) gains one new conditional step in its existing dispatch flow:

  1. Dispatch normally via claude -p/opencode run through TokenReply — unchanged from today.
  2. parse-result.ts runs as today; a new shared check flags the XTML pattern if present in the raw result text.
  3. If flagged: the controller runs a new deterministic parser script directly (a plain Node invocation, no subagent dispatch) — a TypeScript port of KimiK3ToolParser.extract_tool_calls's non-streaming logic — to decode the tool name(s) and argument(s) from the raw XTML text.
  4. The controller executes each decoded tool call itself, in order, using its own Read/Edit/Bash tools — the same tools offload-implementer already grants via --allowedTools. No new trust surface beyond "execute a specific, fully-decoded action with tools already permitted" — bounded per-action, not an open-ended loop.
  5. The controller resumes the same Claude Code session (claude -p --resume <sessionID> — the same mechanism offload-implementer's fix-rounds already use) with a message describing what was executed and its result, so the model continues its own turn normally from there.
  6. If a later turn in the same session hits the same XTML leak again, repeat steps 2-5 for that turn. No cap is enforced by this mechanism itself — the existing fix-round round cap (3) already bounds the overall task.

Components

New

scripts/runners/kimi-k3-xtml-parser.ts

Ported extraction logic: locates the tools channel, extracts each call block's tool name and argument blocks, reverses HTML-entity escaping on attribute values, JSON-decodes non-string-typed arguments (falling back to raw text on malformed JSON, matching the source's own tolerance). Exposes one function returning the decoded tool calls plus any unwrapped plain-text content. Non-streaming only — offload-implementer never consumes a live stream, so the source's streaming/buffering variant and its adjust_request step (a vLLM server-side concern) are both out of scope.

Modified

scripts/runners/claude-code.ts / opencode.ts

Each runner's parseResult gains a check against the new parser module. If the XTML channel marker is present, the returned ParsedResult flags it (exact field shape — new optional field vs. reusing existing status values — is an implementation-plan-level decision, not fixed here) so offload-implementer's controller logic knows to run the recovery step rather than trusting the runner's own is_error/subtype.

Modified

skills/offload-implementer/SKILL.md

New conditional step inserted between the existing Step 5 (extract session ID/status) and Step 6 (hand back to the normal flow): when the XTML flag is set, run the new parser, execute the decoded call(s), then re-dispatch via --resume with a result-description message, looping back to Step 5 for that turn's fresh result.

Reference only

D:/Workspace/Library/vllm/vllm/tool_parsers/kimi_k3_tool_parser.py

Not imported or depended on — Python, part of a project DigiSmith doesn't install. Read completely for the exact regex/decoding behavior to port faithfully into TypeScript, nothing more.

Data flow

Raw dispatch text (already captured in the existing events file, no new capture mechanism needed) → XTML-leak check (existing runner parseResult) → ported extractor (new module) → {tool, arguments}[] → controller executes each via its own Read/Edit/Bash → controller builds a plain-text result summary → fed back into the same Claude Code session via --resume, exactly like an existing fix-round dispatch.

Error handling

  • XTML channel marker present but the extractor decodes zero real calls (badly malformed beyond the ported parser's own tolerance) — treat as a genuine, non-recoverable error; fall back to today's plain BLOCKED disposition rather than looping or guessing.
  • Executing a decoded call itself fails (e.g. a Bash command errors) — report that failure back to the model via the same --resume message (describe the error, not just silence), letting the model's own next turn decide how to react, same as a normal tool error would surface in an unmodified dispatch.
  • This mechanism does not change the existing round cap. Repeated recovery across multiple turns of the same task still counts toward offload-implementer's existing fix-round cap (3) — no separate, uncapped retry budget introduced.

Out of scope

Explicitly ruled out during brainstorming, recorded so it isn't re-litigated:

  • A standing local HTTP proxy server sitting between Claude Code/OpenCode and TokenReply — considered, would need new persistent-process infrastructure (start/track/stop, Depot-style); the resume-based approach above needs none of that.
  • LLM-based decoding (dispatching a subagent to interpret the garbled text) — unnecessary once the format is confirmed deterministic and fully documented by vLLM's own parser; a plain ported function is cheaper, faster, and more reliable than a model call.
  • A full custom agentic loop/runner replacing claude -p/ opencode run entirely for this model+provider combination — the resume mechanism already gives Claude Code's own conversation and safety harness back control after each recovered turn; no need to reimplement conversation management from scratch.
  • Chutes as an alternative route to kimi-k3 — considered, not tested (Jack declined, "no chutes"). Not part of this design.
  • The streaming variant of vLLM's parser (partial-tag-overlap buffering, incremental content emission) — offload-implementer always consumes a completed dispatch's full captured output, never a live stream, so none of that logic is needed.

Testing

  • Unit tests for the new parser module against the real garbled text captured live during this session's investigation (both the Bash-call and Write-call examples) — must decode the correct tool name and arguments from each.
  • Entity-decoding edge cases (a value containing an escaped &quot; or &amp;) and typed-argument edge cases (a non-string argument that is valid JSON, and one that is malformed JSON and must fall back to raw text) — ported directly from the source's own documented behavior, not invented fresh.
  • Runner-level tests confirming claude-code.ts/opencode.ts correctly flag a fixture event containing the XTML marker.
  • A real live dispatch re-test once implemented, following this session's own established pattern (disposable scratch worktree, independent verification via git log/file existence — never trusting the dispatch's own self-reported status) — confirming a task that previously failed silently now actually completes.

Open risks

  • Argument-shape mismatch risk, not yet verified: the design assumes a decoded call's argument names (e.g. content/file_path for a Write call, command for a Bash call) map directly onto the controller's own tool parameter names. Only two real examples have been observed live so far (one Bash call, one Write call) — this should be verified against a few more real dispatches during implementation, not assumed to generalize perfectly.
  • Multi-call turns are unverified live — the format supports multiple call blocks in one tools channel, but every real example captured this session contained exactly one. The design executes all decoded calls in order per turn; this path has no live confirmation yet.
  • This is fully dependent on TokenReply's current (broken) behavior remaining stable. If TokenReply changes their kimi-k3 serving (fixes it properly, or breaks it differently), this recovery mechanism may need rework or could become dead code. Not a reason to avoid building it, but worth remembering it's scaffolding around a third-party bug, not a permanent architectural fixture.
