Goal & Motivation

A general lifecycle-hook mechanism for DigiSmith itself, modeled on the same shape as WordPress actions/filters, git hooks, and npm lifecycle scripts (postinstall, prepublish): specific points in DigiSmith's own SDLC pipeline can fire a hook, which can be a stock hook (a behavior DigiSmith ships built-in) or a custom hook (a consumer's own registered instructions for that point, local to their own repo).

This design was triggered by two real, same-day use cases surfacing during and right after W.4.1's (auto version-bump on finish) own brainstorm and execution:

Use case 1

Version bump on merge

W.4.1 already shipped this wired directly into finishing-a-development-branch's Option 1 body. This design retrofits it to be the first stock hook instead.

Use case 2

Stale plugin cache

A separate Claude Code session, on a different project, ran on an installed DigiSmith plugin cache built before W.6 retired subagent-driven-always — the old, retired skill was still physically present and got invoked, running logic that no longer reflects DigiSmith's real design. The source repo was never wrong; a consumer installation just never got told to refresh.

Both are now real post-finish stock hooks under this mechanism.

Architecture Overview

A lifecycle hook is a markdown instructions file, executed the same way a skill is — the agent reads it and follows it live — but triggered automatically at a fixed point in another skill's own flow, rather than matched by a description:. There is exactly one lifecycle point today: post-finish, fired from finishing-a-development-branch's Option 1 (Merge Locally) after it fully completes — merge, tests, push, worktree cleanup, and branch deletion have all already happened.

post-finish is a general point, not "post-Option-1" specifically — it means "after finishing-a-development-branch completes whichever integration decision was taken." Only Option 1 actually fires it today, since that's the only path with a real merge to main and the only one either stock hook has anything to do. If a future hook needs to fire after Option 2 (push + PR) or Option 3 (keep as-is), it's the same post-finish point wired into that option's own flow — not a new point name.

Hook files live in .digismith/hooks/post-finish/ in whatever repo is currently being worked in. DigiSmith's own two stock hooks are committed there in this repo (confirmed not gitignored here). A consumer repo's own custom hooks live in their own copy of that same folder, committed or not at their own discretion. There is no separate registry file or config — the folder's contents are the registry.

Hook File Format

Each hook file uses the exact same template as a SKILL.md — YAML frontmatter (name:, description:) followed by an instructions body. Anyone who already knows how to write a DigiSmith skill already knows how to write a hook. The description: field stops driving discovery (nothing matches against it — a hook fires because it's present in the right folder, not because its description matched intent), but it stays useful documentation for anyone reading the folder.

One flat .md file per hook — no sibling prompt files needed, since neither of today's two hooks requires one. Multiple hook files sharing a point fire in filename sort order, hence the 01-/02- prefixes below (today's two happen to have a real ordering dependency — see "The two stock hooks").

Firing Mechanism

A single small reference doc spells out the "fire hooks for point X" procedure once: given a point name, list .md files in .digismith/hooks/<point>/ (skip entirely if the folder doesn't exist — most repos won't have one), sorted by filename, and for each one, read it and follow its instructions exactly as if invoking that skill directly (frontmatter and all). Any skill wanting to fire a hook at some point just references this doc with the point's name — no duplicated procedure.

Location: skills/finishing-a-development-branch/fire-lifecycle-hook.md — a sibling file inside that skill's own folder, following the same convention already used for task-reviewer-prompt.md inside subagent-driven-development's folder, rather than inventing a new shared top-level convention for what is (for now) a single consumer. If a second lifecycle point in a different skill shows up later, that's the trigger to promote this doc to a real shared location — a small extension then, not a rewrite now.

Firing itself is unconditional: finishing-a-development-branch's own prose just checks whether .digismith/hooks/post-finish/ has any files in whatever repo is currently being worked in — no IS_DIGISMITH check at the firing level. Each hook file's own gate (if it needs one) lives inside that file.

The Two Stock Hooks

Both stock hook .md files gate on IS_DIGISMITH (plugin.json has "name": "digismith") internally — they only ever exist as real files inside DigiSmith's own repo anyway, but the explicit gate is cheap, self-documenting insurance and matches the "every hook names its own gate" rule above.

PathRole
.digismith/hooks/post-finish/01-version-bump.md Retrofit of W.4.1's already-shipped behavior. IS_DIGISMITH gate → node --experimental-strip-types .digismith/hooks/post-finish/scripts/bump-plugin-version.ts --base "$(git rev-parse ORIG_HEAD)" → on BUMPED, commit both version files with a pathspec and push this hook's own commit — a small second push, moments after the merge's own push, since this hook fires after Option 1's push already happened. ORIG_HEAD is still valid at firing time — nothing between the merge and hook-firing changes it.
.digismith/hooks/post-finish/02-plugin-reinstall.md New. IS_DIGISMITH gate → claude plugin marketplace update jazurite && claude plugin install digismith@jazurite --scope user → print an explicit reminder that other already-running Claude Code sessions on the same machine need a manual restart to pick up the refreshed cache (a hard CLI limitation, not something this hook can fix).
.digismith/hooks/post-finish/scripts/bump-plugin-version.ts
+ bump-plugin-version.test.ts		 Relocated from top-level scripts/, unchanged otherwise — same 9-test Vitest suite, same reuse of scripts/cli-args.ts (relative import path adjusted), same repo-root CWD assumption. Mirrors the existing skills/subagent-driven-development/scripts/ convention: a hook's backing scripts live in a scripts/ subfolder next to the .md file(s), scoped per lifecycle point.

Ordering matters here, not just cosmetically: 01 must fire before 02, so the reinstalled plugin cache reflects the freshly-bumped version too.

Revised Option 1 Flow

finishing-a-development-branch's Option 1 (Merge Locally) becomes: merge → test → push → clean up worktree + delete branch → fire post-finish hooks (new, final step, via the shared firing-mechanism doc).

This is a real simplification of that skill's own body: the IS_DIGISMITH gate check and the version-bump invocation both move out of Option 1's own prose entirely, replaced by one generic "fire post-finish hooks" step that's identical for every consumer repo, DigiSmith included.

Testing & Verification

  • bump-plugin-version.ts + its test: unchanged logic, unchanged suite — just discovered from its new path (default Vitest config has no custom test-file pattern, so anything named *.test.ts anywhere in the repo is picked up already).
  • The three markdown files (01-version-bump.md, 02-plugin-reinstall.md, and the shared fire-lifecycle-hook.md) are prose, like any SKILL.md — no automated harness. Verified by careful read-through plus a real end-to-end run, the same pattern W.4.1's own Task 2 used.
  • Same chicken-and-egg as W.4.1: this plan's own finish step will need to execute the corrected, updated finishing-a-development-branch by hand (reading it from this branch, not the stale installed plugin) — which is itself the first real proof the mechanism works, including both stock hooks firing in the right order.

Explicitly Out of Scope

  • Any lifecycle point besides post-finish (post-brainstorm-approval, post-plan-approval, pre-merge, etc.) — deferred until a second point has a real use case, per this item's own original YAGNI reasoning.
  • Cross-repo hook sharing (the same custom hook active in multiple consumer repos) — deferred as its own future idea, tentatively map letter Y2 or whichever letter is next unclaimed when it's actually brainstormed.
  • Wiring post-finish into Option 2 (push + PR) or Option 3 (keep as-is) — the point exists conceptually for them, but nothing wires it in yet since no hook needs it there today.
