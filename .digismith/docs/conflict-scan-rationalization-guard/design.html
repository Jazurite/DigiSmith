Conflict-Scan Rationalization Guard

Date: 2026-09-05 Map item: W.7 (first activation of subagent-driven-development)

Problem

subagent-driven-development's Setup step requires scanning a plan once for conflicts before dispatching Task 1 — including "tasks that contradict each other or the plan's Global Constraints" — and presenting every finding to the human partner as a batched question before execution begins. Observed live in a session on a different project: the session found exactly this kind of conflict (a Global Constraint contradicting the actual codebase convention), reasoned "this is a wording bug in my constraint, not a real conflict between tasks," and silently fixed the prose itself instead of asking — reading only the "between tasks" half of the rule's explicit "or the plan's Global Constraints" clause.

The rule itself is unambiguous; this was a rationalization, not a genuine misreading. But the Setup step has no explicit guard against this specific temptation, unlike the fix loop later in the same skill, which has a whole Common Rationalizations table for exactly this shape of shortcut (e.g. "This finding is obviously wrong, I'll drop it" → "Silent discards are forbidden"). The pre-flight scan has no equivalent — a real, structural gap that will recur anywhere this skill runs, not just in the project where it was observed.

Fix

Add one paragraph to skills/subagent-driven-development/SKILL.md's Setup section, immediately after the existing "Present everything you find to your human partner..." paragraph:

Don't adjudicate a finding yourself because you're confident it's your own mistake rather than a real conflict — "this is just a wording bug in my constraint, not a real conflict between tasks" is the same silent-discard pattern the fix loop's breaker forbids, one step earlier. A Global Constraint contradicting the actual codebase IS a finding under the first bullet above; present it and let your human partner decide which text governs, even when you're sure you already know the answer.

No other part of the file changes. No code, no new interfaces — this is a single-file, single-paragraph prose addition.

Why inline, not the existing table

The skill's one existing Common Rationalizations table lives with the fix loop, much later in the file. An agent that reasons its way past the Setup step's rule would encounter that table only after already having rationalized — too late to catch the exact failure mode observed. The guard belongs at the point of temptation, the same way the fix loop's own table sits directly next to the rule it guards, not in a single master table.

Scope

In scope: the one paragraph above, inserted into the Setup section. Out of scope: any other change to subagent-driven-development, any change to the fix loop's existing table, any change to writing-plans' Execution Handoff or the retired subagent-driven-always logic (unrelated — see backlog/digismith-lifecycle-hooks-y.md for that separate thread), and the stale-plugin-cache propagation gap that originally surfaced this finding (tracked separately in the same backlog item).

Verification

No automated test harness covers SKILL.md prose (same as W.4.1's Task 2). Verification is a careful read-through confirming: the new paragraph is inserted in the right place, reads clearly in context, doesn't contradict anything else in the Setup section, and every other section of the file is unchanged.
