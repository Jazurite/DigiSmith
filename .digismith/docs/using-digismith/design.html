Problem & Goal

Getting from "I have a ticket" to "I'm building it" is currently manual: invoke jira-intake, remember the team/branch-naming standard, create the branch by hand, then separately invoke superpowers:brainstorming. MEMORY.md already names this gap E — "the spine... the prescriptive driver that enforces stage order and routes to everything else" — but E has never been started; it sat untouched in Tier 1 while G and A shipped instead.

The goal here is not E's full future scope. It's one new skill, using-digismith (name already set by MEMORY.md's map), that closes the specific gap Jack described: after a real ticket exists, create the correctly-named implementation branch and hand off into the existing brainstorming → plan → build pipeline. E grows into its fuller "routes to everything" role over time, as later map items (QA handoff, delivery, etc.) each add their own routing step to this same skill — this build is the first slice, not a placeholder to be replaced.

Non-Goals

  • Not building B (spec seam). Carrying ticket context into brainstorming so it doesn't start cold is B's eventual, fuller job. This build does the simplest possible version — pass ticket.md's content into the invocation — as a stand-in B can later replace without disturbing the rest of using-digismith.
  • Not building E's fuller routing (QA handoff, delivery, estimation, etc.). Only the intake → branch → brainstorming handoff ships now.
  • Not modifying jira-intake. It stays exactly as shipped, independently invocable for intake-only use; using-digismith calls it, not the reverse.
  • Not re-implementing any part of brainstorming's or writing-plans's own terminal-step chaining. Each already declares what it invokes next (brainstorming → writing-plans; writing-plans → subagent-driven-development/executing-plans) — duplicating that chain here would violate DigiSmith's own philosophy #2 ("duplicating a Superpowers capability is a bug, not a feature").
  • Not handling a ticket with no real key. A Door 2 draft that hasn't been upgraded to a real ticket (see Error Handling) stops this skill before any branch is created — same manual path as today.

Architecture — Three Steps, Not Four

It initially reads like "chain four pipeline stages together," but brainstorming and writing-plans each already declare their own next step as a hard-coded terminal move. using-digismith's real job is only the part nothing else owns:

Step 1

Get a Real Ticket

If this conversation doesn't already have one, invoke digismith:jira-intake. If it produces a key-less Door 2 draft, stop here — see Error Handling.

Step 2

Create the Branch

<Key>__<slug> as an isolated worktree, reusing jira-intake's own slug derivation on the ticket title.

Step 3

Hand Off

Invoke superpowers:brainstorming from inside that worktree, with ticket.md's content passed in as seed context. Superpowers' own chain takes over from there, untouched.

Branch Naming & Worktree Mechanics

  • Format: <ticket.md's Key field>__<slug> — e.g. EMKT-9001__fix-cart-drawer-padding-mobile. Using the ticket's actual Key (rather than a hardcoded EMKT- prefix) means this works correctly regardless of JIRA project prefix, with no separate repo-type detection needed.
  • Slug: reuse jira-intake's slug-derivation algorithm on the ticket's title verbatim — same determinism guarantee, not a second implementation to keep in sync.
  • Creation: prefer a native worktree tool if the session has one; fall back to superpowers:using-git-worktrees otherwise.
  • Reuse over duplication: before creating anything, check whether a worktree for this exact branch name already exists (e.g. resuming a ticket started in an earlier session). If so, switch into it instead of creating a second one.

Error Handling & Edge Cases

  • No real key yet (a Door 2 draft never upgraded to a real ticket) → stop after intake. Explain that using-digismith needs a real ticket key to name a branch; the user can continue manually, or run Door 1 later once the ticket is real. No branch, no worktree, no pipeline invocation.
  • Existing worktree/branch for this ticket → switch into it; never create a duplicate.
  • jira-intake's own stop conditions (no JIRA tool and declines to paste, sparse paste, etc.) → using-digismith doesn't proceed past whatever jira-intake itself decided; this isn't a new failure mode to reinvent, just don't advance past it.
  • Branch name collision with an unrelated ticket (the git-branch-level case, distinct from jira-intake's own docs-folder collision check) → don't silently reuse a stranger's branch. Ask before proceeding — the same "never silently overwrite/reuse" posture used everywhere else in this project.

Testing / Verification

No automated test suite — consistent with every DigiSmith skill so far. Verification is a dogfooding pass after implementation:

  1. Happy path — a fixture ticket.md with a real Key already on disk; confirm using-digismith derives the correct branch name, creates the worktree, and constructs the brainstorming handoff with the ticket's actual content included. (Verifying the constructed invocation's content is the achievable bar here — a dogfood subagent can't complete a full live, AskUserQuestion-gated brainstorming session end-to-end, the same limitation surfaced testing jira-intake's confirmation-gated edge cases.)
  2. No ticket yet — confirm jira-intake is triggered first, and the skill continues once a real key exists.
  3. Key-less Door 2 draft — confirm a clean stop, no branch or worktree created.
  4. Resuming an existing worktree — confirm reuse rather than duplication.
  5. Branch-name collision with an unrelated ticket — confirm the skill asks rather than silently reusing someone else's branch.

Relationship to Other Map Items

  • B (spec seam, Tier 4, not yet built) — this skill's ticket-context hand-off to brainstorming is a deliberately minimal stand-in for B's eventual fuller design. When B ships, it replaces this one step; the rest of using-digismith doesn't need to change.
  • E's fuller scope — QA handoff routing, delivery routing, and the rest of "routes to everything else" — is explicitly deferred to later map items, each adding their own step to this same skill.
  • A (jira-intake) — unchanged; still independently invocable for intake-only use.
  • H (subagent-driven always, Tier 2) and L (refinement, Tier 4) — not touched by this build.
