Problem & motivation

digismith:offload-implementer (map items K.2/K.3/K.6) already routes one explicitly-requested subagent-driven-development task to a third-party model via a pluggable gateway/runner — but only when the human asks for it, task by task. subagent-driven-development's own Model Selection section already classifies every implementer task into a complexity tier (mechanical / integration / architecture) purely to pick which Claude model handles it — that tier signal exists today but has never been used to make a vendor decision.

This item was originally K.9 inside the K-lineage ("model tiering"), then promoted to its own letter, Z, once its real scope — native, automatic per-task model selection inside subagent-driven-development itself, not a side-channel skill — outgrew K. The full vision (backlog/native-model-router-z.md) is a multi-criteria, multi-vendor router: cost, latency, context-window fit, human override, and more, still largely unscoped. Z.1 is deliberately the smallest possible first slice of that vision: one fixed rule, reusing infrastructure that already ships, applied to one of the two dispatch roles subagent-driven-development has (the implementer; the task/final reviewer role is Z.2, a separate, later design).

Scope

When subagent-driven-development's Task Loop Step 1 classifies an implementer task's complexity signal as mechanical (1-2 files, complete spec — today's "use a fast, cheap model" tier), the controller automatically follows offload-implementer's existing dispatch procedure instead of an Agent-tool Claude subagent dispatch — no explicit per-task ask required. Provider and runner still resolve from the active profile exactly as they do for offload-implementer's explicit-ask path (today: tokenreply/claude-code, per K.6's defaults) — the one thing Z.1 changes is passing --role mechanical to print-config.ts instead of the --role task every existing caller hardcodes today. kimi-k3 becomes the practical model in play only because Z.1 also teaches tokenreply.ts's model(role) to return it for the mechanical role (see Components below) — the routing rule itself is role-based, not a special-cased vendor/model bypass. Integration and architecture tier tasks are entirely unaffected — they continue to dispatch to Claude exactly as they do today.

Fix rounds 1-3 for an auto-offloaded task continue on the same offloaded session, the same way a fix round already works for an explicitly-requested offload today.

Architecture

No new decision engine, scoring system, or "Model Router" script exists in Z.1 — the routing "decision" is a single fixed conditional, not a computation. Concretely:

  1. subagent-driven-development's Task Loop Step 1 ("Dispatch the implementer") computes the task's complexity signal as it already does today (unchanged: 1-2 files + complete spec → mechanical; multi-file/integration → standard; design judgment → most capable).
  2. New branch: if the signal is mechanical, the controller does not dispatch an Agent-tool subagent. Instead it follows offload-implementer's Steps 1 through 6 directly (resolve config, ensure runner ready, build the task prompt via digismith:inject-standards Scenario 4, dispatch, extract session/status, hand back to the normal review flow) — resolving task_offload_runner/task_offload_provider from the active profile exactly as the explicit-ask path does, with one change: Step 1's print-config.ts invocation passes --role mechanical instead of the --role task every existing caller hardcodes. OffloadRole (scripts/providers/types.ts) already models this exact distinction and chutes.ts's model(role) already branches on it (task → Kimi-K3-TEE, mechanical → a cheap Gemma model) — the scaffolding predates Z.1, it was simply never invoked with mechanical by anything until now.
  3. Everything downstream of the dispatch — review package generation, task review, the fix loop, ledger entries — is unmodified subagent-driven-development, exactly as it already treats an offloaded task today.
  4. The XTML tool-call leak recovery mechanism (offload-implementer's Step 5.5) is inherited automatically, since Z.1 reuses that same dispatch procedure verbatim. Its existing ceiling (viable for tasks needing roughly 3 or fewer tool calls total, bounded by the shared fix-round cap of 3) is accepted as a known limitation for this first slice — mitigated, not eliminated, by the fact that mechanical-tier tasks by definition need few tool calls in the first place.

kimi-k3 is the deliberate choice for the mechanical role over kimi-k2.7 (which stays the task-role default, unchanged), even though K.3 reverted TokenReply's own default away from kimi-k3 after confirming its tool-calling bug live. The reasoning: that revert was about protecting the task-role, general-purpose path (still kimi-k2.7 after Z.1); the new mechanical-role path only ever sees mechanical-tier tasks specifically, which are the shape of task least likely to hit the bug's practical ceiling.

skills/offload-implementer/SKILL.md

No changes

Z.1 reuses its Steps 1-6 procedure by reference/invocation, not by copying or modifying its content. Its own "explicit ask only" framing in Overview/When to Use stays accurate for its own direct-invocation path (which keeps hardcoding --role task, unaffected); Z.1 documents its own trigger condition entirely within subagent-driven-development.

Error handling

  • Runner/provider prerequisite missing (any failure case in offload-implementer's own Prerequisites/Error Handling — binary not on PATH, credential env var unset, print-config.ts non-zero exit, Depot's ensure-claude-code reporting not-ready) → fall back to a normal Claude cheap-tier Agent-tool implementer dispatch, silently and without blocking the task. This mirrors K.1's own established fallback philosophy ("falling back to in-session generation whenever it's off, unavailable, or returns something malformed"). Note the fallback in the task's ledger entry as a one-liner so it's visible after the fact why a mechanical task didn't auto-offload.
  • The dispatched runner genuinely errors, or the fix-round cap is hit with open findings → unchanged from offload-implementer's own disposition: report BLOCKED/surface the open findings to the human partner. Z.1 does not add a new escalation path (e.g., silently falling back to a Claude implementer mid-task after a failed offload attempt) — a stuck auto-offloaded mechanical task surfaces exactly the same way a stuck explicitly-offloaded task does today.
  • XTML leak detected → unchanged, handled entirely by the inherited Step 5.5.

Out of scope for Z.1

  • Z.2 (routing for the task-reviewer/final-reviewer role) — a separate sub-item, separate design, not touched here.
  • Any routing criteria beyond the single fixed mechanical→kimi-k3 rule: no cost or latency scoring, no context-window fit check, no per-profile opt-out flag, no other vendor/model choice. This is deliberately the narrowest possible slice of the "Model Router" vision in backlog/native-model-router-z.md, not an attempt at the full router.
  • Mid-task fallback from kimi-k3 to Claude after a failed offload attempt.
  • Any change to offload-implementer's own explicit-ask path or its profile-driven provider/runner resolution.

Relationship to W

This modifies subagent-driven-development — a vendored Superpowers primitive, squarely map item W's territory (primitive content activation, per W.2's fork-provenance tagging convention). backlog/native-model-router-z.md flagged this exact collision as "not yet raised with whichever session/thread is driving W" before Z was ever designed for real. Rather than blocking on a separate W-focused conversation, this design applies W.2's existing activation convention directly — the same pattern W.4, W.6, and W.7 already established for their own first activations of other primitives (this is subagent-driven-development's second activation, after W.7's conflict-scan guard). Worth a one-line note in MEMORY.md's W row once this ships, so a future W-focused session isn't surprised by it.

Verification

scripts/providers/tokenreply.ts's change is genuinely unit-testable, following the pattern registry.test.ts already uses for chutes.ts (lines 26-27: explicit expect(chutes.model("mechanical")).toBe(...) assertions) — add the equivalent pair for tokenreply.model("mechanical") → "kimi-k3" and tokenreply.model("task") → "kimi-k2.7" (regression-guarding the unchanged default). The existing generic assertConforms check already exercises both role values for every provider, so it won't itself catch a wrong return value — the new explicit assertions are required, not optional.

SKILL.md prose has no automated test harness (same precedent as W.4.1 and W.7). Verification there is a careful read-through confirming: the new branch is inserted at the right point in Step 1, reads clearly alongside the existing complexity-tier logic, correctly references offload-implementer's procedure and the --role mechanical flag without duplicating its content, and the rest of the file (fix loop, final review, Finish) is unchanged. A live smoke test — running one real plan containing a mechanical-tier task through subagent-driven-development and confirming it actually auto-offloads to kimi-k3 without an explicit ask — is the practical implementation-plan-level verification; not performed as part of this design.
