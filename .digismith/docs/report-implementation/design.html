Problem & Goal

When map item G (standards injection) finished, Jack got a rich HTML implementation report (docs/superpowers/reports/2026-08-05-standards-injection-report.html) summarizing the build: what shipped, a per-task review table, the final-review findings and how they were resolved, the merge commit list. It was written by hand, in-session, after the fact. Every DigiSmith feature since (A, E, M) skipped this — no report exists for any of them.

The goal is to make this automatic and required rather than something the controller session may or may not remember to do: a new skill, digismith:report-implementation, that generates the same shape of report for every subagent-driven-development plan, without needing to be asked.

Non-Goals

  • Not covering finishing-a-development-branch's Option 2 (push + PR). A PR often merges later on GitHub, in nobody's Claude Code session — there is no session present to observe that event or write a report about it. Left for a future slice if it turns out to matter.
  • Not covering plans executed via superpowers:executing-plans ("jdi" — Jack's own nickname for it). That path has no per-task ledger in the shape this skill reads; its trigger condition (see Architecture) simply won't match.
  • Not automating the "Post-Merge Sweep" section. G's report had one because Jack asked for a follow-up sweep of deferred Minor findings after merging. That stays a manual, occasional thing this skill doesn't try to trigger or generate on its own.
  • Not modifying subagent-driven-development or finishing-a-development-branch (both Superpowers files). This skill inserts itself by trigger-matching at the right moment, the same way capture-ephemeral-url hooks in after finishing-a-development-branch's PR-creation option without editing that skill's file.

Architecture

New skill: digismith:report-implementation. Its trigger is narrow and specific: a subagent-driven-development plan's final whole-branch review has just come back clean (all findings fixed, parked, or accepted) — right before that skill's own Finish step deletes the plan's workspace (.superpowers/sdd/<plan>/). This is earlier than "after the branch is merged," and deliberately so: the ledger and per-task review detail that make the report worth reading exist only in that soon-to-be-deleted workspace (or in the controller's own conversational memory, which is not durable across compaction). Because every merge in this repo's history has been a fast-forward, the commit range this skill cites (MERGE_BASE..HEAD) is already final at that point — nothing about it changes once finishing-a-development-branch actually runs.

Step 1

Gather Sources

Read the plan file (Goal/Architecture/task list), the ledger (progress.md — per-task completion lines, deferred minors, final-review findings, parked rulings), and git log --oneline / git diff --stat over MERGE_BASE..HEAD.

Step 2

Render the HTML

Reuse the exact template/CSS from docs/superpowers/reports/2026-08-05-standards-injection-report.html — same section shape, same visual language. Populate each section from Step 1's sources (see Report Sections below).

Step 3

Write and Commit

Save to docs/superpowers/reports/<plan's date-slug>-report.html (same date/slug the plan and spec already use) and commit it — as part of the same commit range this report describes, so the report and the code it documents land together.

After Step 3, control returns to subagent-driven-development's own Finish step exactly as written (delete the workspace, then invoke finishing-a-development-branch) — this skill doesn't touch or duplicate that sequencing, it just runs once, immediately before it.

Report Sections

Same shape as G's report, adapted to pull from the ledger instead of the controller's memory:

  • Header — badge (e.g. "implementation complete — ready to merge"), title, date, map item, commit range.
  • Summary — one paragraph, links to the design spec and implementation plan.
  • What Was Delivered — one card per task, drawn from each task's brief "Files" section (what was created/modified) plus its one-line purpose from the plan.
  • Build Process — table: task number, what was delivered, review verdict, deferred minors — one row per Task <N>: complete (...) line in the ledger.
  • Final Review & Fix — table: finding, resolution — sourced from the ledger's final-review line plus any fix-round and parked/adjudicated lines. Omit this section entirely if the final review had zero findings (nothing to report beyond "clean").
  • Merge — commit list from git log over the plan's range.

Data Flow

ledger + plan file + git log/diff → populated HTML template → docs/superpowers/reports/<date-slug>-report.html → committed

Error Handling & Edge Cases

  • No ledger found at the expected workspace path → this skill's trigger doesn't really apply (likely a "jdi"/executing-plans run) — skip silently, don't fabricate a report from nothing.
  • Ledger present but missing expected lines (e.g. no final-review line yet — this skill fired too early) → generate what's derivable from what exists, and note the gap in the report rather than guessing at unwritten content.
  • Report file already exists at the target path (a re-run) → ask before overwriting, matching jira-intake's existing-file posture rather than silently clobbering.
  • Empty commit range (MERGE_BASE == HEAD) → stop and say so; this shouldn't happen if the trigger fires at the right point, so treat it as a signal something upstream is wrong rather than emit a vacuous report.

Testing / Verification

No automated test suite — consistent with every DigiSmith skill so far. The capture-ephemeral-url plan's own real ledger was already deleted by the time this skill exists, so verification uses a reconstructed fixture instead of an invented toy scenario:

  1. Rebuild a fixture ledger matching what that plan's actual ledger contained (from this session's own record of it) at a temporary path.
  2. Point the skill at that fixture ledger plus the real git history for commit range c25f658..abb3ac1, which still exists in this repo.
  3. Confirm the rendered report's Build Process and Final Review & Fix tables match what actually happened (3 tasks approved; one parked report-hygiene item; the final-review fix wave and its one parked residual finding), and that the commit list matches git log for that real range.
  4. Separately dogfood the "no ledger found" and "report already exists" edge cases against empty/pre-existing fixtures.

Relationship to Other Map Items

  • G — this skill's report template is lifted directly from G's hand-written report; no change to G itself.
  • E (using-digismith) — unchanged; this skill triggers at the opposite end of the pipeline, after implementation, not at intake.
  • D (delivery, Tier 5, not yet built) — a future, fuller D could reference or link these reports as part of "verification"/"announcement," but this skill doesn't wait for D to exist.
