Problem

Confirmed live twice in one session (backlog/offload-blocked-by-permission-classifier-k.md), across both configured runners (claude-code and opencode): Claude Code's own auto-mode permission classifier refuses the credential-fetch-then-spawn action shape that digismith:offload-implementer's dispatch step requires — after every real DigiSmith-side prerequisite (runner on PATH, credential resolved, print-config.ts exiting 0) has already passed. This is confirmed environmental, not a DigiSmith bug.

subagent-driven-development's "Mechanical-tier auto-offload" paragraph (Z.1's own mechanism) already has four named fallback triggers — runner not on PATH, credential env var unset, print-config.ts exits non-zero, Depot's readiness check fails — and falls back gracefully to a normal Claude cheap-tier dispatch for any of them. A classifier refusal isn't one of the four, so today a controller has to recognize the pattern live and manually route around it, which is exactly what happened building K.4: the same refusal was silently re-discovered on all three of that plan's mechanical tasks, one wasted attempt per task, because nothing remembered the first one.

Scope

Extends subagent-driven-development's existing "Mechanical-tier auto-offload" paragraph only — the vendored primitive's own automatic path. Two things change: the paragraph's fallback-trigger list gains a fifth trigger (a live classifier refusal), and every mechanical-tier task after the one that first discovers it checks for that discovery before attempting its own dispatch.

Out of scope: digismith:offload-implementer itself is untouched — its Error Handling table stays exactly as it is today, since this fix targets only the automatic mechanical-tier path, not an explicitly-requested offload. Also out of scope: anything that tries to unblock the classifier itself (the only real lever is the user's own Claude Code permission settings, entirely outside this repo's control and not something to prompt for automatically) and any persistence across separate plan runs or sessions (see "Error handling & edge cases" for why this is deliberately per-run, not durable).

Detection

A classifier refusal is categorically different from every disposition already in offload-implementer's Error Handling table: the Bash tool call attempting the dispatch command (the credential-export-then-spawn shape) is refused outright by the harness itself before the resolved runner's process ever starts. Recognizable by two things together:

  • No events file is produced at all — not empty, not partial, simply never created — because the process that would have written it never ran.
  • The tool result itself carries an explicit permission-refusal notice from the harness, not any command output, exit code, or stderr text from claude/opencode — distinct from a genuine runner error (which produces some real output), a Bash tool timeout (already handled separately as "not a failure by itself"), or a missing prerequisite (already caught earlier, before any dispatch is attempted, by the PATH/credential/print-config.ts checks).

Caching in the ledger

On first detection within a plan run, record it as a new ledger line — not just in-session/controller memory — using the same append-only convention every other ledger line already follows, e.g.:

Task <N>: mechanical-tier offload environment blocked (classifier refusal) — falling back to Claude for the rest of this plan

Ledger-based rather than an in-memory flag because the ledger is this skill's own designed-for-compaction-survival mechanism (per its own "conversation memory does not survive compaction" warning) — a plan that spans a compaction should still remember the block on resume, the same way it already remembers which tasks completed.

Every later mechanical-tier task, before attempting anything, scans the ledger for that line first. If present, it skips the offload attempt entirely and dispatches straight to a normal Claude cheap-tier implementer — no wasted attempt, no re-discovery.

Where this lands

Entirely within subagent-driven-development's existing "Mechanical-tier auto-offload" paragraph (the vendored primitive DigiSmith forks) — extending its existing sentence "If any of offload-implementer's own prerequisites aren't met (runner not on PATH, credential env var unset, print-config.ts exits non-zero, Depot's readiness check fails) — fall back to a normal Claude cheap-tier Agent-tool dispatch instead" with a fifth trigger, plus a new short instruction: check the ledger for an existing block-discovery line before attempting any mechanical-tier task's first dispatch. No changes to digismith:offload-implementer, K.2/K.3/K.6, or the existing memory note/backlog item — those stay as the informal record this design formalizes into the skill's own text.

Error handling & edge cases

  • Environment-wide, not runner-specific. Both configured runners were independently confirmed blocked by the identical action shape (credential-fetch-then-spawn), not by anything specific to one binary. The cached block therefore applies plan-wide regardless of which runner a later task would have used — a task configured for opencode still skips its attempt even if the discovery happened on a claude-code-runner task, and vice versa.
  • Never generalized across plan runs. The backlog item's own finding is explicit that this is "likely session/harness-specific... don't generalize to 'offload is broken everywhere.'" Caching lives only in this plan's own ledger, which is deleted once digismith:report-implementation has run and the plan finishes — the next plan, in a possibly-different session or with possibly-different permission settings, starts with a clean slate and gets a fair, fresh attempt at real offload. This is a deliberate choice, not an oversight: a durable, cross-session flag risked permanently disabling a real optimization based on stale evidence, which is exactly what a peer session's Approach 3 alternative would have risked (see design discussion).
  • Must not fire on a genuine runner error. A dispatch that starts and then fails (bad exit code, malformed output, TokenReply/Chutes returning a real HTTP error) is already the existing "dispatched runner genuinely errors → BLOCKED" disposition in offload-implementer's own Error Handling table — untouched by this design. The two must stay distinguishable: this trigger requires that the dispatch command itself never ran.

Testing / verification

This is a prose change to a controller-facing skill, not executable code — there is no automated test suite to run. Verification is: (1) the updated paragraph reads unambiguously to a fresh controller with no memory of this incident (the same bar every DigiSmith skill edit is held to); (2) the next real plan that hits a live classifier refusal is watched to confirm the ledger line gets written on first discovery and later mechanical tasks actually skip their attempt — this can't be forced deterministically since the block is environment-dependent, so it's confirmed opportunistically on the next real occurrence rather than in a dedicated test task.
