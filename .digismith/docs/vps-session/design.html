Overview

A previous session hand-provisioned a real Hetzner VPS and got a persistent, interactive claude session running on it inside tmux, reachable over SSH from anywhere — the thing backlog/vps-session-hosting-x.md originally proposed as a new letter. Every step of that setup was done by hand, one SSH command at a time, and hit nine distinct real gotchas along the way (broken local SSH config, pnpm's global-bin-dir path, pnpm's build-script approval gate, systemd killing the detached tmux server on disconnect, broken nested shell-quoting, an exec claude trap that could kill the whole session, and the CLAUDE_CODE_OAUTH_TOKEN / interactive-login distinction — full list in the backlog file).

V.3 turns that hard-won manual sequence into a real, repeatable script: reconnect to an already-provisioned VPS session in one command, and verify its health without attaching. It does not provision new infrastructure — the VPS itself is assumed to already exist, set up by hand once, the same way it was this first time.

This slots into Depot (map item V) as a fourth machine-wide resource, alongside the packages/ clone, the OpenCode server (V.1), and the Agentic Bridge proxy (V.2). Unlike those three, there is nothing for Depot to spawn or own the lifecycle of here — the resource being "ensured" is a remote, already-running tmux session, not a local process Depot starts and tracks by PID.

Architecture

A standalone TypeScript script, scripts/vps-session/cli.ts, run via node --experimental-strip-types — same convention as scripts/agentic-bridge/server.ts. Two subcommands, status and connect, sharing one internal health-check routine:

node --experimental-strip-types scripts/vps-session/cli.ts status
node --experimental-strip-types scripts/vps-session/cli.ts connect

Both entry points work identically whether invoked directly from a raw terminal (no Claude Code session involved at all) or by a Claude Code session acting on digismith:depot's instructions when asked ("connect me to my VPS," "check my VPS status") — one script, no duplicated logic between the human path and the agent path.

Every remote command in this design is issued as a single non-interactive ssh invocation per check (ssh ... "<command>"), except the final step of connect, which execs into an interactive ssh -t ... tmux attach and hands the terminal over directly. Nothing about this script itself is long-running — it is a short-lived controller for a long-lived remote resource, the same relationship this session already proved out driving the VPS by hand over many separate SSH connections.

Config File

~/.digismith-depot/vps.json — sibling to ~/.digismith-depot/opencode-server.json and ~/.digismith-depot/agentic-bridge.json, machine-wide like the rest of Depot's state, not per-repo:

{
  "host": "46.225.49.140",
  "user": "root",
  "identity_file": "~/.ssh/jazurite",
  "tmux_session": "claude-main"
}

No creation or edit tooling — this file is written by hand once, matching V.3's software-state-only scope (no automated VPS provisioning). Absent file → both commands stop immediately with a plain "no VPS configured, create ~/.digismith-depot/vps.json" message; neither command guesses a host.

Command: status

Runs every check below over one-shot, non-interactive SSH calls and reports each result plainly. Never modifies anything on the VPS — a pure read.

CheckHowWhy it matters
SSH reachablessh -o BatchMode=yes -o ConnectTimeout=10 -i <identity_file> <user>@<host> trueEverything else depends on this succeeding first.
Lingering enabledloginctl show-user <user> -p Linger, expect Linger=yesWithout this, systemd kills every process tied to the SSH login session — including a detached tmux server — the moment that SSH connection closes. Hand-confirmed as the actual root cause of the session vanishing mid-setup.
Toolchain on PATHExplicitly source nvm and pnpm before checking — see callout below — then claude --versionA plain non-login, non-interactive SSH command does not source ~/.bashrc, so nvm/pnpm's PATH additions are invisible unless sourced explicitly.
tmux session alivetmux list-sessions, look for the configured session nameThe actual persistent resource this whole design exists to keep available.
Credentials persistedtest -f ~/.claude/.credentials.jsonConfirms the one-time interactive OAuth login has actually been completed on this machine — without it, the tmux session will be sitting at a login prompt, not a working session.
The toolchain check cannot just run ssh host "claude --version" — that gotcha was hit directly: nvm's install script appends its init lines to ~/.bashrc, which bash only sources for genuinely interactive shells. Every remote command in this design explicitly sources nvm and sets PNPM_HOME first, mirroring exactly what worked by hand: 
export NVM_DIR="$HOME/.nvm"; [ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh"
export PNPM_HOME="$HOME/.local/share/pnpm"; export PATH="$PNPM_HOME/bin:$PNPM_HOME:$PATH"

Command: connect

Runs every status check, auto-fixing what's safely fixable, then attaches:

  1. SSH unreachable → stop, report (see Error Handling). Nothing past this point is attempted.
  2. Lingering not enabled → auto-fix: loginctl enable-linger <user>, then re-check.
  3. Toolchain missing → stop, report which piece (nvm/node/pnpm/claude) is missing and point at the manual install steps. Never auto-installs — same disposition Depot already takes for a missing opencode/claude locally (see its own Error Handling table).
  4. tmux session dead or absent → auto-fix: write ~/start-claude.sh fresh via a heredoc with a quoted delimiter (never a nested-inline-escaped command — that's the exact bug hand-hit and fixed this way), chmod +x it, then: 
    #!/bin/bash
source ~/.config/claude-code.env 2>/dev/null
cd ~
claude
echo "=== claude exited with code $? ==="
exec bash
    Deliberately not exec claude as the last line — if claude exits for any reason, exec bash keeps the pane (and therefore the tmux session, and therefore the server) alive instead of the whole session vanishing. Then: 
    tmux new-session -d -s <tmux_session> "/root/start-claude.sh"
tmux pipe-pane -o -t <tmux_session> "cat >> /root/claude-session.log"
    The pipe-pane logging is included by default — losing all diagnostic output when a session unexpectedly dies was a real, costly gap hit hand-debugging this the first time.
  5. Credentials missing → not auto-fixed (can't be — it's an interactive browser OAuth flow by design). Reported as a warning, but connect still proceeds to attach; the user completes login themselves, exactly as done by hand the first time.
  6. Attach — the final step, replacing the script's own process: 
    exec ssh -i <identity_file> -o IdentitiesOnly=yes -t <user>@<host> "tmux attach -t <tmux_session>"

Depot Integration

skills/depot/SKILL.md gains a new "Resource: VPS Session" section, documenting this as a fourth resource alongside the existing three. Its "Which Operation" table entry: invoked directly by the user (by name or by asking a Claude Code session to do it) → status or connect depending on intent; never auto-invoked by bootstrap/adopt — unlike the packages/ clone, this is not a per-ticket dependency most tickets need, matching the same opt-in disposition V.1/V.2 already use for their own resources.

Testing

Per map item U's standing default, Vitest for anything genuinely unit-testable: config-file parsing/validation, the ssh/tmux command strings the script constructs, and the health-check result aggregation logic (what combination of checks maps to what reported status) are all pure functions, tested directly. The actual SSH/tmux interaction itself is not meaningfully unit-testable — mocking an SSH session would test the mock, not the behavior that actually matters — so, matching Depot's own existing V.1/V.2 practice, that part is live-verified against the real VPS as part of implementation, not covered by automated tests.

Out of Scope

  • Provisioning a new VPS — no Hetzner API calls, no server creation/teardown. The box is assumed to already exist.
  • Multiple VPSes — one config file, one host. Not a concern for a single-user personal tool; revisit only if it ever actually comes up.
  • Auto-invoking from bootstrap/adopt — deliberately opt-in only, see Depot Integration above.
  • Relocating the Agentic Bridge (or any other Depot resource) to run on the VPS — a materially different, much larger idea (real network auth, dev/prod separation) that was deliberately split out during this same brainstorm into its own backlog item, backlog/practice-devprod-infra-x.md, rather than designed here.
  • Automating the one-time interactive OAuth login — can't be automated by design (a real browser flow), and isn't attempted.
