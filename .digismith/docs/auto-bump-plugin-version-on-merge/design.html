Background

DigiSmith's installed plugin cache is version-keyed (~/.claude/plugins/cache/jazurite/digismith/<version>/) and only refreshes when .claude-plugin/plugin.json's "version" actually changes. Nothing today makes bumping that version part of merging a DigiSmith feature — it's a manual step, and it has already been missed seven times in a row (backlog/plugin-version-bump-cicd-automation.md), each miss requiring a hand correction once finally caught. A second, related drift was found while designing this: .claude-plugin/marketplace.json embeds its own copy of the version and is already stale (0.20.0-beta against plugin.json's 0.23.0-beta) — the same unmaintained-by-hand problem, in a second file.

Fix: finishing-a-development-branch — already activated for DigiSmith in W.4 (its Option 1 now pushes to origin after a local merge) — gains one more step: after a successful Option 1 merge, if the repo being finished is DigiSmith's own, bump both version files automatically as part of the same flow. A general lifecycle-hook mechanism (stock vs. custom hooks at various SDLC points, of which this would be one) was raised and explicitly deferred to its own future brainstorm — see backlog/digismith-lifecycle-hooks-y.md (map item Y). This spec covers only the narrow, direct fix.

Gating: the new step must never fire for any other project that installs and uses this same forked skill — only for DigiSmith's own repo. It reuses the exact DigiSmith-tracked-work check brainstorming already established in W.5: the target repo's .claude-plugin/plugin.json has "name": "digismith".

Section 1 — bump-plugin-version.ts

A new script, scripts/bump-plugin-version.ts, in the same style as scripts/check_vendored_skills.ts — exported, independently testable functions plus a thin main() for CLI use:

  • computeNextVersion(current: string): string — parses major.minor.patch[-prerelease] via a strict regex, throws if it doesn't match. Returns major.(minor + 1).0[-prerelease] as a plain integer increment on the minor field (never decimal arithmetic on the string) — e.g. "0.23.0-beta" → "0.24.0-beta". The prerelease suffix (-beta) is preserved verbatim, including its absence.
  • readPluginVersion(pluginJsonPath: string): string — reads and JSON.parses the file, returns its "version" field, throws a clear error if the field is missing.
  • bumpVersionInFile(filePath: string, nextVersion: string): void — reads the file as text and replaces the first "version": "..." occurrence via a targeted regex substitution (not a full JSON.parse/stringify round-trip, so neither file's key order, indentation, or trailing newline drifts). Throws if no "version" field was found to replace.
  • versionChangedSince(repoRoot: string, baseSha: string, pluginJsonRelPath: string): boolean — runs git show <baseSha>:<pluginJsonRelPath>, parses its "version", and compares it against the current working-tree value. Used for the idempotency guard (Section 2).

main() (invoked as node --experimental-strip-types scripts/bump-plugin-version.ts [--base <sha>], run from the repo root — matching how check_vendored_skills.ts is already invoked):

  1. Reads the current version from .claude-plugin/plugin.json.
  2. If --base <sha> was given and versionChangedSince(...) returns true (the incoming branch's own commits already changed the version), prints SKIPPED already changed by incoming branch (<old> -> <current>) to stdout and exits 0 without writing anything.
  3. Otherwise, computes the next version, writes it into both .claude-plugin/plugin.json and .claude-plugin/marketplace.json (marketplace.json's own drifted value is overwritten with the same next version, not incremented from its own stale number — plugin.json is the single source of truth), and prints BUMPED <old> -> <next> to stdout, then exits 0.
  4. Any parse/read/write failure exits 1 with a clear stderr message — same fail-loud convention as check_vendored_skills.ts.

Section 2 — Wiring into finishing-a-development-branch

finishing-a-development-branch's Option 1 (Merge Locally) section gains two small additions, both DigiSmith-repo-only:

  1. Immediately after git pull and before git merge <feature-branch>, capture BASE_SHA=$(git rev-parse HEAD) — the base branch's pre-merge tip.
  2. After the merged result's tests pass (the skill's existing "once the merged result is green" point, immediately before its existing git push origin <base-branch> step): check whether <MAIN_ROOT>/.claude-plugin/plugin.json exists and has "name": "digismith". If so, run node --experimental-strip-types scripts/bump-plugin-version.ts --base "$BASE_SHA". If its output starts with BUMPED, stage and commit both version files in their own small commit (git add .claude-plugin/plugin.json .claude-plugin/marketplace.json && git commit -m "chore: bump plugin version") — never amended into the merge commit. If the output starts with SKIPPED, do nothing further (log it, move on). Either way, proceed to the existing push step immediately after, so origin receives the merge and (when it happened) the bump together in the same push.

If the plugin.json check fails (any other repo, or DigiSmith's own repo missing that file for some reason), skip both new steps entirely — Option 1 continues exactly as it does today. No change to Option 2, Option 3, the detached-HEAD 2-option menu, or Step 6's cleanup.

No test re-run is needed after the bump commit: a grep across every *.test.ts file in this repo (done during brainstorming) found zero tests asserting a literal version-string value from either JSON file — the version bump cannot regress anything the suite checks.

Testing

  • scripts/bump-plugin-version.test.ts, matching check_vendored_skills.test.ts's own style (real file I/O and real git commands against small fixtures, no mocking): computeNextVersion covers a normal bump, a suffix-less version, and a malformed string (throws); bumpVersionInFile covers a successful replace and a missing-field throw, using a temp JSON fixture file; versionChangedSince uses a small local git fixture repo (git init + a commit with one version, then a working-tree edit to a different version) to prove both the "changed" and "unchanged" cases for real, the same style check_vendored_skills.test.ts's own clone tests already established.
  • Manual verification after implementation: run finishing-a-development-branch's Option 1 for real once (this plan's own merge, finishing itself) and confirm both plugin.json and marketplace.json land on the same next version in one extra commit, pushed alongside the merge.

Out of scope

  • The general lifecycle-hook mechanism (stock/custom hooks across multiple SDLC points) — explicitly deferred to its own future brainstorm; see backlog/digismith-lifecycle-hooks-y.md (map item Y).
  • Any change to Option 2 (push + PR) or Option 3 (keep as-is) — the version-bump only makes sense at the moment a change actually lands on main via a local merge; a PR's eventual merge happens outside this skill's control.
  • CI/CD infrastructure (GitHub Actions or similar) — the original backlog item's suggested shape, superseded by this simpler, skill-level fix per Jack's own re-confirmed reasoning this session.
