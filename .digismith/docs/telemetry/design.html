Problem & Goal

Once a ticket ships, DigiSmith has no record of how the work actually happened — which tools got called, how many turns a stage took, where a skill hand-off stumbled, what decisions got made along the way. That's a closed loop with no data feeding back into it: every improvement to DigiSmith's own process today comes from Jack's memory of a session, not from evidence.

Telemetry closes that loop for DigiSmith's own process. When a repo's profile has logging: true, the full Claude Code session transcript for a ticket's build — everything from the moment using-digismith starts working it to the moment superpowers:finishing-a-development-branch's merge decision is made — gets copied back into DigiSmith's own repo as a raw, structured record. No analysis ships with this feature; the goal is building the corpus a future pass can mine for improvement opportunities.

This was originally proposed as "log every action for data collection," covering both DigiSmith's own process and the shipped product's runtime behavior (e.g. a Shopify theme's post-deploy user behavior). Those turned out to be two unrelated engineering problems with no shared infrastructure — this design covers DigiSmith's own process only. Shipped-product telemetry is deferred as a separate, later sub-project (see Roadmap Update).

Non-Goals

  • Not analysis, dashboards, or reporting. This feature captures and stores raw transcripts only. Mining them for patterns is explicitly future work.
  • Not shipped-product telemetry. Runtime behavior of the theme/app itself, post-deploy, is a separate sub-project — different stack entirely (client-side instrumentation, a collection endpoint, a data pipeline), not touched here.
  • Not redacted or filtered. The captured transcript is copied verbatim, including any consumer-repo code, ticket content, or raw tool output it contains. See Accepted Risk.
  • Not a manual toggle. No flag or spoken phrase turns capture on or off for a single session — it's purely gated by the repo's profile, same mechanism as ticket, ephemeral, and reporting.
  • Not crash-recovering. If a session never reaches finishing-a-development-branch's merge decision (abandoned mid-work, session just ends), nothing gets copied back. No retry or backfill mechanism exists for this.
  • Not merged across sessions. A ticket resumed in a later session produces a second, independent telemetry file under the same slug folder — not stitched into the first.

Architecture

Profile Field — profiles/<name>.yml

New boolean field logging, same shape as ticket/ephemeral/ reporting. Proposed defaults: emma.yml → true (this is the UAT target), personal.yml → false.

Start Marker — .digismith/telemetry-marker

A small state file in the repo being worked in, written once using-digismith begins working a ticket under a logging: true profile. Same "config, not generated docs output" treatment as .digismith/profile: sits beside .digismith/docs/, is never git add -f'd, and must be physically present in whatever working directory the work continues in.

.digismith/telemetry-marker
transcript: /Users/jack/.claude/projects/-Volumes-D-.../<session-id>.jsonl
start_line: 142
started_at: 2026-08-12T09:14:00Z
repo: shopify-hub
slug: fix-cart-drawer-padding-mobile

The transcript path is located by the same rule Claude Code itself uses to store session history: ~/.claude/projects/<cwd-with-/-replaced-by-->/, then the most-recently-modified .jsonl file in that directory — the file actively being appended to by the running session. This is a best-effort heuristic (see Error Handling), not a guaranteed session-ID lookup, since no tool in this environment exposes the current session ID directly. repo in the marker (and later in the metadata header) is the basename of the consumer repo's git top-level directory (git rev-parse --show-toplevel) — e.g. shopify-hub.

using-digismith

Step 0/1 gains marker write

After profile resolution, if the active profile's logging is true: locate the current session's transcript file, record its path and current line count, and write .digismith/telemetry-marker in the original checkout — before any worktree exists, same ordering .digismith/profile already follows.

using-digismith

Step 2.6 gains marker copy

Alongside the existing .digismith/profile copy into the new/attached worktree, copy .digismith/telemetry-marker too, if it exists — a plain file copy, never git add. A worktree checks out only committed files, so without this the marker would simply be absent when capture time comes.

new skill: telemetry

Triggers after finishing-a-development-branch's merge decision

Same integration pattern as M and N: a separate skill DigiSmith invokes right after a Superpowers primitive completes, not an edit to Superpowers' own skill file. Reads .digismith/telemetry-marker from the current working directory — absent → skip silently, nothing to capture. Present → read all transcript lines after start_line, prepend one metadata JSON line (repo, slug, ticket key if any, session id, start/end timestamps), and write the result to DigiSmith's own repo at .digismith/telemetry/<repo-name>/<slug>/<start-timestamp>.jsonl, then commit it. DigiSmith's own repo path is resolved via the same "is cwd itself DigiSmith, else ask and remember for this session" rule inject-standards already uses. Deletes .digismith/telemetry-marker from the working directory after a successful capture, so a later reuse of the same worktree doesn't replay a stale marker.

Data Flow

Ticket start (logging: true): using-digismith Step 0/1 → locate live transcript file → write .digismith/telemetry-marker in the original checkout → Step 2.6 copies it into the worktree.

During the build: nothing else happens — the transcript keeps growing on its own as Claude Code writes it; Telemetry adds no runtime overhead or extra instrumentation during the session itself.

Ticket end: superpowers:finishing-a-development-branch reaches its merge decision → the telemetry skill triggers → reads the marker → slices the transcript from start_line to end-of-file → writes + commits the sliced, metadata- prefixed copy into DigiSmith's own repo → deletes the marker from the working directory.

logging: false or no profile file: no marker is ever written; the telemetry skill's post-merge check finds nothing and is a silent no-op.

Error Handling & Edge Cases

  • No .digismith/telemetry-marker at capture time (logging was off, or the marker was lost/never copied into the worktree) → skip silently, no error surfaced. Never blocks the merge.
  • Transcript file from the marker no longer exists, or the most-recently-modified .jsonl heuristic picked the wrong file at start time (e.g. two DigiSmith sessions running against the same repo directory concurrently) → best-effort only in this MVP; report a one-line note that capture couldn't be completed rather than failing the merge step. Not solved robustly here — flag as a known limitation.
  • DigiSmith's own repo path can't be resolved (not the cwd, and the user declines to provide it this session) → skip capture with a one-line note, same non-blocking stance as the missing-marker case.
  • Ticket resumed across multiple sessions → each session that reaches a merge decision (or, more precisely, each session with its own marker) produces its own telemetry file under the same slug folder. Not an error — documented non-goal.
  • Profile has no logging key at all (an older profile file predating this feature) → treat as false, same as any other missing boolean field defaulting to off.

Accepted Risk

DigiSmith's repo is going public, and captured transcripts are committed unredacted. A telemetry file can contain a consumer repo's proprietary source code, full JIRA ticket content, and raw tool output — all of it becomes publicly visible in DigiSmith's git history the moment it's committed. This was raised explicitly during this brainstorm (2026-08-12): recommended against it, Jack chose to commit as-is anyway. Recorded here as a deliberate, informed decision rather than an oversight. If this needs to change later (redaction, gitignoring .digismith/telemetry/, or keeping DigiSmith private after all), that's a revision to this design, not a bug fix.

Testing / Verification

No automated test suite — consistent with every DigiSmith skill so far. Manual dogfood walkthrough:

  1. logging: true (Emma profile), full ticket flow start to finish → marker written at Step 0/1, survives the worktree copy, and a telemetry file lands at the expected .digismith/telemetry/<repo>/<slug>/... path in DigiSmith's repo once finishing-a-development-branch reaches its merge decision.
  2. Captured file's content check: only lines from the recorded start_line onward are present — no earlier, unrelated conversation leaks into the capture.
  3. logging: false (Personal profile, default) → no marker ever written, no telemetry file produced, no other behavior change.
  4. No profile file at all → unaffected, existing behavior.
  5. Marker present but transcript file missing/renamed at capture time → skip gracefully with a one-line note; the merge step itself still completes.
  6. Real UAT (the actual acceptance bar for this feature): run the full flow against Emma's repository on a real JIRA ticket, end to end, and confirm the captured file is legible and contains the expected tool-call/skill-invocation sequence.

Independent of both — doesn't consume or produce either's output.
  • superpowers:finishing-a-development-branch — unmodified itself; Telemetry observes its merge decision as a trigger point, same non-invasive relationship M has with "push and create PR."
