Goal

Add dg clickup move-task. It changes the home List of a ClickUp task through ClickUp's public API v3. The v2 update-task call cannot do this (it fails with 400 TASK_035). No Frontdoor session is needed. The stored CLICKUP_API_TOKEN authenticates the call.

The public API was chosen over Frontdoor on 2026-09-26. Frontdoor stays only as a reference if the two ever behave differently.

The v3 route was proven live on 2026-09-26. It moved DGS-78 (14zcebru2p7) from Pavilion into B.1 with body {"move_custom_fields": true}. The response was {"data":{"task_id":"14zcebru2p7","new_list_id":"1301150000002300"}}, and the status was kept.

Client (packages/clickup-client)

  • Add ClickUpClient.moveTask(taskId, listId, options = {}). It sends PUT https://api.clickup.com/api/v3/workspaces/${teamId}/tasks/${taskId}/home_list/${listId}.
  • The v3 URL is absolute, so axios ignores its /api/v2 base URL for this call. The client keeps one axios instance. The Authorization header and the rate limiter stay shared. The workspace id is the existing CLICKUP_TEAM_ID.
  • Add the type ClickUpMoveTaskOptions in snake_case, like ClickUpTaskWriteBody:
    • status_mappings?: { source_status: string; destination_status: string }[] (by status id, for a destination List that lacks the task's current status)
    • move_custom_fields?: boolean
    • custom_fields_to_move?: string[] (stays in the type, but the command does not expose it)
  • Add the type ClickUpMoveTaskResponse as { data: { task_id: string; new_list_id: string } }.
  • The method returns the raw response body, like the other methods. An empty options object sends {}.
  • For a task in multiple Lists, only the home List changes. This is ClickUp's behavior, and the client does not change it.

Command (packages/cli/src/clickup/move-task.ts)

dg clickup move-task --task <id> --list <id>
    [--status-map <srcStatusId>=<dstStatusId>]...
    [--move-custom-fields]
  • The command follows the create-list pattern: createMoveTaskCommand(clientFactory = createClient), JSON output on stdout, and clickup move-task: <message> on stderr with exit code 1 on failure.
  • --task and --list are required. An empty or whitespace-only value fails before any client call.
  • --status-map repeats. Each value splits on the first =. A value with no =, or an empty side, fails before any client call.
  • --move-custom-fields is a boolean flag. It sets move_custom_fields: true. The command never sends the field when the flag is absent.
  • Register the command in packages/cli/src/clickup/index.ts. Add one line to packages/cli/README.md.

Tests

All tests use mocks. No test calls real ClickUp.

LayerCases
Client (client.test.ts)PUT method; absolute v3 URL with the team id, task id and list id; options sent as the body; {} sent when no options are given; response body returned.
Command (move-task.test.ts)Flags parse into the right moveTask call; repeated --status-map; --move-custom-fields on and off; empty --task; empty --list; malformed --status-map; client failure sets exit code 1.

Parallel work with DGS-137

A second worker builds dg clickup update-list (DGS-137) at the same time, in its own worktree. Both builds touch the client package and packages/cli/src/clickup/index.ts. Edits stay additive:

  • moveTask goes right after deleteTask in client.ts. Its types go right after ClickUpTaskWriteBody in types.ts.
  • The command registers after updateTaskCommand in index.ts.
  • Whoever finishes second rebases on main.

Both builds are lineage D.3 and share .digismith/docs/D/D.3/handoff.md. Each build keeps its own folder: D/D.3/add-dg-clickup-move-task-command/ here, and D/D.3/add-dg-clickup-update-list-command/ for DGS-137. When this build writes the handoff, it reads the existing note first and carries forward the other worker's entries.

Live check

The build makes no real ClickUp call. After the build, the worker stops and reports to the maestro. The maestro names the live move. The worker does not assume a ticket or a target List.

Out of scope and follow-ups

  • --custom-field on the command (custom_fields_to_move). The client type keeps the option. The command can add it later.
  • dg clickup move-folder (DGS-75).
  • The Frontdoor PUT /tasks/v2/taskPosition call.

Follow-up for the handoff and the report (no ticket): no ClickUp command prints the response body of a failed call. Axios shows only "Request failed with status code 400". A failed --status-map is hard to debug because of this. The fix belongs in a shared error helper in the client or in lib.ts, not in this command.
