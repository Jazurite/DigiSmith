Problem

DigiSmith has no way to know what a dispatch actually cost. The Claude Agent SDK's self-reported total_cost_usd is unreliable for non-Anthropic models (K.3's own spike finding), and nothing currently converts a dispatch's real token counts into an actual dollar figure for any provider. This item builds that missing piece: a small, generic calculation tool — not tied to offload dispatches specifically, not an analytics platform, just a token counter with real pricing data behind it.

Scope

A standalone calculation tool usable for any dispatch — a native Claude Code session just as much as an offloaded one via Chutes or TokenReply. Given a provider, a model, and real token usage (input/output/cache counts), it returns a computed cost record. Nothing more.

Explicitly not in scope for this item: comparing gateway cost against the native-Claude-Code equivalent (split out as its own sub-item, K.4.2, since "which native model represents the comparison baseline" is a real, separate design question deferred rather than decided here); any analytics service, dashboard, or persistent store (a future, not-yet-assigned map letter's job — this tool is one thing that letter could eventually consume, not something it needs to exist for); cumulative/running totals (same reasoning); live-fetched pricing (a hardcoded table for now, matching how K.3's own provider definitions are hardcoded too).

Architecture

Structurally modeled on two things that already do this well: vLLM's own tool_parsers/ directory (one file per model family, a common interface, a registry — confirmed via the local reference clone at D:/Workspace/Library/vllm to have no pricing concept anywhere, so only the organizational pattern is being borrowed, not any actual logic), and DigiSmith's own existing scripts/providers/ convention (chutes.ts/ tokenreply.ts/registry.ts). One file per pricing source, a shared interface, a lookup registry — adding a new provider or model later means adding one file and registering it, the same motion as adding a new vLLM tool parser or a new DigiSmith GatewayProvider.

This pricing table is deliberately separate from K.3's GatewayProvider interface — a native Claude Code dispatch never goes through K.3's pluggable-provider system at all, so folding pricing into that interface would leave no natural home for Anthropic's own rates. The token counter's registry treats "anthropic" as just another provider entry alongside "chutes" and "tokenreply".

Components

New

scripts/token-counter/types.ts

PricingEntry interface — {inputPricePerMillion, outputPricePerMillion, cacheReadPricePerMillion?} — and the CostRecord shape returned by the compute function.

New

scripts/token-counter/{chutes,tokenreply,anthropic}-pricing.ts

One file per pricing source. Seeded with real figures already gathered this project: Chutes/moonshotai/Kimi-K3-TEE (~$3/$15 per 1M), TokenReply's kimi-k2.7/kimi-k3/gpt-5.6-luna (the last confirmed at $0.02/$0.12 per 1M; the others flagged for re-verification per K.3's own existing backlog note). Anthropic's file seeded with whatever current published rate applies to the model(s) DigiSmith actually uses.

New

scripts/token-counter/registry.ts

resolvePricing(provider, model): PricingEntry | undefined — same shape as scripts/providers/registry.ts's resolveProvider.

New

scripts/token-counter/compute.ts

computeTokenCost(provider, model, usage): CostRecord — the actual calculation. Pure function, no I/O, fully unit-testable. Calls the webhook dispatch (below) as a side effect after computing, never as part of the return value.

Data flow

Any caller with real usage numbers (a runner's already-parsed ParsedResult, or a native Claude Code session's own reported usage) calls computeTokenCost directly — no dispatch-specific wiring required for the tool itself to work. As one concrete consumer, offload-implementer can call it after its existing Step 5 (session ID/status extraction) and append the resulting CostRecord to the task's report file, but that integration is a separate, later wiring decision, not part of building the tool itself.

Webhook mechanism

After computing a CostRecord, if an environment variable (e.g. DIGISMITH_TOKEN_COUNTER_WEBHOOK_URL) is set, POST the record as JSON to it — fire-and-forget, a short timeout, logging any failure but never throwing. Unset (the case today, since no consumer exists yet) → skip entirely, pure no-op. This is the literal "hookable to a future API" requirement: whatever eventually consumes these records (a future analytics letter, not yet assigned) just needs to run a listener and set one environment variable — no change to this tool required when that day comes.

Error handling

  • Unknown provider/model combination — return the record with costUsd: null and a clear "no pricing data for provider/model" marker, rather than throwing or guessing. A caller can still see the real token counts even when pricing is missing.
  • Webhook POST fails or times out — logged, never thrown. A future, not-yet-built consumer being unreachable must never break whatever real dispatch triggered the computation.

Out of scope

  • K.4.2 — the native-Claude-Code-vs-gateway comparison logic itself (which specific Anthropic model represents "ran natively," and the actual comparison/decision presentation) — deliberately split out, not decided here.
  • Any analytics service, dashboard, or persistent store — a future, not-yet-assigned map letter's territory. This tool is something that letter could consume, not something built to require it existing.
  • Cumulative/running totals — same reasoning as above.
  • Live-fetched pricing — hardcoded table only, consistent with how K.3's own provider definitions work today.
  • Wiring into offload-implementer or any other specific caller — this design builds the standalone tool; actual integration into a consumer's flow is a separate, later decision.

Testing

  • Unit tests for computeTokenCost against the real pricing table — known provider/model combinations produce correct cost math; an unknown combination returns costUsd: null with the marker, never throws.
  • A mocked-fetch test confirming the webhook fires when the environment variable is set, and is skipped entirely when it isn't.
  • No live dispatch test needed — this tool never touches dispatch execution itself, only already-captured usage numbers handed to it by a caller.
