Problem

runConnect's recovery branch (packages/cli/src/vps/connect.ts, the !status.agentAlive.ok case) always calls buildCreateWorkspaceCommand whenever the named agent isn't found. herdr's own workspace create does not dedupe by label, confirmed live by creating two workspaces with the same --label digismith-main and getting two independent, identically-labeled workspaces back.

A killed-but-recovering OpenCode process leaves its herdr pane alive — only the agent registration for that name disappears (herdr agent get opencode-main → agent_not_found). Every real crash/reconnect cycle through dg vps connect therefore abandons the surviving pane and creates a brand-new workspace instead of reusing it. This is not a correctness bug — the new agent still ends up healthy — just orphaned-workspace clutter on the VPS that nothing ever cleans up. Confirmed live during X.1's Task 6 (2026-09-23); full detail in backlog/vps-connect-workspace-dedup-x1.md.

Confirmed herdr JSON shapes

Confirmed locally (2026-09-24) by starting a local herdr server and running these commands directly, rather than assuming shapes from the backlog note's prose description alone.

herdr workspace list

{"result":{"type":"workspace_list","workspaces":[
  {"workspace_id":"w2","label":"opencode-k3-spike","pane_count":1, ...},
  {"workspace_id":"w3","label":"classifier-trial-1","pane_count":1, ...}
]}}

herdr pane list --workspace <id>

{"result":{"type":"pane_list","panes":[
  {"pane_id":"w2:p1","agent_status":"idle","workspace_id":"w2", ...}
]}}

herdr agent start on an already-occupied pane

{"error":{"code":"agent_pane_busy","message":"agent target pane w2:p1 is not an available shell"},"id":"cli:agent:start"}

Exit code is non-zero (1) for this error, matching the existing convention that herdr prints its JSON errors to stdout (see describeSshFailure's own comment in run-command.ts).

Recovery flow

Before creating a new workspace, list existing workspaces, filter to ones whose label matches config.workspace_label, and for each match (in list order), list its panes and attempt agent start on each pane (in list order) until one succeeds. Only fall through to today's buildCreateWorkspaceCommand path if every candidate pane comes back agent_pane_busy, or there were no label matches at all.

No pre-filtering on the pane list's own agent_status field — that field could be stale between the list call and the start attempt. agent start's own response is the single source of truth for whether a pane is actually available.

New builders/parsers (checks.ts)

FunctionShape
buildWorkspaceListCommand(config)→ SshCommand running herdr workspace list
buildPaneListCommand(config, workspaceId)→ SshCommand running herdr pane list --workspace <id>
parseWorkspaceListOutput(exitCode, stdout)→ { workspaceId: string; label: string }[]. Empty array on any exit-code or parse failure — soft-fail by design.
parsePaneListOutput(exitCode, stdout)→ string[] of pane IDs in list order. Empty array on failure.
isAgentPaneBusyError(exitCode, stdout)→ boolean. True only when exit≠0 and the parsed JSON is exactly {error:{code:"agent_pane_busy"}}.

Placed in checks.ts alongside the existing read/check-style builders and parsers (buildAgentGetCommand, parseAgentGetOutput, etc.) — the mutating buildCreateWorkspaceCommand/buildStartAgentCommand stay in connect.ts, matching the existing split.

Orchestration (connect.ts)

New function tryReuseExistingPane(config): boolean:

  1. List workspaces, filter to label === config.workspace_label.
  2. For each matching workspace (in order): list its panes, and for each pane (in order) run buildStartAgentCommand(config, paneId) — the same builder already used for a freshly-created pane, unchanged.
    • Exit 0 → log which pane was reused, return true. The agent is already started; nothing further to do.
    • agent_pane_busy → try the next candidate pane, then the next workspace.
    • Any other failure → hard failure, process.exit(1), same treatment as today's start-agent failure on a freshly created pane.
  3. All candidates exhausted (or no label matches at all) → return false.

runConnect's !status.agentAlive.ok branch becomes:

if (!status.agentAlive.ok) {
  // integration install stays unconditional here — idempotent, machine-wide,
  // not workspace-specific
  const integrationInstall = runSshCommand(buildInstallHerdrIntegrationCommand(config));
  ...

  if (!tryReuseExistingPane(config)) {
    // today's create-workspace-and-start-agent path, unchanged
  }
}

Error handling

The workspace list/pane list calls themselves are treated as soft-fail: if either comes back with an unexpected error (SSH hiccup, malformed JSON — anything other than a clean list), parseWorkspaceListOutput/parsePaneListOutput simply return an empty array, which reads as "no reusable candidates" and falls through to creating a new workspace exactly as today. This is a leak-reduction optimization on top of an already-working recovery path — it must never make connect less reliable than it is today, so a failure in the optimization itself never blocks reaching a healthy session.

A confirmed agent_pane_busy is the only signal treated as "move to the next candidate." Every other agent start failure — on either a reused or freshly created pane — remains a hard, terminal failure, unchanged from today's behavior.

Testing

Vitest unit tests for the five new builders/parsers, added to connect.test.ts (or a checks.test.ts if one exists), using the real captured JSON shapes above — same style as the existing builder/parser tests in that file. Cases: multi-workspace list with a label match and a non-match, an empty/malformed list, a real agent_pane_busy error payload (true) vs. a different error code (false) vs. success (false).

tryReuseExistingPane and runConnect itself stay live-verify-only, consistent with X.1's own precedent (no mocked SSH/spawnSync for the orchestration layer).

Live verification: reuse X.1's Task 6 crash-simulation — kill the OpenCode process on the VPS, run dg vps connect again, and confirm via herdr workspace list that no new duplicate workspace was created and the existing pane was reused.

Out of scope

  • status.ts gaining an orphaned-workspace warning (the backlog note's optional item 4) — deliberately deferred, kept out of this build to stay focused on the connect-path fix.
  • Auto-closing already-busy or already-leaked workspaces — never done automatically. A "busy" pane only means it isn't an available shell right now, not that it's abandoned; closing it is a much bigger, riskier call than reusing an idle one.
  • Refreshing the TokenReply credential on a reused pane. TOKENREPLY_API_KEY is only injected via --env at herdr workspace create time — a reused pane keeps whatever key was current when its workspace was originally created. If the key was rotated since then, agent start still succeeds (it's not aware of credentials at all) and the agent fails authentication later, at runtime, rather than at connect time. The old always-create path didn't have this gap, since every workspace got a fresh key. Noted here as a known limitation (found during final review) rather than fixed — closing it would mean sourcing the credential file before every reused-pane agent start, which needs its own design pass if it ever causes a real failure.
  • Backfilling report.html for X.1 and adding letter X's row to MEMORY.md's map table — a separate housekeeping gap noticed in passing, spun off as its own task rather than folded into this build.
