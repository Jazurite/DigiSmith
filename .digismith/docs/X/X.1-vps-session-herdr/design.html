Overview

X.1 replaces V.3 in place. Same purpose — a persistent, reach-from-anywhere coding session hosted on the Hetzner VPS — same CLI surface (dg vps status, dg vps connect), same config file path (~/.digismith-depot/vps.json). Two things change: the payload becomes OpenCode+TokenReply (default model kimi-k2.7) instead of claude, and the persistence mechanism becomes herdr instead of raw tmux+SSH.

The swap is deliberate, not incidental. Two real spikes (2026-09-19, 2026-09-22) confirmed herdr survives a genuine SSH disconnect on the actual VPS without needing the loginctl enable-linger fix V.3's tmux approach required — tested with lingering explicitly disabled as a controlled variable, both for a bare idle server and for a real OpenCode+TokenReply agent mid-conversation. The classifier-avoidance question that also motivated investigating herdr (does routing dispatch through it dodge Claude Code's auto-mode permission classifier — K-lineage's own problem) was tested too and came back genuinely inconclusive, not confirmed — that question stays open, tracked separately in backlog/offload-blocked-by-permission-classifier-k.md, and plays no role in this design. X.1 is scoped on the persistence result alone.

Map placement: this is X's territory by explicit decision, not a V sub-item, even though the shape (a Depot-style ensure/status/connect resource) looks similar to V.1/V.2/V.3. X stays the letter for "the VPS as a place things run"; V stays Depot's own narrower resource-management pattern.

Architecture

packages/cli/src/vps/ gets its internals rewritten, not relocated — same files, same dg vps status/connect entry points, different implementation underneath:

  • config.ts — same host/user/identity_file fields; tmux_session is replaced by two herdr-native identifiers, workspace_label and agent_name (herdr addresses things by name, not a single session string).
  • checks.ts/status.ts — SSH reachable → herdr installed → herdr server running → toolchain on PATH (node/pnpm/opencode, via the same explicit nvm-sourcing dance V.3 already had to work out — a plain non-login SSH exec still doesn't source ~/.bashrc) → workspace/agent alive → OpenCode actually running as a state distinct from "pane alive, agent dead" (same distinction V.3 already drew for claude) → TokenReply credential file present. The lingering check is dropped entirely — nothing on the VPS needs it once claude/tmux are retired.
  • connect.ts — same "run every check, auto-fix what's safe, then attach" shape as V.3. Auto-fixable: herdr server not running → start it; workspace/agent missing or dead → recreate (herdr workspace create + herdr integration install opencode if not already installed + herdr agent start). Never auto-installs herdr itself — same disposition V.3 already takes for nvm/node/pnpm/ claude. Final step: ssh -t ... herdr agent attach <agent_name>, replacing tmux attach.
Carried forward as an assumption, not a verified fact: if OpenCode itself crashes inside a herdr pane, the pane is assumed to survive (drops to its underlying shell, the same way V.3's exec bash fallback kept a dead claude from taking the whole tmux session down with it) — herdr panes are terminal panes, and a terminal pane's underlying shell doesn't die just because its current foreground process exited. Neither spike tested this directly. Worth a real check early in implementation; if it turns out false, this design needs a fallback-shell equivalent to V.3's launcher script.

Config File

~/.digismith-depot/vps.json — same location as V.3, updated shape:

{
  "host": "46.225.49.140",
  "user": "root",
  "identity_file": "~/.ssh/jazurite",
  "workspace_label": "digismith-main",
  "agent_name": "opencode-main"
}

Same disposition as V.3: hand-written, no creation/edit tooling, no automated VPS provisioning. Absent file → both commands stop immediately with a plain message; neither guesses a host.

Credential & Provider Config

This is where X.1 genuinely improves on V.3, not just swaps mechanisms. V.3's credential step (claude's OAuth login) is a real browser flow — un-automatable by design, so connect could only warn and proceed. TokenReply's credential is a plain API key, already sitting in ~/.digismith-depot/.env on the local machine — trivially copyable.

  • Credential file on the VPS: ~/.config/tokenreply.env, sourced before OpenCode launches — same shape as V.3's ~/.config/claude-code.env, holding a plain API key instead of an OAuth token.
  • connect auto-fixes this, unlike V.3's claude-OAuth case: if the file is missing on the VPS, copy the value from the local .digismith-depot/.env — write-locally-then-scp, the same pattern that avoided the nested-SSH-quoting trap in both spikes (a $schema key got silently mangled to "\": the one time this was attempted as an inline ssh host "... $VAR ..." command instead). Never build the remote command by interpolating the credential into a quoted SSH argument.
  • opencode.json provider config: also auto-written if missing, generated via DigiSmith's own already-working scripts/providers/print-config.ts tokenreply --role task --runner opencode — no new integration code; this already produces the correct JSON block, confirmed live in both spikes. Default model is kimi-k2.7 (the task role), matching K.3's own reliability-driven default — kimi-k3 has a confirmed-flaky tool-calling bug (three distinct failure signatures logged across backlog/tokenreply-kimi-k3-tool-calling-failure.md) and stays opt-in, never the default here.

connect's full auto-fix list: herdr server, workspace/agent, the TokenReply credential file, and opencode.json — genuinely more self-healing than V.3, not just a mechanism swap wearing V.3's old clothes.

Same read-only, non-modifying contract as V.3 — every check below over one-shot SSH calls, plain report.

Command: connect

Runs every status check, auto-fixing what's safely fixable, then attaches:

  1. SSH unreachable → stop, report. Nothing past this point is attempted.
  2. herdr missing → stop, report, point at herdr's own installer. Never auto-installs.
  3. Toolchain missing (node/pnpm/opencode) → stop, report exactly which piece, point at manual install steps. Never auto-installs — same stance V.3 already takes.
  4. herdr server not running → auto-fix: start it (nohup herdr server &, matching the exact invocation confirmed live in both spikes to survive an SSH disconnect).
  5. Workspace/agent missing or dead → auto-fix: herdr workspace create if the workspace doesn't exist, herdr integration install opencode if not already installed, then herdr agent start <agent_name> --kind opencode --pane <id> -- --model tokenreply/kimi-k2.7.
  6. TokenReply credential missing on the VPS → auto-fix: copy from the local .digismith-depot/.env, write-locally-then-scp. If it's also missing locally, stop and report — nothing to copy.
  7. opencode.json missing or malformed → auto-fix: regenerate via print-config.ts, write-locally-then-scp.
  8. Attach — the final step, replacing the script's own process: 
    exec ssh -i <identity_file> -o IdentitiesOnly=yes -t <user>@<host> "herdr agent attach <agent_name>"

Migration from V.3

The existing hand-provisioned tmux+claude session on the VPS becomes dead weight once this ships. Not automated — a one-time teardown, not a reusable operation worth building tooling for. Manual steps during rollout: kill the claude-main tmux session, remove ~/start-claude.sh and claude's credentials file. loginctl enable-linger is left as-is (nothing will need it going forward, but leaving it on is harmless — not worth another risky toggle for no real gain).

Error Handling

CaseDisposition
vps.json absentStop immediately, plain message: no VPS configured.
SSH unreachableReport the actual SSH error plainly. No retry.
herdr not installedStop, point at the platform-appropriate installer (Unix curl \| sh for the VPS itself, since it's Linux). Never auto-install.
nvm/node/pnpm/opencode missing on the VPSStop, report exactly which piece is missing, point at manual install steps (nvm install script, corepack enable, pnpm add -g opencode-ai then pnpm approve-builds --global opencode-ai — pnpm skips postinstall scripts by default, hit live in both spikes). Never auto-install.
herdr server fails to startStop, show the log content, don't retry silently.
Workspace/agent recreated but OpenCode immediately crash-loopsconnect still attaches (pane assumed to survive, see Architecture's callout); status reports "workspace alive, OpenCode not running" as a distinct non-healthy state.
TokenReply credential absent on both VPS and locallyStop, report clearly — nothing to auto-copy.
opencode.json write failsReport the actual error plainly, don't silently continue as if it succeeded.

Testing

Same split V.3 already established, per map item G.2's standing toolchain default (Vitest): config-file parsing/validation, the ssh/herdr command strings the script constructs, and the health-check result-aggregation logic are pure functions, tested directly. The actual herdr/SSH orchestration itself is not meaningfully unit-testable — mocking it would test the mock, not the behavior that matters — so, matching V.1/V.2/V.3's own existing practice, that part is live-verify-only, confirmed against the real VPS as part of implementation.

Out of Scope

  • Provisioning a new VPS — no Hetzner API calls, no server creation/teardown. Same as V.3.
  • Multiple VPSes — one config file, one host. Same as V.3; not a concern for a single-user personal tool.
  • Auto-invoking from bootstrap/adopt — opt-in only, same as V.3.
  • The classifier-avoidance question — tested (2026-09-22), genuinely inconclusive, K-lineage's own open question, plays no role here. See backlog/offload-blocked-by-permission-classifier-k.md.
  • Relocating other Depot resources (Agentic Bridge, etc.) onto the VPS with real network auth — the separate, deliberately-unrelated idea in backlog/practice-devprod-infra-x.md.
  • claude support — retired along with V.3's tmux approach, not preserved as a parallel option. If a future need arises for a claude-backed persistent session again, that's a new design, not a flag on this one.
