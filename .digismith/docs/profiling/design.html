Problem & Goal

Jack works across contexts DigiSmith currently treats identically: real Emma client tickets that want the full SDLC (JIRA ticket, standards injection, ephemeral-deploy capture, an implementation report), and personal projects that want the same brainstorm → spec → plan → build → review → commit/merge core but none of the ticket-tracking or deployment machinery around it. Today every skill's behavior is fixed, so the only way to get the lighter shape is to manually skip steps by hand — an undocumented, ad hoc deviation from pillar 5's prescriptive stance ("no skipping spec because it felt small"), not a declared choice.

Profiling makes that variation a first-class, named, per-repo setting: a profile is a small set of on/off toggles over the stages that already exist (ticket intake, standards injection, ephemeral-deploy capture, implementation reporting). Two profiles ship now — Emma (everything on) and Personal (ticket, standards, and ephemeral off; brainstorm, spec, plan, build, review, and reporting stay on) — and the mechanism is built to add more later by plugging in a different combination, not by writing new code per profile.

Non-Goals

  • Not an inheritance/composition system. When G was built, it deliberately adapted Agent OS's pattern with "no profile/inheritance system." This feature doesn't reopen that — profiles here are flat, independent files with no extends/override chain. A future profile that needs to share config with another is still two separate files.
  • Not auto-detected. The profile is always an explicit choice the user makes (first use or an explicit switch) — never inferred from repo signals. This is additive to, not a replacement for, inject-standards's existing Shopify-repo-layer heuristic, which still governs repos that have no profile file at all (see Architecture).
  • Not retroactive. Switching a repo's profile mid-point only changes decisions for stages not yet entered. A ticket already mid-build under Emma doesn't un-inject standards it already received.
  • Not toggles for unbuilt stages. Delivery (D), QA handoff (I), design review (F), and estimation (J) aren't built yet, so there's nothing to gate — no toggle keys are added for them now. When one of those ships and a profile actually needs to vary on it, extend the schema then.
  • Not a separate switch-profile skill. Switching is a front-door intent inside using-digismith (same pattern as its existing "ticket only, no build" door), not a new skill file.

Architecture

Profile Definitions — profiles/<name>.yml

A new top-level profiles/ directory in DigiSmith's own repo, one flat YAML file per profile. Ships with two:

profiles/emma.yml
---
name: emma
standards: [global, shopify, team]
ticket: true
ephemeral: true
reporting: true

profiles/personal.yml
---
name: personal
standards: []
ticket: false
ephemeral: false
reporting: true

standards is a list of standards/ subfolder names to make eligible for matching; an empty list means inject-standards is never invoked for this repo. ticket, ephemeral, and reporting are booleans. Stages that don't vary between either profile today — brainstorm, spec, plan, build, review, commit/merge — have no toggle key; they're structural to using-digismith's core and Superpowers' own chain, not profile-dependent.

Active Profile — .digismith/profile

In the consuming repo, a one-line plain-text file containing just the active profile's name (e.g. emma), living alongside the existing .digismith/docs/ convention. Plain text, not YAML — it's a single value today, and a second field can be added later without needing one now (YAGNI).

using-digismith

New Step 0: Resolve Profile

Before Step 1 ("Get a Real Ticket"), check for .digismith/profile in the repo root. Missing → first use in this repo → list profiles/*.yml (resolved via the same "locate DigiSmith, ask if unknown" rule inject-standards already uses), present via AskUserQuestion, write the choice. Present → read it. If it names a profile with no matching profiles/<name>.yml, treat as stale (see Error Handling).

using-digismith

Step 1 becomes conditional

If the active profile's ticket is false, skip invoking jira-intake entirely — no ticket.md is written. Derive the slug directly from the feature description, applying the exact same deterministic rule jira-intake Step 3.1 already defines (lowercase, drop filler words, kebab-case) — restated inline here since jira-intake itself isn't invoked in this path, not reinvented as a different algorithm.

using-digismith

Step 2 branch naming becomes conditional

ticket: true → <Key>__<slug> (unchanged). ticket: false → <slug> alone, no key prefix.

using-digismith

New front-door intent: switch profile

"Switch this repo's profile to X" is recognized alongside the existing "ticket only, no build" door. Validate X against profiles/*.yml, state the behavioral delta (which stages turn on/off) via AskUserQuestion, then overwrite .digismith/profile on confirmation.

inject-standards

New Step 0: Profile Gate

Before Step 1 (read index.yml), check for .digismith/profile in the repo currently being worked in. Present → only folders in the active profile's standards list are eligible for matching, in every scenario (1-4) — an empty list means skip straight to "proceed without a Standards section," same as the existing zero-standards-exist path. Missing (no profile file — e.g. DigiSmith's own repo, or a repo that hasn't adopted profiling) → unchanged, existing behavior, including the Step 3 Shopify-repo-layer heuristic. Additive only; nothing already shipped changes for a repo with no profile.

capture-ephemeral-url

New pre-check

Before Step 1 (Resolve Ticket Key), read .digismith/profile in the repo the PR was opened in. ephemeral: false → report one line ("skipping ephemeral capture — personal profile") and stop; don't poll CI. Missing profile file → unchanged, existing behavior.

report-implementation

Scoped ticket field

When the active profile has ticket: false, the generated report's metadata omits the ticket-key field entirely instead of leaving it blank — there's no ticket to reference. Everything else about the report (delivered work, per-task review table, final-review findings, commit list) is unaffected; reporting: true for personal means the report itself still runs in full.

Data Flow

First use: using-digismith invoked in a repo → .digismith/profile absent → list profiles/*.yml → user picks → write name to .digismith/profile → continue Step 1 gated by the chosen profile.

Every later trigger (this session or a future one): .digismith/profile → profile name → profiles/<name>.yml → relevant toggle → gate this skill's own stage. Each of the four consuming skills ( using-digismith, inject-standards, capture-ephemeral-url, report-implementation) performs this lookup independently, at its own trigger point — there is no central orchestrator relaying the decision, since M and N already trigger on their own conditions (a PR's CI check, a plan's final review passing) outside using-digismith's control, often in a different session.

Mid-point switch: explicit "switch profile" request → validate against profiles/*.yml → confirm behavioral delta → overwrite .digismith/profile. Next trigger of any of the four skills reads the new value; nothing already in flight is revisited.

Error Handling & Edge Cases

  • .digismith/profile names a profile with no matching profiles/<name>.yml (deleted or renamed) → treat as stale, re-run the first-use picker rather than guessing or silently falling back.
  • profiles/ is missing or empty in DigiSmith's own install → shouldn't happen (ships with two), but if it does, stop and report clearly — same can't-proceed pattern jira-intake already uses for its own blocking conditions.
  • User declines to pick a profile on first use → using-digismith stops after explaining a profile is required to proceed, same edge-case shape as the existing key-less-ticket stop.
  • No .digismith/profile exists at all (repo predates this feature, or using-digismith was never run in it) → every consuming skill treats this as "no profile set," falling back to its prior, unrestricted behavior — non-breaking for every repo already using DigiSmith today.
  • "Switch profile" requested but no .digismith/profile exists yet → not an error, same flow as first use.

Testing / Verification

No automated test suite — consistent with every DigiSmith skill so far. Manual dogfood walkthrough:

  1. First use, pick Emma → ticket flow, branch naming, standards injection, ephemeral capture, and reporting all behave exactly as they do today (regression check).
  2. First use, pick Personal → jira-intake never invoked, branch named <slug> with no key, inject-standards proceeds without a Standards section, a PR in this repo skips ephemeral capture with the one-line notice, and the end-of-plan report generates with no ticket field.
  3. .digismith/profile names an unknown profile → re-prompts instead of guessing.
  4. Repo with no .digismith/profile at all → every consuming skill behaves exactly as it did before this feature shipped.
  5. Mid-point switch Emma → Personal (and back) → behavioral delta stated correctly before confirmation; a ticket already mid-build under the old profile isn't revisited.

Relationship to Other Map Items

  • E (using-digismith) — gains the Step 0 profile resolution, conditional Step 1/2, and the new switch-profile front door. Its core job (ticket → branch → brainstorming hand-off) is unchanged when a profile has everything on.
  • G (inject-standards) — gains an additive profile gate ahead of its existing scenario logic. Repos with no profile file see zero behavior change.
  • M (capture-ephemeral-url) — gains a pre-check; unaffected when ephemeral: true or no profile file exists.
  • N (report-implementation) — gains one conditional field omission; otherwise unaffected.
  • A (jira-intake) — unchanged itself; using-digismith simply stops calling it when ticket: false.

Roadmap Update

Adds a new row to MEMORY.md's map table: O — Profiling, "A per-repo behavior profile (standards subset, ticket/ephemeral/reporting on-off) that existing stages consult independently at their own trigger point." Placed in Tier 1 ("the frame") alongside G and E — it's a prerequisite gate for both, not a later pipeline stage.
