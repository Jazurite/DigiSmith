Problem

After finishing-a-development-branch completes, the running session's context keeps everything from the just-finished feature — full implementation detail, review findings, doc content — none of which is useful for whatever comes next. Jack's request: a cleanup step that offers to clear the session's context once the work is genuinely done, so the next piece of work starts fresh instead of carrying that bloat forward.

The clear_context preference

A new key in the existing per-repo preferences store (map item H), read and written through digismith:preferences exactly like finish_option (H.1) and ssh_key (H.2) already are — no new storage mechanism. Values: yes or no. Unset means no default has been chosen yet for this repo.

Placement

A new Step 7: Offer to Clear Context in finishing-a-development-branch, placed after Step 6 (Cleanup Workspace) and before the Quick Reference table. Applies only after Option 1 (Merge Locally) and Option 2 (Push and Create PR) — never Option 3 (Keep As-Is), which is a deliberate deferral, not completion. This is the same distinction Step 4.5 already draws for its own follow-up ("never Option 3").

Applies in every repo this skill runs in, DigiSmith's own included — unlike the three stock post-finish hooks (version bump, plugin reinstall, history update), which are gated to DigiSmith's own repo and currently only ever fire there (confirmed: bootstrap/ adopt do not propagate .digismith/hooks/post-finish/ into consumer repos today). Because this needs to work everywhere, it is wired directly into finishing-a-development-branch's own body — the same way H.1's finish_option and H.2's ssh_key already are — not built as a fourth stock hook.

Flow

Mirrors Step 3.5/4.5's existing shape exactly:

  1. Check clear_context via digismith:preferences' get.
  2. Unset → ask: "Clear this session's context now that the feature is done?" After the answer, a separate follow-up: "Remember this as your default for this repo?" — yes writes the value via digismith:preferences' set; no proceeds for this run only, asking again next time.
  3. Set to yes → skip the ask, announce "Using saved default for this repo: clearing context now. Say 'don't clear' to override once."
  4. Set to no → skip silently, proceed without clearing.
  5. Explicit override present in the human partner's own message for this specific run (either direction) wins for that run only — the saved value is never touched by an override alone, same restraint Step 3.5 already applies to finish_option.

Clear-call mechanics

When proceeding to clear, invoke mcp__ccd_session_mgmt__clear_session with session_id: "self". Critical ordering: the clear only takes effect once the current turn ends and the session goes idle — nothing said before that point survives into the next context — so the assistant's complete final summary (what shipped, what's next) must be said before this tool call, never after. The call itself also carries its own app-level approval prompt, independent of this feature's own conversational ask (except in auto or bypass-permissions mode). If the human partner sends another message before the session goes idle, the queued clear is silently dropped by the tool itself — an existing safety net this design relies on rather than re-implements.

Unresolved-thread warning

Before clearing, scan the conversation for any unresolved thread unrelated to the feature just shipped — a pending question, a task mentioned but not started, something asked to be revisited later. If one exists, say so plainly as part of the final message, before the clear call: "Note: before I clear this session's context, you still have [X] open from earlier — nothing's tracking that after this clears, so make a note if you want to come back to it." This is a verbal warning only — no file is written, no memory entry is created; the human partner carries the information forward themselves. If nothing unresolved is found, skip this silently.

Scope

Out of scope: persisting unresolved-thread state anywhere (explicitly declined in favor of a plain warning); a fourth stock post-finish hook or propagating hooks to consumer repos (this feature doesn't need that infrastructure); any change to Option 3's behavior; verifying whether clear_session re-triggers full session-start initialization (MEMORY.md/CLAUDE.md reload) — not load-bearing for this design since nothing here depends on it, and will be observable empirically the first time this actually runs.
