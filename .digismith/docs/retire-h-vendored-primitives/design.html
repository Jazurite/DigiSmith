Background

Map item H (Subagent-driven always) is implemented today by a standalone native DigiSmith skill, digismith:subagent-driven-always, which intercepts digismith:writing-plans' Execution Handoff step from the outside — skipping its "1. Subagent-Driven / 2. Inline?" question and defaulting unconditionally to digismith:subagent-driven-development. This is the same "H/Q-style interception" pattern map item W exists to move away from, and W.5 just proved the fold-in mechanism works for real (retiring Q into brainstorming/writing-plans directly).

Jack's direction, raised immediately after W.5 shipped: retire H the same way, and also change the actual policy while doing it — instead of an unconditional "always subagent-driven" default, reason autonomously about task complexity (still never asking the user which to use). Reading H's own current content surfaced the real constraint this idea has to resolve: H's "always subagent-driven" default exists specifically because two other shipped map items depend on it — N (report-implementation) needs the per-task ledger only subagent-driven-development produces, and G (inject-standards) was assumed to have nothing to inject into otherwise. Jack's answer, when asked directly: build the missing lightweight equivalent for the inline path rather than accept the gap.

Section 1 — Classification logic, folded into writing-plans' Execution Handoff

Once writing-plans finishes writing the plan (it already knows the task count and content — no re-derivation needed), instead of presenting the "1. Subagent-Driven / 2. Inline?" question, it reasons autonomously: 1-2 tasks with no unusual risk or isolated-context need → inline-eligible (invoke digismith:executing-plans directly); 3+ tasks, or fewer tasks that are unusually risky or need isolated context → subagent-driven (invoke digismith:subagent-driven-development directly). This absorbs H's other two existing branches unchanged: explicit user request for inline execution (still respected, never overridden) and no-subagent-capability environments (still an automatic fallback, not a judgment call). The user-facing question stays permanently gone — the new branch is autonomous reasoning, not a third live question.

Section 2 — executing-plans gains a lightweight ledger, built from scratch

executing-plans currently has no persistent tracking at all — just ephemeral todos. It gains one, reusing the exact path convention report-implementation already checks: .superpowers/sdd/<plan-basename>/progress.md. Since a given plan only ever goes one way (inline or subagent-driven, never both), there is no collision risk, and report-implementation's existing "does a ledger exist" check needs no change — only what it does once it finds one. The first line distinguishes which mechanism produced it: # Inline-execution ledger — plan: <plan file path> (vs. SDD's # SDD ledger — plan: ...).

Per task, after all its steps complete (implementation, tests, commit — the last bite-sized step is always "Commit" per writing-plans' own task structure), executing-plans' Step 2 gains a brief self-check pass (completeness, quality, discipline — the same spirit as subagent-driven-development's implementer self-review, not the full ceremony) before appending one ledger line:

Task <N>: complete (commits <base7>..<head7>, self-check: <one-line summary>)

No review-verdict, no fix-round grammar — there is no independent reviewer to produce one. This is executing-plans' first real activation — it has been a dormant, byte-identical clone since W.1.

Section 3 — report-implementation branches its template by ledger type

The Prerequisites section's existing skip condition ("no ledger exists at all → skip silently") stays, but its stale parenthetical example ("e.g. the plan ran via digismith:executing-plans instead") is removed, since that path now also produces a ledger. Once a ledger is found, report-implementation reads its first line to decide which grammar to parse:

SDD ledger

Unchanged

Existing behavior: per-task review verdicts, parked/discarded findings, the final whole-branch review section.

Inline-execution ledger

New, simpler shape

Task list with commits and self-check summaries, no review-verdict column (no independent reviewer existed), and no final-review section at all — inline execution has no equivalent whole-branch review step today, so that section is omitted entirely rather than rendered empty.

This is a real branch in the report template — the two shapes genuinely differ in what they claim happened, not a cosmetic tweak. This is a normal edit to a native DigiSmith skill (map item N), not a vendored-primitive activation — report-implementation was never one of the 14 vendored Superpowers skills.

Section 4 — inject-standards (G): confirmed, no change needed

Re-checked Scenario 1's actual formatting ("Conversation — default, regular chat/implementation work" → read the standards and announce them inline). That is exactly what already happens when a session implements tasks directly rather than dispatching a subagent — inline execution via executing-plans does not create a new kind of context, it just means Scenario 1 is the active one instead of Scenario 4. G's docstring already covers this; H's old claim that G "has nothing to inject into unless a subagent is dispatched" described the old assumption that all real implementation went through subagent dispatch, not an actual limitation in G itself. Zero changes to inject-standards.

Section 5 — Call-sites, retirement, and letter H freed

Checked all references to subagent-driven-always repo-wide (19 files; frozen historical docs under .digismith/docs/** excluded per established convention):

  • README.md — same pattern as Enforcer's paragraph: H's descriptive block is removed, "Six skills" → "Five skills," and the "one right after a plan is saved, before any task code is written" clause drops from the intro sentence (it described H's trigger specifically).
  • skills/adopt/SKILL.md (line 297) — already slightly imprecise even today: H's trigger is specifically writing-plans' Execution Handoff, but adopt never invokes writing-plans at all (it bypasses straight to subagent-driven-development), so H never actually fired in this flow to begin with. After retirement, the mention is simply dropped, leaving only the inject-standards Scenario 4 reference (which genuinely does apply).
  • .digismith/history.html — same retirement-note treatment as Q's status block got in W.5.

skills/subagent-driven-always/ (native DigiSmith skill, not one of the 14 vendored Superpowers primitives) is deleted entirely. Its logic splits three ways: the complexity-decision plus the two unchanged old branches fold into writing-plans (already activated by W.5 — this further diverges the same file); the new ledger/self-check need genuinely activates executing-plans for the first time; report-implementation's template branch is a normal native-skill edit, no vendoring ceremony. MEMORY.md marks H retired (same pattern as Q), letter freed for future reuse. The backlog file retire-subagent-driven-always-h-w6.md is deleted once applied, per the backlog's own convention.
