Overview

Everything DigiSmith can do from a terminal today needs a repo checkout: node --experimental-strip-types scripts/vps-session/cli.ts status only works from inside a clone. V.4 publishes a real CLI package, @digismith/cli, so the same commands install on any machine with pnpm add -g @digismith/cli and run as digismith … or the short alias dg …. It is Depot's distribution surface — the "biggest descendant" of V — and V.3's vps commands are the first thing shipped through it.

The first version is deliberately small: one command group (vps), a minimal build step, no dependencies, manual publish. The package's job in V.4 is to exist correctly and to have a shape that later groups slot into without restructuring.

Decided during this brainstorm, in order: scope is the package only (login/credentials/server connection is a later spec — it needs the server side that backlog/practice-devprod-infra-x.md reserves for letter X) · v1 ships vps only · name @digismith/cli, matching the workspace scope @digismith/jira-client already uses · console names digismith and dg.
Amended 2026-09-12, mid-implementation. The build decision above originally read "no build — Node ≥ 24 strips types natively." That premise does not survive a real install: Node refuses to type-strip any .ts file that resolves to a path under a node_modules directory — confirmed live (ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING, no flag lifts it) and independently reproduced with a minimal two-file test (identical content, one copy under node_modules, one not — only the node_modules copy fails). Since every package manager installs a package's files under node_modules by definition, this ruled out shipping raw .ts for the published package entirely, not just for this machine or for pnpm specifically. The package now builds with tsc to dist/ — see Package Layout — and the bin points at compiled JS. This changes nothing about the source layout, the dispatcher's logic, or how the checkout path is invoked (Node running a .ts file that is not under node_modules — e.g. straight from a clone — is unaffected, confirmed by the same repro).

A new workspace package. The root pnpm-workspace.yaml already globs packages/*, so pnpm install picks it up with no root change.

tsconfig.build.json, in full — a second, sibling config purely for emitting JS; the root tsconfig.json (noEmit: true) still covers type-checking this package's sources exactly as Package Layout originally described:

{

  "exclude": ["src/**/*.test.ts"]
}

rewriteRelativeImportExtensions (TypeScript 5.7+, already the pinned version) is what makes this work without touching a single import statement: the source still imports "./vps/index.ts" verbatim, and the compiler rewrites that specifier to "./vps/index.js" in the emitted output — the same relative-import-with-explicit-extension style the whole repo already uses for native execution, now also valid for a compiled build. TypeScript preserves a literal #!/usr/bin/env node shebang line as the first line of emitted output, so dist/index.js stays directly executable.

No dependencies — the code uses only node: builtins. No new devDependencies either: typescript is already a root devDependency (^5.7.0), and pnpm's workspace script execution already puts the root node_modules/.bin on PATH, exactly how this package's own "test": "vitest run" already resolves a bare vitest with no local devDependency of its own — "build": "tsc -p tsconfig.build.json" works the same way. dist/ is added to the root .gitignore — generated, never committed, rebuilt by prepack on every pnpm pack/pnpm publish so a stale build is never what actually ships. The naming rule for the whole tree is one sentence: the package runs src/index.ts; a command group runs src/<group>/index.ts — no file is called cli. That rule governs src/; dist/ mirrors it mechanically as a compile output, never edited by hand.

README.md is what npmjs.com renders: install line, the two commands, the ~/.digismith-depot/vps.json config shape, and a pointer to this repo. Kept short and plain.

Command Tree and Entry Point

digismith vps status        dg vps status
digismith vps connect       dg vps connect
digismith --version         prints the version from its own package.json
digismith                   usage listing the groups, exit 1

src/index.ts is thin on purpose. It owns exactly three things: a group table mapping a name to that group's run, the top-level usage text, and the process exit code for the cases nothing below it handles. Shape:

#!/usr/bin/env node
import { run as runVps } from "./vps/index.ts";

const GROUPS: Record<string, (argv: string[]) => void> = { vps: runVps };

export function usage(): string { … lists Object.keys(GROUPS) … }
export function resolveGroup(name: string | undefined): ((argv: string[]) => void) | undefined { … }
export function readVersion(): string { … JSON.parse of the sibling package.json … }

function main(): void {
  const [group, ...rest] = process.argv.slice(2);
  if (group === "--version") { console.log(readVersion()); return; }
  const run = resolveGroup(group);
  if (!run) { console.error(usage()); process.exitCode = 1; return; }
  run(rest);
}

if (process.argv[1] && pathToFileURL(process.argv[1]).href === import.meta.url) main();

The self-invocation guard is the same idiom the repo's other entry points use (scripts/agentic-bridge/server.ts, scripts/preferences.ts). Adding a future group is one folder plus one line in GROUPS.

src/vps/index.ts is today's scripts/vps-session/cli.ts with the process-entry seam moved up one level: its main() becomes an exported run(argv: string[]): void that receives the arguments after vps, and its own usage string becomes usage: digismith vps <status|connect>. Everything else — loadVpsConfig, the checks, runConnect's process.exit, exit codes — is unchanged. No other string changes: nothing in connect.ts, checks.ts, status.ts, config.ts, or run-command.ts references the old script path, so those five files move byte-for-byte.

Relocation and Skill Integration

scripts/vps-session/ moves to packages/cli/src/vps/ with git mv, so history is preserved. Content changes are limited to the two named in the previous section (cli.ts → index.ts exporting run; usage strings). The tests move with their modules and keep passing without edits beyond import paths that were already relative.

Every reference to the old path is updated:

  • skills/depot/SKILL.md, "Resource: VPS Session" — the invocation becomes node <digismith-repo>/packages/cli/src/index.ts vps status|connect, plus one sentence noting that once @digismith/cli is installed globally the same thing is digismith vps … / dg vps … from any directory. The skill keeps invoking the checkout path itself — a Claude Code session driving Depot always has one — so nothing in the skill depends on the package being installed.
  • MEMORY.md's V row — V.3's path reference, and a new V.4 entry.
  • .digismith/history.html — V.4 timeline entry and V row (until the Y.1.3 hook exists this is still manual).

.digismith/docs/vps-session/* is not touched — it is the frozen build record for V.3 and keeps its original paths, the same precedent as the toolchain docs still saying "U".

Versioning and Publishing

Own semver, starting 0.1.0. The CLI's version is independent of the plugin's (0.40.0-beta at the time of writing). W.4.1's post-finish version-bump hook edits .claude-plugin/plugin.json and marketplace.json only and is not extended; a CLI release should be a deliberate act, not a side effect of an unrelated skill merge.

Manual publish. From packages/cli:

npm login                       # once per machine; Jack's own account
pnpm pack --dry-run             # inspect the tarball's file list first
pnpm publish --access public

Prerequisites that live with Jack, not the repo: an npm account, and ownership of the digismith org on npmjs.com (unclaimed as of 2026-09-11 — all of digismith, digismith-cli, @digismith/cli, and @jazurite/digismith returned 404). This machine is not logged in to npm; the plan never runs npm login or pnpm publish itself — publishing is a step Jack performs, and the build's acceptance bar stops at a verified tarball and a working global install from that tarball.

Auto-publish on merge is a natural future post-finish hook (Y-lineage); it is recorded as a follow-up in this design's Out of Scope, not built here.

Error Handling

CaseDisposition
No group given (digismith alone)Print the top-level usage to stderr, exit 1.
Unknown group (digismith foo)Same: top-level usage, exit 1. No "did you mean" — one group exists.
--versionPrint the version read from the package's own package.json, exit 0. If that file can't be read (a broken install), print unknown rather than crashing.
Anything inside vpsUnchanged from V.3's Error Handling table: absent vps.json, SSH unreachable, linger failure, toolchain missing, tmux/claude state, credentials absent — all handled by the moved code exactly as before.
Node < 24 on the consumer machineengines.node >= 24 makes pnpm refuse the global install up front with its own message; no runtime check is added.
Running from a checkout without the package installedWorks: node packages/cli/src/index.ts vps status — the path Depot's SKILL.md uses. Unaffected by the node_modules type-stripping restriction, since a checkout path is never a descendant of one.
pnpm pack/pnpm publish run against a stale or missing dist/Can't happen by omission: prepack always rebuilds first. A build failure (a real tsc error) stops the pack/publish outright rather than shipping stale JS.

Testing and Acceptance

Vitest, per the standing default. The five moved test files (config, checks, status, connect) run unchanged. One new file, src/index.test.ts, covers the dispatcher's pure surface: resolveGroup returns the vps runner and undefined for unknown/missing names; usage() names every group in GROUPS; readVersion() returns the version string from package.json. The process-entry main() and everything that shells out to ssh stay live-verify-only, as in V.3.

Acceptance for the build (all runnable on the build machine, none needing the VPS or an npm login):

  1. npx vitest run at the root is green, including the moved and new tests; npx tsc --noEmit -p tsconfig.json is clean with the new include.
  2. node packages/cli/src/index.ts vps status prints V.3's exact vps-session: no VPS configured — create …/vps.json line and exits 1; node packages/cli/src/index.ts and … foo print usage and exit 1; … --version prints 0.1.0 — all four run against the checkout .ts source directly, exactly as before the build was added.
  3. pnpm build (or the prepack it triggers) in packages/cli succeeds and produces dist/index.js and dist/vps/*.js.
  4. pnpm pack (not --dry-run — the tarball is actually inspected and installed next) in packages/cli lists exactly package.json, README.md, and dist/** — no src/, no test files.
  5. pnpm add -g ./digismith-cli-0.1.0.tgz (the packed tarball) puts digismith and dg on PATH on this Windows machine, and running either — dg vps status, digismith vps status, dg --version — actually executes dist/index.js and prints the expected output, rather than crashing with ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING the way a raw .ts bin entry did. Uninstall afterwards.

Out of Scope

  • Login, credentials, "connecting to our server" — needs a server with real auth first; that is X-lineage's practice-devprod-infra idea. Its own spec later, likely as a second command group.
  • Any second command group (depot, prefs, jira, …) — the tree is designed for them; none ships in V.4.
  • Auto-publish on merge — a future post-finish hook, filed as a follow-up.
  • Bundling (esbuild or similar) — a plain tsc compile is enough for a handful of dependency-free files; a bundler stays out of scope unless the dependency count or file count changes that calculus.
  • Changing V.3's behaviour — the move is mechanical; V.3's own outstanding live verification against the real VPS remains outstanding and is unaffected.
  • Skills invoking the installed binary — Depot keeps calling the checkout path; installed-binary detection is not added.
