Overview

Two reporting skills each hardcode their own message template inline. jira-progress-write-back (I.1) has one Progress Update ADF shape, tightly coupled to the PR/ephemeral-deploy flow (Materials & Links, Track checklist) — it doesn't fit incident/investigation tickets at all (surfaced live on EMKT-799, a Make.com IN fulfillment webhook incident): no ephemeral URL, no Materials & Links, no Track checklist to touch, and the content itself is a different kind of update (what's been checked / found / needed, not done / next). Separately, teams-pr-review-notification (I.4, shipped 2026-09-09 by a concurrent session) has its own unrelated hardcoded plain-text Teams message template — same pattern, third copy.

Rather than I.1 growing a second inline template and I.4 staying a disconnected third instance of the same shape, this design decouples templating into its own map letter, Q — freed 2026-09-04 when “Convention enforcement” retired (absorbed into W.5), never reused since. It's a shared mechanism serving multiple consumers, not a sub-item of I (“Reporting”).

Q.1

The templating mechanism

A new skill, generate-comment, owning template selection, content-gathering questions, and filling a Markdown template. Ships with three templates: Progress Update, Investigation Update, and Teams Review Request.

Q.2

Consumer refactor

Refactor the two already-shipped skills, I.1 and I.4, to both call generate-comment instead of rendering their own inline templates — no duplicated template logic.

Architecture

Three skills, splitting “what to say” from “how to deliver it”:

New · Q.1

generate-comment

Owns template selection, content-gathering questions, and filling a Markdown template. Returns filled Markdown text plus a heading-prefix string for dedup-matching (meaningful to I.1 only — I.4 never searches for or edits a previous message, so it ignores this return value).

Existing · I.1, refactored under Q.2

jira-progress-write-back

Unchanged role otherwise — credentials, ticket fetch, dedup-search, description editing, confirm, post. Now calls generate-comment instead of drafting inline, and converts the returned Markdown to ADF right before posting.

Existing · I.4, refactored under Q.2

teams-pr-review-notification

Its content-gathering (scope, PR info, reviewer names, ask line) moves into generate-comment's Teams template handling. Its own Steps become just: call generate-comment, then present the returned text as-is — no conversion step, since Teams consumes plain text directly.

Templates live at skills/generate-comment/templates/progress-update.md, investigation-update.md, and teams-review-request.md — plain Markdown with <placeholder> tokens, directly reviewable and editable.

Emoji in the templates are literal Unicode characters in the Markdown text, not Jira's ADF emoji shortName nodes — this keeps the converter simpler, since a Unicode emoji character just passes through as plain text content.

Markdown→ADF conversion

Lives inside I.1 (not generate-comment), right before posting. generate-comment stays channel-agnostic — it only ever produces Markdown, and never knows anything about any specific consumer's native format. This is exactly what makes I.4 a clean second consumer: Teams needs no conversion at all (the filled Markdown is the final pasteable text), so I.4 simply skips the conversion step I.1 has. A future third consumer (map item I was broadened 2026-09-08 to reporting in general, not just Jira) would follow the same pattern — own its own conversion, or none, without touching generate-comment itself.

The converter supports a deliberately narrow Markdown subset — only what the two Jira templates actually use (Teams needs no conversion, so it doesn't constrain this subset): ###/#### headings (matching I.1's original ADF, which uses level 3 for the date heading and level 4 for its "What's done"/"Next Steps" subheadings — not level 2, corrected during planning), --- rule, **bold**, [text](url) links, - bullet lists, plain text with literal Unicode emoji, and one custom token for Jira mentions (@[Name](accountId), since Markdown has no native mention syntax). No markdown-parser dependency — a small hand-rolled converter, matching the zero-dependency pattern already used elsewhere in this repo (e.g. preferences.ts's hand-rolled key: value parsing instead of a YAML library).

Components

skills/generate-comment/SKILL.md (new, Q.1)

  • Input: template type. If not already known from context, ask (Progress Update, Investigation Update, or Teams Review Request) via AskUserQuestion.
  • Loads templates/<type>.md.
  • Progress content: same as I.1's current Steps 9-10 — check for map item N's report.html for “What's done” bullets (else draft from session work), ask which roles need pinging for “Next Steps,” resolve each name to a Jira accountId via search.
  • Investigation content: ask three bullet groups instead — what's been checked, what's been found, what's needed (and from whom) — same accountId resolution for the “needed from” mentions.
  • Teams Review Request content: absorbed from I.4's current Steps 1-4 — determine single-PR vs. multi-repo-epic scope; gather PR title/URL/ticket key (gh pr view for the on-demand single-PR case, direct ask for multi-repo epics, or whatever the caller already has when auto-offered by finishing-a-development-branch); resolve reviewer name(s) via digismith:preferences get/set on key teams_reviewers, prompting on first use per repo; ask directly for the free-text ask line. No Jira accountId lookup here — Teams reviewer names are plain text, not resolved mentions.
  • Fills the <placeholder> tokens in the loaded Markdown.
  • Returns: filled Markdown text + a heading-prefix string for the caller's dedup-search. The prefix is derived from the template file itself — the text of its first heading line up to (not including) the date placeholder, e.g. “📣 Progress Update” from a first line reading ### 📣 Progress Update – <D/M>. Never hardcoded separately, so a hand-edited template's heading can't silently drift out of sync with what I.1's Step 8 dedup-search actually matches against. I.4 ignores this return value entirely — it never searches for or edits a previously-sent message, since nothing it produces is ever actually sent by DigiSmith.

packages/jira-client/src/markdown-to-adf.ts (new)

The converter, living next to client.ts since it's ADF-domain logic the shared package already owns, with its own markdown-to-adf.test.ts alongside client.test.ts's existing pattern. Exports one function: Markdown string → ADF doc JSON, over the narrow supported subset above. Throws a descriptive error on any construct outside that subset (nested lists, tables, code blocks, etc.) rather than silently dropping or mangling it.

skills/jira-progress-write-back/SKILL.md (modified, Q.2)

  • New early step: determine template type — always Progress when invoked right after capture-ephemeral-url (today's only real path), otherwise ask if invoked standalone/explicitly.
  • Calls generate-comment in place of today's Steps 9-11.
  • Steps 4-7 (Materials & Links / Track checklist description edits) now run only for Progress Update — skipped entirely for Investigation Update.
  • Step 8's dedup-search now matches against the heading-prefix generate-comment returned, instead of the hardcoded “📣 Progress Update –” string — same date-boundary matching logic, just parameterized.
  • New step right before posting: run the filled Markdown through markdown-to-adf.ts.
  • Step 12's confirm-with-user preview now shows the readable Markdown instead of raw ADF JSON.
  • Credentials, confirm/revise/cancel, write, report: unchanged.

skills/teams-pr-review-notification/SKILL.md (modified, Q.2)

  • Steps 1-4 (scope determination, PR info gathering, reviewer-name resolution, ask-line prompt) removed entirely — absorbed into generate-comment's Teams Review Request content-gathering above.
  • Step 5 (render the message) replaced by a single call to generate-comment with template type Teams Review Request, passing through whatever context it already has (single-PR auto-offer case supplies PR title/URL/ticket key directly, same as today).
  • Step 6 (present as plain text, nothing sent) unchanged — the returned Markdown is the final text, no conversion.
  • Everything in its Error Handling table maps onto the equivalent generate-comment content-gathering step instead (e.g. “no PR found for the current branch” is now generate-comment's problem to surface, not I.4's own).

Data Flow

I.1 (Jira)

  1. Invoked as today — right after capture-ephemeral-url succeeds, or explicitly asked for.
  2. I.1 Steps 0-3 unchanged (profile check, ticket key resolution, credentials, fetch ticket).
  3. I.1 determines template type (auto = Progress if from the capture-URL path; otherwise ask).
  4. I.1 hands off to generate-comment with that type; gets back {filledMarkdown, headingPrefix}.
  5. I.1 runs Steps 4-7 (description delta) only if template = Progress.
  6. I.1 Step 8 dedup-searches comments using headingPrefix (same D/M boundary-check algorithm, now parameterized).
  7. I.1 converts filledMarkdown → ADF via markdown-to-adf.ts.
  8. I.1 Step 12: confirm (showing the Markdown, not raw ADF) — post / revise / cancel.
  9. I.1 Steps 13-15: write description (if applicable), write comment, report. Unchanged.

I.4 (Teams)

  1. Invoked as today — auto-offered by finishing-a-development-branch's Option 2 right after a new PR's URL is reported, or explicitly asked for.
  2. I.4 hands off to generate-comment with template type Teams Review Request, passing through whatever PR context it already has from the caller (auto-offer case) or nothing (direct-ask case, generate-comment gathers everything itself).
  3. generate-comment runs its Teams content-gathering (scope, PR info, reviewer names, ask line) and returns {filledMarkdown, headingPrefix}.
  4. I.4 ignores headingPrefix and presents filledMarkdown as-is — no conversion, no confirm-before-post step (nothing is ever posted; this was already true today).

Error Handling

New or changed cases on top of I.1's and I.4's existing tables (I.1: no credentials, ensure-fails, branch mismatch, unresolved mentions, cancel-at-confirm, CLI failure; I.4: no PR found for current branch, no teams_reviewers preference and Jack declines to save one, no ticket key/context available — all unchanged, just relocated into generate-comment's own content-gathering steps):

CaseDisposition
Template file missing/unreadablegenerate-comment stops, reports plainly, no fabricated draft
Markdown outside the supported subset (hand-edited Jira template uses something the converter doesn't handle)Conversion throws before I.1 reaches Step 12; report the unsupported construct plainly — never silently drop or mangle it. Doesn't apply to the Teams template, which is never converted.
Malformed mention token (missing/invalid accountId, Jira templates only)Same as today: stop, ask, never guess an ID
Unrecognized template type requestedgenerate-comment errors and lists the valid types

Testing

  • markdown-to-adf.ts is the highest-value target — real unit tests (Vitest) per construct: heading levels, rule, bold, links, bullet lists, plain text with Unicode emoji, and the mention token — plus one full round-trip test per Jira template (Progress Update and Investigation Update, each filled with sample data, compared against a hand-written expected ADF document), and a negative test confirming an unsupported construct throws rather than silently mis-converting. The Teams template needs no round-trip ADF test since it's never converted — just a fill-and-compare-text test.
  • generate-comment: template-loading and placeholder-filling is a pure function once content answers are gathered — testable without any live Jira calls, for all three templates.
  • I.1's and I.4's own SKILL.md files have no existing automated test suite (they're agentic instruction files, not code) — verification stays manual/live, same as today; only the new markdown-to-adf.ts module and generate-comment's own template-filling logic get real automated tests.

Out of Scope

  • A fourth template type — only Progress Update, Investigation Update, and Teams Review Request are designed here; the mechanism supports adding more later without redesign.
  • Full CommonMark support — the converter only handles the specific subset the two Jira templates use.
  • Any reporting channel beyond Jira and Teams (e.g. Slack, email) — the architecture leaves room for it, but no such channel is built here.
  • Auto-detecting template type from Jira issue metadata, or a profile-level default — explicit ask only, per this design's own decision.
  • Live Teams integration (Graph API, browser automation) — already ruled out by I.4's own design doc (.digismith/docs/teams-pr-review-notification/design.html) and unchanged here; I.4 still only ever produces pasteable text.
