Overview

jira-progress-write-back (map item I.1) ships exactly one hardcoded comment template today — the “📣 Progress Update” shape, tightly coupled to the PR/ephemeral-deploy flow (Materials & Links, Track checklist). Incident/investigation tickets (surfaced live on EMKT-799, a Make.com IN fulfillment webhook incident) don't fit that shape at all — there's no ephemeral URL, no Materials & Links, no Track checklist to touch, and the content itself is a different kind of update (what's been checked / found / needed, not done / next).

This splits template concerns out of I.1 into a new skill, generate-comment, and adds a second template (Investigation Update) alongside the existing Progress Update — both stored as human-editable Markdown files rather than embedded inline in a skill's own steps.

Architecture

Two skills, splitting “what to say” from “how to post it”:

New · I.3

generate-comment

Owns template selection, content-gathering questions, and filling a Markdown template. Returns filled Markdown text plus a heading-prefix string for dedup-matching.

Existing · I.1

jira-progress-write-back

Unchanged role otherwise — credentials, ticket fetch, dedup-search, description editing, confirm, post. Now calls generate-comment instead of drafting inline, and converts the returned Markdown to ADF right before posting.

Templates live at skills/generate-comment/templates/progress-update.md and investigation-update.md — plain Markdown with <placeholder> tokens, directly reviewable and editable.

Emoji in the templates are literal Unicode characters in the Markdown text, not Jira's ADF emoji shortName nodes — this keeps the converter simpler, since a Unicode emoji character just passes through as plain text content.

Markdown→ADF conversion

Lives inside I.1 (not generate-comment), right before posting. generate-comment stays channel-agnostic — it only ever produces Markdown. This keeps the door open for future non-Jira reporting channels (map item I was broadened 2026-09-08 from “QA handoff”/Jira-only to reporting in general) to reuse the same templates and content-gathering logic, each owning its own conversion from the same Markdown source, without generate-comment needing to know anything about any specific channel's native format.

The converter supports a deliberately narrow Markdown subset — only what the two templates actually use: ##/### headings, --- rule, **bold**, [text](url) links, - bullet lists, plain text with literal Unicode emoji, and one custom token for Jira mentions (@[Name](accountId), since Markdown has no native mention syntax). No markdown-parser dependency — a small hand-rolled converter, matching the zero-dependency pattern already used elsewhere in this repo (e.g. preferences.ts's hand-rolled key: value parsing instead of a YAML library).

Components

skills/generate-comment/SKILL.md (new)

  • Input: template type. If not already known from context, ask (Progress Update or Investigation Update) via AskUserQuestion.
  • Loads templates/<type>.md.
  • Progress content: same as I.1's current Steps 9-10 — check for map item N's report.html for “What's done” bullets (else draft from session work), ask which roles need pinging for “Next Steps,” resolve each name to a Jira accountId via search.
  • Investigation content: ask three bullet groups instead — what's been checked, what's been found, what's needed (and from whom) — same accountId resolution for the “needed from” mentions.
  • Fills the <placeholder> tokens in the loaded Markdown.
  • Returns: filled Markdown text + a heading-prefix string (e.g. “📣 Progress Update”) for the caller's dedup-search.

packages/jira-client/src/markdown-to-adf.ts (new)

The converter, living next to client.ts since it's ADF-domain logic the shared package already owns, with its own markdown-to-adf.test.ts alongside client.test.ts's existing pattern. Exports one function: Markdown string → ADF doc JSON, over the narrow supported subset above. Throws a descriptive error on any construct outside that subset (nested lists, tables, code blocks, etc.) rather than silently dropping or mangling it.

skills/jira-progress-write-back/SKILL.md (modified)

  • New early step: determine template type — always Progress when invoked right after capture-ephemeral-url (today's only real path), otherwise ask if invoked standalone/explicitly.
  • Calls generate-comment in place of today's Steps 9-11.
  • Steps 4-7 (Materials & Links / Track checklist description edits) now run only for Progress Update — skipped entirely for Investigation Update.
  • Step 8's dedup-search now matches against the heading-prefix generate-comment returned, instead of the hardcoded “📣 Progress Update –” string — same date-boundary matching logic, just parameterized.
  • New step right before posting: run the filled Markdown through markdown-to-adf.ts.
  • Step 12's confirm-with-user preview now shows the readable Markdown instead of raw ADF JSON.
  • Credentials, confirm/revise/cancel, write, report: unchanged.

Data Flow

  1. Invoked as today — right after capture-ephemeral-url succeeds, or explicitly asked for.
  2. I.1 Steps 0-3 unchanged (profile check, ticket key resolution, credentials, fetch ticket).
  3. I.1 determines template type (auto = Progress if from the capture-URL path; otherwise ask).
  4. I.1 hands off to generate-comment with that type; gets back {filledMarkdown, headingPrefix}.
  5. I.1 runs Steps 4-7 (description delta) only if template = Progress.
  6. I.1 Step 8 dedup-searches comments using headingPrefix (same D/M boundary-check algorithm, now parameterized).
  7. I.1 converts filledMarkdown → ADF via markdown-to-adf.ts.
  8. I.1 Step 12: confirm (showing the Markdown, not raw ADF) — post / revise / cancel.
  9. I.1 Steps 13-15: write description (if applicable), write comment, report. Unchanged.

Error Handling

New or changed cases on top of I.1's existing table (no credentials, ensure-fails, branch mismatch, unresolved mentions, cancel-at-confirm, CLI failure — all unchanged):

CaseDisposition
Template file missing/unreadablegenerate-comment stops, reports plainly, no fabricated draft
Markdown outside the supported subset (hand-edited template uses something the converter doesn't handle)Conversion throws before I.1 reaches Step 12; report the unsupported construct plainly — never silently drop or mangle it
Malformed mention token (missing/invalid accountId)Same as today: stop, ask, never guess an ID
Unrecognized template type requestedgenerate-comment errors and lists the valid types

Testing

  • markdown-to-adf.ts is the highest-value target — real unit tests (Vitest) per construct: heading levels, rule, bold, links, bullet lists, plain text with Unicode emoji, and the mention token — plus one full round-trip test per template (filled with sample data, compared against a hand-written expected ADF document), and a negative test confirming an unsupported construct throws rather than silently mis-converting.
  • generate-comment: template-loading and placeholder-filling is a pure function once content answers are gathered — testable without any live Jira calls.
  • I.1's own SKILL.md has no existing automated test suite (it's an agentic instruction file, not code) — verification stays manual/live, same as today; only the new markdown-to-adf.ts module gets real automated tests.

Out of Scope

  • A third template type (only Progress Update and Investigation Update are designed here; the mechanism supports adding more later without redesign).
  • Full CommonMark support — the converter only handles the specific subset the two templates use.
  • Any non-Jira reporting channel (Slack, email) — the architecture leaves room for it (map item I's broadened scope), but no such channel is built here. This is the backlog item previously captured loosely as a future I.4.
  • Auto-detecting template type from Jira issue metadata, or a profile-level default — explicit ask only, per this design's own decision.
