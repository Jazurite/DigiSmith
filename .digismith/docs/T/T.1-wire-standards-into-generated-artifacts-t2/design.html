Problem

T.1 (the ASD-STE100 writing standard, standards/global/ste100-writing.md) shipped as pure content: three files plus an index entry, with no consumer actually reading them before drafting prose. Neither digismith:generate-comment nor digismith:report-implementation calls digismith:inject-standards at all — both compose free-text content (JIRA/Teams comment bullets, the implementation report's summary paragraph) by filling fixed templates, with no style discipline applied. The same gap exists in digismith:finishing-a-development-branch's PR-description step, which doesn't consult even the pre-existing global/pr-descriptions standard, let alone T.1.

Scope

Three consuming skills, each gaining one new or amended drafting step:

  • digismith:generate-comment — Progress Update and Investigation Update bullets
  • digismith:report-implementation — the {{SUMMARY_PARAGRAPH}} composition step
  • digismith:finishing-a-development-branch — Option 2's PR-description drafting step

Explicitly out of scope:

  • SKILL.md authoring. digismith:inject-standards' existing Scenario 2 ("Creating a Skill") already surfaces ste100-writing as a suggestion when a SKILL.md is being edited — the only real gap is that nothing prompts invoking it in the moment. That's a standing personal discipline, not a code change with a clear home. No mechanical gate added here.
  • Commit messages. finishing-a-development-branch never drafts a commit message — only a PR description — so global/commit-style has no touchpoint in this skill to wire.

Shared Mechanism

All three skills apply the same pattern before composing free-text prose:

  1. Check technical_voice via scripts/voice.ts --action status (the same gate T.7 shipped). OFF → skip straight to today's behavior, unchanged.
  2. ON → read standards/global/ste100-writing.md and its companions (ste100-word-swaps, ste100-use-cases) directly into context and apply them while drafting.
  3. Where a shape-governing standard already exists for the surface (global/pr-descriptions for PR text), read and apply that first — its shape wins. ste100-writing's sentence-level rules operate only inside whatever shape the other standard sets, per the subordination rule already written into ste100-writing.md itself ("Where another standard already governs a surface's overall shape... that standard's shape wins").
This is a direct file read, not a digismith:inject-standards invocation — no suggestion prompt, no full-standard chat announcement on every draft. These are backend drafting steps that can run routinely mid-ticket; re-announcing the full standard text every time would be repetitive noise, working against ai-voice-conversational's own anti-repetition spirit. A caller that already knows exactly which standard it needs doesn't need the suggest-and-confirm ceremony inject-standards exists for.

generate-comment

Step 2 (Progress Update) and Step 3 (Investigation Update)'s drafted bullets go through ste100-writing before being composed into the ADF-bound Markdown-subset block.

Explicit carve-out: Step 4's ask-line (Teams Review Request) is Jack's own verbatim words and is never touched by this — that rule already exists (never auto-translate or rephrase it) and doesn't change. Structured fields (reviewers, ticket-line, pr-links, @[Name](accountId) mention tokens) aren't prose and are unaffected.

report-implementation

{{SUMMARY_PARAGRAPH}}'s two composed clauses (from the plan's own Goal:/Architecture: lines) go through ste100-writing. The fixed closing sentence (the SDD or inline-execution boilerplate) is unchanged — it's a reused literal, not freshly drafted prose each time, so there's nothing to apply the standard to.

finishing-a-development-branch

New step in Option 2, before creating the pull/merge request: draft the PR description applying global/pr-descriptions' shape first (short, plain, no templated headers/checklists), then ste100-writing's sentence-level rules inside that shape.

Testing & Error Handling

No automated tests — this is SKILL.md guidance, not .ts code, the same shape as T.7's own prose-instruction steps (the Voice Gate, Step 0.7). Verification is via each task's subagent spec/quality review plus the final whole-branch review, checked for clarity and consistency with the existing subordination rule.

One real gap, named rather than hidden: report-implementation's new step gets a genuine live exercise for free — T.2 itself runs through report-implementation when it finishes. generate-comment and finishing-a-development-branch's PR step won't get automatic live execution within this ticket: DigiSmith's own repo is ticket: false, so jira-progress-write-back never fires here, and the saved finish_option is merge_locally, which skips Option 2 entirely unless overridden at finish time. Those two are verified by review, not a live run.

Error handling: if ste100-writing.md or a companion file is missing or unreadable while technical_voice reads on, don't block drafting — proceed with today's unstyled behavior and note plainly that the standard couldn't be applied this time, mirroring inject-standards' own non-blocking dispositions elsewhere.

Future Work

Raised during this brainstorm and deliberately left out of scope: a future, category-scoped mode for digismith:inject-standards itself — letting a caller request "the writing standards" or "the coding standards" directly by category, rather than by content-relevance matching or by naming files. This ticket's own direct-read pattern is a reasonable narrow fix, but a fourth consumer needing the same shape would be the signal to generalize it. See backlog/inject-standards-category-scoped-injection.md.
