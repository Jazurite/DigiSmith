Overview

packages/jira-client/src/cli.ts's entry-point guard (line 107) never matches on Windows: 

if (process.argv[1] && import.meta.url === `file://${process.argv[1]}`) {

Windows paths don't carry the file:/// scheme the string comparison expects, so the comparison always fails, main() never runs, and every subcommand silently exits 0 with no real work done. Found live during EMKT-711 (shopify-hub, 2026-09-18): check-credentials falsely reported "ok" with genuinely blank credentials, since the guard failure means the whole switch statement — including its own error handling — never executes at all. Filed as backlog/jira-client-cli-windows-entrypoint-bug.md.

Splitting a separate concern out of this fix: an upload-attachment subcommand plus inline-image support (originally scoped together with this fix as one item) is a new capability, not a bugfix, and belongs to its own later map item (I.6), not bundled here.

The Fix

Swap the guard to: 

if (import.meta.filename === process.argv[1]) {

Matches the pattern already working in scripts/preferences.ts and scripts/fill-template.ts. import.meta.filename is stable since Node 21.2; this package requires Node ≥24, so no compatibility concern. No new import needed (unlike the alternative pathToFileURL(process.argv[1]).href === import.meta.url form used elsewhere in this repo — not needed here since this file has no symlink-resolution requirement the simpler form doesn't already cover).

Testing

cli.test.ts currently only tests the pure helpers (parseArgs, requireArgs) — it never actually invokes the CLI as a process, which is exactly how this bug went unnoticed: nothing exercises the entry guard itself. Add a real subprocess-invocation test following the pattern already established in scripts/providers/print-config.test.ts (execFileSync("node", [SCRIPT_PATH, ...]), asserting real stdout/exit behavior):

  • Run check-credentials with the spawned process's HOME/USERPROFILE env vars pointed at a temp directory containing a real .digismith-depot/.env (no new CLI flag needed — checkCredentials()'s default path already resolves via homedir(), which Node's os.homedir() derives from those same env vars), assert exit 0 and the real "check-credentials: ok" stderr line actually printed by main() — not just that the process didn't crash.
  • Run it again against a missing/incomplete temp credentials file, assert exit 1 and the real CredentialsError message — proving the guard's failure path also actually executes post-fix, not just its happy path.

This is the durable fix for the backlog note's "every subcommand needs re-verifying, no evidence any of them have ever actually executed on Windows" — an automated regression guard instead of a one-off manual check.

Out of Scope

  • I.6 — upload-attachment subcommand and inline-image (ADF Media Platform) support. Different domain (new capability vs. bugfix); picked up separately later.
  • Testing every existing subcommand's Windows behavior beyond check-credentials — the subprocess-test pattern this establishes is reusable for the others later if needed, but proving the guard itself works via one representative subcommand is sufficient for this fix.
