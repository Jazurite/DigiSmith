Problem

Neither bootstrap/adopt (fire on ticket start) nor inject-standards (fires on coding/planning/dispatch) cover a plain conversation with no ticket or task attached — there is no DigiSmith mechanism today that runs on Claude Code's own SessionStart hook event. Surfaced 2026-09-22 during a T-lineage brainstorm on voice selection, once it became clear that a voice standard (map item T) never auto-loads outside a ticket/task context. This closes that gap generally — voice is the first concrete consumer, not the only one.

Delivery Mechanism

A Claude Code plugin can bundle its own hooks/hooks.json that fires automatically in any repo where the plugin is installed and enabled — no per-consuming-repo .claude/settings.json edit required, and it combines additively with any project/user-level hooks rather than overriding them. This resolves the open "which repos does this apply to" question: the plugin itself is the distribution mechanism, matching how every other DigiSmith skill already reaches every consuming repo.

New file: hooks/hooks.json at the plugin root.

{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "*",
        "hooks": [
          { "type": "command", "command": "node --experimental-strip-types \"${CLAUDE_PLUGIN_ROOT}/scripts/session-init.ts\"" }
        ]
      }
    ]
  }
}

matcher: "*" fires on every session_source — startup, resume, clear, compact, and fork — so the banner survives a /clear or a context compaction, not just a fresh launch. The compaction case mirrors a pattern Claude Code's own docs name directly: re-injecting context after compaction.

Init Sequence

SessionStart hooks are non-interactive — they cannot invoke a skill or tool, only read files and print plain text to stdout, which Claude then sees as context. scripts/session-init.ts:

  1. Checks for .digismith/profile in the invoking session's working directory. Not present (repo never bootstrapped, or plugin enabled somewhere DigiSmith isn't actually used) → exit 0, print nothing. This is the common case across most sessions a Jack-wide plugin install touches, so silence here matters.
  2. Calls the voice contract (below). Its result, if any, folds into the same banner line.
  3. Prints one terse line to stdout, e.g. DigiSmith: profile=emma, voices=conversational — kept minimal since this now runs on every session start/resume/clear/compact for every DigiSmith-tracked repo, not just ticket-scoped work where token cost is already budgeted for.

.digismith/preferences.yml (map item H's own store — operational settings like finish_option/ssh_key) is deliberately not read here: nothing in it is worth announcing on every session start, and the three approved init-sequence pieces (voice, profile, banner) don't call for it. .digismith/profile (map item O) is the only file this step reads.

Voice Integration Contract

digismith:voice doesn't exist yet — it's being designed separately, in the T-lineage session. Rather than this feature hard-coding knowledge of voice's eventual preference schema (or blocking on that other brainstorm finishing first), session-init.ts defines a narrow contract the future digismith:voice build can satisfy independently:

Contract: if scripts/voice-init.ts exists at the plugin root and exports a default async function () => Promise<string | null>, session-init.ts imports and calls it, appending a non-null return value to the banner. If the file doesn't exist, the step is skipped entirely — no error, no log line.

This means voice's own build adds exactly one new file with that one export shape; nothing in this feature needs to change when it ships. The T-lineage session will be notified of this exact contract once this design is approved, so it can build against it directly.

Failure Mode

A missing .digismith/profile is always silently benign — exit 0, no output — matching the same precedent every other consumer of a missing DigiSmith config file already follows (map items G.2, H, P).

A genuine unexpected exception — voice-init.ts existing but throwing, or an unrelated filesystem error reading .digismith/profile — is different: session-init.ts wraps its own top-level logic in a try/catch and on an unhandled error prints a one-line warning to stderr and exits non-zero. SessionStart can't block session start regardless of exit code, so this never gets in the way; it just means a genuinely broken script doesn't fail invisibly. Open to making this fully silent too if hook noise turns out to be unwelcome in practice — cheap to flip later.

Testing

Vitest, colocated as scripts/session-init.test.ts, following the existing .digismith/hooks/post-finish/scripts/*.test.ts shape (real filesystem fixtures in a temp dir, not mocked fs). Cases: no .digismith/profile → silent exit 0 and empty stdout; profile present, no voice-init.ts → banner with just the profile; a fake voice-init.ts returning a string → appended to the banner; a fake voice-init.ts returning null → banner unaffected, same as if the file didn't exist; a fake voice-init.ts that throws → stderr warning, non-zero exit, process doesn't crash uncaught.

Out of Scope

  • Building digismith:voice itself — that's the separate T-lineage brainstorm; this feature only defines the contract it can plug into.
  • A per-repo opt-out. If a repo has the plugin enabled but doesn't want the banner, the existing "no .digismith/profile → silent" behavior already covers the common case; a dedicated toggle is deferred until someone actually hits the case where a repo has a profile but wants the hook off.
  • Any init-sequence content beyond profile + preferences + voice (e.g. a fuller "what changed since last session" summary) — flagged as a possible future idea, not designed here.
