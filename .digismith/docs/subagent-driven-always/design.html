Problem & Goal

superpowers:writing-plans ends every plan with an Execution Handoff question: "1. Subagent-Driven (recommended) / 2. Inline Execution — Which approach?" Left as-is, this asks the same question on every single plan DigiSmith drives, even though the answer is always the same for every profile currently in use — N (report-implementation) depends entirely on the per-task review and final-review ledger that only subagent-driven-development produces, and G (standards injection) has nothing to inject into unless an implementer subagent actually gets dispatched. Inline execution silently breaks both.

H's goal: remove that question from the flow. When a DigiSmith-driven plan reaches Execution Handoff, skip straight to subagent-driven-development without asking — matching the map's original framing, "there is no option 2."

Non-Goals

  • Not a profile-gated toggle. Considered and dropped during this brainstorm — every current profile (emma, personal, jazurite) has reporting: true, so every profile already depends on the ledger subagent-driven-development produces. There's no profile today where an "opt out" branch would be safe to take.
  • Not a task-count rule. Also considered and dropped: routing single/sequential- task plans to executing-plans instead of subagent-driven-development was briefly proposed, but executing-plans is explicitly the no-subagent fallback (its own skill file says so) — it never dispatches an implementer subagent and produces no ledger, so it breaks G and N regardless of task count.
  • Not a patch to Superpowers' own writing-plans file. That file is part of a third-party, machine-wide plugin; editing it would change execution behavior for every non-DigiSmith project on the machine too. H intercepts via a DigiSmith-side trigger instead — see Architecture.
  • Not a change to the plan document header. writing-plans' own boilerplate ("REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans") stays exactly as Superpowers writes it inside the committed plan file — it's informational text, not a live decision point, so there's nothing for H to intercept there.
  • Not scoped to using-digismith-started builds only. Deliberately a standalone rule, not folded into using-digismith's Step 3 handoff — a build that started mid-flight (ticket and branch already existed before DigiSmith touched it, same shape as this session's own Emma UAT) still needs H to fire when it reaches Execution Handoff.

Architecture

One new skill, skills/subagent-driven-always/SKILL.md. No new persisted state — no marker file, no profile field — unlike G/O/P. It's a pure behavioral rule keyed to a trigger point inside a third-party skill's own flow, the same implicit-trigger pattern M and N already use ("once a PR is open," "the moment a plan's final review comes back clean") rather than an explicit call from using-digismith or any other DigiSmith skill.

Trigger

The moment superpowers:writing-plans reaches its Execution Handoff step and is about to present the "Subagent-Driven / Inline Execution" choice.

Behavior

default path

Skip the prompt, go straight to subagent-driven-development

Don't ask the two-option question. Announce that Subagent-Driven Development is being used (per DigiSmith map item H), then invoke superpowers:subagent-driven-development directly.

explicit override

User asked for inline anyway

If the user has explicitly requested inline execution for this specific plan — stated earlier in conversation, or in response to H's announcement — honor it and invoke superpowers:executing-plans instead. Not a live question H asks; only activates if the user volunteers it.

environment fallback

No subagent capability available

If the environment genuinely can't dispatch subagents (no Agent tool or equivalent), fall back to superpowers:executing-plans automatically — exactly the scenario that skill's own file documents as its reason to exist.

Scope

Global to any DigiSmith-installed environment — no profile gating (see Non-Goals). Fires regardless of whether the current build started via using-digismith or was already mid-flight when DigiSmith first touched it.

Trigger & Behavior Flow

superpowers:writing-plans finishes writing and saving the plan → reaches its Execution Handoff section → this skill's trigger condition matches before the two-option question is presented → default path invokes subagent-driven-development directly, unless the user has already stated a preference for inline execution (→ executing-plans) or the environment can't support subagents at all (→ executing-plans, environment fallback). No state is written or read at any point in this flow.

Error Handling & Edge Cases

  • User explicitly insists on inline execution → respected, not overridden. Recorded as an intentional, user-directed exception — not a failure of H.
  • No subagent capability in this environment → falls back to executing-plans automatically. Recorded as an environmental constraint, not a choice — distinct from the explicit-override case above.
  • A plan has exactly one task → no special case needed. subagent-driven-development dispatches one implementer subagent per task whether there's 1 task or 5; H's default path applies unchanged.
  • Profile has reporting: false in the future (no such profile exists today) → out of scope for this design, since H is unconditional. If a profile like this is ever added, whether H should still apply to it is a decision for that profile's own change, not a silent behavior shift here.

Testing / Verification

No automated test suite — consistent with every DigiSmith skill so far. Manual dogfood walkthrough:

  1. Four constructed dogfood scenarios (Task 1 — default path, explicit override, no-subagent-capability, single-task plan), each dispatching a subagent to reason through SKILL.md against one Execution Handoff condition and report which Superpowers skill it would invoke. Not a live trigger-point run: the skill didn't exist yet when this plan's own Execution Handoff was reached, so this plan's own build couldn't exercise the real trigger — see item 4 below for where that first happens.
  2. Mid-conversation, explicitly ask for inline execution on a plan → confirm executing-plans is used instead, without argument.
  3. Confirm the plan document's own header text is unchanged from Superpowers' default boilerplate.
  4. Real UAT: the Emma repo UAT already underway is a live test of this exact behavior once H ships and that session reaches its own Execution Handoff point.

Relationship to Other Map Items

  • G (standards injection) — H is a precondition for G to ever fire; G injects into "every implementer subagent's brief," which only exist under subagent-driven-development.
  • N (implementation reporting) — same relationship: N depends on the ledger grammar only subagent-driven-development produces. H guarantees that ledger exists for every DigiSmith-driven plan.
  • O (profiling) — considered as the mechanism for H (a profile toggle), explicitly rejected; see Non-Goals.
  • E.2 (spine, remaining scope) — H is deliberately independent of using-digismith for the same reason E.2 remains unbuilt: a mid-flight build (no using-digismith Step 0–3 ever ran) still needs to hit this trigger correctly.
