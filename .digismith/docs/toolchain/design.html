Overview

Jack has standing tool/technology defaults for common greenfield decisions — test runner, styling approach, E2E framework, script language, package manager, Node install method — that currently exist only in his head. Every digismith:brainstorming session that hits one of these either burns a fresh AskUserQuestion round re-deciding something already decided, or risks picking differently and needing a correction after the fact (higher cost than just asking).

Source: surfaced mid-brainstorm on the Jira REST-migration spec (2026-08-27) — asked “which test runner?” fresh, Jack answered Vitest, then immediately volunteered SCSS and Playwright as also being standing defaults, unprompted. Two more confirmed 2026-09-08/09 during live Hetzner VPS setup for map item X (persistent VPS-hosted session): pnpm over npm for global CLI installs, and nvm over a distro-packaged Node install — both corrected mid-flow on a task with no connection to digismith:brainstorming or DigiSmith self-development at all. That observation shaped this design's own scope decision (see Out of Scope).

This becomes map item U, Toolchain — the next free letter (T is already tentatively claimed by a separate technical-writing-content-voice backlog idea).

Storage

toolchain.yml at DigiSmith's own repo root — global to Jack, the same way standards/ is, not per-consuming-repo the way .digismith/preferences.yml (map item H) is. These are Jack's own standing tool choices, not project-specific config. Flat domain: choice pairs, plain text, no YAML library — same hand-rolled parsing precedent as preferences.ts: 

# DigiSmith-managed. Standing toolchain defaults, dictated by Jack.
test_runner: Vitest
styling: SCSS
e2e_framework: Playwright
script_language: TypeScript (over Python, absent existing precedent to match)
package_manager: pnpm (workspace/monorepo management and global CLI installs)
node_installation: nvm (over distro-packaged Node — apt/NodeSource — on a server)

Skill: digismith:toolchain

scripts/toolchain.ts, mirroring digismith:preferences' shape but simpler — no --path override (this file has exactly one location, not one per consuming repo) and no single-key get (the store stays small and is always read as a unit, not looked up key-by-key mid-flow).

list

Prints every domain/choice pair. Empty or missing file → prints nothing, not an error.

set --domain <d> --value <v>

Writes/overwrites one entry, creating the file (with header comment) if it doesn't exist yet. Preserves every other entry already set.

clear --domain <d>

Removes one entry if present; no-op (not an error) if it was never set.

Locates DigiSmith's own repo the same way digismith:preferences and digismith:inject-standards already do: current working directory is the DigiSmith repo (.claude-plugin/plugin.json with "name": "digismith") → use directly; otherwise ask once for DigiSmith's repo path and remember it for the session.

Invoked automatically by digismith:brainstorming (below), or directly on request — “what are my toolchain defaults,” “set my default styling to X,” “clear my default for Y.”

Brainstorming Integration

One new paragraph at the top of digismith:brainstorming's existing “Ask clarifying questions” step — not a map item W primitive-replacement activation (W tracks closing gaps against upstream Superpowers or folding in retired DigiSmith mechanisms like H/Q); this is an ordinary cross-cutting hook into the vendored skill, the same way map item G's standards already get surfaced during brainstorming without needing a W entry of their own.

Before posing a clarifying question about a tooling/stack choice, run list and check for a matching domain. Match by meaning, not rigid key names — the same fuzzy-relevance spirit inject-standards already uses, just against a handful of domain labels instead of standard descriptions. A match found → state the assumption plainly (“Test runner: defaulting to Vitest per your standing default — say the word if you want something else this time”) instead of an AskUserQuestion, but still honor an immediate override in the same turn. No match → ask as normal, and if Jack volunteers a standing preference in his answer (the way this whole mechanism was born), offer to set it via digismith:toolchain before moving on.

Data Flow

  1. digismith:brainstorming reaches its “Ask clarifying questions” step and has a tooling/stack question queued up (e.g. “which test runner?”).
  2. Runs digismith:toolchain's list once (cheap, small file) and holds the result for the rest of this step.
  3. For each queued tooling question, checks the list for a matching domain by meaning.
  4. Match → states the assumption inline, skips the AskUserQuestion, continues to the next question. Jack can still override in his next message; the overridden value is not written back automatically (see Out of Scope).
  5. No match → asks via AskUserQuestion as today. If Jack's answer reads as a standing preference rather than a one-off choice, offers to record it via digismith:toolchain set.

Error Handling

CaseDisposition
toolchain.yml missinglist prints nothing; brainstorming asks every tooling question fresh, same as before this mechanism existed — not an error.
File present but malformed/unparseableTreated as empty, same as missing. Never blocks the brainstorming flow.
set invoked without --valueFails clearly (exit 1), same convention as preferences.ts. Never silently sets an empty string.
clear on a domain that was never setSilent no-op, still reports success.
Ambiguous match (a queued question could plausibly map to more than one stored domain) Ask as normal rather than guess — a wrong silent assumption is worse than one extra question.

Testing

  • scripts/toolchain.ts's list/set/clear are pure file-parsing logic, same shape as preferences.ts's existing tests — unit-tested with Vitest: round-trip a value through set then list, overwrite an existing domain, clear a present and an absent domain, missing/malformed file reads as empty.
  • The brainstorming-side consult paragraph is agentic instruction text, not code — verified live (ask a tooling question with and without a matching stored default, confirm the assumption-and-skip behavior and the override path both work) rather than by an automated suite.

Out of Scope

  • Any trigger point beyond digismith:brainstorming. The VPS session's pnpm/nvm corrections happened completely outside brainstorming, which argues for a broader “any session, any tooling choice” version — deliberately deferred to its own backlog item (backlog/toolchain-general-trigger-scope.md) rather than folded in here, per Jack's own scope call. This design's mechanism only ever fires inside brainstorming's clarifying-questions step.
  • Auto-writing an override back to the file. If Jack overrides a stated assumption in the same turn, that turn's choice is used as-is; it is not automatically persisted as the new standing default — that would need its own explicit confirmation, out of scope here.
  • Enumeration/inspection UI beyond list. No search, no per-domain history, no categorization — the file stays small and flat.
  • A per-repo override tier. These are Jack's own defaults, not project config; unlike map item H, there is no per-repo layer.
