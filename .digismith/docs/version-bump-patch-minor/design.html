Background

.digismith/hooks/post-finish/scripts/bump-plugin-version.ts's computeNextVersion always increments the minor version field and resets patch to 0, with no distinction between a patch-worthy change and a minor-worthy one. This was caught live on 2026-09-08 by a separate Claude Code session (digismith-64) applying three fix(...) commits (jira-progress-write-back credential-path fixes) directly to main: the script bumped 0.29.0-beta straight to 0.30.0-beta instead of the patch-level 0.29.1-beta those commits actually warranted. Caught before pushing further and corrected by hand. Full incident writeup: backlog/check-vendored-skills-hardening.md, under its ## bump-plugin-version.ts (map item W.4.1) section (now superseded by this spec — see Section 4 of the plan for its retirement).

Checked the full history of .claude-plugin/plugin.json's version field: every bump on record, back to 0.1.0, has been X.Y.0 → X.(Y+1).0. There has never been a patch-level bump. DigiSmith's own commits already follow conventional prefixes (fix:, feat:, chore:, docs:) fairly consistently — the raw material for a real patch-vs-minor decision already exists in commit history; the script simply never looks at it.

Section 1 — bumpTypeSince

A new exported function, bumpTypeSince(baseSha: string, cwd: string = process.cwd()): "patch" | "minor", added to bump-plugin-version.ts alongside the existing versionChangedSince (same file, same real-git-fixture testing style — no mocking). It runs git log <baseSha>..HEAD --format=%s via spawnSync in cwd (throws on a non-zero exit, matching the file's existing fail-loud convention), splits stdout into non-empty lines, and returns "patch" only when that list is non-empty and every line matches /^fix(\([^)]*\))?:/ — anchored at the start, so fix: and fix(bootstrap): and fix(bootstrap,adopt): all match, while git's own fixup!: ... marker commits correctly do not (the anchor requires fix to be immediately followed by either ( or :, and fixup! is neither). Every other case — an empty commit range, any feat/docs/ chore/unrecognized-prefix commit anywhere in the range, or any mix of fix with anything else — returns "minor". This conservative default is deliberate: a single docs(...) commit in this repo can change load-bearing SKILL.md content that genuinely needs the plugin cache invalidated, so a mixed batch is never assumed to be patch-safe.

Section 2 — computeNextVersion's new parameter

computeNextVersion(current: string, bumpType: "patch" | "minor" = "minor"): string gains a second, defaulted parameter. "minor" (the default) is byte-for-byte today's existing behavior — increments the minor field, resets patch to 0, keeps the prerelease suffix — so every existing call site and every existing test keeps passing completely unchanged. "patch" increments only the patch slot (major and minor untouched, prerelease suffix still preserved). Major-version bumps are explicitly out of scope — DigiSmith stays at major 0 throughout its beta lifetime per standing convention, and nothing here changes that.

Section 3 — Wiring into main()

main() changes minimally: today, when args.base is provided, it already calls versionChangedSince(args.base, PLUGIN_JSON_PATH) to decide whether to skip. Now, immediately after that check passes (i.e., a bump is actually going to happen), and only when args.base is provided (there's no commit range to inspect without a base to compare against), it also calls bumpTypeSince(args.base) and passes the result into computeNextVersion. The no---base manual-invocation path — the exact path used during the incident that found this bug — keeps defaulting to "minor", unchanged, since there's no commit range available to inspect.

Testing

  • New describe("bumpTypeSince", ...) block in bump-plugin-version.test.ts, reusing the existing initVersionFixtureRepo real-git-repo fixture helper (extended to accept a list of commit messages instead of just one fixture commit, or built up via sequential real commits in each test — no mocking, consistent with every other test in this file). Cases: a range of pure fix(...) commits → "patch"; a range with one feat(...) mixed in → "minor"; a range with one docs(...) or chore(...) mixed in → "minor"; a range containing a fixup!: ... commit → "minor" (proves the anchored regex correctly rejects git's own fixup marker); an empty range (base equals HEAD, no new commits) → "minor".
  • New case in the existing describe("computeNextVersion", ...) block: the "patch" argument bumps only the patch slot (e.g. "0.29.0-beta" + "patch" → "0.29.1-beta" — the exact transition the real incident needed), and confirm the existing minor-bump tests still pass unchanged with no second argument supplied (proving the default preserves current behavior exactly).
  • Manual verification after implementation: none required beyond the automated suite — this change has no user-facing CLI surface beyond what's already tested, and the next real DigiSmith merge through finishing-a-development-branch's post-finish hook will exercise it live regardless.

Out of scope

  • Major-version bumps — DigiSmith stays at major 0 through beta; nothing in this change introduces a path to major 1.
  • A diff-content-based heuristic (classifying by which files/lines actually changed rather than by commit-message prefix) — considered and rejected: more accurate in principle, meaningfully more complex, and this repo's commit-message discipline has been reliable enough in practice that the added complexity isn't justified (YAGNI).
  • Retiring the now-superseded backlog/check-vendored-skills-hardening.md ## bump-plugin-version.ts (map item W.4.1) section — handled as the implementation plan's own final task, same pattern every other W sub-item this session has used for its originating backlog item.
