Overview

DigiSmith's map item I.1. After work lands on an Emma ticket, post or update JIRA's real native formatting — status lozenges, emoji, a dated progress comment — instead of a markdown approximation. Consumes M's (capture-ephemeral-url) captured Preview/Theme-Editor URLs. Never touches status or performs a workflow transition — that stays a manual, human decision by standing design constraint.

Grounded in a real example rather than an invented format: EMKT-784's actual ticket shows the exact target shape — a description with a 🔗 Materials & Links table and a 📦 Track checklist, and a comment thread carrying a dated 📣 Progress Update skeleton that gets edited in place (not duplicated) as the same day's work progresses. This skill reproduces that shape mechanically, on demand, rather than requiring it to be typed by hand each time.

Write 1

Description

Idempotent, upsert-style. This repo's own Materials & Links table row, and (only if the section already exists) the Technical Development line of the Track checklist.

Write 2

Comment

A dated "📣 Progress Update" skeleton — What's done / Next Steps — created fresh or updated in place if today's already exists.

Trigger & Gating

Offered right after digismith:capture-ephemeral-url (M) succeeds — the same relationship M itself has to superpowers:finishing-a-development-branch's "push and create PR" step — or whenever explicitly asked to post/update the JIRA progress update for a given ticket.

No new profile field. I.1 only makes sense when a real ticket key exists, which is exactly what the active profile's existing ticket field (map item O) already gates. ticket: false profiles (digismith, jazurite, personal) never resolve a ticket key in the first place — I.1 has nothing to attach to and does not run. Adding a second field would duplicate a gate that already exists.

Ticket key resolution mirrors digismith:capture-ephemeral-url Step 1 exactly: parse <Key> from the current branch name against ^([A-Z]+-\d+)__. A non-matching branch name means asking directly for the key rather than guessing — never look it up.

Description Write: Materials & Links Table

Fully automatable: every value in this table is something DigiSmith directly witnesses (M's captured URLs, the PR just opened). Format, confirmed against EMKT-784's real description:

CountryPreview ThemeCustomizePull Request
JP[Link][Link][Link]

Single-market scope

I.1, as designed here, runs against exactly one repo/PR/ticket at a time and writes exactly one row. No classification logic decides whether a repo "counts" as a market, no comparison against a known market list, no cross-repo awareness at all — that entire problem (detecting which markets a ticket touches, looping across them, deciding when the set is complete) belongs to I.2 (multi-repo distribution), deferred in full. I.1 only ever sees the one repo it's currently running in. The table may already carry other rows from earlier work on this ticket (by a human, or later by I.2) — I.1 leaves every row but its own untouched.

Row label: derived from the current repo's directory name — strip a shopify-template- prefix and uppercase the remainder if present (shopify-template-jp → JP); otherwise use the repo name as-is (e.g. shopify-hub). Just a label, not a branch — the table is written the same way either way.

Upsert rule

  • Table missing entirely → create it with this single row.
  • Table exists, this row's label already present → replace that row's three link cells in place.
  • Table exists, this row's label not present yet → append a new row.

Description Write: Track Checklist

Conservative by design. The full checklist (Technical Development, Storybook Conversion, Design Review, QA, Engineering Code Review, Translations, Rollout) covers stages DigiSmith cannot attest to — a human approved a design, QA actually ran, translations arrived. Fabricating a status for any of those would be worse than leaving the checklist alone.

I.1 touches only the Technical Development line: its status node and the emoji checkmark list beneath it. Every other stage line is read and re-emitted byte-for-byte unchanged, since the whole field is replaced on every write (see The ADF Technique).

If the Track section doesn't exist yet

Skip it — don't scaffold the other stages from nothing; their names and order vary per ticket and aren't DigiSmith's to invent. Report plainly that the Track update was skipped because no existing section was found, so a human can set one up if they want this ticket to carry it at all.

Marking it done (single-repo scope)

I.1 has no visibility into whether a ticket needs other repos too — that cross-repo awareness is I.2's job, not modeled here at all. So within I.1's own scope, adding this repo's checkmark is the whole of what it's tracking: the Technical Development line's status node is set straight to green ("DONE") the same write that adds the checkmark. If a ticket later turns out to need more repos, reopening this status is I.2's concern when it exists, not something I.1 hedges against today.

Comment Write: Progress Update

Verbatim shape, confirmed from EMKT-784's real comment thread:

### 📣 Progress Update – <D/M>
---
#### ✅ What's done
* <bullet>
* <bullet>
👆 All links (Preview Theme, Customize, Pull Request, Storybook) are in the ticket description above.
#### 🎯 Next Steps:
* **<emoji> <Role> Needed >** (@mention, @mention) — <ask>
* **<emoji> <Role> >** (@mention) — <ask>

Dedup, not duplicate

Before creating anything, check the issue's existing comments for one already matching ### 📣 Progress Update – <today's date>. Found → update it via commentId. Not found → create new. This is confirmed real behavior, not a hypothetical: EMKT-784's own progress comment was created at 03:58 and edited in place at 09:30 the same day once the PH blocker cleared — same comment, not a second one.

"What's done" — source

Prefer N's (report-implementation) already-generated implementation report when this session produced one (.digismith/docs/<slug>/report.html) — augment, don't re-derive, per DigiSmith's own philosophy. When N hasn't run (e.g. I.1 invoked standalone, or the plan used superpowers:executing-plans instead of subagent-driven-development), draft bullets fresh from the session's actual work instead.

"Next Steps" — source

No reliable automatic source: this repo's CODEOWNERS only names a team (@emma-sleep/OnlineStore), not individuals, so it cannot resolve who specifically gets tagged for code review, design approval, or QA. Ask the user each round: which roles need a ping this update, and who for each. Skip a role entirely if there's no one to tag rather than inventing a placeholder mention.

Resolve each provided name to a JIRA accountId via lookupJiraAccountId before building its mention node. A name that doesn't resolve stops and asks for clarification — never guess an ID; an unresolved mention node renders as nothing or breaks the whole write.

The ADF Technique

The trap: reading a ticket back (getJiraIssue, any responseContentFormat) renders special nodes as pseudo-HTML — <custom data-type="status">DONE</custom>. This is read-only. Sending that literal text back via contentFormat: "markdown" does not re-parse into a real node — it round-trips as visibly broken literal text on the actual ticket. Confirmed by testing directly on a live ticket.

What works: contentFormat: "adf" on editJiraIssue / addCommentToJiraIssue, value set to a stringified real ADF document ({"type":"doc","version":1,"content":[...]}). The response echoes special nodes back with an auto-assigned data-id="id-N" — that data-id's presence is the tell distinguishing "really created a node" from "echoed my text back unparsed."

Node schemas (confirmed against the ADF reference and EMKT-784 itself)

NodeShapeNotes
status{"type":"status","attrs":{"text":"DONE","color":"green"}} color ∈ neutral|purple|blue|red|yellow|green
emoji{"type":"emoji","attrs":{"shortName":":check_mark:","text":"✅"}} Standard shortcode — no id needed, server resolves it
mention{"type":"mention","attrs":{"id":"<accountId>"}} accountId from lookupJiraAccountId
expand{"type":"expand","attrs":{"title":"..."},"content":[...]} Real collapsible panel — not used by I.1's current skeleton, available if a future shape needs it

Standard nodes (paragraph, heading, bulletList/listItem, table and its children, hardBreak, text with strong/link marks) all work as expected via the same ADF path.

Whole-field replacement

editJiraIssue/addCommentToJiraIssue replace the entire field value — there is no patch/append. Every write (Materials table row, Track line, comment body) means: fetch the current field as ADF, splice in only the changed piece in memory, submit the whole document back. This is why the Track checklist's other-stage lines must be preserved verbatim rather than reconstructed — reconstruction risks silently dropping content this skill doesn't understand.

JIRA Tool Detection

Mirrors digismith:jira-intake's own principle: infer which JIRA/Atlassian-capable tool is available in the current session rather than hardcoding one connector's tool names. Not found → say so plainly, don't fabricate a write. cloudId resolution follows the same tool's own guidance (site hostname first, else getAccessibleAtlassianResources).

Confirm-Before-Write

Both writes are team-visible, external-system side effects — unlike DigiSmith's own internal docs, this isn't something to publish silently. Draft the full comment body and the description delta (table row, Track line) and show them before calling editJiraIssue/addCommentToJiraIssue. This applies every time, not just the first: JIRA's own edit history is visible to the whole team, so a bad automatic write is a social cost, not just a technical one.

Error Handling

CaseDisposition
No JIRA-capable tool in sessionStop, say so plainly. Don't fabricate a write.
Branch doesn't match <Key>__<slug>Ask directly for the ticket key rather than guessing.
Custom, site-uploaded emoji with no resolvable idSkip the icon; plain status pill/text only. No connector tool exists to enumerate site emoji.
Mention name doesn't resolve via lookupJiraAccountIdStop and ask for clarification. Never guess an accountId.
Mistaken/duplicate comment already postedNo delete capability exists via this connector — edit it via commentId instead of creating a corrective second comment.
Track section absent from the descriptionSkip the Track update, report why. Never scaffold the full stage list from nothing.

Out of Scope

  • Status transitions — standing constraint, stays manual by design, not revisited here.
  • I.2, multi-repo distribution — a separate map sub-item. I.1 as designed here handles exactly one repo/PR/ticket at a time, with zero cross-repo awareness. Everything about multiple markets belongs to I.2, deferred in full:
    • Detecting which markets/repos a ticket touches at all.
    • Looping I.1 (or its writes) across that full list.
    • Multi-row Materials-table orchestration — knowing which rows already exist across the set, not just this one.
    • Cross-market completion tracking — whether the Technical Development stage should reopen from DONE back to IN PROGRESS when a ticket turns out to need another market after I.1 already marked one repo's work complete.
  • Custom site-emoji ID lookup — no discovered path through this connector; noted as a known gap, not solved here.
  • Full Track-checklist scaffolding — deliberately not automated; see Track Checklist.
