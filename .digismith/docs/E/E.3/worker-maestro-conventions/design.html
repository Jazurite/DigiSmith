1. What changes, and why

Jack's direction (2026-10-03): drop the clan letters, the lineage keys, and the map-item letters as a naming convention for the repo's own files. The ticket is the unit instead. A ticket's key comes from its tracker — DGS-nnn on ClickUp, EMKT-nnn on JIRA, the same <PREFIX>-<number> shape for any future tracker.

This reaches only the repo's own naming of files and folders under .digismith/. ClickUp's own clan folders and lists (A: Primitives through E: Methodology, and their sub-lists such as E.3: Conventions) stay exactly as they are — confirmed by Jack. The source of this change is the Flux design (DGS-154, E.4), whose own worker and maestro conventions were left as an interim pick pending this ticket; this design is what Flux now builds against.

Two folders replace the old, single, flat .digismith/docs/<slug>/ convention (and its letter-nested variant, G.3, formally superseded by this design):

Ticket-keyed

.digismith/board/

A ticket's working files: design, plan, report, and the rest. One folder per ticket.

Session-keyed

.digismith/sessions/

Files about a running session: the maestro's note, a worker's brief. Never ticket-keyed, because a maestro outlives any one ticket.

2. Board: a ticket's working files

Folder: .digismith/board/<KEY>—<slug>/ — the ticket key, an em dash (U+2014, no surrounding spaces), then the title as a slug. Example: .digismith/board/DGS-158—ticket-based-naming-architecture/. The format is decided (Jack, 2026-10-03); section 9 covers the character-level risks and the build/parse rules.

Contents keep today's file set and shape, role-named, no date prefix: ticket.md (when the active profile tracks one), design.html, plan.md, report.html. Commit-vs-gitignore stays a per-repo choice, same mechanism as today (digismith:jira-intake's git check-ignore check), now pointed at .digismith/board/ instead of .digismith/docs/.

One folder per ticket, not one per build. This drops the old per-build numbering (G.3) outright — the ticket key already identifies the unit of work uniquely, so a ticket too big for one worker splits by ClickUp subtask or by worker (section 5), never by a new folder number. If a shipped ticket is reopened later and a new plan or report would collide with the old one, the new file takes a numeric suffix only on that collision (plan-2.md) — the same pattern already used once by hand for an earlier addendum, now written down instead of improvised.

A one-off slice of a larger ticket (one comment, one spike) writes no new board folder of its own — see section 6.

3. Sessions: files about a session

.digismith/sessions/ holds two kinds of file, by who the file is about — never by ticket:

  • The runbook (workbox.md): shared, cross-session operating notes. Unchanged: flat, at .digismith/sessions/workbox.md, git-excluded.
  • Per-session folders, named by the session's own name — a worker's herdr agent name, or a maestro's Desktop session name:
    • .digismith/sessions/<session-name>/note.md — the maestro's own handoff note (replaces .digismith/docs/<Clan>/handoff.md). Only the maestro writes one; a worker never does (Flux, decided 2026-10-03: a worker has no handoff note and no resume).
    • .digismith/sessions/<session-name>/brief.md — the maestro's brief for a worker, written before the worker is dispatched.

The brief lives here, not in board/, for three reasons: it instructs a session, not a ticket's output; when one ticket splits across two workers (section 5), each worker needs its own brief while sharing one board folder, which a ticket-keyed brief location would collide on; and it already carries the same git-exclude treatment handoff.md has today. Both filenames stay git-excluded.

5. Splitting a ticket across workers

Decided (Jack, 2026-10-03):

  1. Two or more workers on one ticket: each writes only inside its own nested folder, .digismith/board/<KEY>—<slug>/worker-<agent-name>/ — the nested folder's name is the worker's own herdr agent session name (the stable address), e.g. worker-dgs-154 or worker-dgs-154-comment.
  2. When the ticket finishes, the maestro sums and merges all workers' material into one set directly in the ticket folder (one design.html, one plan.md, one report.html). Workers never merge. How the maestro merges material that collides on filename is a separate item, backlog/maestro-merges-worker-material.md (Jack) — not designed here.
  3. One worker on a ticket: no nested folder. It writes directly in the ticket folder.

After the merge is checked, the maestro removes the nested worker-<agent-name>/ folders — not keeps them. Proposed safe order, so nothing is lost for good:

  • When the active profile commits board files (today's per-repo choice, unchanged): commit the nested folders as they stand → merge into the ticket folder's top level → check the merged set → commit the merged set → remove the nested folders → commit the removal. Every byte survives in git history even though the working tree ends up with one clean set.
  • When the active profile gitignores board files: that history safety net does not exist, so removal is truly permanent. Open for Jack (section 11): either the merge step always archives the nested folders somewhere durable first, or this case accepts the same loss-on-delete risk any other gitignored file already carries.

Principle: workers do not know about each other. A worker only knows what its own brief tells it. The maestro is the only party that sees the whole ticket, so it alone:

  • names each worker's nested folder in that worker's own brief (.digismith/sessions/<agent-name>/brief.md), and
  • sorts out any earlier top-level files itself — moving a first worker's pre-existing top-level files into its own worker-<agent-name>/ folder — before a second worker starts, so neither worker ever has to reason about the other's existence.

6. The one-off worker, resolved

"No ticket, no work" (Jack, 2026-10-03) removes the old open question — which ticket number a one-off worker (a comment poster, a spike) carries — outright. Every dispatched worker carries exactly one ticket key: its own, if the work is that ticket's own work, or its parent ticket's key, if the work is a one-off slice of larger work already underway. There is no longer a worker with no ticket at all: if the work is worth a dispatch, it is worth a ticket first, even a one-line one.

A one-off slice of a larger ticket writes no new board folder. It works inside its parent ticket's existing board folder (as its own nested worker-<agent-name>/ folder, per section 5, since it is — by definition — an additional worker on a ticket that already has material), or writes nothing to board/ at all if its output is only a ClickUp comment.

7. The maestro's note and resume list

The note (.digismith/sessions/<session-name>/note.md) keeps digismith:handoff's existing Done / Decisions / Next / Open-problems shape — only its path moves, from .digismith/docs/<Clan>/handoff.md.

The resume list's own behavior — show candidate next tasks, show in-progress tickets/tasks/workers, ask Jack, never continue alone — is already decided separately ([[project_maestro-resume-trigger]]). The exact field shape of each candidate row (ticket key, title, status, which worker if any) is Flux's (DGS-154) own concern once this naming lands, not a new design surface this ticket needs to add. Flagging it here so it is not silently dropped, not designing it in this document.

9. Non-ASCII characters: build and parse rules

Board folder name — em dash (U+2014)

RiskWhere it bitesHandling
Typing it — no keyboard key for U+2014Manual folder creation Folders are never hand-typed. One shared module builds the name (see below); a thin dg board path <key> <title> command gives a human a copy-pasteable result when needed.
Windows: legacy codepages (cp1252/437) can mangle non-ASCII when a script does byte I/O instead of UTF-8Any Windows-side consumer repo — this repo's own VPS is UTF-8-only and Windows-retired ([[project_vps-single-source-of-truth]]) Every script reads and writes the name as UTF-8 explicitly (Node does this by default); never pass it through a codepage-sensitive shell builtin.
macOS: HFS+/APFS Unicode normalization (NFD) vs. Linux's raw bytes (NFC) Cross-machine sync — low risk here (VPS-only), relevant for other repos The shared module normalizes to NFC before writing. U+2014 has no decomposed form, so this risk is really about the slug's own characters, not the dash itself.
git's path quoting: core.quotepath=true (default) escapes any byte ≥0x80 in git status/git diff output as octal, and naive line-splitting of that output breaksgit status, any script scanning board folders Set core.quotepath=false in this repo so paths print as real UTF-8. Independently, every script parses git output with -z (NUL-terminated), never by line-splitting, as defense in depth.
Tools or regexes that assume ASCII-only path segments update-history.ts's parseReport(), lineage-handoff.ts, any slug-format validator Splitting happens once, in one place (see below); downstream code only ever sees the already-split key/slug strings, which stay plain ASCII.
Em dash (—) vs. hyphen (-) vs. en dash (–) look alike in narrow fonts; a human retyping the name may substitute a hyphen out of habitManual lookups, copy-paste, re-derivation The parser fails loudly if no U+2014 is found in the string, rather than silently guessing a different separator.
Case: tracker keys should compare case-insensitively but store canonicallyLookup by ticket keyThe builder always uppercases the key going in; the parser uppercases before comparing.
Sort order: directory-listing sort ≠ ticket creation order (DGS-10 sorts before DGS-9), and U+2014 sorts after all ASCII in byte order Any tool listing board folders chronologically Never rely on directory-listing order for ticket order; sort on the parsed numeric part of the key when order matters.

Build and parse (one shared module, proposed location scripts/board-path.ts):

  • Build: folderName(key, title) = `${key.toUpperCase()}—${slugify(title)}` — slugify is the existing deterministic algorithm (lowercase, drop filler words, non-alphanumeric runs collapse to a single ASCII hyphen, truncate to ~40 characters at a word boundary). That algorithm only ever emits ASCII hyphens, so the slug can never contain U+2014 itself — a hard constraint on the algorithm, not a new one.
  • Parse: split the folder name at the first U+2014. Before it: the key, validated against ^[A-Z]+-\d+$ case-normalized. After it: the slug, untouched. Because the slug can never contain an em dash, first-occurrence splitting is unambiguous.
  • Every consumer (the handoff skill, session-init.ts, writing-plans, report-implementation, update-history.ts) imports this module's buildFolderName/parseFolderName rather than re-deriving the split.

Session title / workspace label — ⚚ (U+269A)

A different surface than the folder-name risks above: titles and labels, not filesystem paths.

RiskWhere it bitesHandling
skills/handoff/SKILL.md's title-to-path matching reads the session title verbatim (via get_session)Resolving which note or brief a session owns The match only needs the <KEY> prefix before the first space — the parser splits on the first space, same "split on the known separator, ignore the rest" approach as the board-path parser, so it never needs to understand ⚚ itself.
Any tool that reads or displays the title and assumes ASCII (an older terminal, a log viewer, a non-UTF-8 CI step)herdr sidebar, pane titles, session listings Precedent already proven: ⚚ already ships in herdr workspace labels today (workbox.md, since 2026-09-29) and has worked across herdr, SSH, and Claude session titles — no new risk, carrying forward a character already live on this stack.
A title used as a filename or path componentNot done today, and not proposed here A session title is never parsed into a filesystem path; only the <KEY> prefix is ever extracted from it, for the session-name lookups in section 3.

A sibling module, proposed location scripts/session-path.ts, builds and parses .digismith/sessions/<session-name>/{note,brief}.md the same way.

12. The brief template

Generalized from the two real specimens on disk: .digismith/docs/E/E.3/brief.md and .digismith/docs/E/E.4/brief.md. The maestro always writes the brief; a worker never writes its own. It lives at .digismith/sessions/<agent-name>/brief.md (section 3) and stays git-excluded, same treatment as today's handoff.md pattern.

Required sections, in order, with no section skipped:

  1. Title and intro. # Brief: <TICKET-KEY> <short name>, then one paragraph: who sent it (the maestro, naming its own Desktop session), when (UTC+7, UTC in brackets), the worker's identity (its ticket key), its herdr agent name, its herdr session, its account, and its board folder path. When the ticket runs two or more workers (section 5), the intro also names this worker's own nested folder, worker-<agent-name>/.
  2. "You have a maestro" — standing collaboration rules, copied verbatim every time, never paraphrased: 
    - A maestro supervises you. It answers routine questions. Jack answers the design questions,
  in your pane or through the maestro.
- Ask your questions as plain text at the end of your turn, one at a time. Do not use
  AskUserQuestion forms: the maestro reads your pane, and a form is hard to read and answer
  from outside.
- Stop at every checkpoint below. Wait for "approved" before you continue.
- Never post externally: no ClickUp, JIRA or Teams writes. The maestro does those.
- Never push or merge until the maestro sends "approved: push".
- Never delete a file permanently. Move it aside and report the path.
- Never read or print a token. Work in a worktree under .worktrees/, not in the main checkout.
- You keep no state across tickets: no handoff note, no resume. When you stop, report to the
  maestro (see Report, below) and wait. The maestro closes you.
- Write short, plain sentences (the repo's technical voice).
  3. Goal. The ticket id and ClickUp list, the exact command to read it, and the scope — ticket-specific.
  4. Context (optional, included only when there is one). Whatever the maestro already decided, or explicitly has not, so the worker does not re-litigate or assume — named to fit the ticket ("Decided so far," "Vocabulary," "Interim rules"), not a fixed heading.
  5. Sources to read first. A ticket-specific reading list.
  6. Checkpoints. A numbered list. "After the sources: tell the maestro what you read, what is unclear, and your first question" is always the first one.
  7. Report. What the worker owes the maestro when it stops — at a checkpoint, or at the end of the ticket — since the worker keeps no state once its workspace closes: 
    - Result: what you did, in one or two sentences.
- Commit(s): the short hash and message of anything you committed.
- Comment ids: any ClickUp/JIRA comment ids you asked the maestro to post (you never post
  them yourself).
- Files: what you wrote or changed, as paths.
- Open questions: anything still unresolved, so the maestro can carry it forward. If it is
  not in this report, it does not exist once your workspace closes.
  8. Standing limits. Copied verbatim every time: 
    - If a call is blocked, stop and tell the maestro what was blocked. Do not rename the call,
  split it, or send it to another agent to get around the block.
- Memory is tight: check free -h before assuming headroom for another worker.
- Times in UTC+7 first, UTC in brackets. Read date before you write a time.

This closes the long-standing "what does a worker report back" question: the Report section above is the answer, baked into every brief from here on rather than re-asked per ticket.
