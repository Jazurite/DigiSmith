1. What Flux is

A flux is the cycle that renews a session. It has two flavors because the two kinds of session end differently:

Procedure

Worker flux

A herdr CLI worker exits and its workspace is closed. A worker has no handoff note and no resume: the maestro already holds the result.

Procedure

Maestro flux

The Desktop maestro cannot exit and restart. It clears itself, a kicker session wakes it with the word Arise, and it shows Jack a list.

Flux is a Protocol (Jack, 2026-10-03). The worker flux, the start of a ticket and the maestro flux are the Procedures inside it. digismith:handoff (A.1) is the Primitive they share.

3. Rules of the protocol

  1. No resume starts any work. Decided (Jack, 2026-10-03 17:58 UTC+7). "Continue with Next" no longer exists anywhere. A resume reads the note, shows a short list, and asks Jack.
  2. A worker has no handoff note and no resume. Decided (Jack, 2026-10-03 21:30 UTC+7). It starts from the maestro's brief and nothing else, and it is deleted at the flux. Its only identity is the ticket number (DGS-XXX), not a lineage. The only resume is the maestro's.
  3. The maestro holds all the state; a worker's context is protected by auto-compact only. Decided (Jack, 2026-10-03 21:38 UTC+7). A ticket that is too big for one worker is split by the maestro between workers. No note, ledger or extra rule carries a worker's state.
  4. No clear before the maestro's note exists. Proposed (the skill already says "no note, no clear"). It applies to the maestro flux only, because a worker has no note.
  5. Nothing runs in the background at a clear or an exit. Proposed, from the failed subagent kicker: clear_session killed a background subagent about 1 s after the turn ended (exit 137, 2026-10-03 17:45 UTC+7).
  6. A kick is not an approval. Proposed, from the harness notice in the A' test: a peer message cannot grant escalation. Arise therefore only asks for a read-only list and never carries a go.
  7. The maestro keeps its seat. Decided. It runs as a Desktop session on dev0. Running it as a herdr agent is ruled out. Only workers choose an account.
  8. Every step has one owner (worker, maestro, Jack or kicker) and names what it reads and writes. A skill, a hook or dg workbox can then run a step later.

4. Worker flux

Used when a worker finishes its ticket. No /clear, no reused pane, no handoff note, no resume. Decided (Jack, 2026-10-03): the workspace is closed, which replaces the reusable slot (DGS-121, DGS-126); and a worker has no handoff (Jack, 21:30 UTC+7). The maestro already holds the result (the worker's report, the PR, the ClickUp ticket), so nothing is written for the next worker.

If a ticket is too big for one worker, the maestro splits the work between workers (decided, rule 3). The worker flux has no Check Gate, because it does no clear and writes no note. 6. Maestro flux

Only the maestro uses clear_session, on self, effective when its turn ends. Decided (Jack, 2026-10-03 17:48): the kicker is a Desktop session that Jack opens and deletes by hand. Decided (Jack, 21:33): there is no Check Gate in the maestro flux. Decided (Jack, 21:44): there are no signal words. When a flux is due, the maestro asks Jack one question, "kicker open? flux now?", and Jack's yes is the signal. After that yes the maestro writes the note, arms the kicker and clears, with no further gate.

#StepOwnerReadsWrites
M1When a flux is due, ask Jack in one message: "kicker open? flux now?". Put the ready-to-paste kicker instruction in the same message, with the maestro's own session id filled in (from get_session self), and end the turn. Writing nothing yet.MaestroOwn session idThe question and the instruction on screen

The kicker's "armed" reply starts the next turn. Order. With no gate, the gate-before-arming fix of the first draft is not needed: after Jack's yes nothing makes the maestro wait for him. The kicker question comes first and in the same message as the flux question, because the kicker must be open before the maestro arms it, and the kicker instruction needs only the maestro's session id, not the note. What stays is that the arming (M3) and the clear (M4) are two turns, because the kicker's "armed" reply is a message, and a message that arrives before a turn ends drops the queued clear. The kicker starts polling only after it sent "armed", which starts the clearing turn. The gap between them is a risk in the failure table.

Fallback: if the kick is lost or held, Jack types Arise in the maestro and gets the same list. Jack's first requirement (something other than Jack types the resume text) is M5.

7. The kicker instruction

Proposed: the template lives in the runbook (untracked), next to the maestro steps. It is Workbox operations for Jack's VPS, not a feature of the plugin that ships to everyone. The maestro fills in its session id at M1.

You are the kicker for a maestro flux. Never call clear_session, stop_session,
archive_session or delete_session, and do nothing except these steps.
1. Wait for the message KICK, then reply "armed".
2. Poll get_session on session <MAESTRO_SESSION_ID> every 10 s. When isRunning is
   false on 3 checks in a row, send_message to that session with exactly: Arise
   If 15 minutes pass with no idle session, stop and report "no clear seen".
3. Report the result line and the send time (UTC+7, UTC in brackets). Then stop.

Changes from the A' test text: the wake-up is Arise alone (the test sent "resume. Continue with Next"), and the 15-minute limit is new (proposed). notify_when_idle is still untested, so polling stays.

Kicker options tested

  • Background subagent. Failed. clear_session kills it: a command in it ended with exit 137 about 1 s after the turn ended (17:45 UTC+7, comment 1301150000057204).
  • Node setInterval process (spike, 2026-10-03, .digismith/docs/E/E.4/node-kicker-spike/ (it moves with DGS-159's file moves), script kicker.mjs). Delivery is unproven: the session's Unix socket speaks an undocumented, versioned protocol, and claude --resume --print may lock against the live process. Not pursued.
  • Still untested: a herdr CLI worker as the kicker, and notify_when_idle as the wait. Both are build 2 candidates, not part of this design.

8. The A.1 skill change

Two tracked skill changes besides this design. Both are small because the maestro-specific work (fetch main, workers, tickets) stays in the runbook, not in a skill that ships to every user. First, skills/handoff/SKILL.md:

  • Description and Invoked By: add Arise as a resume trigger, next to "resume" and "pick up where we left off".
  • Resume Mode step 4: replace "State Done and Next in a few lines, then ask 'Continue with <Next>?'" with: state Done in a few lines, show Next and the open problems as a short numbered list of candidates, and ask which one Jack wants. Start nothing. This applies to every resume, not only the maestro's (decided by Jack's rule: no resume starts work).
  • Rationalizations: the row "Resume found a note, so I'll start on Next" stays true and needs no change.
  • Check Gate: the gate stays for an ordinary handoff and clear. The maestro flux has none (Jack, 21:33), so the skill needs a clause, proposed: "when the human partner's message is a yes to your own question 'kicker open? flux now?', skip the Check Gate: write the note, show it, and go on to the kick and the clear." No signal word is needed (Jack, 21:44): the maestro's own question and Jack's yes are the signal. The gate for every other clear, including a "hand off and clear" Jack types himself, is unchanged. Without the clause the skill's own gate would stop the maestro flux at M3.
  • SessionStart trigger (Invoked By, third bullet): add a clause, proposed: ignore the line in a worker started by the maestro with a brief (its first message tells it to read a brief), because a worker has no note and no resume. A worker's title (<KEY> ⚚ <short name>) carries a ticket key, never a lineage key, but the old mapping sends it to _unlettered, so the key-match rule does not reliably ignore the line; the clause is what makes it true.
  • scripts/session-init.ts: unchanged (proposed). The pointer line says "or say resume", and Arise comes from the kicker or from Jack, who knows it from the runbook.

Named change: digismith:finishing-a-development-branch Step 7

Decided (Jack, 2026-10-03 21:38 UTC+7): the handoff flow is removed for a worker. File: skills/finishing-a-development-branch/SKILL.md, Step 7 "Hand Off" (line 375). It is one clause, plus a matching half-sentence in the Quick Reference note at line 398:

11. How build 1 is checked

  • The skill text is reviewed against Jack's rule: no sentence left that starts work on a resume, and no "Continue with Next".
  • The existing tests for the lineage script and the SessionStart line (scripts/lineage-handoff.test.ts, scripts/session-init.test.ts) stay green and are not changed in Part B; DGS-159 changes the scripts and their tests.
  • A live run of the maestro flux with Jack present (a Desktop kicker, M1 to M7) shows that Arise produces a list and not an action. This needs Jack and the maestro, so the maestro runs it after the build.
  • The finishing skill is read to confirm a worker started with a brief skips Step 7 and that Option 1, Option 2 and Option 3 behave as before for a session that is not such a worker.
  • The runbook is checked by reading it against the tables in sections 4 to 6: every step has an owner, reads and writes.
