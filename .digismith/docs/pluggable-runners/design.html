Overview & core idea

K.3 made the gateway vendor pluggable for K.2's digismith:offload-implementer — Chutes or TokenReply, chosen per-profile, both dispatched the same way: through OpenCode. The runner — the coding-agent tool that actually reads files, edits, and runs commands during an offloaded task — has stayed hardcoded to OpenCode this whole time.

This design makes the runner pluggable too: OpenCode or Claude Code itself, chosen per-profile, the same shape K.3 already established for vendors. K.6 originally framed this territory as a benchmark study ("compare OpenCode vs. Claude Code head-to-head") — this design promotes it to real, shippable infrastructure. A head-to-head benchmark run is a natural follow-on once both runners actually exist side by side, not something this design does itself (see Out of Scope). No new map letter — same precedent K.3 set when it reused K's own reservation instead of inventing letter W.

Scope decisions

Decided during brainstorming, each with the alternative it beat:

DecisionChosenRejected alternative
Claude Code integration mechanism Headless claude -p CLI, spawned as a subprocess — real, documented, non-interactive dispatch, structurally parallel to opencode run Embedding the Claude Agent SDK as a library (the K.3 spike's approach) — no subprocess parity with OpenCode, no port/server; Remote Control was also considered and ruled out entirely — it's a cross-device UI continuity feature (syncs a session's UI state to claude.ai/mobile), not a network API; no port, no way for an external dispatcher to attach
Terminology Runner — the config field, type, and provider capability field all use this term "Harness" (the standard industry term, but reads as a process rather than an actual executing thing); "rig"/"cab" (continues Depot's transport-theme naming, but adds a metaphor without improving clarity over "runner")
Where the branching lives Approach A — one skill (offload-implementer), the 4 of 7 steps that actually differ by runner branch internally Approach B — a second, parallel claude-code-implementer skill with a routing step. Would duplicate the 3 runner-agnostic steps plus Error Handling across two files that must stay in sync by hand — exactly the "verbatim duplication of a logic block" this project's own review rubric treats as a defect
Vendor/runner compatibility Each GatewayProvider declares supportsRunner: RunnerName[] — a general mechanism. Confirmed today: TokenReply supports both (the spike proved ANTHROPIC_BASE_URL works against it); Chutes' public docs only show an OpenAI-compatible endpoint, no confirmed Anthropic Messages API compatibility, so it lists ["opencode"] only Hardcoding "Claude Code only works with TokenReply" as a special case — same practical effect today, but doesn't generalize if a future vendor (or Chutes itself) adds Anthropic-protocol support
Depot's role for Claude Code ensure-claude-code — a stateless readiness check (is claude on PATH?). No process, no pid, no port tracked — there's nothing to track, since claude -p spawns fresh per dispatch and needs no warm server No Depot involvement at all (simpler, but breaks the "everything offload-related goes through Depot" consistency the user wants, including as a future hook point for token/cost analytics); Depot tracking active session IDs machine-wide (real new tracked state, not needed today — session IDs already live in the plan's own SDD workspace, matching how OpenCode session IDs are tracked today)
Missing claude CLI Report plainly, point at npm install -g @anthropic-ai/claude-code, never auto-install Auto-install on demand — would break symmetry with depot/SKILL.md's existing, explicit "don't attempt to install opencode silently" rule
Event/result parsing Real code — scripts/runners/parse-result.ts <runner> <events-file>, called from the skill instead of hand-rolled jq/prose per runner Prose-only, mirroring today's OpenCode Step 5 exactly (bash + manual JSON-field navigation described in the SKILL.md text) — works, but doesn't reduce duplication the way moving logic into a tested module does
Claude Code auth header ANTHROPIC_AUTH_TOKEN (Bearer-style), matching what the K.3 spike actually proved working against TokenReply ANTHROPIC_API_KEY (X-Api-Key header) — also documented and supported, but not the form the spike verified live

Architecture

Same shape as K.3's GatewayProvider Strategy pattern, one level over: a Runner interface with one concrete module per runner, resolved by a registry factory. New folder scripts/runners/, mirroring scripts/providers/: 

// scripts/runners/types.ts
export type RunnerName = "opencode" | "claude-code";

export interface RunnerConfig {
  // shape varies by runner; consumers treat it opaquely and pass it
  // straight through to print-config.ts's JSON output
  [key: string]: unknown;
}

export interface ParsedResult {
  status: "success" | "error" | "interrupted";
  resultText: string | null;
  sessionId: string | null;
  costUsd?: number;
}

export interface Runner {
  name: RunnerName;
  buildConfig(provider: GatewayProvider, role: "mechanical" | "task"): RunnerConfig;
  parseResult(eventsFile: string): ParsedResult;
}
// scripts/runners/opencode.ts
// buildConfig: today's buildOpencodeProviderBlock, moved here unchanged.
// parseResult: reads OpenCode's JSONL events, finds the last
// type:"text" event, extracts .part.text (not top-level .text) and
// .sessionID (top-level) — codifies today's Step 5 prose exactly.
export const opencode: Runner = { name: "opencode", buildConfig, parseResult };
// scripts/runners/claude-code.ts
// buildConfig: returns { baseUrl: provider.baseUrl, credentialEnv:
// provider.credentialEnv } — the two env vars offload-implementer
// exports as ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN before spawning
// `claude -p`.
// parseResult: reads claude -p --output-format stream-json's last line
// (type:"result"), maps subtype "success"|"error"|"interrupted" to
// ParsedResult.status, .result -> resultText, .session_id -> sessionId,
// .cost.total_cost_usd -> costUsd.
export const claudeCode: Runner = { name: "claude-code", buildConfig, parseResult };
// scripts/runners/registry.ts
const runners: Record<RunnerName, Runner> = { opencode, "claude-code": claudeCode };

export function resolveRunner(name: string): Runner | undefined {
  return runners[name as RunnerName];
}

GatewayProvider (in scripts/providers/types.ts) gains one field: supportsRunner: RunnerName[]. Resolution logic (in offload-implementer's Step 1, or a small shared helper) checks the resolved runner is in the resolved provider's list before proceeding — same "never write a config that can't authenticate" principle K.3 already established for unknown providers.

Components

  • scripts/runners/types.ts, opencode.ts, claude-code.ts, registry.ts — new, mirrors scripts/providers/'s shape.
  • scripts/runners/parse-result.ts — new CLI (node scripts/runners/parse-result.ts <runner> <events-file>), prints a uniform {status, resultText, sessionId, costUsd?} JSON object regardless of which runner produced the raw events.
  • scripts/providers/types.ts — adds supportsRunner: RunnerName[] to GatewayProvider. chutes.ts: ["opencode"]. tokenreply.ts: ["opencode", "claude-code"].
  • scripts/providers/print-config.ts — gains --runner <name>. Delegates config-building to the resolved Runner.buildConfig(); for opencode, output is byte-identical to today (the OpenCode-specific logic simply moves into scripts/runners/opencode.ts rather than living inline in print-config.ts).
  • profiles/*.yml — every profile gains task_offload_runner: opencode | claude-code, default opencode — every existing profile keeps behaving identically until someone opts in.
  • skills/depot/SKILL.md — new operation ensure-claude-code: validate claude on PATH (and that --bare is supported), return ready/not-ready. No file written, no process tracked — stop-opencode-server has no Claude Code equivalent, since there's no process to stop.
  • skills/offload-implementer/SKILL.md — Steps 1 (config), 2 (ensure), 4 (dispatch), 5 (parse) become runner-conditional. Steps 0 (intent), 3 (prompt-building), 6 (hand-back), and Error Handling stay untouched — genuinely runner-agnostic already.

Data flow

Fresh dispatch, either runner

  1. Resolve task_offload_runner (default opencode) and task_offload_provider from the active profile — same resolution mechanism K.3 already uses.
  2. Validate: does the resolved provider's supportsRunner include the resolved runner? No → stop, report BLOCKED, same disposition as an unrecognized provider name today.
  3. Runner-conditional config + readiness:
    • opencode: print-config.ts --runner opencode ... → write opencode.json (unchanged). Depot's ensure-opencode-server → get a port.
    • claude-code: print-config.ts --runner claude-code ... → {baseUrl, credentialEnv}. Depot's ensure-claude-code → confirm claude is on PATH. No port, no config file — two env vars to export at dispatch time.
  4. Runner-conditional dispatch:
    • opencode: unchanged — opencode run --attach <url> --model <provider>/<model> --auto --format json --dir <worktree> "$PROMPT" > events.jsonl
    • claude-code: ANTHROPIC_BASE_URL=... ANTHROPIC_AUTH_TOKEN=... claude -p "$PROMPT" --bare --model <model> --permission-mode auto --output-format stream-json --allowedTools "Read,Edit,Bash" > events.jsonl, subprocess cwd set to the task worktree at spawn time (no --dir flag exists for claude)
  5. scripts/runners/parse-result.ts <runner> events.jsonl → uniform {status, resultText, sessionId, costUsd?}.
  6. Record sessionId for fix rounds — same opencode-sessions.jsonl file, now runner-agnostic (just an id, not opencode-specific).
  7. Hand back to normal flow: report contract, review, fix loop — entirely unchanged.

Fix round

Same as above, but dispatch adds --session <id> (opencode) or --resume <id> (claude-code) instead of starting fresh.

Why --bare doesn't break standards injection: Step 3 already inlines the full inject-standards output as literal prompt text before either runner launches — it's not a live skill invocation. --bare only skips auto-discovery of skills/CLAUDE.md/hooks, not content already pasted into the prompt.

Error handling

Extends offload-implementer's existing table:

CaseDisposition
Resolved provider doesn't list the resolved runner in supportsRunner Stop, report BLOCKED — same as today's unrecognized-provider-name case.
claude not on PATH (ensure-claude-code) Stop, report plainly, point at npm install -g @anthropic-ai/claude-code. Never auto-install.
claude -p run genuinely errors (result.subtype: "error" or "interrupted") Report as BLOCKED, same disposition a stuck opencode run gets today.
--resume <id> no longer resolves (session pruned, expired, different machine) Same disposition as OpenCode's "captured sessionID no longer resolves" case — report plainly, re-dispatch as a fresh task, not a fix round.
A status reply can lie Unchanged, runner-agnostic — still independently verify a real commit exists before trusting DONE.
Fix round hits the cap (3) Unchanged, runner-agnostic — user decides, no auto-escalation to a different runner.

Testing

  • scripts/runners/opencode.ts: buildConfig — behavior-preserving move of today's buildOpencodeProviderBlock (existing print-config.test.ts cases carry over unchanged). parseResult — new tests against realistic OpenCode JSONL fixtures (nested .part.text).
  • scripts/runners/claude-code.ts: buildConfig — tests resolving {baseUrl, credentialEnv} per provider. parseResult — tests against synthetic stream-json fixtures built from the documented schema: success, error, interrupted.
  • scripts/runners/registry.ts: known/unknown, same shape as resolveProvider's tests.
  • scripts/providers/registry.test.ts: extend to assert supportsRunner is present and valid for both providers.
  • print-config.ts: extend existing CLI tests to cover --runner opencode (unchanged output) and --runner claude-code (new shape).
  • scripts/runners/parse-result.ts: CLI contract tests, same execFileSync pattern as print-config.test.ts.
  • No tests for offload-implementer/depot SKILL.md edits — prose files, task-level review only, matching how K.3 treated its own skill-file changes.
Honest risk: the stream-json fixtures are built from documented schema, not a captured real run — claude -p hasn't actually been invoked in this project yet. Same category of gap K.3 handled with an explicit "manually confirm the CLI contract end to end" plan step; this plan needs the equivalent for a real claude -p invocation before calling it done.

Out of scope

  • Running an actual head-to-head benchmark — building the infrastructure both runners need to be comparable is this design's job; running the comparison and publishing results is K.6's remaining piece, a natural follow-on once this ships.
  • K.4 — gateway-vs-native-Claude-Code cost comparison. Noted as a forward-compatible detail: claude -p's stream-json result already carries real cost.total_cost_usd/token counts natively, which K.4 can consume directly without the SDK-cost-estimate workaround the K.3 spike needed.
  • K.5 — running multiple gateways in parallel.
  • K.7 — vendor benchmark (Chutes vs. TokenReply vs. future gateways).
  • Depot-based token/cost analytics — raised during brainstorming as a reason to route everything through Depot, but not built here. Documented as a future direction: a candidate third Depot resource, hooking into the cost/usage data both runners' ParsedResult can now surface.
  • Automatic runner selection or fallback (e.g. auto-switching if claude isn't installed) — switching is a manual profile edit, same stance K.3 took for provider switching.
  • Chutes gaining Anthropic Messages API compatibility — if it ever does, enabling it is a one-line change to chutes.ts's supportsRunner, not a design change. Not chased down further here since it's unconfirmed either way.

Open questions

  • Whether claude -p --output-format stream-json's real output matches the documented schema exactly — needs a live invocation to confirm before implementation treats the schema as gospel (see Testing's honest-risk callout).
  • Whether TokenReply's Trial-tier rate limiting (429s roughly every 5-10 tool calls, noted in K.3's spike) meaningfully affects a real claude -p dispatch the same way it did the SDK spike — not a blocker for this design, but worth watching during the first real test.
