Overview

G.3.1's post-merge review (Fable-model, 2026-09-12) found two real gaps in digismith:inject-standards, both first exposed by G.3.1 being the first prose-only, multi-file standard under standards/global/: (1) nothing mechanically stops a prose-writing standard from being injected into a subagent's pure code-dispatch prompt (Scenario 4), and (2) a matched standard's cross-references to sibling files dangle, since a subagent has no plugin-path visibility to follow them itself. Filed as backlog/inject-standards-prose-scope-gate.md; this design resolves both.

Schema additions

Two new optional fields on a standards/index.yml entry, both backward-compatible — absent on all 11 pre-existing entries, no behavior change for them:

FieldValuesEffect
kindabsent (default), or proseMarks a standard as prose-only guidance (not code, not a checkable pattern) — see Scenario 4 gate below
companionsabsent (default), or a list of sibling file names in the same folderFiles always injected alongside this one when it's matched, in any scenario — see Companion injection below

digismith:index-standards (the skill that writes index.yml) documents both fields in its Step 6 schema/example, and its Step 4 (proposing a description for a new/changed file) gets one added line: when a new file reads as prose style guidance rather than a code/process pattern, propose kind: prose alongside the description; when it cross-references sibling files by path, propose a companions: list. Still just a proposal the user confirms, same as the description itself.

Scenario 4 prose gate

inject-standards Step 3 (today: the Shopify-repo-layer auto-include gate) gets one more rule, unconditional and independent of repo type: any entry with kind: prose is excluded from Scenario 4 entirely — never suggested, never matched, never auto-included, regardless of how well its description fits the dispatch's context. Scenario 4 dispatches are always code-implementer subagents (via offload-implementer); nothing today dispatches a subagent whose job is drafting prose, so a prose-kind standard has no legitimate Scenario 4 use case to weigh against the false- positive risk the review found. Scenarios 1-3 (conversation, skill authoring, planning) are unaffected — a human-facing session can still legitimately want writing guidance while planning or authoring a SKILL.md, which is exactly G.3.1's own stated use case.

Companion injection

inject-standards Step 6 (Inject) gets one addition, applying identically across Scenarios 1-4: whenever a matched entry has a companions: list, its listed files are read and injected immediately alongside it, formatted the same way as the primary match (same --- Standard: ... --- block in Scenarios 1/4, same reference/copy-content choice in Scenarios 2/3). This is a general primitive — any future multi-file standard gets it for free by adding the field, not just G.3.1's three files.

standards/index.yml's ste100-writing entry gets kind: prose and companions: [ste100-word-swaps, ste100-use-cases]. The other two ste100 entries get kind: prose only — they're reference material meant to travel with the core file, not to be matched and injected standalone, so they need no companions list of their own.

Out of scope

  • Any change to shopify//team/'s existing repo-qualification gate — untouched, this is a new, independent rule
  • Retroactively auditing which past Scenario-4 dispatches might have picked up the ste100 standards before this gate existed — not tracked, not worth reconstructing
  • A general "companions are bidirectional" rule — ste100-word-swaps/ ste100-use-cases don't get their own companions: pointing back at ste100-writing, since they're not expected to be matched independently
