Background & Trigger

W.1 (merged 2026-08-29) did a pure, static, byte-identical clone of all 14 Superpowers skills into skills/vendored-<name>/, explicitly declared "a snapshot, not a mirror" with no sync tooling — future upstream improvements were to be pulled in manually, skill by skill, if and when noticed. All 14 clones are dormant: nothing in DigiSmith calls into any of them yet.

Two gaps in that plan surfaced immediately, before any primitive had actually been activated:

  • A vendored skill's frontmatter description: is currently byte-identical to its still-live superpowers: counterpart — nothing marks it as a DigiSmith fork from inside the skill itself. vendored/PROVENANCE.md records provenance for the whole batch, but that file isn't visible from a skill listing or from opening the skill's own SKILL.md.
  • "No sync tooling, pull in manually if and when wanted" has no actual mechanism behind it — there's no way to know what upstream has changed without manually diffing 14 skill folders by hand against whatever Superpowers plugin version happens to be installed.

This document specs the general, reusable mechanism for both gaps — applicable to any of the 14 vendored skills, activated or still dormant — using no specific primitive's content as its subject.

Scope: W.2 vs. the Rest of the Initiative

This slice is infrastructure only: a naming/description convention plus one diff-check script. It deliberately does not include:

  • Call-site cutover — redirecting DigiSmith's existing internal references (bootstrap, adopt, subagent-driven-always, enforcer, capture-ephemeral-url, etc.) from superpowers:<name> to digismith:<name> for all 14 skills. Content-neutral (the vendored copies are still byte-identical to upstream today) but broad-touching — deliberately deferred to its own future item, tentatively W.3.
  • Any actual primitive content change — e.g. fixing finishing-a-development-branch's Option 1 never pushing to origin (backlog/no-push-after-local-merge.md), the leading candidate for the first real activation. That's its own item, sequenced after W.3, once call sites actually point at the vendored copy that would need to diverge.

What W.2 delivers is the pattern both of those later items will reuse: how an activated skill announces its fork provenance, and how anyone (activated skill or not) can check what upstream has changed since the W.1 baseline.

Architecture & Components

1. Fork-provenance tag

At activation, a skill's frontmatter description: gets a short parenthetical appended: (DigiSmith fork of Superpowers' <name>). This serves two purposes at once: visible provenance from a skill listing or the raw file, and the "deconflict the description from the still-active superpowers:<name> original" step vendored/PROVENANCE.md's Activation checklist already calls for (today both descriptions are identical and harmless; that stops being true the moment either skill's content diverges). This is documented as an addition to that existing checklist, not a new file. Not applied to any skill by this slice — dormant skills keep their untouched upstream description until they're actually activated.

2. scripts/check_vendored_skills.ts

TypeScript, run directly via node scripts/check_vendored_skills.ts — the repo's root package.json already requires Node ≥24 and carries typescript as a devDependency, and Node 24's built-in type stripping runs a script this simple with no new runtime dependency (no tsx/ts-node added). On-demand only — no scheduled job, no lifecycle hook; covers all 14 vendored skills every run, dormant or activated alike.

Resolve upstream

Globs ~/.claude/plugins/cache/claude-plugins-official/superpowers/*/skills/ and picks the most-recently-modified hash directory. Never hardcodes a specific hash (W.1's recorded 44c9b2d6e889 is already just a point-in-time snapshot, not a stable identifier across Superpowers updates).

Three-way diff

Per skill: baseline (the W.1 clone commit's copy, via git show <sha>:skills/vendored-<name>/...), upstream-now (freshly resolved), and local-now (working tree). Reports baseline→upstream-now as the headline "what changed upstream" signal, and baseline→local-now separately as "what you've customized" context — never conflated into one diff, which is what would happen with a naive two-way comparison once a skill has actually diverged.

Data Flow

  1. Resolve the installed Superpowers plugin's skills/ directory (see Architecture above). Fail loudly if none is found.
  2. Read the baseline commit SHA from vendored/PROVENANCE.md (a6418858b5374c2506d1ff799b2dcb418bff53d1 — the exact commit that performed W.1's original clone).
  3. For each of the 14 vendored skills, for every file that existed in the skill at baseline:
    • Read baseline content via git show <sha>:<path>.
    • Read upstream-now content from the resolved plugin directory. Missing → note as "removed upstream."
    • Read local-now content from the working tree.
    • Compute and print diff(baseline, upstream-now) and, only if non-empty, diff(baseline, local-now) as a clearly separated second block.
  4. Print a one-line summary per skill (no drift / N files changed upstream / also locally diverged) followed by full diff detail for anything non-empty.
  5. Pure stdout report. No files written, no state mutated, nothing auto-applied.

Error Handling & Known Limitations

  • Plugin cache not found (Superpowers not installed, or a different marketplace layout) → fail loudly with a clear message, exit non-zero. No partial report — either the upstream side of the comparison is available for all 14 skills or the script doesn't pretend to have checked any of them.
  • Baseline SHA unresolvable (e.g. history was rewritten and the commit no longer exists) → fail loudly, point at vendored/PROVENANCE.md for a human to fix the recorded SHA. Never silently fall back to a two-way diff — that's exactly the "your own edits drown the real signal" failure mode this design exists to avoid.
  • File removed upstream → reported as "removed upstream" for that file, not a crash; the rest of the skill's files still get compared normally.
  • Multiple installed plugin versions on disk. "Most-recently-modified directory" is a heuristic, not a guarantee — if Claude Code ever leaves stale hash directories behind after an update without cleaning them up, mtime could theoretically point at the wrong one. Not investigated further here; worth a second look if the script ever reports something that doesn't match the actually installed version.

Testing / Verification

  • Run the script for real once built — nine days have passed since the 2026-08-20 baseline, so this is a genuine first check for real upstream drift, not just a dry run against zero expected output.
  • Confirm the baseline→upstream-now and baseline→local-now blocks stay correctly separated for at least one skill by temporarily editing a local vendored copy, re-running, and checking the local edit shows up only in the local-divergence block.
  • Confirm a missing/renamed plugin cache directory produces the loud failure described above rather than a silent empty report.

Future Phases (W.3+, Not Designed Here)

  • W.3 — call-site cutover. Redirect every DigiSmith internal reference to superpowers:<name> over to digismith:<name>, for all 14 vendored skills, as one content-neutral pass (content is still byte-identical to upstream at that point — this is purely about which skill DigiSmith's own call sites actually invoke).
  • First real activation — finishing-a-development-branch. After W.3, actually diverge its content to add the missing push step in Option 1 ("Merge Locally"), using this document's fork-provenance tag convention and diff-check script as the supporting mechanism. Its own future brainstorm, undesigned here beyond the trigger already on record in backlog/no-push-after-local-merge.md.
  • Activating other primitives — one at a time, each its own brainstorm, order dictated by future need.

Open Questions

  • None blocking W.2. The "multiple installed plugin versions" limitation noted above is worth revisiting if it ever actually bites, not speculatively hardened against here.
