Problem & Goal

DigiSmith's real Emma workflow doesn't always start at using-digismith. Jack's actual routine pulls a ticket ID through his own Atlassian MCP connector and lets vanilla superpowers:brainstorming/superpowers:writing-plans produce a spec and plan directly — using-digismith never runs. By the time he wants DigiSmith's behavior active (profile-scoped standards injection, the unified docs convention, the Emma standards subset), .digismith/profile was never written, enforcer never fired (it gates on repo identity or that same file), and the spec/plan sit in Superpowers' default locations in the wrong format. This is exactly the friction backlog/mid-development-workflow-injection.md was deliberately deferred waiting for — DigiSmith's pipeline assumed starting from the top, with no entry point for work already mid-stream.

The goal is a single command, digismith:init, that is safe to invoke regardless of where a ticket's work actually stands — the same way git init is safe to run in a fresh directory or an already-initialized repo. It inspects state and either kicks off the existing fresh-start flow or adopts already-existing artifacts into DigiSmith's conventions, then hands off to the same build stage either way.

Non-Goals

  • Not redesigning enforcer, inject-standards, or jira-intake. All three are reused as-is; this feature only adds a new caller for each, never new logic inside them.
  • Not renaming a branch that doesn't match <Key>__<slug>. capture-ephemeral-url already degrades gracefully on a non-matching branch name (asks for the key directly) — confirmed by reading its Error Handling section — so adopting a differently-named branch as-is is sufficient; no rename step is needed.
  • Not supporting joining at any pipeline stage other than the one recurring case: ticket known, spec written, plan written, nothing built yet. Joining before a spec/plan exists, or mid-build, is out of scope for this pass — narrower scoping was an explicit choice, not an oversight.
  • Not building content-diffing or partial-redo recovery for a re-run. The already-initialized check (see below) makes re-running init on a fully set-up ticket a plain no-op report, not a repair tool for a run that failed partway through — that failure mode is left for a future pass if it turns out to matter.

Architecture — One Front Door, Two Internal Workers

digismith:init is the only skill either Jack or a future session invokes by name for starting or resuming ticket work. It dispatches to one of two internal-only workers, neither of which is meant to be triggered directly:

Front door

digismith:init

Checks whether this worktree is already initialized; if not, detects fresh-start vs. mid-stream and dispatches accordingly.

Internal

digismith:bootstrap

Renamed from today's using-digismith, logic unchanged: profile → ticket → telemetry marker → branch/worktree → hand off to brainstorming.

Internal

digismith:adopt

New. Backfills profile/ticket/branch state for work that already has a spec and plan, then relocates those docs and hands off straight to the build stage.

bootstrap and adopt keep their own SKILL.md files and remain independently readable/testable — only their trigger surface changes: neither declares a user-facing "use when" description anymore, since init is the only caller.

Already-Initialized Check

.digismith/profile is DigiSmith's own equivalent of .git/: both bootstrap (Step 2.6) and adopt (its own equivalent step) copy it into the worktree as the last thing they do before handing off to the build. init checks for it first, before any detection logic runs:

  • Present in the current working directory → this worktree was already fully set up by DigiSmith. Report plainly — "Already initialized for DigiSmith (profile: <name>, docs at .digismith/docs/<slug>/)" — and stop. No re-detection, no re-relocating docs, no questions asked. Same posture as git init on an existing repo: a notice, not a cascade.
  • Absent → proceed to Detection Logic below.

Detection Logic

Only reached when .digismith/profile is absent from the current working directory. Checked in order:

#SignalDispatch
1Current branch is the repo's base branch (main/master)fresh start → bootstrap
2Already on a feature branch, and .digismith/docs/<slug>/plan.md already exists for itnormal resume → bootstrap (its existing branch/worktree reuse logic already covers this)
3Already on a feature branch, no .digismith/docs/ for it, but a plan file exists somewhere (Superpowers' default location, or wherever the user points)mid-stream → adopt
4On a feature branch, no plan found anywhereambiguous → ask directly, never guess

bootstrap (Fresh-Start Path)

Unchanged from today's using-digismith: Step 0 (resolve/pick profile) → Step 1 (get ticket via jira-intake, or derive slug directly under ticket: false) → Step 1.5 (telemetry marker) → Step 2 (create/attach branch+worktree; copy .digismith/profile and the telemetry marker in) → Step 3 (hand off to superpowers:brainstorming, passing ticket content as seed). Only the file is renamed and its trigger narrowed to internal-only; no process step changes.

adopt (Mid-Stream Path)

Step 1

Confirm Inputs

Ask for whatever isn't already obvious: ticket key, path to the existing plan (required), path to the existing spec (optional — some tickets skip brainstorming entirely).

Step 2

Resolve Profile

Reuse bootstrap Step 0 verbatim — same resolution and first-use picker.

Step 3

Derive the Slug

Current branch already matches <Key>__<slug> → reuse that slug. Otherwise derive from the ticket title via jira-intake Step 3.1's algorithm — same one bootstrap already restates inline for its ticket: false path.

Step 4

Write ticket.md

Invoke jira-intake Door 1 with the already-known key — reuses its detection, template, and collision handling rather than duplicating it. Skipped entirely if the active profile's ticket field is false, same as bootstrap.

Step 5

Adopt Branch/Worktree

Reuse bootstrap Step 2's exact reuse/attach/create logic. Whatever already exists is adopted as-is — no renaming, even off-convention. Copy .digismith/profile (and the telemetry marker, if logging is on) into the worktree, same as bootstrap Step 2.6/2.7.

Step 6

Relocate the Docs

Reuse enforcer Step 2/5's "Verified" move-and-correct logic directly: rewrap the existing spec into enforcer's HTML shell at .digismith/docs/<slug>/design.html (respecting gitignore/commit and publish_artifact); move the plan as-is to .digismith/docs/<slug>/plan.md. No spec found → skip design.html, note it, proceed with the plan alone.

Step 7

Hand Off to Build

Invoke superpowers:subagent-driven-development directly against the relocated plan.md — brainstorming/writing-plans already ran outside DigiSmith, so they're skipped. subagent-driven-always and inject-standards Scenario 4 apply unmodified from here on, exactly as if writing-plans had just finished normally.

Error Handling & Edge Cases

  • Detection ambiguous (row 4 above) → ask directly: "start fresh, or is there a plan somewhere I should adopt?" Never guess.
  • adopt invoked but no plan file can be found or provided → stop, explain a plan file is required for this path; don't fabricate one or silently fall back to bootstrap.
  • Active profile has ticket: false → skip jira-intake/ticket.md entirely, same as bootstrap — adopt isn't ticket-mandatory just because the recurring case usually has one.
  • Branch name collision with an unrelated ticket during Step 5's branch reuse → same as bootstrap today: ask via AskUserQuestion, never silently reuse a stranger's branch.
  • jira-intake's own stop conditions (no JIRA tool and the user declines to paste, sparse paste, existing-file collision, etc.) → adopt doesn't proceed past whatever jira-intake itself decided; not a new failure mode to reinvent.
  • No spec found, only a plan → not an error (see Step 6) — some tickets go straight from a raw need to a hand-written plan with no formal spec step.

Testing / Verification

No automated test suite — consistent with every DigiSmith skill so far. Verification is a dogfooding pass after implementation:

  1. Fresh start — on the base branch, invoke init; confirm it dispatches to bootstrap and the existing fresh-start behavior is unchanged.
  2. Normal resume — on a feature branch with .digismith/docs/<slug>/plan.md already present; confirm dispatch to bootstrap, which reuses the existing worktree rather than creating a new one.
  3. Mid-stream adopt, happy path — a fixture feature branch with a plan (and a spec) sitting in Superpowers' default locations; confirm init dispatches to adopt, which writes ticket.md, relocates both docs into .digismith/docs/<slug>/ correctly formatted, and constructs the subagent-driven-development hand-off against the relocated plan.
  4. Mid-stream adopt, plan only — same as above but no spec file exists; confirm design.html is skipped without error and the hand-off still proceeds.
  5. Already-initialized — re-invoke init in a worktree that already has .digismith/profile; confirm a plain report-and-stop, no re-processing.
  6. Ambiguous state — feature branch, no plan anywhere; confirm init asks rather than guessing.
  7. Off-convention branch name — adopt a branch that doesn't match <Key>__<slug>; confirm it's adopted as-is with no rename attempt.
