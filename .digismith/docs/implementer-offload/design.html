Overview

DigiSmith's map item K.2. Lets a single task inside a real superpowers:subagent-driven-development plan run on a Chutes-hosted third-party model instead of Claude, when explicitly asked for. Distinct from K.1 (scripts/model_offload.py), which offloads DigiSmith's own single-shot document generation (no tool access needed) — K.2 needs a real autonomous implementer with file/git access, which a bare completion call cannot provide.

Grounded in a passed spike, not speculation: a Chutes-hosted model (Kimi K3), driven by OpenCode — a real autonomous coding agent, not a raw API call — autonomously read a file, ran a failing test suite, diagnosed a real seeded bug, fixed it correctly, and re-verified, independently confirmed afterward rather than trusted from its own report. See Spike Evidence.

Trigger

Explicit, per-task

You ask for it when dispatching a specific task. No automatic classification of "qualifying" tasks — that responsibility stays with you.

On failure

Surfaces, never silent

Higher stakes than K.1's document rewrap — a stuck or bad attempt is reported plainly, never quietly handed to a Claude implementer without you knowing.

Trigger: Explicit Per-Task Opt-In

Nothing in subagent-driven-development's own task loop changes by default. When dispatching a specific task, you say you want it offloaded (however phrased — "offload this to Kimi", "use OpenCode for this one"); the controller then invokes digismith:offload-implementer for that task instead of the normal implementer dispatch. Every other task in the same plan still gets a normal Claude implementer unless you say otherwise for it too — offload is a per-task choice, not a plan-wide mode.

Architecture: Controller-Driven, Not Agent-Tool Dispatch

Claude Code's Agent tool has no non-Anthropic model routing (confirmed twice: during K.1's own feasibility spike, and again this session). A normal implementer is a fresh, isolated Agent subagent; an offloaded task cannot be that. Instead, the controller itself — the session driving subagent-driven-development — shells out to the opencode CLI directly via Bash, waits for it to finish, and reads its output. This is a real, structural difference from normal dispatch, not just an implementation detail: OpenCode's run transcript lands directly in the controller's own context (the way the spike's output did), rather than staying isolated in a separate subagent transcript the way a Claude implementer's full working context does. The controller's context cost per offloaded task is therefore higher than a normal dispatch — worth knowing, not a blocker.

Server Lifecycle: Persistent Server, Fresh Session Per Task

opencode run alone starts a fresh process per invocation. For a plan with multiple offloaded tasks, that's repeated cold-start cost with no benefit — subagent-driven-development already dispatches one fresh implementer context per task deliberately (its own "no context pollution" principle), so nothing is gained by also restarting the underlying process each time.

Verified live this session: a persistent opencode serve process, with two separate opencode run --attach <url> calls against it (no session flags on either), get genuinely isolated sessions — the second call had no memory of information given to the first. Persistent server, fresh session per task, confirmed to hold together in practice, not just assumed compatible.

Start

The first time digismith:offload-implementer is invoked in a plan, start the server in the background and capture its PID directly from the launch ($! in the same shell invocation) — not by scanning for a listening port afterward, which is a weaker, racier signal: 

opencode serve --port <port> --hostname 127.0.0.1 > opencode-server.log 2>&1 &
SERVER_PID=$!

Record the PID and port in this plan's SDD workspace (.superpowers/sdd/<plan-basename>/, alongside the existing ledger) so later offloaded tasks in the same plan reuse the same server instead of starting a second one, and so the stop step knows what to kill.

Reuse

Every subsequent offloaded task in the same plan attaches to the already-running server: 

opencode run --attach http://127.0.0.1:<port> --model chutes/moonshotai/Kimi-K3-TEE --auto --dir <task-worktree> "<task prompt>"

No session flag — a bare run against an attached server starts a new, isolated session by default, exactly the property verified above.

Stop

Explicit, not automatic after each task — "runs until we say close." When offloaded work is done for this plan (last offloaded task completes, or the plan finishes), kill the tracked PID: 

taskkill //PID <SERVER_PID> //F

(Windows-specific — this environment has no pkill in Git Bash. A Unix environment would use kill <SERVER_PID>.) If the plan's own workspace gets deleted at the end of subagent-driven-development (per its existing Finish step) without an explicit stop having happened yet, stopping the server is part of that same cleanup — never leave it running orphaned past the plan's own lifetime.

Task Framing & Report Contract

Reuse the exact same scripts/task-brief extraction a normal implementer gets — the brief file is the single source of requirements either way. The prompt handed to opencode run wraps that brief with the same report contract the Claude implementer template already uses (see subagent-driven-development's implementer-prompt.md): write a full report to a named report file, then reply with a short status line — Status: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT, commits created, one-line test summary, concerns. OpenCode has real file write access (confirmed by the spike), so it can write that report file exactly like a Claude implementer does — nothing downstream needs a special case for where the report came from.

Dispatch with --format json, not the default human-readable output. Verified live: every event in the JSON stream carries a real sessionID (ses_fbdaa8bcdffeA5QpSHTpk8pd1x-shaped), and text events carry the actual response content — so this one format gives both the status contract text (read from the final text event) and the session ID needed later for fix-round resumption (see Fix Loop), in one pass. Record the captured sessionID in this plan's SDD workspace alongside the task's other bookkeeping — it's the only reliable way to resume this exact task's session later; guessing or using --continue ("continue the last session") is a weaker, order-dependent substitute since a shared server may see other tasks' sessions in between.

Review Stays Unchanged

The diff an offloaded task produces goes through the exact same task-reviewer dispatch as any other task — same review-package script, same reviewer template, same calibration. Offload replaces the implementer role only; nothing about spec-compliance or quality review needs to know or care that the diff came from OpenCode rather than a Claude subagent.

Fix Loop

Rounds 1-3 resume OpenCode itself — re-run opencode run --attach ... --session <captured sessionID> against the exact session this task's original attempt used (captured per Task Framing above), carrying the review findings verbatim, same shape as resuming a Claude implementer that has an intact context. This is not a new decision, just the existing fix-loop pattern applied consistently.

Per the explicit decision behind this design: if OpenCode's own fix attempt gets stuck, or round 3 closes without every finding addressed, this surfaces to you rather than silently escalating to a Claude implementer. Rounds 4-5 do not happen automatically the way they would for a normal implementer (dispatch a fresh, more capable model) — report the open findings and let you decide whether to keep trying offloaded, hand the task to a Claude implementer, or park it. Higher stakes than K.1's document rewrap justify not automating this choice away.

Model Choice

Default: moonshotai/Kimi-K3-TEE — the only model actually proven end-to-end by the spike. GLM 5.2 (zai-org/GLM-5.2-TEE) failed badly on a raw one-shot completion earlier this session (burned its entire token budget on structured reasoning for a one-sentence question, never answered), but that was a different task shape (unbounded single completion, not a tool-use loop) — worth re-testing inside OpenCode specifically before ruling it out, not assumed settled either way. Model selection beyond the default is not built in this version; changing it means editing the --model flag and the opencode.json provider block by hand.

Environment Notes

GotchaFix
Aider (the first candidate harness) requires Python <3.13; this environment has only 3.14.5 Use OpenCode instead — Node-based, sidesteps the Python version entirely. Not revisited unless a future environment actually has a compatible Python and a specific reason to prefer Aider.
pnpm add -g opencode-ai installs but the binary is broken pnpm skips postinstall scripts by default. Use pnpm add -g --allow-build=opencode-ai opencode-ai — remove any broken prior install first, or the postinstall gets skipped again on top of an already-present package.
No pkill in this Windows Git Bash environment Use taskkill //PID <pid> //F instead, with the PID captured at server start time ($!).

Security Note

opencode serve without OPENCODE_SERVER_PASSWORD set is unsecured (it says so on startup). Acceptable here because the server binds to 127.0.0.1 only — never 0.0.0.0 or a network-reachable hostname — so it's unreachable outside this machine. Never enable --mdns (which defaults the hostname to 0.0.0.0) for this use case.

Spike Evidence

Full writeup: backlog/k2-implementer-offload-opencode-chutes.md. Summary: a disposable scratch repo (Python, pytest) with a deliberately seeded date-matching bug (the same shape as a real bug found independently in map item I.1 earlier this session) — 5 tests, 1 failing, confirmed RED first. Task given to OpenCode/Kimi K3: run the tests, fix the bug, don't weaken the tests, no hint what the bug was. It read both files, ran pytest itself, diagnosed the real bug from the failure output, edited the file with a correct fix (a boundary check, matching the same fix Kimi proposed earlier via a raw completion call on the unrelated real bug — consistent judgment, not a fluke), re-ran pytest to confirm green, and reported accurately. Independently re-verified afterward: 5/5 tests genuinely passing, the real diff matched what was reported, the test file was untouched.

Out of Scope

  • Automatic task classification — no logic decides which tasks "qualify" for offload; that's your call, every time.
  • Multi-provider selection — one model, one provider (Chutes), hardcoded as the default. K.1's own Future Phases already named broader multi-provider routing as its own separate scope, not built here either.
  • Testing at real plan scale — the spike proved the mechanism on a 2-file, single-function bug. A real multi-file DigiSmith task (e.g. a SKILL.md-shaped target) is untested. The first real use of this skill against a real plan task is that test — go in expecting to learn something, not expecting a guaranteed clean pass.
  • Automatic rounds 4-5 escalation — deliberately not automated; see Fix Loop.
