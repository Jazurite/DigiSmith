Overview & core idea

K.2 (digismith:offload-implementer) currently offloads one subagent-driven-development task at a time to a single hardcoded provider — Chutes, via a persistent OpenCode server. K.1 (scripts/model_offload.py) separately offloads DigiSmith's own mechanical HTML-generation steps (enforcer's spec rewrap, report-implementation's report render) to Chutes too, via a direct HTTP call. Both are single-provider today; K ("Model tiering") already reserves "multi-provider routing beyond the single hardcoded Chutes provider" as undesigned scope in MEMORY.md.

K.3 generalizes both mechanisms so the user can choose or switch between AI gateway providers (Chutes, TokenReply, future ones) per-mechanism, instead of being locked into whichever provider each skill shipped with.

Spike evidence

Sparked 2026-08-28 while investigating a Chutes-subscription-expiry concern for K.2. Discovered TokenReply (tokenreply.com), a unified OpenAI/Anthropic-compatible gateway to 40+ providers, and live-tested an entirely different offload path — the Claude Agent SDK's query() pointed at TokenReply via ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN, running Kimi K2.7 as the actual coding agent.

Confirmed working

Real tool-calling loop

Genuine Read/Bash/Edit calls; a full fix→test→commit cycle succeeded for real (commit 070cb6b, 3/3 tests passing, independently verified).

Gotcha

Config inheritance

query() loads the full user/project Claude config by default. settingSources: [] does not stop the Skill tool from loading — only disallowedTools: ["Skill"] does.

Obstacle

Trial-tier rate limiting

HTTP 429 roughly every 5-10 tool calls on TokenReply's free tier, with a 60s auto-retry backoff. Untested whether Plus removes it.

Methodology finding

Don't trust SDK cost estimates

Agent SDK reported total_cost_usd: $1.39 for a run TokenReply's own dashboard billed at ~$0.007-0.008/request (costBasis: "unknown" for non-Anthropic models). K.4 turns this into a feature — out of scope here.

Real TokenReply pricing observed for kimi-k2.7 (Trial tier): $0.95 input / $4.00 output / $0.19 cache-read per 1M tokens, capped at 200K context — smaller than the 1M context Chutes advertises for kimi-k3 directly. A real capability difference between providers, not just cost.

Scope decisions

Decided during brainstorming, each with the alternative it beat:

Which mechanisms generalize K.1 and K.2 together, sharing one pluggable-provider mechanism K.2 only (the backlog item's original framing)
K.2's harness Keep OpenCode; parameterize its provider config block Adopt the Claude Agent SDK path used in the spike (would blur into K.6's harness-benchmark territory)
TokenReply credential storage Plain env var (TOKENREPLY_API_KEY), same pattern Chutes already uses via {env:...} substitution A new OS-keychain/encrypted-file credential manager mirroring chutes-ai's manage_credentials.py
Provider selection granularity Two independent profile fields — model_offload_provider (K.1) and task_offload_provider (K.2, new) One shared field forcing both mechanisms onto the same provider
Provider config shape Config-as-code: one TypeScript module per vendor implementing a shared interface (Strategy pattern) Config-as-data: one YAML file per vendor under a new providers/ folder
Scripting language TypeScript, run via Node 24's native (stable, on-by-default) type stripping — no tsx/ts-node dependency Leave model_offload.py in Python; write only new K.3 code in TypeScript

Architecture

Each gateway vendor is a service implementing a shared interface (Strategy pattern) rather than a row in a config file. A factory resolves a provider name — read from a profile field — to the concrete service: 

// scripts/providers/types.ts
export interface GatewayProvider {
  name: string;
  baseUrl: string;
  credentialEnv: string;
  model(role: "mechanical" | "task"): string;
  contextWindow: number;
}
// scripts/providers/chutes.ts
export const chutes: GatewayProvider = {
  name: "chutes",
  baseUrl: "https://llm.chutes.ai/v1",
  credentialEnv: "CHUTES_API_KEY",
  contextWindow: 1_048_576,
  model(role) {
    return role === "task"
      ? "moonshotai/Kimi-K3-TEE"
      : "google/gemma-4-31B-turbo-TEE";
  },
};
// scripts/providers/tokenreply.ts
export const tokenreply: GatewayProvider = {
  name: "tokenreply",
  baseUrl: "https://api.tokenreply.com/v1", // verify against TokenReply's own docs
  credentialEnv: "TOKENREPLY_API_KEY",
  contextWindow: 200_000,
  model() {
    return "kimi-k2.7";
  },
};
// scripts/providers/registry.ts
const providers: Record<string, GatewayProvider> = { chutes, tokenreply };

export function resolveProvider(name: string): GatewayProvider | undefined {
  return providers[name];
}

Adding a vendor later means writing one new file that implements GatewayProvider and adding it to the registry map — never editing a shared branch of if/else logic.

Components

  • scripts/providers/types.ts, chutes.ts, tokenreply.ts, registry.ts — new.
  • scripts/providers/print-config.ts — new. A small CLI (node scripts/providers/print-config.ts <provider> --role task) that resolves a provider and prints its config as JSON, used by K.2's SKILL.md so it never re-implements resolution logic inline.
  • scripts/model_offload.py → ported to scripts/model_offload.ts. Calls resolveProvider(profile.model_offload_provider) and uses .model("mechanical") / .baseUrl / .credentialEnv generically. The provider !== "chutes" gate in today's offload() is removed — any registered provider now works. Run via plain node scripts/model_offload.ts (Node 24 native type stripping).
  • skills/offload-implementer/SKILL.md Step 1 — changed. Reads task_offload_provider from the profile, shells out to print-config.ts, and writes opencode.json's provider block from the returned values instead of the hardcoded chutes block. Steps 2-6 (server management, dispatch, status extraction, verification) are untouched.
  • profiles/*.yml — every existing profile gains task_offload_provider alongside the existing model_offload_provider, both defaulting to chutes so existing profiles keep working unchanged.
  • skills/digismith:enforcer and digismith:report-implementation SKILL.md docs — one-line invocation update each, from python scripts/model_offload.py ... to node scripts/model_offload.ts .... The stdout/exit-code contract is unchanged, so this is the only edit needed in either skill.

Data flow

K.1 — mechanical generation

Prompt → model_offload.ts reads .digismith/profile → resolves model_offload_provider → resolveProvider(name) → credential from process.env[provider.credentialEnv] → calls provider.baseUrl's chat-completions endpoint with provider.model("mechanical") → validates HTML shape → stdout content (exit 0) or stderr status (exit 1), same contract as today.

K.2 — task offload

Dispatch request → offload-implementer Step 1 reads profile → resolves task_offload_provider → shells out to print-config.ts → writes opencode.json's provider block from the returned JSON → Steps 2-6 proceed exactly as today (Depot-managed shared OpenCode server, dispatch, status extraction, independent verification).

Error handling

Each mechanism keeps its own existing failure philosophy — K.3 adds a new failure mode (unresolvable provider) to both, handled consistently with how each already treats a broken prerequisite:

  • K.1 (falls back by design): an unknown provider name or missing credential env var is treated exactly like today's provider != "chutes" skip — clear stderr status, exit 1, caller falls back to in-session generation. No silent misattributed output.
  • K.2 (never silently falls back to Claude): an unknown provider name or missing credential makes print-config.ts exit non-zero with a clear message; Step 1 stops and reports BLOCKED before ever dispatching — the same disposition already documented for a missing opencode binary. Fails fast rather than burning a dispatch attempt against a config that can't authenticate.
  • Existing Chutes-specific error handling in model_offload.py (HTTP errors, malformed/empty response, malformed HTML shape) carries over unchanged — these failure modes were already provider-agnostic, not Chutes-specific logic to rewrite.

Testing

  • scripts/test_model_offload.py → ported to scripts/model_offload.test.ts (Vitest). Covers provider resolution (known name → correct service, unknown → graceful skip), credential lookup, and the generalized HTTP call against mocked fetches for at least two providers; existing HTML-shape validation logic carries over unchanged.
  • Each scripts/providers/*.ts gets a cheap shape-conformance test — satisfies GatewayProvider, round-trips through resolveProvider.
  • print-config.ts is small and pure enough to unit-test the same way: asserts correct JSON for a known provider/role, non-zero exit for an unknown one.
  • K.2's own OpenCode dispatch stays live-tested only, matching this project's existing convention — no automated harness for that part changes.

Out of scope

  • K.4 — gateway-vs-native-Claude-Code cost comparison.
  • K.5 — running multiple gateways in parallel.
  • K.6 — harness benchmark (Claude Code vs. OpenCode); a different layer entirely, which is exactly why K.3 keeps OpenCode fixed as K.2's harness.
  • K.7 — vendor benchmark (Chutes vs. TokenReply vs. future gateways).
  • TokenReply account creation/payment — the user's own action, never DigiSmith's, same standing boundary as Chutes credential handling elsewhere in this project.
  • Automatic provider selection or fallback (e.g. auto-switching on a rate limit) — switching is a manual profile edit for now.

Open questions

  • TokenReply's real API base URL needs to be verified against its own docs at implementation time — https://api.tokenreply.com/v1 above is a placeholder, not confirmed by the spike (the spike went through the Claude Agent SDK's own base-URL config, not a directly observed REST endpoint).
  • Whether a paid TokenReply tier actually removes the rate-limiting seen on the Trial tier — untested, not a blocker for this design.
