Background

Confirmed live 2026-09-11 (backlog/review-templates-dont-guard-ai-attribution.md): an implementer subagent committed with Co-Authored-By: Claude Haiku 4.5 despite both the inlined global/commit-style standard and the repo owner's own broader standing rule — no AI attribution anywhere, full stop — telling it not to. The task reviewer that reviewed the diff afterward flagged this only as "unverifiable," and its own report phrased the finding as if the trailer were expected ("the required attribution... was added per session rules") — backwards from this repo's actual policy. Only caught because the controller independently ran git show --format=fuller -s instead of trusting either the implementer's report or the reviewer's assumption.

Root cause, from the backlog item's own analysis: every Claude Code subagent's baseline instructions include appending a Co-Authored-By: Claude trailer by default. A repo-specific override competes with that baseline instinct and, at least once, lost — a non-deterministic failure mode. A reviewer subagent checking for this after the fact is itself another LLM call, and one already demonstrably got it backwards when nothing told it what this repo's actual policy was. Prevention (a mechanical, deterministic check run by the controller) is therefore the primary defense; a review-time instruction is a secondary layer, not the other way around.

Section 1 — check-attribution

New script, skills/subagent-driven-development/scripts/check-attribution, matching review-package's own bash style and conventions (set -euo pipefail, usage-error exit code 2). Usage: check-attribution BASE HEAD.

Runs git log BASE..HEAD --format=%B (the full commit body, which includes any trailers) and greps it, case-insensitively, for:

co-authored-by:.*claude|co-authored-by:.*anthropic|generated with.*claude|generated with.*anthropic|🤖

Deliberately not a bare claude/anthropic keyword match — this repo's own commit messages legitimately mention "Claude Code" in ordinary descriptive ways (e.g. a commit that updates a Claude Code skill reference), and a bare-keyword check would false-positive on those. The three sub-patterns above target only the actually-confirmed attribution shapes: a Co-Authored-By: trailer naming Claude or Anthropic, a "Generated with" phrase naming either, or the 🤖 footer emoji from the standard PR-description signature.

Exit 0 and silent when nothing matches. Exit 1 when something does, printing the matching commit SHA(s) and the matched line(s) to stderr — clear enough for the controller to know exactly what to fix without re-deriving it.

Section 2 — review-package's new prerequisite

scripts/review-package (in skills/subagent-driven-development/, current behavior fully described in this session's own reading of the file) calls check-attribution BASE HEAD immediately after validating that BASE and HEAD both resolve, before writing anything. A hit: the script prints check-attribution's own failure output, plus one line naming that the review package was not written because of it, and exits 1 — nothing is written to disk. A clean result: proceeds exactly as today, byte-for-byte unchanged.

This is the primary defense: it fires the moment the controller tries to generate any review package — task-level, fix-round re-review, or final whole-branch — before any reviewer subagent is ever dispatched. A caught violation gets fixed at the source (amend the local, unreviewed commit) rather than flowing into a review round that then has to catch and adjudicate it.

Section 3 — code-reviewer.md's mandatory step

skills/requesting-code-review/code-reviewer.md — used both as subagent-driven-development's final whole-branch review template and standalone by requesting-code-review itself (which has no plan file, so it can't always route through review-package's plan-file-keyed workspace resolution) — gains one new required command alongside its existing "Git Range to Review" block:

<path-to-skill>/subagent-driven-development/scripts/check-attribution BASE HEAD

A hit is an automatic Critical finding, full stop, regardless of anything else found in the diff — worded exactly that plainly in the template, removing any room for a reviewer to talk itself into treating it as anything softer. This is this fix's second, secondary layer: it covers the standalone-review path that can't go through review-package at all, since the reviewer subagent here already has live git access per this template's own existing "read-only review" instructions.

This is requesting-code-review's first-ever content divergence from upstream Superpowers — gains the fork-provenance tag in its frontmatter description:, per W.2's established activation convention, and an entry in vendored/PROVENANCE.md's "Skills activated" list.

Section 4 — closing the manual-fallback bypass, fixing the root cause

skills/subagent-driven-development/SKILL.md's Step 3 ("Review the task") currently documents a manual fallback for environments without bash: git log --oneline, git diff --stat, and git diff -U10, redirected by hand into one file — this path skips review-package entirely, and with it, Section 2's check. That fallback instruction gains one inserted line: run check-attribution BASE HEAD first, and stop (fix the commit) if it reports a hit, before doing anything else in that fallback.

skills/subagent-driven-development/task-reviewer-prompt.md gains one explicit policy line the original incident's root cause shows was missing: "This project forbids AI/assistant attribution anywhere in commit messages or PR descriptions — no exceptions. If you see one despite this, it is a real violation, not something the project might have wanted." By the time a task reviewer receives a package, Section 2 already guarantees it's clean — this line exists purely so that if a controller ever hands a reviewer a package generated some other way (the fallback in this section, or a future path this design didn't anticipate), the reviewer has an explicit, correct policy to check against instead of defaulting to the harness's own baseline assumption the way the original incident's reviewer did.

Testing

  • check-attribution is a bash script in the same untested-by-vitest category as review-package and sdd-workspace (this skill's other bash scripts) — verified live: a small local git fixture repo with a clean commit range (exit 0, silent), a range containing a Co-Authored-By: Claude Haiku 4.5 <noreply@anthropic.com> trailer (exit 1, correctly identifies the commit and matched text), a range containing an unrelated commit that merely mentions "Claude Code" in ordinary prose with none of the three sub-patterns (exit 0 — proves the narrowed regex avoids the false-positive this design deliberately designed around), and a range containing the 🤖 footer emoji alone (exit 1).
  • review-package's new prerequisite: run it once against a fixture range with a planted attribution commit — confirm exit 1, confirm no file was written to the workspace directory. Run it once against a clean range — confirm output and file-write behavior are unchanged from before this plan.
  • The template and SKILL.md changes are agentic instruction text, not code — verified by reading the rendered diff for correctness, the same way this session's own prior prose-only tasks (e.g. W.4.1's finishing-a-development-branch edit) were verified, rather than by an automated suite.

Out of scope

  • PR-description attribution checks (the 🤖 footer / "Generated with Claude Code" pattern in a PR body rather than a commit message) — this design's check-attribution pattern would catch it if pointed at the right text, but nothing in this plan wires a PR-creation path (finishing-a-development-branch Option 2) to call it. A real but separate gap, not raised by the confirmed incident this fix responds to.
  • Any change to Claude Code's own baseline commit-instruction behavior — out of DigiSmith's control entirely; this design only ever reacts to what a subagent actually committed, never tries to suppress the underlying instinct at its source.
  • A broader, general-purpose "does this text contain AI attribution" utility usable outside the review flow — check-attribution is scoped to the two call sites this design actually needs (Section 2, Section 3/4); extracting a shared library is unwarranted for two callers.
