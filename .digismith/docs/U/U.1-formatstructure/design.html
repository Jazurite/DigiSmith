Overview

Letter U was assigned 2026-09-19 to fully decouple @digismith/cli (packages/cli) from Depot's own "V" lineage — the CLI's binaries, dispatcher, and publishing mechanics are a distinct concern from Depot's ensure-* resource-management concern, even though V.4 originally built the package as "Depot's distribution surface." Research during this brainstorm confirmed the split needs no code move and no refactor of vps/ depot themselves — the existing GROUPS dispatcher in src/index.ts already treats them as pure, decoupled consumers.

The session's scope grew from there once HubSpot's own CLI (hs, cloned locally to D:\Workspace\Library\hubspot-cli for reference) came up as a structural model: a real, multi-domain CLI (hs account, hs cms, …) built on yargs, with uniform nested subcommands and branded help. Jack's direct call: adopt that same mechanism — yargs, not a hand-rolled dispatcher — and give digismith its own brand identity in the terminal, reusing the purple accent already established across every generated design.html/ report.html. This design covers both: the ownership split, and letter U's first real activation (the yargs-based domain framework).

Ownership split (U vs. V)

Confirmed via direct inspection of packages/cli/src/: index.ts is a flat GROUPS: Record<string, (argv: string[]) => void> map wiring in vps and depot, neither of which references the other or the dispatcher beyond a plain run(argv) contract. Both of the backlog's open questions resolve the simple way:

  • The package does not move location — map-letter ownership is a documentation/ responsibility concept, same precedent as V.4/V.5 coexisting with V.1–V.3's non-CLI code.
  • V.5's depot command group needs no refactor to become a consumer — it already is one, structurally.

The one real ownership artifact: packages/cli/package.json's description reads "DigiSmith's command line — Depot's distribution surface", framing ownership as Depot's. This changes to ownership-neutral language reflecting U's framework, V's vps/depot as its consumers.

Domain-oriented CLI framework

Adopts yargs as a real runtime dependency, reversing V.4's original "zero runtime dependencies" decision — recorded here explicitly rather than left as silent drift. Each domain (vps, depot) becomes a yargs "bucket" command ({ command, describe, builder, handler: () => {} } with demandCommand(1, '') forcing a subcommand), composed of leaf command modules that wrap the logic functions already exported by each existing file (ensureClone, refreshClone, runStatusChecks, runConnect, etc.) — no logic changes, only the argv-parsing shell around each is replaced.

This mirrors HubSpot's actual mechanics (bucket → leaf composition, manual import wiring, no filesystem auto-discovery, nested subcommands never flattened with dashes) while deliberately not copying two things that don't fit a two-domain personal CLI: HubSpot's sibling-file-plus-folder layout (DigiSmith keeps its own established <domain>/index.ts bucket convention) and its centralized i18n lang/en.js module (describe strings stay inline — nothing here is user-facing product copy needing translation).

Root setup in src/index.ts:

yargs(hideBin(process.argv))
  .scriptName("digismith")
  .command(vpsCommand)
  .command(depotCommand)
  .demandCommand(1, "")
  .strict()
  .version(readVersion())
  .parse();

.strict() rejects typos (previously silent no-ops); every bucket getting demandCommand(1, '') means dg depot alone now shows its subcommands instead of falling through to the old hand-written usage() string, which is retired entirely.

Every user-facing command keeps its exact current argv shape (dg depot clone ensure, dg vps status, …) — this is an internal restructure, not a breaking change to command surface.

Branding

Adds picocolors (tiny, zero-deps, auto-detects TTY/NO_COLOR) as a second new dependency. Reuses the purple accent already established in every generated design.html/report.html (#7a4fb5 light / #b892ea dark) so the CLI reads as the same product as DigiSmith's docs, not a separately-branded tool. Deliberately no ASCII logo — DigiSmith's own writing standard (T.1, ASD-STE100) favors plain, unembellished output; a splashy banner would contradict it.

src/lib/brand-help.ts replaces yargs' default --help output (.help(false), manual -h/--help wiring) with a renderer driven by each module's own already-declared command/describe metadata — no yargs internals hacking. Root help gets a one-line bold-purple wordmark (digismith — personal SDLC CLI); every level gets a Usage: line and a Domains:/Commands:/Options: section with bold-purple command names and dim descriptions, e.g.:

$ dg --help

digismith — personal SDLC CLI

Usage: dg <domain> <command> [options]

Domains:
  vps      reconnect to the Hetzner VPS's persistent claude session
  depot    manage machine-wide shared resources (clone, opencode, bridge)

  -h, --help     show help
  --version      show version number

Non-goals

  • No new global option groups (HubSpot's commonOpts.ts equivalent — --account, --debug, etc.) — the one existing flag, depot bridge ensure --repo <path> (currently hand-parsed via argv.indexOf), becomes a proper declared yargs .option('repo', { type: 'string' }) on that single leaf; nothing speculative is added beyond that migration.
  • No command aliasing (yargs supports command: [canonical, ...aliases] for free later if a real need arises — not invented here).
  • No auto-publish-on-merge hook — V.4's own flagged future work, stays deferred.
  • No login/credentials/server work — deferred to letter X per V.4's original note, unchanged by this split.
  • process-lifecycle.ts is untouched logic — confirmed V's own Depot resource-lifecycle code, not shared CLI framework.

Testing

Existing unit tests against the pure logic functions (ensureClone, runStatusChecks, etc.) are unaffected — those functions don't change. Tests that currently invoke the old run(argv) shells directly move to either calling the logic functions directly (preferred, matching how most of the existing suite likely already works) or exercising the built CLI via spawnSync against dist/index.js, the same pattern cli.test.ts already established for packages/jira-client (I.5). The plan will enumerate exactly which existing test files need updating once writing-plans reads them.

Rollout & compatibility

Pure internal restructure plus two new dependencies — no consumer-facing breaking change to command surface. packages/cli keeps its own semver (currently 0.1.0-beta); this plan does not itself require a version bump decision beyond whatever writing-plans/the final review judges appropriate for a dependency addition of this size on a pre-1.0 package.
