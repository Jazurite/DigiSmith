Overview

packages/jira-client replaces the Atlassian MCP connector as I.1's (jira-progress-write-back) transport, calling Jira's REST API v3 directly with a personal API token instead of going through a session-specific MCP tool. Root-caused and proven live on EMKT-756 (2026-08-27), not speculative — see below.

Fixes

The description-write bug

I.1's very first live run had to skip its description write entirely because of this. Direct REST returns real, correctly structured ADF for every field — confirmed by direct comparison against the same field, same ticket.

Also fixes

Two more confirmed gaps

No attachment-content download existed through the connector at all; the connector itself dropped and reconnected mid-session under a new tool-name prefix. Direct REST has neither problem.

Why: The MCP Connector Bug

The bug: the Atlassian MCP connector's getJiraIssue, called with responseContentFormat: "adf", returns genuine ADF for comment.comments[].body — but a lossy rendered-markdown hybrid for the description field specifically, the same request parameter notwithstanding. Tables, status lozenges, and emoji flatten into <custom data-type="..."> pseudo-HTML that cannot be safely reconstructed into real ADF nodes. This is a bug in the connector's own internal rendering — confirmed by fetching the exact same field on the exact same ticket via direct REST and getting correctly structured status/table/expand nodes back.

The fix, proven live: a personal Jira API token (generated at id.atlassian.com/manage-profile/security/api-tokens), used with HTTP Basic Auth (email:token) directly against https://<site>.atlassian.net/rest/api/3/... — not the api.atlassian.com/ex/jira/{cloudId}/... gateway, which is OAuth-app-only and returned 403 when tried.

  • GET /rest/api/3/issue/{key}?fields=description — real ADF, confirmed against a live ticket.
  • GET /rest/api/3/attachment/content/{id} — downloads actual image bytes (follow the 303 redirect).
  • PUT /rest/api/3/issue/{key} with {"fields":{"description": <ADF doc>}} — writes back successfully (204).

No responseContentFormat/contentFormat parameter anywhere in this path — REST API v3's description/comment bodies are ADF by default. That parameter was purely a connector-side concept, not something the migration needs to replicate.

Architecture

skills/jira-progress-write-back/SKILL.md (I.1) │ subprocess/Bash, one call per operation ▼ ~/.digismith/repo/packages/jira-client/src/cli.ts │ (provisioned by digismith:depot) │ reads ~/.digismith/.env directly (email, token, site) │ HTTP Basic Auth, native fetch — zero runtime deps ▼ https://<site>.atlassian.net/rest/api/3/...

The MCP connector is removed from I.1's path entirely — not supplemented, replaced. jira-client is a thin transport layer only: it owns Jira's REST shape and nothing else. Every piece of ADF business logic I.1 already has — description-delta splicing, Track-checklist upserts, comment date-matching — stays exactly where it is, in the skill. Moving that logic into the client would create a second place it could drift out of sync with the skill that actually understands it.

Distribution: considered and rejected

Two alternatives were considered before landing on the digismith:depot-provisioned local clone: fetching individual source files fresh from GitHub on every call (works, but re-fetches on every single invocation with no caching, and a consumer repo still needs some place to run the fetched code from), and publishing to a real npm registry (the canonical decoupled answer, but adds a real release/versioning step for a personal tool with effectively one consumer). Depot's sparse local clone gets the same no-local-dev-checkout-dependency property as either alternative, without either's cost.

Package Layout

DigiSmith/ ├── pnpm-workspace.yaml ├── package.json (root, private:true, devDeps: typescript, vitest) ├── packages/ │ └── jira-client/ │ ├── package.json │ ├── src/ │ │ ├── client.ts (exported functions — the real logic) │ │ ├── client.test.ts (vitest) │ │ └── cli.ts (thin subcommand dispatch → calls client.ts) │ └── tsconfig.json ├── scripts/ │ └── model_offload.py (untouched — K.1's existing Python tooling) └── skills/ └── jira-progress-write-back/ (I.1 — migrates, see below)

No build step. Node 24 runs .ts files directly (native type-stripping) — confirmed on this machine before committing to the design. cli.ts is invoked as node .../cli.ts <subcommand> ..., no tsc compile, no dist/ output. This is the first package in a monorepo layout chosen specifically because more TypeScript packages are expected here over time — the workspace tooling is meant to make the second package cheap to add, not just to house this one.

Language and tooling choices — TypeScript over matching K.1's existing Python precedent, pnpm for workspace management, Vitest for tests — all follow Jack's standing defaults captured in backlog/opinionated-tech-stack-defaults.md (tentative map letter U), surfaced during this same brainstorm.

Credentials: Bootstrap-on-First-Use

Skill (I.1) needs to call the Jira client │ ▼ Does ~/.digismith/.env exist with all three values? │ │ yes no │ ▼ │ Skill prompts via AskUserQuestion: │ email, API token (with the │ id.atlassian.com token-gen URL), │ site hostname │ │ │ ▼ │ Writes ~/.digismith/.env │ (creates ~/.digismith/ if needed) │ │ ◄────────────────────────────────────┘ ▼ Client reads it, makes the real call
  • ~/.digismith/.env — home directory, outside every git repo (DigiSmith's own and every consumer's). Structurally cannot land in a git-committed profiles/*.yml, which fully resolves the original security concern that blocked this migration from being scoped in the first place.
  • The client itself never prompts — it's a non-interactive subprocess. It fails fast with a distinct "no credentials found" signal on stderr/exit code; only the skill layer (which has AskUserQuestion) prompts.
  • The token itself never touches argv, the process list, or shell history — only non-secret arguments (issue key, file paths) are ever passed on the command line. The client reads the token directly out of the .env file inside its own process.
  • No dotenv npm dependency — three key-value lines are hand-parsed, matching how profiles/*.yml is already hand-parsed elsewhere in this repo rather than pulling in a YAML library.
  • Once written, no repeat prompting — true for every future session, in every consumer repo, on that machine.

Client API Surface

FunctionREST callCLI subcommand
checkCredentials() none — reads ~/.digismith/.env check-credentials
getIssue(key, fields) GET /issue/{key}?fields=... get-issue --key <K> --fields <csv>
updateDescription(key, adfDoc) PUT /issue/{key} (fields.description) update-description --key <K> --file <adf.json>
addComment(key, adfDoc, commentId?) POST .../comment or PUT .../comment/{id} add-comment --key <K> --file <adf.json> [--comment-id <id>]
getAttachmentContent(id, outPath) GET /attachment/content/{id} (follows redirect) get-attachment --id <ID> --out <path>

Each function lives in client.ts and is independently unit-testable; cli.ts is a thin dispatcher only. ADF payloads for update-description/add-comment are passed as a --file path — the skill writes the composed JSON document to a scratch file first — avoiding CLI-length/quoting issues with large documents, the same pattern K.1's model_offload.py already uses for its --prompt-file. Exit codes stay 0/1 throughout, status detail to stderr, matching that same precedent.

I.1 Migration — Step Diff

StepChange
Step 2 — "Detect the JIRA Tool" Replaced. Defensive digismith:depot ensure check (in case bootstrap didn't run this session), then the credential-bootstrap check from above.
Step 3 — "Resolve cloudId" Removed entirely. Pure MCP-connector routing concept — direct REST just targets https://${JIRA_SITE}/rest/api/3/... using the site hostname already in .env. One fewer step, not a swapped implementation of the same one.
Step 4 — "Fetch the Current Ticket" Changed. Calls get-issue. No more responseContentFormat guessing or per-session tool-name mapping. This is the exact step that broke on EMKT-756.
Steps 5–13 (ADF business logic, confirmation gate) Unchanged. Materials & Links delta, Track checklist delta, comment date-matching boundary check, and the mandatory Confirm-Before-Write gate — none of this logic ever lived in the connector.
Steps 14–15 — write description / write comment Changed. Call update-description / add-comment instead of the MCP tool. Same whole-field-replace semantics as before.

get-attachment exists on the client but is not wired into any current I.1 step — the EMKT-756 screenshot gap was ad hoc (viewing an attachment referenced in a comment mid-conversation), not part of I.1's structured write-back flow. It's available capability for a future step, not a required part of this migration.

Error Handling

CaseDisposition
~/.digismith/.env missing or incomplete Trigger the bootstrap-prompt flow (above) rather than failing outright — this is an expected first-run state, not an error.
Jira returns an HTTP error (auth, permissions, malformed field) Report the failure plainly with whatever detail the response body carries. No silent retry, no fallback write in a different format — same disposition I.1 already documents for its existing MCP-tool failure case.
Network/connection error reaching *.atlassian.net Report plainly. No retry.
digismith:depot's defensive check finds the clone missing and provisioning also fails Stop, report the underlying error (see that skill's own Error Handling) — don't attempt to fetch/run jira-client any other way.

Every other case in I.1's existing Error Handling table (unresolved mention name, duplicate comment, Track section absent, unrecognized Materials & Links shape) is untouched by this migration — those are all about the ADF business logic in the skill, not the transport.

Testing

client.ts's five functions are unit-tested directly with Vitest (mocking fetch) — no subprocess spawning needed to exercise the real logic, which is the point of keeping cli.ts a thin, separately-un-unit-tested dispatcher. I.1's own migrated steps get verified the same way the rest of I.1 already is — reasoning-only against fabricated ADF fixtures during implementation, with the real acceptance bar being an actual live run against a real ticket (as EMKT-756 already served for the pre-migration version).

Out of Scope

  • The Track-section Deliverable/Per-Market template — a separate, larger design already in backlog/track-section-template.md, explicitly noted there as being in tension with I.1's current single-checkmark Step 7 and more naturally I.2's concern. Not touched by this migration; I.1's Step 7 (Track checklist) logic is carried over unchanged.
  • I.2, multi-repo distribution — unaffected scope boundary, unchanged from I.1's existing design.
  • Publishing jira-client as a real npm package — considered and rejected; see Architecture.
  • Wiring get-attachment into a real I.1 step — the function exists; no current step calls it.
