Problem

TokenReply's kimi-k3 route emits Kimi K3's raw, undecoded "XTML" tool-call format (<|open|>tools<|sep|>...) instead of executing a real tool call — a server-side misconfiguration (TokenReply hasn't wired up vLLM's KimiK3ToolParser for this route), root-caused and documented in backlog/tokenreply-kimi-k3-tool-calling-failure.md. The prior investigation confirmed this is not a client-protocol issue: dispatching via opencode (pure OpenAI-format function-calling, zero Anthropic translation) produced the identical leak as claude-code's Anthropic-format traffic. Independently verified against the real vLLM source (D:/Workspace/Library/vllm): OpenAI's tool_calls shape is vLLM's actual canonical/native tool-calling target (kimi_k3_tool_parser.py's own docstring says so explicitly), and Anthropic-format support is a translation adapter (vllm/entrypoints/anthropic/serving.py) layered on top of that same native pipeline. Since both client protocols bottom out in the same unconfigured pipeline, no client-side format choice fixes this — the fault is entirely on TokenReply's deployment.

A recovery mechanism already exists (kimi-k3-xtml-tool-call-recovery, shipped 2026-09-05, map item K.3): the controller manually decodes a leaked call, executes it with its own tools, and resumes the dispatched session. Live-verified twice, it works, but it is bounded and visible — every recovery cycle burns one of the shared fix-round cap's 3 rounds, making it viable only for tasks needing roughly 3 or fewer tool calls total, and it requires a human/AI controller to drive the loop by hand each time.

Since TokenReply is not expected to fix their server-side configuration on any predictable timeline, this design takes the fix into DigiSmith's own hands: rather than recovering after a leak reaches the controller, intercept and repair it before it ever reaches the dispatched Claude Code session at all.

Approaches ruled out

Ruled out

Switch client wire format to OpenAI's

The original instinct — since TokenReply/vLLM is OpenAI-native, request tool calls in OpenAI's format instead of Anthropic's. Disproven: the opencode trial already used pure OpenAI-format function-calling and produced the identical leak. The bug is server-side, upstream of any client protocol choice.

Ruled out

Automated CLI-level orchestrator

Considered first: a script that drives the existing decode/execute/resume loop programmatically instead of a human/AI controller doing it by hand. Set aside because it would need to reimplement Claude Code's own Read/Edit/Write/Bash tool semantics from scratch in plain Node.js (e.g. matching Edit's exact "old_string must be unique" check) — real risk of subtly diverging from Claude Code's actual, already-correct tool behavior, for no benefit over letting Claude Code do what it already does well.

Architecture

A small local HTTP proxy, managed by digismith:depot as a shared, persistent resource (mirroring V.1's shared OpenCode server — one instance, started on first use, reused across every concurrent dispatch). offload-implementer's claude-code runner points ANTHROPIC_BASE_URL at this local proxy instead of TokenReply directly. The proxy buffers each response (no true streaming — nothing consumes this live, it all gets captured to a file either way) and, if it detects the XTML leak, decodes and converts it into a genuine Anthropic tool_use block before relaying it. If there's no leak, the response passes through untouched — the proxy is a safe no-op for any other model.

Internally, this replicates vLLM's own intended architecture: OpenAI's tool_calls shape is the canonical decode target (exactly what kimi-k3-xtml-parser.ts already produces, unchanged from the existing recovery mechanism), and one new conversion step — OpenAI-shaped call → Anthropic tool_use block — mirrors vLLM's own _convert_tool_use_block in reverse. The proxy is, in effect, doing on the client side exactly what TokenReply's server should already be doing.

The result this surfaces: because the fix happens inside the single claude -p HTTP round-trip, Claude Code's own agentic loop just continues normally — it sees a corrected tool call, executes it with its own real tool engine, and keeps going, all within the same dispatch process. offload-implementer doesn't need Step 5.5's separate --resume dance for kimi-k3 through this path at all anymore — a single claude -p call just works, the same as any healthy model today. This is a bigger simplification than "recovery without a human in the loop" — it's "no recovery step exists from the caller's perspective."

Components

  1. scripts/agentic-bridge/server.ts (new) — the proxy itself. Forwards requests to TokenReply's real endpoint using whatever auth header the client already sent (no separate credential-reading needed), buffers the full response, and either passes it through or converts it.
  2. New converter, toAnthropicToolUse(decoded: DecodedToolCall[]) (added alongside kimi-k3-xtml-parser.ts) — the one genuinely new piece of decode logic: decoded tool calls → real Anthropic tool_use content blocks + stop_reason: "tool_use".
  3. Depot gains two capabilities: ensure-agentic-bridge (start if not running, return its local URL — same shape as V.1's ensure-opencode-server) and stop-agentic-bridge.
  4. skills/offload-implementer/SKILL.md change: the claude-code runner's dispatch step calls ensure-agentic-bridge first and points ANTHROPIC_BASE_URL at its local URL instead of provider.baseUrl directly — same pattern already used for the existing ensure-claude-code readiness check.
  5. Step 5.5 docs: narrowed to explicitly note claude-code shouldn't need it anymore in practice, but left intact for opencode (out of scope for this proxy — see below) and as the fallback path for an undecodable leak (see Error Handling).

Data flow

  1. Controller calls ensure-agentic-bridge → gets http://localhost:<port>.
  2. Dispatches claude -p ... --model kimi-k3 with ANTHROPIC_BASE_URL pointed at that local URL (auth token unchanged — still the real TokenReply key, now relayed through the proxy).
  3. Proxy forwards to TokenReply, buffers the response.
  4. No leak → relay untouched.
  5. Leak → decode, convert, relay the corrected response. Claude Code's own agentic loop executes the tool call and continues within the same dispatch — no second claude -p --resume call needed.
  6. Task completes (or genuinely fails) through the dispatch's normal single invocation, same as any healthy model.

Error handling

CaseBehavior
Leak detected but undecodable (toolCalls empty despite the leak flag — malformed beyond what the parser tolerates)Relay the original leaked text through unchanged. This is exactly the case where the existing xtmlLeakDetected flag downstream and Step 5.5's documented BLOCKED path still matter, even for claude-code — the proxy fixes the common case, not every conceivable malformed one.
TokenReply itself errors (5xx, timeout)Relay the error through unchanged — never mask or swallow it.
Proxy fails to startDispatch fails loudly, consistent with K.2's existing "failures surface, never silently fall back" philosophy.
Multiple tool calls in one leaked turn (never observed live yet, per the backlog's "still unverified" note)The converter naturally handles an array of decoded calls → an array of tool_use blocks, so this should work the first time it's actually seen, even though it's untested today.

Testing

  • Unit tests for toAnthropicToolUse, using Task 1's existing real fixtures (BASH_CALL_FIXTURE, WRITE_CALL_FIXTURE, MULTI_CALL_FIXTURE) as inputs.
  • Unit tests for the proxy's passthrough vs. conversion branching, against a mocked upstream — no real TokenReply calls in the automated test suite.
  • The real test: a live dispatch through the proxy with kimi-k3, checking that a single, ordinary claude -p call (no manual recovery, no --resume) produces a genuinely completed task — same discipline as every other live test in this investigation, independently verified via git log, never the dispatch's own self-report.

Out of scope

  • opencode runner support. Confidence in Claude Code's --resume session behavior comes from this whole investigation's own live testing; the same confidence doesn't yet exist for opencode's --session behavior. opencode dispatches to TokenReply remain unprotected by this proxy — Step 5.5 stays the documented (manual) path for that runner.
  • True streaming. The proxy buffers the full response before deciding anything; it does not forward partial chunks live. Nothing today consumes a dispatch's output in real time (everything is captured to a file for offline parsing), so this is a deliberate simplification, not a limitation anyone has hit yet.
  • Reimplementing tool execution. The proxy never executes anything itself — it only repairs the response format and lets Claude Code's own tool engine do the work. See "Approaches ruled out" above.
  • Flipping the default model back to kimi-k3. A deliberate follow-up decision, made only after live-verifying this proxy actually works end-to-end — not an automatic side effect of merging this design. kimi-k2.7 remains the shipped default in scripts/providers/tokenreply.ts until that verification happens.

Open risks

  • Streaming/SSE framing at the wire level, unverified. claude -p likely requests stream: true from its base URL even though nothing consumes it live. Whether Claude Code's own HTTP client tolerates a non-streaming JSON response when it requested a stream, or whether the proxy needs to wrap its single buffered result in minimal SSE event framing to satisfy the client, is a real technical unknown — worth an early spike before building the rest of the proxy around an assumption here.
  • Multi-call-per-turn recovery, still unverified. Carried over from the existing recovery mechanism's own open risk: all real dispatches across this whole investigation have made exactly one tool call per leaked turn. The converter is written to handle an array, but that path has never been exercised against a real dispatch.
  • Argument-shape coverage. 4 clean real-world data points exist so far (2 Bash, 2 Write), all clean with no renaming needed; Edit/Read/Grep/Glob shapes remain untested against a real leak.
