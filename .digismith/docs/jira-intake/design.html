Problem & Goal

DigiSmith's roadmap (MEMORY.md) defines A as: "Ticket exists → ingest it; doesn't → shape one from a raw need." Philosophy #4 frames this as "one entry point, two doors" — both converge into the same downstream flow. Right now there is no mechanism for either door: no way to pull a JIRA ticket into a structured, usable artifact, and no way to turn a raw need into one either.

The goal is a single skill that produces a consistently-shaped ticket artifact regardless of which door was used — the foundation later stages (eventually B's spec seam, L's codebase grounding) can rely on having the same fields in the same place.

Non-Goals

  • Not grounding the ticket in the codebase — which files/areas it touches. That's L (Tier 4), a separate capability. This spec resolves MEMORY.md's open question ("A and L may be one skill, not two") in favor of keeping them separate: A stops once it has a well-structured ticket.
  • Not estimating Story Points. The template has a field for it — captured as-is when an ingested JIRA ticket already has one set — but A never estimates it. That's J's job (Tier 3, dual-track estimation).
  • Not writing back to JIRA. The "shape one from a raw need" door produces a local draft only. Turning that into a real JIRA ticket is the noted "JIRA write-back" shared primitive — not built anywhere yet, out of scope here.
  • Not building any real JIRA API/MCP integration. No such tool exists in this environment today. A assumes whatever session is actually using it may or may not have one, checks at runtime, and falls back to pasted content when it doesn't.

Architecture — One Skill, Two Doors

A single skill, jira-intake. Both doors write the same template (see below) — the fork is only in how the content gets gathered.

Door 1

Ticket Exists

Ask for the ticket key. Check whether a JIRA/Atlassian-capable tool is available in the current session (see Detection Logic). If yes, fetch by key. If no, ask the user to paste the ticket content directly. Map the result into the template — no confirmation step, since this is transcription of already-real content, not a draft.

Door 2

Raw Need → Shaped Ticket

Take the user's description as the seed. Ask only what's missing to fill required fields (typically Acceptance Criteria, if none were stated) — one question at a time, never a batch of questions for information already inferable from what was said. Draft the ticket, confirm with the user before writing — same ask → draft → confirm shape discover-standards already uses.

Ticket Template & Output

Both doors write this same shape to docs/<feature-slug>/ticket.md, inside the repo currently being worked in — the same folder specs/plans/reports will eventually use for that feature, gitignored, matching the existing convention already in place for Emma repos.

# <Title>

**Key:** EMKT-1234 (Door 1 only — omitted if the ticket doesn't exist yet)
**URL:** https://... (Door 1 only, if available)
**Story Points:** 3 (captured as-is if already set; otherwise "TBD" — A never estimates)

## Description

...

## Acceptance Criteria

- ...
- ...

Slug derivation: lowercase the title, replace non-alphanumeric runs with a single hyphen, truncate to a handful of significant words (roughly 40 characters, cut at a word boundary). E.g. "Fix cart drawer padding on mobile checkout" → fix-cart-drawer-padding-mobile.

JIRA Detection Logic

Door 1 does not assume any specific JIRA integration exists. At runtime, check whether a JIRA- or Atlassian-capable tool is available in the current session (the same kind of runtime check inject-standards already does for its own scenario detection — infer from what's actually available, don't hardcode an assumption). If found, use it to fetch the ticket by key. If not found, tell the user plainly and ask them to paste the ticket content instead — never block on JIRA access that doesn't exist in this environment today.

Error Handling & Edge Cases

  • No JIRA tool available and the user declines to paste content → stop cleanly, explain that jira-intake needs either a JIRA tool in this session or pasted ticket content to proceed. Don't fabricate a ticket.
  • docs/<slug>/ already exists: same ticket key (a re-run/refresh) → confirm before overwriting ticket.md. Different ticket, same slug (collision) → ask whether to disambiguate (append the ticket key to the slug, or choose a different slug) rather than silently overwriting.
  • Existing ticket.md at the target slug has no Key/URL set (a Door 2 draft) and Door 1 is now being run — this is the expected "draft became real" path, not a collision. Treat it as an upgrade: fill in Key/URL/Story Points on the existing file rather than creating a duplicate or asking about a conflict.
  • Pasted content too sparse to extract a title/description → say so, offer either a cleaner paste or switching to Door 2's raw-need flow instead.
  • Raw-need description already complete enough (title, description, and acceptance criteria all inferable) → skip the clarifying question entirely. Same principle discover-standards follows: don't ask for information already given.

Testing / Verification

No automated test suite — these are instruction files, consistent with G's established convention. Verification is a dogfooding pass after implementation:

  1. Door 1 against a real ticket, paste-based (no JIRA tool exists in this environment yet) — confirm the template maps correctly, including Story Points when the pasted ticket has one set.
  2. Door 2 from a genuinely rough, incomplete raw need — confirm it asks only for what's missing, drafts, confirms, and writes.
  3. Re-run intake on the same ticket key — confirm the overwrite-confirm path fires instead of silently clobbering the existing file.
  4. A slug collision between two different tickets — confirm the disambiguation path fires rather than one ticket silently overwriting the other.
  5. Run Door 2 to create a draft, then run Door 1 for the same feature once a real ticket exists — confirm it upgrades the existing file in place (Key/URL/Story Points filled in) rather than treating it as a collision.

Relationship to Other Map Items

  • L (refinement & exploration, Tier 4) grounds the ticket A produces in the actual codebase. Deliberately kept separate — see Non-Goals.
  • J (estimation, Tier 3) is responsible for actually filling in Story Points via its dual-track methodology. A's template just reserves the field.
  • B (spec seam, Tier 4) will eventually carry A's ticket.md into superpowers:brainstorming so a spec session doesn't start cold. Until B exists, that handoff is manual — the user reads or references ticket.md themselves when starting to brainstorm.
  • JIRA write-back (shared primitive, not yet built) would be what turns Door 2's local draft into a real JIRA ticket. Out of scope here.
