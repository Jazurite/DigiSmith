Summary

Replaced DigiSmith's two inconsistent storage conventions — docs/superpowers/{specs,plans,reports}/ (type-organized, DigiSmith's own repo only) and docs/<slug>/ticket.md (consumer repos, hardcoded gitignored) — with one: .digismith/docs/<feature-slug>/{ticket.md, design.html, plan.md, report.html}, wherever DigiSmith writes docs, with commit-vs-gitignore an explicit per-repo choice instead of an assumption. Task 1 migrated DigiSmith's own repo (13 existing files across 5 shipped features, plus docs/history.html) into the new structure and fixed every cross-reference. Task 2 updated report-implementation's path-derivation logic to write into the new structure going forward (and gained a simplification: the feature slug is now just the plan file's parent folder name, and sibling links are same-folder instead of ../specs//../plans/). Task 3 updated jira-intake's consumer-repo ticket path and added the ask-once/detect commit-vs-gitignore logic, plus updated using-digismith's reference to where ticket.md lives. Followed the full Superpowers process: brainstorming → spec → writing-plans → superpowers:subagent-driven-development (3 tasks, each dispatched to a fresh implementer subagent and independently reviewed) → a final whole-branch review, plus 1 fix round before merge.

Reference documents are not linked here. This feature's own design.html and plan.md are the one deliberate exception to the very convention this branch establishes: per the plan's own Global Constraints they stayed at docs/superpowers/specs/2026-08-08-unified-docs-convention-design.html and docs/superpowers/plans/2026-08-08-unified-docs-convention-plan.md throughout execution, because moving the plan mid-flight would have broken subagent-driven-development's task-brief/review-package scripts, which reference it by fixed path. They are moved by hand, once, after this plan's SDD run fully completes. Because neither file is in this report's own folder yet, report-implementation's omit-the-link-if-the-file-isn't-there rule dropped both links rather than rendering a 404 — working as designed.

Final Review & Fix

Ready to merge: With fixes — 1 Critical, 6 Important, and 5 Minor findings, resolved in one comprehensive whole-branch fix wave (opus); 1 Important is documented as a follow-up rather than fixed, and 1 Minor stays deferred.

SeverityFindingResolution
Critical report-implementation's new parent-dir slug derivation would mis-resolve to plans for THIS plan itself, since it's deliberately excluded from migration and sits at docs/superpowers/plans/, not .digismith/docs/<slug>/ — it would misfile the very report this branch is about to generate on itself, writing to .digismith/docs/plans/report.html. Fixed — Step 1 now guards the parent-directory shortcut. It first checks whether the plan's path actually matches .digismith/docs/<something>/plan.md. If yes, the parent directory name is the slug as before (the fast normal-case path). If no, it falls back to parsing the slug out of the plan's own <date>-<slug>-plan.md filename — stripping the leading <date>- and trailing -plan.md — and uses .digismith/docs/<that-slug>/ for everything downstream. Verified end-to-end by generating this very report: the fallback fired and correctly produced unified-docs-convention, not plans.
Important standards/team/docs-conventions.md now contradicts jira-intake's new path/gitignore behavior — it described tickets at docs/<feature>/ticket.md and claimed they are unconditionally gitignored. Fixed — the ticket line now reads .digismith/docs/<feature-slug>/ticket.md, and the gitignore line now scopes the always-gitignored claim to specs/plans/progress-reports while stating that for tickets it is an explicit per-repo choice, asked once and then remembered. The file's lines about specs/plans/reports living elsewhere were deliberately left untouched — per the design spec's own investigation they describe the Emma team's separate docs/development-workflow.md convention, unrelated to DigiSmith's storage.
Important using-digismith still asserted ticket.md is unconditionally gitignored, as the reason a freshly created worktree won't contain it — reasoning that became sometimes-false once Task 3 made gitignoring a per-repo choice. Fixed — both places (Step 1's explanation and Quick Reference row 1) are rewritten around the always-true reason: a worktree checks out only what is already committed, and ticket.md has just been written, so it isn't committed yet — and in a repo that chose the gitignored option it never will be. Gitignoring is now presented as one specific reason among others rather than the rule.
Important report-implementation doesn't honor a consumer repo's gitignore choice — Step 4 unconditionally runs git add then git commit on the report path, which hard-fails on an ignored path ("Use -f if you really want to add them"). Fixed — Step 4 now runs git check-ignore -q on the target report path before staging. Ignored → the report is written but not staged or committed, and the skill says plainly that it wasn't committed because this repo's .digismith/docs/ is gitignored, matching the user's own earlier choice; it neither re-asks nor forces with -f. Not ignored → git add/git commit proceed as before. Error Handling and the Quick Reference row were updated to match.
Important jira-intake's .gitignore detection was a naive text-match for a literal .digismith/ string, which misses real ignore patterns. Fixed — replaced with the authoritative method, git check-ignore -q .digismith/docs/, read by exit code, with an explicit statement that exit code 1 means "not ignored" and is not a command failure. This correctly handles bare .digismith (no trailing slash), wildcards, negations, comments, nested .gitignore files, .git/info/exclude, and a global core.excludesFile. Verified empirically: a fixture repo whose .gitignore contains bare .digismith returns exit 0 — the exact case the old string match would have missed.
Important The .gitignore append instruction just said "append", with no guard against clobbering the file or against a missing trailing newline fusing the new entry onto an existing last line. Fixed — Step 3.3 now spells out the mechanics: create the file fresh if it doesn't exist; otherwise read the existing content first, add a newline if the last line lacks one, then append a single new line containing .digismith/, using an append operation and never a tool or redirect that replaces the whole file.
Important design.html/plan.md have no enforcement point: superpowers:brainstorming and superpowers:writing-plans are third-party skills that don't know the .digismith/docs/<slug>/ convention exists, so nothing tells them where to save a NEW feature's spec or plan. Documented, not fixed — per the reviewer's own calibration this is "a genuine follow-up feature, not a merge blocker". Recorded as a new bullet in MEMORY.md's Open questions section, naming the gap plainly, noting that this very branch's own spec and plan are the proof of it, and identifying using-digismith's hand-off to superpowers:brainstorming as the natural place to eventually pass the target folder explicitly — to be decided when it is actually blocking someone, not preemptively.
Minor Formatting drift: three placeholder bullets in report-implementation's Step 2a drop the bold-name + em-dash convention used by their neighbours. Stays deferred — cosmetic only, and it matches the plan's own literal replacement text rather than being implementer-introduced. Carried over from Task 2's deferred minor; confirmed still valid at ledger triage.
Minor "Committed" wording clarity: choosing the "committed" option read as though the skill would itself commit something. Fixed — Step 3.3 now states that choosing "committed" doesn't itself commit anything; it just means the file is left tracked-and-not-ignored, so it becomes part of whatever commit the user (or a later skill) makes normally.
Minor Untracked-vs-committed distinction in Step 3.3's third branch: it concluded "committed" from directory existence alone, so an aborted prior run that left untracked files behind would be silently misread as a prior decision. Fixed — that branch now checks git ls-files .digismith/docs/. Non-empty output → genuinely committed, don't ask. Directory exists on disk but nothing tracked → treated as the "ask once" branch instead of assuming committed.
Minor No tracked record of the pending spec/plan move — this feature's own design.html and plan.md are deliberately excluded from the migration and must be moved by hand afterwards, with nothing in git saying so. Recorded — MEMORY.md's new Open-questions bullet states in git-committed text that this branch's own spec and plan ended up at the old docs/superpowers/ location, and this report's Summary callout documents the exclusion, its rationale, and the by-hand follow-up move.
Minor Gitignore-entry-no-op-on-tracked-files edge case: adding .digismith/ to .gitignore has no effect on files git already tracks. Fixed incidentally — closed by the untracked-vs-committed fix above. The append now only ever happens in the ask-once branch, which by construction fires only when git ls-files .digismith/docs/ is empty, so the skill can no longer add an entry that would be a no-op against already-tracked files.
